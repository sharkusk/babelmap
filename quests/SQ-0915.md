## MEASURED — `Graphic.Data` is an Amiga disk font, and it is font 3

`Lost Treasures of Infocom, The_Disk5.adf` (Beyond Zork), 2,600 bytes. Beside `Beyond Zork` (46,472 — the interpreter, same size as Sherlock's) and `Story.Data` (261,632 — the z5).

It opens `00 00 03 F3` — an AmigaDOS hunk executable, one CODE hunk of 2,532 bytes — but the code is the four-byte `moveq #0,d0 / rts` stub every Amiga **disk font** begins with, and `DFH_ID` (`0x0F80`) sits at +0x12 exactly where `DiskFontHeader` puts it. So it is a font file, not a picture archive and not a program.

Read out of its `TextFont`:

| field | value |
|---|---|
| `tf_YSize` / `tf_XSize` | **8 / 8** |
| `tf_Baseline` | 6 |
| `tf_LoChar` | 32 |
| `tf_CharData` / `tf_Modulo` | 0x6E / 190 |
| `tf_CharLoc` | 0x65E |

`0x65E − 0x6E = 1520 = 8 rows × 190`, so the geometry closes on itself. `dfh_Name` is empty — the interpreter loads the segment directly rather than asking `diskfont.library` for it by name.

Rendering codes 32–126 settles what it is: arrows, diagonals, horizontal rules at three heights, verticals, the full box-drawing corner/tee set, solid and half blocks, the graded fill bars at 79–87, and then **26 angular runic glyphs at 97–122**. That is the Z-Machine Standard's font 3 (ZMSD §16), and the runes are Beyond Zork's.

## Why this is worth doing

`crates/app/src/render/bitfont.rs` already carries font-3 glyphs and already renders the box-drawing half, but its runes are `EXTRA_GLYPHS` — **hand-drawn placeholders**, as its own test says ("the hand-drawn runic placeholders", `glyph_coverage_font3_runic_placeholders`). The authoritative 8x8 bitmaps for those 26 codepoints are sitting on a release floppy we already mount, at the same cell size our bitfont uses, so this is a substitution rather than a design problem.

Beyond Zork displays runes as an atmosphere/puzzle element, so these are player-visible.

## Two shapes it could take, and they differ in ambition

1. **Transcribe** the 26 glyphs into `EXTRA_GLYPHS` as literal bytes, with a test that reads them back off the floppy and asserts they match — the same "pin the constant against the shipped artefact" pattern as `v6_amiga_shipped_interpreter.rs`. Self-contained, no runtime dependency, skips vacuously without the fixture.
2. **Read the font off the medium at runtime** when the story came off a disk that carries one, the way `native_sound` reads `Sound/`. More faithful, and it would generalise if another release ships a font — but nothing else here is known to, so 1 is probably the right size unless the whole font (not just the runes) turns out to differ from ours.

Worth checking the box-drawing half against ours either way: if Infocom's own shapes differ from what `bitfont.rs` draws, that is a fidelity bug hiding in the half we thought was right.

## Reproducing

`adfread.py` in the session scratchpad reads the ADF; the font parses with the offsets above. No new dependency — `blorb::medium` already mounts the disk and `assets::files` already lists `Graphic.Data`.

## Done, but NOT as filed — the premise was wrong and the real defect was elsewhere

Commit 0d6ecd87. Gate 0, clippy clean, 5604/5604 (was 5601).

### The filed plan would have changed nothing a player sees

`bitfont.rs` is reached only from `render/screen.rs` and `render/v6_layout.rs` — the **v6** paths. *Beyond Zork* is **v5**, so it never goes through the pixel composite: its runes are drawn by the **terminal's own font**, from the codepoints `font3_translate` returns. Swapping `EXTRA_GLYPHS` for Infocom's bitmaps would have been invisible. Those entries are defensive only (a v6 story printing font-3 code 97 would reach them; none is known to). The module header now says this so the next reader does not repeat the mistake.

### What the shipped font was actually good for

It is the only oracle available that can falsify the **question** rather than the answer. Every other harness here asks whether babelmap does what `font3_translate` says; this asks whether that table is right.

It is not. **Codes 71–74 rendered `U+FFFD`.** They are unassigned in ZMSD §16, so bocfel emits a replacement character and we copied that — but the Amiga release *draws* them: one inked pixel in one corner of the cell, a different corner each, verified as exactly one pixel per glyph. They are the faint members of the room-corner family at 63–66 and now map to `▝ ▗ ▖ ▘`. A Beyond Zork player was seeing `\u{FFFD}` where the machine drew a corner mark.

### The rule that was pinned, rather than the four codes

`crates/app/tests/suites/font3_shipped_font.rs` (in the `engines` group) parses the font off the floppy and asserts: **no font-3 code the Amiga inks may translate to something invisible.** Falsified by restoring `71..=74 => '\u{FFFD}'`, which names all four. Plus a non-vacuity case (the file really is 8×8, `LoChar` 32, ≥80 of 95 codes inked) and shape spot-checks pinned as corner/edge occupancy rather than exact bitmaps, because the claim is which glyph a code denotes, not Infocom's letterforms.

### Code 79 is an exception and had to be written down as one

The rule flagged it, correctly by its own terms, and it is still not a defect. 79 is the **empty** member of the meter-bar family at 79–87: its only ink is the top and bottom rail, and 80–87 — which we render as the graded left-blocks `▏▎▍▌▋▊▉█` — drop those same rails. The family reads as a gradient starting at nothing, so a space is the consistent zero, and Unicode has no rails-only cell to do better with. The exception carries an assertion that keeps it earning itself: it fails if 79 stops being exactly two full rows.

### Deliberately not asserted away

Unicode cannot express all of font 3, and the suite says so rather than pretending: 38/39 are rules at two different heights and both become `─`; 79–87 lose their rails; 123–126 are reverse-video variants of 92–96 and lose the reversal. Those are the terminal's limits, not bugs.

### Font parse, for whoever needs it next

4-byte `moveq #0,d0 / rts` stub, `DiskFontHeader` (`Node` 14, `dfh_FileID` = `0x0F80`, revision, segment, 32-byte name), then `TextFont` whose 20-byte `Message` precedes `tf_YSize`. Measured: YSize/XSize 8/8, baseline 6, LoChar 32, CharData `0x6E`, Modulo 190, CharLoc `0x65E` — and `0x65E − 0x6E = 1520 = 8 × 190`, so the geometry closes on itself. `dfh_Name` is empty; the interpreter loads the segment directly rather than asking `diskfont.library` by name. The parser lives in the test file rather than `blorb`, because nothing in production reads it.
