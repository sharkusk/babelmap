## MEASURED — `Graphic.Data` is an Amiga disk font, and it is font 3

`Lost Treasures of Infocom, The_Disk5.adf` (Beyond Zork), 2,600 bytes. Beside `Beyond Zork` (46,472 — the interpreter, same size as Sherlock's) and `Story.Data` (261,632 — the z5).

It opens `00 00 03 F3` — an AmigaDOS hunk executable, one CODE hunk of 2,532 bytes — but the code is the four-byte `moveq #0,d0 / rts` stub every Amiga **disk font** begins with, and `DFH_ID` (`0x0F80`) sits at +0x12 exactly where `DiskFontHeader` puts it. So it is a font file, not a picture archive and not a program.

Read out of its `TextFont`:

| field | value |
|---|---|
| `tf_YSize` / `tf_XSize` | **8 / 8** |
| `tf_Baseline` | 6 |
| `tf_LoChar` | 32 |
| `tf_CharData` / `tf_Modulo` | 0x6E / 190 |
| `tf_CharLoc` | 0x65E |

`0x65E − 0x6E = 1520 = 8 rows × 190`, so the geometry closes on itself. `dfh_Name` is empty — the interpreter loads the segment directly rather than asking `diskfont.library` for it by name.

Rendering codes 32–126 settles what it is: arrows, diagonals, horizontal rules at three heights, verticals, the full box-drawing corner/tee set, solid and half blocks, the graded fill bars at 79–87, and then **26 angular runic glyphs at 97–122**. That is the Z-Machine Standard's font 3 (ZMSD §16), and the runes are Beyond Zork's.

## Why this is worth doing

`crates/app/src/render/bitfont.rs` already carries font-3 glyphs and already renders the box-drawing half, but its runes are `EXTRA_GLYPHS` — **hand-drawn placeholders**, as its own test says ("the hand-drawn runic placeholders", `glyph_coverage_font3_runic_placeholders`). The authoritative 8x8 bitmaps for those 26 codepoints are sitting on a release floppy we already mount, at the same cell size our bitfont uses, so this is a substitution rather than a design problem.

Beyond Zork displays runes as an atmosphere/puzzle element, so these are player-visible.

## Two shapes it could take, and they differ in ambition

1. **Transcribe** the 26 glyphs into `EXTRA_GLYPHS` as literal bytes, with a test that reads them back off the floppy and asserts they match — the same "pin the constant against the shipped artefact" pattern as `v6_amiga_shipped_interpreter.rs`. Self-contained, no runtime dependency, skips vacuously without the fixture.
2. **Read the font off the medium at runtime** when the story came off a disk that carries one, the way `native_sound` reads `Sound/`. More faithful, and it would generalise if another release ships a font — but nothing else here is known to, so 1 is probably the right size unless the whole font (not just the runes) turns out to differ from ours.

Worth checking the box-drawing half against ours either way: if Infocom's own shapes differ from what `bitfont.rs` draws, that is a fidelity bug hiding in the half we thought was right.

## Reproducing

`adfread.py` in the session scratchpad reads the ADF; the font parses with the offsets above. No new dependency — `blorb::medium` already mounts the disk and `assets::files` already lists `Graphic.Data`.
