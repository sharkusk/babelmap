--- note 2026-07-16T04:17:08Z ---

RESOLVED as `peel-layer <direction>` (588d5f3), after the original framing turned out to be wrong twice.

THE REPORT DID NOT REPRODUCE. Peeling from a sub-layer already worked at every level:
  - `peel_region` is layer-agnostic: `src = layer_of(start)`, and `new_layer(Some(src), ..)` nests correctly. Probed: peel #3 out of sub-layer 1 -> layer 2 with parent=Some(1).
  - The app action works too: standing in a sub-layer, PeelLayer went layers [0,1] -> [0,1,2], viewed=Some(2).
  - Sub-layers DO grow: `place_incremental` inherits `layer_of(prev)`, so rooms discovered while in a sub-layer join it (I had guessed otherwise from `upsert_room`'s MAIN_LAYER default — wrong; the default is overwritten on placement).

THE REAL CAUSE, from the user's own map: layer 1 "Cellar" is 35 rooms forming exactly ONE planar region, so `region == whole_layer` and peel returns None. `peel_region` cuts only on PORTAL edges (Up/Down/In/Out) — that is its entire definition of a seam — and Zork's underground is planar-connected throughout, so no seam exists to find. Their main layer has 4 regions (Up a Tree, Attic, etc. hang off portals), which is why peeling worked there and never in the Cellar. Nothing to do with sub-layers at all.

USER CONFIRMED the symptom was "nothing at all, silently".

SECOND WRONG TURN: user chose "cut at a selected edge" — but there IS no edge selection. `DeleteSelectedConnection` and `RelabelSelectedEdge` both take "the first outgoing connection" of the selected room, i.e. an arbitrary edge on any room with multiple exits, and `AppState` has no `selected_edge` at all. Real edge selection would fix three commands at once and is worth its own quest. User chose the cheaper `peel-layer <dir>` instead: name the seam by direction, no new UI.

SHIPPED:
  - `peel_at_edge(graph, from, dir)` in mapper/layer.rs. Severs the named passage AND ITS RECIPROCAL, then peels the far side. The reciprocal is the load-bearing detail: a passage is two connections (A-E->B, B-W->A), so cutting only the named one leaves the back-edge holding the halves together and NO seam could ever cut (mutation-verified: dropping it fails 2 tests). Deliberately just that pair, not every edge between the rooms — if A also reaches B another way that is a second passage, the boundary is not real, and NotASeam says so.
  - `region_with_cut(graph, start, &dyn Fn(&Connection) -> bool)` — `planar_region` is now a call with a no-op cut.
  - `PeelRefusal { WholeLayer, NoSuchPassage, NotASeam, LeavesLayer }`; `peel_region` returns Result instead of Option so the reasons live in one place. Test call sites needed no change — `Result::expect` exists (only one real break: the app action).
  - `Action::PeelLayer(Option<Direction>)`, `peel-layer [direction]` parsing via `parse_direction` (same vocabulary as game commands), and `peel_refusal_message` — refusals now name the room/passage and point at the way forward.

VERIFIED ON THE USER'S REAL MAP: 13 cuttable seams inside the Cellar layer, e.g. `Troll Room -W-> Maze` peels the whole 11-room Maze; `East-West Passage -E-> Round Room` peels 18. Direction is meaningful — you peel what is THROUGH that door, so which side you get depends on where you stand.

Tests: 4 in mapper/layer.rs (seam cut on a portal-free chain, reciprocal severing, way-round rejection, portal/no-passage/leaves-layer), 2 in input.rs (the refusal speaks, then the named cut works), 1 in slash.rs (optional direction arg). Workspace 28 binaries green, clippy unchanged at 25. No README/style.toml change: peel is not in the README, and the message uses the existing status line.

NOT DONE, worth a quest: real edge selection (`selected_edge` + map-pane hit-testing + keyboard cycling) would let peel/delete/relabel all act on a picked edge instead of an arbitrary one.
