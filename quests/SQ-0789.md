--- note 2026-08-12T05:57:17Z ---

USER PROPOSAL 2026-08-11:

> "story info panel should list all side-cars detected. maybe there's an easy way to pick which one to use from there and save that selection to the game specific config?"

**WHY THIS IS BETTER THAN IT LOOKS: it rescues an idea SQ-0734 had to reject, by putting a human in the loop.**

SQ-0734 explicitly rejected **stem-based auto-discovery** — looking for `<story-stem>.pic` or similar beside the story — on measured grounds: every Infocom Amiga release names its archive `Pic.data`, so a name rule requires the user to rename, a wrong rename is undetectable, and the format offers almost nothing to validate a pairing (a part number and a picture count; no release number, no serial). The failure mode is *plausible but wrong art* — Arthur's plates drawn into Zork Zero — with nothing on screen to say so.

**Discovery for DISPLAY is a different act from discovery for PAIRING.** Listing every candidate beside the story and letting the user choose is safe precisely because the human supplies the assertion the format cannot: they know which game they own. Auto-pairing is unsafe for exactly the reason listing is safe. So this proposal does not reopen SQ-0734's rejection — it routes around it, and it is the natural home for the discovery logic that rejection forbade using silently.

WHAT IT NEEDS, in order:
1. **Discovery** — enumerate plausible art sidecars beside the story: `*.pic`, `*.mg1`/`*.mg2`, `*.eg1`/`*.eg2`, `*.cg1`/`*.cg2`, and Blorbs. Do NOT filter to a matching stem; the whole point is to show what is there. `crates/blorb`'s `InfocomPics::parse` can then report each one's flavour, picture count and part number, so the list can be informative rather than a bare filename.
2. **Display** in the story info panel, with enough to choose by: flavour (Amiga / MCGA / EGA / CGA), picture count, part number, and which one is currently in effect.
3. **Selection** writing `pictures = "<name>"` to the per-game sidecar `<game_dir>/config.toml` — bare lines, absent key = inherit, **never templated** (CLAUDE.md). That is SQ-0734's tier 3, so this feature produces exactly the configuration that quest already consumes; no new mechanism.

WHY IT MATTERS MORE SINCE 2026-08-11: the PC decoder (SQ-0735) means a single game commonly has several *usable* renditions. Zork Zero in `stories/` has `zork0.pic` (Amiga), `zork0.mg1` (MCGA), `zork0.eg1` (EGA), `zork0.cg1` (CGA) **and** `Zork0.blb`. Arthur has five plus a Blorb. Choosing between them is a real user decision that currently requires hand-editing a config file, and there is no way to discover the options from inside the app.

DEPENDENCY: **SQ-0734 must land first** — it defines the config key, the precedence, and the loud-failure behaviour for a named archive that does not decode. This quest is the UI over that. Do not start it while SQ-0734 is in flight.

CONSIDER, not decided: whether selecting a rendition should also move the interpreter number, since SQ-0734 rules that the archive's flavour selects it unless set explicitly. If so, the panel should say so — silently changing the emulated machine because the user picked prettier art would be surprising, and header byte 0x1E is not inert (`crates/zvm/src/cpu/exec.rs:4052` branches on it).

Every new UI element must be styleable via `style.toml` (ColorScheme field + `style.rs` selector + render apply); never hard-code styles.

--- note 2026-08-12T05:58:00Z ---

DESIGN DIRECTION 2026-08-11, user: **"perhaps a launch options dialog box?"**

**This is a better home than the info panel, and the reason is semantic rather than aesthetic: everything being chosen here is consumed at BOOT.**

- The art archive is opened and its pictures resolved when the story starts. Changing it mid-session means re-resolving resources under a running game — the same class of problem as swapping memory under a game that never learns it happened (CLAUDE.md's restore rule), and not something to invite casually from an inspection panel.
- The interpreter number is worse: header byte **0x1E** is read by the story itself, and `crates/zvm/src/cpu/exec.rs:4052` branches on `read_byte(0x1E) == 6`. A game that has already booted has already made decisions from it. Offering to change it from a panel during play would be offering something we cannot honestly deliver.

So the two surfaces divide cleanly, and both are probably worth having:

- **Story info panel — INSPECTION.** Lists every detected sidecar with flavour (Amiga / MCGA / EGA / CGA), picture count, part number, and which is currently in effect. Read-only. Answers "what do I have and what am I using?"
- **Launch options dialog — CHOICE.** Shown before the story boots, where a boot-time decision can actually be honoured. Writes `pictures = "<name>"` to the per-game sidecar `<game_dir>/config.toml` (bare lines, absent key = inherit, never templated). Answers "start this game how?"

The original proposal's mechanism is unchanged — discovery, display, write to per-game config — only the surface moves and gains a natural moment to act.

WHAT ELSE MIGHT BELONG IN A LAUNCH DIALOG, worth deciding deliberately rather than letting it accrete: interpreter number (which SQ-0734 rules the archive flavour selects unless set explicitly — so it should be *visible* here, and the dialog should say when picking art moves it, since silently changing the emulated machine because someone chose prettier art is exactly the kind of surprise this dialog exists to prevent), and v6 render mode. Resist making it a general per-game settings editor; the case for it is boot-time-only choices.

CONVENTIONS THAT APPLY (project standing policy, not this quest's to invent): shared-chrome dialogs use Tab / Shift-Tab for focus, Enter to activate (per-modal ButtonId -> Action), Esc to cancel; Space is widget-reserved. Shift-Tab must reverse any Tab-cycler. Every new UI element must be styleable via `style.toml` — ColorScheme field, `style.rs` selector, render apply — never hard-coded.

DEPENDENCY UNCHANGED: SQ-0734 must land first; it defines the config key, the precedence, and the loud-failure behaviour for a named archive that does not decode. The discovery-for-display-is-safe / discovery-for-pairing-is-not distinction recorded above applies to both surfaces equally.

OPEN, not decided: whether the launch dialog appears always, on a modifier, or only when more than one rendition is detected. Showing it unconditionally would put a keypress between the user and every game they launch, which is a real cost for the common case of a story with exactly one art source.

--- note 2026-08-12T05:59:07Z ---

SCOPE EXPANSION 2026-08-11, user:

> "we can also allow the user to override the interpreter-number there? and any other options. we can have a check-box to save these options as the default launch parameters (i.e. update the game specific config)"

**THE CHECKBOX IS THE GOOD IDEA HERE AND SHOULD BE NAMED AS A PRINCIPLE:** the dialog's settings apply to **this launch**; the checkbox **persists them** to `<game_dir>/config.toml`. That gives a try-before-you-commit path — pick the EGA art, see how it looks, and only write it down if you keep it — which is exactly right for choices whose effect you cannot predict from a filename. Without it, every experiment is a config edit you have to remember to undo.

**Interpreter number belongs here without question.** It is read from header byte 0x1E by the story itself at boot (`crates/zvm/src/cpu/exec.rs:4052` branches on `read_byte(0x1E) == 6`), so it is boot-time by nature and cannot honestly be offered anywhere else. It also interacts with the art choice, and the dialog must make that visible: SQ-0734 rules that **the archive's flavour selects the interpreter number unless one is set explicitly**. So picking `.eg1` moves an *auto* interpreter to the IBM machine, while an explicit setting overrides it. Show the derived value and where it came from; silently changing the emulated machine because someone chose prettier art is the surprise this dialog exists to prevent.

**"AND ANY OTHER OPTIONS" — TAKE IT, BUT WITH A COHERENT ADMISSION RULE, or this becomes a second settings screen that drifts from the first.** The rule that makes the dialog make sense: **admit an option only if it cannot be changed after boot.** Boot-time choices have no other home, which is the whole argument for the dialog. Anything the running app can already change belongs in the existing config screen, and duplicating it here creates two editors for one value.

Candidates that pass that test: the art archive, the interpreter number, and plausibly the v6 render mode (hybrid vs raster) if the pipeline cannot switch live — **verify that rather than assuming it**. Candidates that fail it: colours, styles, map behaviour, anything already live-editable.

If an option is genuinely useful at launch AND changeable later, prefer showing it here and having both surfaces write the same key, rather than forking the storage.

**CONSTRAINT ON WHAT THE CHECKBOX WRITES**, from CLAUDE.md: the per-game sidecar is *"a bare-lines sidecar `<game_dir>/config.toml` (at most a few keys; absent key = inherit) — never templated"*. A dialog that writes every field it displays would violate that in spirit and in practice, and would also destroy the inherit semantics — a key present with the global default is not the same as a key absent. **Write only what the user actually changed from the inherited value**, matching how `write_config` already writes only non-default values while still updating keys already present.

CONVENTIONS (standing policy): Tab / Shift-Tab focus, Enter activates (per-modal ButtonId -> Action), Esc cancels, Space is widget-reserved — which matters here, since Space is the natural checkbox key and is already spoken for; check how existing modals toggle. Every element styleable via `style.toml` (ColorScheme field + `style.rs` selector + render apply); never hard-code.

STILL OPEN: whether the dialog appears always, on a modifier, or only when there is something to choose. With interpreter number and other options in it, "only when multiple renditions exist" no longer covers the cases — but putting a keypress in front of every launch is a real cost. A modifier (launch normally; hold a key for options) may be the resolution.

TRIGGER DECIDED 2026-08-11, user — this closes the "always / modifier / only-when-there-is-a-choice" question left open above:

> "launch dialog should be a specific key, for example shift-enter when launching or double right click"

**Opt-in on an explicit gesture, never automatic:**
- **Shift-Enter** on a selected story in the browser, where plain Enter launches directly as today.
- **Double right-click** on a story, where the existing mouse launch gesture launches directly.

Plain launch is untouched, so nobody who does not want the dialog ever meets it. That disposes of the cost recorded earlier (a keypress in front of every launch) and also removes the need for any "show it only when multiple renditions exist" heuristic — the user asks for it when they want it, regardless of what the story happens to have. Simpler and better than the conditional-display idea it replaces.

It also fits the project's existing modifier convention: Shift modifies the default action rather than introducing a separate mode, the same shape as Shift-Tab reversing any Tab-cycler ([[keyboard-nav-conventions]]). Shift-Enter reads as "launch, but let me choose first", not as a distinct command.

TWO IMPLEMENTATION POINTS PASSED TO THE LANE:
1. **Discoverability** — a gesture nobody knows about is a feature nobody uses. It must be surfaced wherever the browser already advertises its keys (footer hint, help overlay), not left to the docs.
2. **Both gestures must reach the same code path**, bound through the single `slash::COMMANDS` registry (`src/slash.rs`, verb-noun names, keys bind to command strings) rather than a hardcoded match arm — that is the standing rule and it is what stops the keyboard and mouse paths drifting into two variants.

FLAGGED AS POSSIBLY NOVEL: double **right**-click may have no precedent in this codebase's input model. The lane was told to check what browser mouse handling already exists and, if there is none, to propose the closest fit rather than bolting on a new gesture recogniser.
