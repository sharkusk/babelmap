USER PROPOSAL 2026-08-11:

> "story info panel should list all side-cars detected. maybe there's an easy way to pick which one to use from there and save that selection to the game specific config?"

**WHY THIS IS BETTER THAN IT LOOKS: it rescues an idea SQ-0734 had to reject, by putting a human in the loop.**

SQ-0734 explicitly rejected **stem-based auto-discovery** — looking for `<story-stem>.pic` or similar beside the story — on measured grounds: every Infocom Amiga release names its archive `Pic.data`, so a name rule requires the user to rename, a wrong rename is undetectable, and the format offers almost nothing to validate a pairing (a part number and a picture count; no release number, no serial). The failure mode is *plausible but wrong art* — Arthur's plates drawn into Zork Zero — with nothing on screen to say so.

**Discovery for DISPLAY is a different act from discovery for PAIRING.** Listing every candidate beside the story and letting the user choose is safe precisely because the human supplies the assertion the format cannot: they know which game they own. Auto-pairing is unsafe for exactly the reason listing is safe. So this proposal does not reopen SQ-0734's rejection — it routes around it, and it is the natural home for the discovery logic that rejection forbade using silently.

WHAT IT NEEDS, in order:
1. **Discovery** — enumerate plausible art sidecars beside the story: `*.pic`, `*.mg1`/`*.mg2`, `*.eg1`/`*.eg2`, `*.cg1`/`*.cg2`, and Blorbs. Do NOT filter to a matching stem; the whole point is to show what is there. `crates/blorb`'s `InfocomPics::parse` can then report each one's flavour, picture count and part number, so the list can be informative rather than a bare filename.
2. **Display** in the story info panel, with enough to choose by: flavour (Amiga / MCGA / EGA / CGA), picture count, part number, and which one is currently in effect.
3. **Selection** writing `pictures = "<name>"` to the per-game sidecar `<game_dir>/config.toml` — bare lines, absent key = inherit, **never templated** (CLAUDE.md). That is SQ-0734's tier 3, so this feature produces exactly the configuration that quest already consumes; no new mechanism.

WHY IT MATTERS MORE SINCE 2026-08-11: the PC decoder (SQ-0735) means a single game commonly has several *usable* renditions. Zork Zero in `stories/` has `zork0.pic` (Amiga), `zork0.mg1` (MCGA), `zork0.eg1` (EGA), `zork0.cg1` (CGA) **and** `Zork0.blb`. Arthur has five plus a Blorb. Choosing between them is a real user decision that currently requires hand-editing a config file, and there is no way to discover the options from inside the app.

DEPENDENCY: **SQ-0734 must land first** — it defines the config key, the precedence, and the loud-failure behaviour for a named archive that does not decode. This quest is the UI over that. Do not start it while SQ-0734 is in flight.

CONSIDER, not decided: whether selecting a rendition should also move the interpreter number, since SQ-0734 rules that the archive's flavour selects it unless set explicitly. If so, the panel should say so — silently changing the emulated machine because the user picked prettier art would be surprising, and header byte 0x1E is not inert (`crates/zvm/src/cpu/exec.rs:4052` branches on it).

Every new UI element must be styleable via `style.toml` (ColorScheme field + `style.rs` selector + render apply); never hard-code styles.
