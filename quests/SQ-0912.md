## What is known

Every `Sound/sN.nam` index names a sample AND a pitch file; SQ-0907 uses the first and ignores the second. The pitch files are **eleven bytes on every effect of both games**, MIDI-shaped:

```
00 09 90 <note> 40 FF 00 <nn> 90 <note> 00
```

`90 <note> 40` is Note-On, channel 0, velocity 64; `90 <note> 00` is the matching Note-Off. The note appears twice and varies per effect; `<nn>` before the Note-Off varies too (`00 01`, `00 04`, `00 07`, `80 00`) and looks like a delta time — duration or truncation. **A model that reads only byte 3 is ignoring that field**, and should say why.

MEASURED notes, Sherlock: 74 on eleven of fifteen effects, then 72 (s8, s14), 68 (s11), 79 (s13). Lurking Horror: 74 on five, 76 on four, 83 on two, 67, 84, 90.

## The controlled experiment this corpus hands you

Sherlock's effects **11, 12 and 13 all name the same `heart` sample** — byte-identical, asserted in `native_disk_sound.rs` — against notes **68, 74, 79**. Today all three sound the same, which is audibly wrong. If the model is right, 13 plays roughly a fifth above 11 and nothing else differs. That is falsifiable by ear against a real Amiga recording.

## Strong prior, NOT a finding

**74 looks like the reference note**: it is the commonest by a wide margin, and on Lurking Horror every effect that uses it plays at the sample's stated rate while the others do not. That suggests `rate × 2^((note − 74)/12)`. Do not ship it on that basis — it is a hypothesis fitted to a small sample, and the one thing already known to be an unreliable oracle here is arithmetic that merely looks tidy.

## How to settle it, in order

1. **Infocom's own Amiga interpreter.** The best lead by far, and this project has used the same source before: `v6_amiga_global_colour_pair.rs` quotes `amiga/yzip3.c` and `amiga/yzip.h` for `DEF_BACK`/`DEF_FORE`, and `v6_amiga_shipped_interpreter.rs` reads the 68000 code off the release floppies. The Amiga plays a sample by writing a PERIOD to the hardware, and a note is an index into a period table — so the routine that handles `sound_effect` will contain the mapping outright, turning this from inference into reading. Look for the sound entry point in that source, and for a period or rate table beside it.
2. **A reference rendition.** Same method that made SQ-0907's decoding trustworthy rather than plausible: a real Amiga recording, or another interpreter that implements disk-native Infocom sound. **`stories/Lurking.blb` is already ruled out** — its rates diverge from the disk on eight of fourteen with no consistent ratio (pinned in `the_decoded_samples_are_the_blorbs_samples`), so it cannot be back-fitted into a pitch model.
3. **The `heart` experiment above**, as a check on whatever 1 or 2 produce — never as the derivation.

## Scope note

Playback already resamples: `audio` mixes at 44100 and the AIFF wrapper states the sample's own rate, so applying a pitch is a change to the rate written into that wrapper, not new DSP. Keep the disk's stated rate as the base and the note as a multiplier, so a wrong model is one line to correct.

## Approach 1, investigated — and it lands on a precise anchor rather than an answer

**Do not go to the leaked C source first.** This project has already been burned by it: `v6_amiga_shipped_interpreter.rs` records that `yzip.h`'s `DEF_BACK` is 11 where every release floppy says 12, because the leak is a development snapshot. The authoritative artefact is the 68000 interpreter Infocom actually shipped, and `interpreter()` in that suite already extracts one — the binary is a file on the floppy named after the game.

MEASURED on `The Lurking Horror` (42,224 bytes, `0x000003F3` AmigaDOS hunk executable, off *Lost Treasures* disk 4):

- **No period or note table.** A sweep for any run of eight or more u16s falling by a semitone-ish ratio finds nothing.
- **No clock constants.** PAL 3546895, NTSC 3579545, their halves, ProTracker's 8363 and 428, and a 16.16 semitone multiplier all occur zero times.
- **No filenames.** `.mid`, `.nam` and `s10` never appear; names are built at runtime.

So the pitch is not table-driven and the answer is in code, not data. But the data region at **`0x05612`** names exactly where to look:

```
\x01\x02\x04\x08   audio.device\0   Sound/\0Sound/\0   S\0.NAM\0
```

Three things at once:

1. `{1, 2, 4, 8}` is the classic `ioa_Data` channel-allocation array handed to `OpenDevice("audio.device", …)` — Paula's four channels.
2. **The game drives AmigaOS `audio.device`**, not the hardware directly. That fixes the mechanism: pitch is `ioa_Period` on a `CMD_WRITE` or `ADCMD_PERVOL` request, and period = clock ÷ rate. Whatever the note does, it ends up in that field.
3. `Sound/` + `S` + `.NAM` are the fragments it composes `Sound/S<n>.NAM` from at runtime, which is why no filename appears whole.

## The sized next step

Disassemble 68000 from the code that references `0x05612` and from the `OpenDevice` call, and find where `ioa_Period` is written. That is a bounded read of a 42 KB binary with a named target, not a search. babelmap has no 68000 disassembler — this is an external tool (`vasm`/`vlink` companions, Ghidra, or `m68k-linux-gnu-objdump -b binary -m m68k`, remembering an AmigaDOS hunk file needs its header skipped or parsed).

Sherlock's own interpreter is the cross-check: if both compute the period the same way, the model is Infocom's rather than one game's — the same argument that settled the `.dat` container in SQ-0907.

## Still true

`stories/Lurking.blb` remains unusable as an oracle here (rates diverge on eight of fourteen with no consistent ratio), and Sherlock's `heart` at notes 68/74/79 remains the falsification experiment for whatever the disassembly yields.

## READ OUT OF THE SHIPPED BINARY — the model is equal temperament, and here are its constants

Disassembled `The Lurking Horror`'s Amiga interpreter (42,224 bytes, off *Lost Treasures* disk 4) with capstone's M68K backend. The hunk file parses as 147 hunks; **hunk 8** (CODE, file offset `0x4298`, 3,892 bytes) is the sound module — it holds the only `IOAudio` field stores in the program:

| file offset | instruction | field |
|---|---|---|
| `0x4642` | `move.w <ea>,$2e(a2)` | `ioa_Cycles` |
| **`0x4766`** | **`move.w d0,$2a(a0)`** | **`ioa_Period`** |
| `0x4774` | `move.w d0,$2c(a0)` | `ioa_Volume` |
| `0x4794` | `move.w d0,$2c(a1)` | `ioa_Volume` |

At the period store, `d0` is the **return value of the routine at `0x48da`**:

```
0x475a  bsr.w   $48da          ; four longwords pushed: d0, d1, d2, d3
0x475e  lea.l   $10(a7),a7
0x4762  movea.l -$8(a6),a0     ; the IOAudio request
0x4766  move.w  d0,$2a(a0)     ; ioa_Period = that return value
```

### The three constants in `0x48da`, decoded

| immediate | IEEE 754 double | what it is |
|---|---|---|
| `3FF0F38F 91ADE7DA` | **1.05946309** | 2^(1/12), the equal-tempered semitone ratio, typed as a rounded decimal |
| `408F4000 00000000` | **1000.0** | kHz ↔ Hz |
| `40ABF6FA E147AE14` | **3579.49** | the **NTSC** Amiga colour-burst clock in kHz (3579545 Hz) |

So the period is Paula's own `period = clock ÷ rate` on the NTSC clock, with the note applied to the rate as a power of the semitone ratio. **The "strong prior" in the earlier note is confirmed as the mechanism** — but read, not fitted.

### The signature, from the stack frame

After `link a6`, arguments sit at `8(a6)` upward. The routine reads:

- `8(a6)` and `$c(a6)` together as a **double** — the sample rate;
- a **byte** at `$13(a6)` — the low byte of the third longword argument;
- a **byte** at `$17(a6)` — the low byte of the fourth.

Both bytes are widened to double before use. So it is `period(rate, note_a, note_b)` and **there are TWO notes, not one against a fixed reference**. At the call site the two came from different places: one is a byte at `<table> + index + 1` off the long pointer at `$40.l`, the other a byte at `<arg> + 0x78`. One of them is the `.mid` file's note; the other is very likely a per-sample base note the interpreter tracks — which would explain why 74 merely *looks* like a universal reference in the file survey.

### What is NOT yet settled

The `jsr $0.l` targets are unresolved relocations to C-library float helpers, so the exact operator order — which call is `pow`, which is multiply, which is divide — is inferred from operand flow rather than read. The shape is almost certainly

```
period ≈ 3579.49 * 1000 / (rate * 1.05946309^(note_a - note_b))
```

but that expression should be confirmed before shipping, by resolving hunk 8's RELOC32 entries against the library hunk names, or by fitting it to the corpus now that the two-note structure is known.

**This also reopens the Blorb-rate divergence.** SQ-0907 recorded eight of fourteen rates disagreeing with `Lurking.blb` under a one-note model. With two notes there is a second degree of freedom, so it is worth re-testing whether the Blorb's figures are simply this formula evaluated — the earlier "no consistent ratio" conclusion assumed a single note.

### Reproducing

Capstone with `CS_ARCH_M68K` / `CS_MODE_M68K_000` disassembles it; the binary is an AmigaDOS hunk file (`0x000003F3`), so the header and per-hunk lengths must be walked before feeding bytes to the disassembler. Sherlock's own interpreter is the cross-check: same constants there means the model is Infocom's rather than one game's.
