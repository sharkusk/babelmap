## What is known

Every `Sound/sN.nam` index names a sample AND a pitch file; SQ-0907 uses the first and ignores the second. The pitch files are **eleven bytes on every effect of both games**, MIDI-shaped:

```
00 09 90 <note> 40 FF 00 <nn> 90 <note> 00
```

`90 <note> 40` is Note-On, channel 0, velocity 64; `90 <note> 00` is the matching Note-Off. The note appears twice and varies per effect; `<nn>` before the Note-Off varies too (`00 01`, `00 04`, `00 07`, `80 00`) and looks like a delta time — duration or truncation. **A model that reads only byte 3 is ignoring that field**, and should say why.

MEASURED notes, Sherlock: 74 on eleven of fifteen effects, then 72 (s8, s14), 68 (s11), 79 (s13). Lurking Horror: 74 on five, 76 on four, 83 on two, 67, 84, 90.

## The controlled experiment this corpus hands you

Sherlock's effects **11, 12 and 13 all name the same `heart` sample** — byte-identical, asserted in `native_disk_sound.rs` — against notes **68, 74, 79**. Today all three sound the same, which is audibly wrong. If the model is right, 13 plays roughly a fifth above 11 and nothing else differs. That is falsifiable by ear against a real Amiga recording.

## Strong prior, NOT a finding

**74 looks like the reference note**: it is the commonest by a wide margin, and on Lurking Horror every effect that uses it plays at the sample's stated rate while the others do not. That suggests `rate × 2^((note − 74)/12)`. Do not ship it on that basis — it is a hypothesis fitted to a small sample, and the one thing already known to be an unreliable oracle here is arithmetic that merely looks tidy.

## How to settle it, in order

1. **Infocom's own Amiga interpreter.** The best lead by far, and this project has used the same source before: `v6_amiga_global_colour_pair.rs` quotes `amiga/yzip3.c` and `amiga/yzip.h` for `DEF_BACK`/`DEF_FORE`, and `v6_amiga_shipped_interpreter.rs` reads the 68000 code off the release floppies. The Amiga plays a sample by writing a PERIOD to the hardware, and a note is an index into a period table — so the routine that handles `sound_effect` will contain the mapping outright, turning this from inference into reading. Look for the sound entry point in that source, and for a period or rate table beside it.
2. **A reference rendition.** Same method that made SQ-0907's decoding trustworthy rather than plausible: a real Amiga recording, or another interpreter that implements disk-native Infocom sound. **`stories/Lurking.blb` is already ruled out** — its rates diverge from the disk on eight of fourteen with no consistent ratio (pinned in `the_decoded_samples_are_the_blorbs_samples`), so it cannot be back-fitted into a pitch model.
3. **The `heart` experiment above**, as a check on whatever 1 or 2 produce — never as the derivation.

## Scope note

Playback already resamples: `audio` mixes at 44100 and the AIFF wrapper states the sample's own rate, so applying a pitch is a change to the rate written into that wrapper, not new DSP. Keep the disk's stated rate as the base and the note as a multiplier, so a wrong model is one line to correct.

## Approach 1, investigated — and it lands on a precise anchor rather than an answer

**Do not go to the leaked C source first.** This project has already been burned by it: `v6_amiga_shipped_interpreter.rs` records that `yzip.h`'s `DEF_BACK` is 11 where every release floppy says 12, because the leak is a development snapshot. The authoritative artefact is the 68000 interpreter Infocom actually shipped, and `interpreter()` in that suite already extracts one — the binary is a file on the floppy named after the game.

MEASURED on `The Lurking Horror` (42,224 bytes, `0x000003F3` AmigaDOS hunk executable, off *Lost Treasures* disk 4):

- **No period or note table.** A sweep for any run of eight or more u16s falling by a semitone-ish ratio finds nothing.
- **No clock constants.** PAL 3546895, NTSC 3579545, their halves, ProTracker's 8363 and 428, and a 16.16 semitone multiplier all occur zero times.
- **No filenames.** `.mid`, `.nam` and `s10` never appear; names are built at runtime.

So the pitch is not table-driven and the answer is in code, not data. But the data region at **`0x05612`** names exactly where to look:

```
\x01\x02\x04\x08   audio.device\0   Sound/\0Sound/\0   S\0.NAM\0
```

Three things at once:

1. `{1, 2, 4, 8}` is the classic `ioa_Data` channel-allocation array handed to `OpenDevice("audio.device", …)` — Paula's four channels.
2. **The game drives AmigaOS `audio.device`**, not the hardware directly. That fixes the mechanism: pitch is `ioa_Period` on a `CMD_WRITE` or `ADCMD_PERVOL` request, and period = clock ÷ rate. Whatever the note does, it ends up in that field.
3. `Sound/` + `S` + `.NAM` are the fragments it composes `Sound/S<n>.NAM` from at runtime, which is why no filename appears whole.

## The sized next step

Disassemble 68000 from the code that references `0x05612` and from the `OpenDevice` call, and find where `ioa_Period` is written. That is a bounded read of a 42 KB binary with a named target, not a search. babelmap has no 68000 disassembler — this is an external tool (`vasm`/`vlink` companions, Ghidra, or `m68k-linux-gnu-objdump -b binary -m m68k`, remembering an AmigaDOS hunk file needs its header skipped or parsed).

Sherlock's own interpreter is the cross-check: if both compute the period the same way, the model is Infocom's rather than one game's — the same argument that settled the `.dat` container in SQ-0907.

## Still true

`stories/Lurking.blb` remains unusable as an oracle here (rates diverge on eight of fourteen with no consistent ratio), and Sherlock's `heart` at notes 68/74/79 remains the falsification experiment for whatever the disassembly yields.

## READ OUT OF THE SHIPPED BINARY — the model is equal temperament, and here are its constants

Disassembled `The Lurking Horror`'s Amiga interpreter (42,224 bytes, off *Lost Treasures* disk 4) with capstone's M68K backend. The hunk file parses as 147 hunks; **hunk 8** (CODE, file offset `0x4298`, 3,892 bytes) is the sound module — it holds the only `IOAudio` field stores in the program:

| file offset | instruction | field |
|---|---|---|
| `0x4642` | `move.w <ea>,$2e(a2)` | `ioa_Cycles` |
| **`0x4766`** | **`move.w d0,$2a(a0)`** | **`ioa_Period`** |
| `0x4774` | `move.w d0,$2c(a0)` | `ioa_Volume` |
| `0x4794` | `move.w d0,$2c(a1)` | `ioa_Volume` |

At the period store, `d0` is the **return value of the routine at `0x48da`**:

```
0x475a  bsr.w   $48da          ; four longwords pushed: d0, d1, d2, d3
0x475e  lea.l   $10(a7),a7
0x4762  movea.l -$8(a6),a0     ; the IOAudio request
0x4766  move.w  d0,$2a(a0)     ; ioa_Period = that return value
```

### The three constants in `0x48da`, decoded

| immediate | IEEE 754 double | what it is |
|---|---|---|
| `3FF0F38F 91ADE7DA` | **1.05946309** | 2^(1/12), the equal-tempered semitone ratio, typed as a rounded decimal |
| `408F4000 00000000` | **1000.0** | kHz ↔ Hz |
| `40ABF6FA E147AE14` | **3579.49** | the **NTSC** Amiga colour-burst clock in kHz (3579545 Hz) |

So the period is Paula's own `period = clock ÷ rate` on the NTSC clock, with the note applied to the rate as a power of the semitone ratio. **The "strong prior" in the earlier note is confirmed as the mechanism** — but read, not fitted.

### The signature, from the stack frame

After `link a6`, arguments sit at `8(a6)` upward. The routine reads:

- `8(a6)` and `$c(a6)` together as a **double** — the sample rate;
- a **byte** at `$13(a6)` — the low byte of the third longword argument;
- a **byte** at `$17(a6)` — the low byte of the fourth.

Both bytes are widened to double before use. So it is `period(rate, note_a, note_b)` and **there are TWO notes, not one against a fixed reference**. At the call site the two came from different places: one is a byte at `<table> + index + 1` off the long pointer at `$40.l`, the other a byte at `<arg> + 0x78`. One of them is the `.mid` file's note; the other is very likely a per-sample base note the interpreter tracks — which would explain why 74 merely *looks* like a universal reference in the file survey.

### What is NOT yet settled

The `jsr $0.l` targets are unresolved relocations to C-library float helpers, so the exact operator order — which call is `pow`, which is multiply, which is divide — is inferred from operand flow rather than read. The shape is almost certainly

```
period ≈ 3579.49 * 1000 / (rate * 1.05946309^(note_a - note_b))
```

but that expression should be confirmed before shipping, by resolving hunk 8's RELOC32 entries against the library hunk names, or by fitting it to the corpus now that the two-note structure is known.

**This also reopens the Blorb-rate divergence.** SQ-0907 recorded eight of fourteen rates disagreeing with `Lurking.blb` under a one-note model. With two notes there is a second degree of freedom, so it is worth re-testing whether the Blorb's figures are simply this formula evaluated — the earlier "no consistent ratio" conclusion assumed a single note.

### Reproducing

Capstone with `CS_ARCH_M68K` / `CS_MODE_M68K_000` disassembles it; the binary is an AmigaDOS hunk file (`0x000003F3`), so the header and per-hunk lengths must be walked before feeding bytes to the disassembler. Sherlock's own interpreter is the cross-check: same constants there means the model is Infocom's rather than one game's.

## The Blorb is an ORACLE for this, not a distraction — earlier note corrected

Both this quest and SQ-0907 recorded `stories/Lurking.blb` as unusable for pitch, on the grounds that its rates diverge from the disk with "no consistent ratio". That was measured under a **one-note** model and is wrong.

With the semitone constant now read out of the interpreter, the relation is exact: `12·log(disk ÷ blorb) / log(2)` over all fourteen effects gives

| effect | `.mid` note | disk Hz | Blorb Hz | semitones | implied base note |
|---|---|---|---|---|---|
| 3, 4, 6, 7 | 76 | 15360 / 20480 / 18430 | 9676 / 12902 / 11610 | **8.000** | 68 |
| 8, 9 | 83 | 18430 | 17396 | **1.000** | 82 |
| 12 | 67 | 20480 | 13669 | **7.000** | 60 |
| 10 | 84 | 15360 | 15360 | **0.000** | 84 |
| 11, 13, 15, 16, 18 | 74 | 18430 / 15360 / 11100 / 18000 | same | **0.000** | 74 |
| 17 | 90 | 32910 | 31250 | 0.896 | — |

Thirteen exact to three decimals. So the Blorb hands us the **effective** rate, and subtracting the `.mid` note from it yields the second argument the disassembly showed — the per-sample base note the interpreter reads from its own table.

**The bases are not in the `.dat` header.** Grouped against the header's `flags` word (`0x003C`, `0x013C`, `0x0032`, `0x0132`) they do not correlate: effects 3 and 4 share base 68 across two different flag values, and 11 and 12 share flags `0x0132` across bases 74 and 60. So the table the disassembly reads (`$40.l + idx + 1`, and `<arg> + 0x78`) lives in the interpreter, not the sound files.

## Which gives two independent routes to finish

1. **Extract the base-note table from the interpreter binary**, at the two addresses the call site reads. Works for both games and is the real answer.
2. **Derive it from the Blorb for Lurking Horror** as a cross-check on route 1 — if the table extraction reproduces 68, 68, 68, 68, 82, 82, 84, 74, 60, 74, 74, 74, 74 then it is right, and Sherlock's table can then be trusted without a Blorb of its own.

Route 2 is only a check: Sherlock has no reference rendition here, so shipping from Blorb-derived numbers alone would leave the game it matters most for (three `heart` effects at 68/74/79) unverified.

## Effect 17 is the loose end

0.896 semitones, and its disk rate of 32910 Hz is beyond what Paula can clock a channel — the minimum period is around 124, giving roughly 28.9 kHz. So either the interpreter clamps, or the Blorb's author did. Identify which before implementing, because a clamp belongs in the model.

## `stories/Sherlock.blb` exists — a second reference rendition, and it changes the model

The earlier note said "Sherlock has no reference rendition here". Wrong: `stories/Sherlock.blb`, 488,794 bytes, fifteen `Snd ` resources numbered 3–17, exactly matching the floppy's effects.

### The semitone model is confirmed on a second game

`12·log(disk ÷ blorb) / log(2)` over all fifteen: **0.000, 2.000, 6.000, 2.000** — every one a whole number, no exceptions at all (Lurking had one). Two independent games, twenty-nine of thirty effects exact. The equal-tempered model read out of the interpreter is not a coincidence of one title.

### …and it DISPROVES a per-sample base note

The earlier note tabulated "implied base" per sample from Lurking's data, where each base happened to be constant per sample. Sherlock's `heart` breaks that outright — one byte-identical sample, three effects, three different shifts:

| effect | `.mid` | note | disk Hz | Blorb Hz | semitones | implied base |
|---|---|---|---|---|---|---|
| 11 | `heart1.mid` | 68 | 18430 | 13032 | 6 down | **62** |
| 12 | `growl.mid` | 74 | 18430 | 18430 | 0 | **74** |
| 13 | `heart3.mid` | 79 | 18430 | 16419 | 2 down | **77** |

No single base explains all three, and note-minus-74 does not either (effect 13's note is ABOVE 74 yet its rate goes DOWN). **So both notes are per-EFFECT**, which is exactly what the disassembly said — the second byte comes from `<arg> + 0x78`, a per-effect structure, not from the sample.

Note the two `.mid` files are shared across effects the same way samples are (`clk.mid` serves six of Sherlock's), so the pitch file is not a per-effect quantity either. The base lives only in the interpreter's table.

### The consequence for implementation, and it is the important one

**A release disk alone is not sufficient to play these at the right pitch.** The `.dat` gives the unpitched rate, the `.mid` gives one note, and the other note exists only inside the game's own interpreter binary. Two routes follow, and the first is self-contained:

1. **Read the table out of the interpreter that ships on the same disk.** `The Lurking Horror` and `SHERLOCK` are files on their own floppies, so nothing external is needed — but the table must be located reliably per game, which is the fragile part and wants a signature rather than a hard offset.
2. **Take the effective rate from a Blorb when one is present**, and play unpitched when it is not. Correct where it applies and honest where it does not.

### `Sherlock.blb` is a RATE oracle, not a byte oracle

Unlike `Lurking.blb`, its samples are not byte-identical to the disk: every effect is exactly **one frame shorter**, and effect 13 is **eleven** shorter with two leading bytes trimmed. Leading bytes otherwise match. An authoring trim, harmless for rates, but do not write a byte-equality assertion against this file the way `the_decoded_samples_are_the_blorbs_samples` does against Lurking's.

### Still open

Lurking's effect 17 (note 90, disk 32910 Hz, Blorb 31250, 0.896 semitones) remains the single ragged case across both games. 32910 Hz is past what Paula can clock a channel, so a clamp is the likely explanation and belongs in the model.

## SHIPPED — and the answer is on the Macintosh disc, not in the interpreter's data segment

`/MAC/SOUND` on `treasures/LostTreasures2.iso` settled everything the last three notes were circling. It is Sherlock's sound set (nine of its files are byte-length-exact matches for the Amiga samples) laid out as TWO files rather than three:

- `S<n>` — the identical `.dat` container, no extension.
- `M<n>` — the eleven-byte pitch blob with the `.nam` index appended (`…90 <base> 00 | 01 00 | "S12" 00…`), present ONLY for effects 8, 11, 13 and 14.

Those four are exactly the four whose Amiga `.mid` does not read 74. And in them the two notes DIFFER: `M8` 72/68, `M11` 68/68, `M13` 79/68, `M14` 72/68.

### Which retires the "base note lives in the interpreter binary" line of attack entirely

Both notes are in the pitch file. No table extraction, no per-game signature, no Blorb dependency. A release disk IS sufficient — the earlier note's "not sufficient" conclusion was drawn from the Amiga files alone, where the second note is invisible because it equals the first.

### The finding: the Amiga never bends a sound

MEASURED on all 22 pitch files across both games — `note == base` on every one, so the ratio is exactly 1. Sherlock's `heart` sounds identical for effects 11, 12 and 13 on an Amiga because the notes differ between FILES (68, 74, 79), not within one, and it is the within-one difference the interpreter divides by. **The quest's premise is false for Amiga media**, and the fix changes no Amiga rate. `every_amiga_pitch_file_is_a_unison_pair` pins that over the real floppies.

### The Blorbs follow a third model and are not followed

`Sherlock.blb` shifts exactly those four effects, by `note − 74` — a fixed reference no disk states anywhere — and is self-inconsistent on effect 13 (note 79, yet shifted DOWN 2 like the note-72 effects, and effect 13 is also the one whose samples are trimmed 11 frames rather than 1). `the_decoded_samples_are_the_blorbs_samples` now asserts only what both models share: the gap is a whole number of semitones. Its docs are corrected; the old text claimed the Blorb "baked in" the interpreter's model, which it does not.

### Unsettled, and marked as such in the code

The SIGN. `base` is constant at 68 across all four M-files while `note` varies, which is what makes `base` the reference — but a unison pair reads the same either way round, so the Amiga corpus cannot check it. `a_macintosh_volume_bends_the_effects_that_have_an_index` and `the_macintosh_release_bends_the_shared_heartbeat` pin it; falsified by flipping `semitones()`, which fails the Macintosh case (4881 vs 17396) and leaves the Amiga case green — exactly the asymmetry the Amiga case's message warns about. A reference rendition of the Macintosh release would settle it.

Fifteen Sherlock effects off `/MAC/SOUND` that were previously unreadable now play, `docs/features/interpreter.md` gained the disk-native sound entry SQ-0907 never got, and effect 17 of Lurking (32910 Hz, 0.896 semitones) stays pinned as the single ragged case rather than smoothed.

--- note 2026-08-19T03:54:04Z ---

Closed on the user's confirmation. NOTE for anyone reading this quest later: the pitch model this quest shipped was **wrong and has been superseded by SQ-0923**. It read the second note in an `sN.mid` as the pitch the sample was recorded at, concluded from the resulting all-unison corpus that the Amiga never bends a sound, and had the Macintosh as the only medium where a pitch file does anything.

The eleven bytes are a MIDI Note-On and its matching Note-Off; the reference note is in the SAMPLE's header (the low byte of the flags word), and the note is transposed by its MIDI channel first. Both media bend, identically. SQ-0923 read that out of the Amiga interpreter's 68000 and verified it against both Blorbs on 27 of 29 effects.

What this quest got right and keeps: reading the pitch files at all, the Macintosh `M<n>` layout (pitch blob + index in one file), and the equal-temperament framing. What it got wrong was which byte is the reference — see SQ-0923 for the disassembly and the corpus check.
