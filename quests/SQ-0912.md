## What is known

Every `Sound/sN.nam` index names a sample AND a pitch file; SQ-0907 uses the first and ignores the second. The pitch files are **eleven bytes on every effect of both games**, MIDI-shaped:

```
00 09 90 <note> 40 FF 00 <nn> 90 <note> 00
```

`90 <note> 40` is Note-On, channel 0, velocity 64; `90 <note> 00` is the matching Note-Off. The note appears twice and varies per effect; `<nn>` before the Note-Off varies too (`00 01`, `00 04`, `00 07`, `80 00`) and looks like a delta time — duration or truncation. **A model that reads only byte 3 is ignoring that field**, and should say why.

MEASURED notes, Sherlock: 74 on eleven of fifteen effects, then 72 (s8, s14), 68 (s11), 79 (s13). Lurking Horror: 74 on five, 76 on four, 83 on two, 67, 84, 90.

## The controlled experiment this corpus hands you

Sherlock's effects **11, 12 and 13 all name the same `heart` sample** — byte-identical, asserted in `native_disk_sound.rs` — against notes **68, 74, 79**. Today all three sound the same, which is audibly wrong. If the model is right, 13 plays roughly a fifth above 11 and nothing else differs. That is falsifiable by ear against a real Amiga recording.

## Strong prior, NOT a finding

**74 looks like the reference note**: it is the commonest by a wide margin, and on Lurking Horror every effect that uses it plays at the sample's stated rate while the others do not. That suggests `rate × 2^((note − 74)/12)`. Do not ship it on that basis — it is a hypothesis fitted to a small sample, and the one thing already known to be an unreliable oracle here is arithmetic that merely looks tidy.

## How to settle it, in order

1. **Infocom's own Amiga interpreter.** The best lead by far, and this project has used the same source before: `v6_amiga_global_colour_pair.rs` quotes `amiga/yzip3.c` and `amiga/yzip.h` for `DEF_BACK`/`DEF_FORE`, and `v6_amiga_shipped_interpreter.rs` reads the 68000 code off the release floppies. The Amiga plays a sample by writing a PERIOD to the hardware, and a note is an index into a period table — so the routine that handles `sound_effect` will contain the mapping outright, turning this from inference into reading. Look for the sound entry point in that source, and for a period or rate table beside it.
2. **A reference rendition.** Same method that made SQ-0907's decoding trustworthy rather than plausible: a real Amiga recording, or another interpreter that implements disk-native Infocom sound. **`stories/Lurking.blb` is already ruled out** — its rates diverge from the disk on eight of fourteen with no consistent ratio (pinned in `the_decoded_samples_are_the_blorbs_samples`), so it cannot be back-fitted into a pitch model.
3. **The `heart` experiment above**, as a check on whatever 1 or 2 produce — never as the derivation.

## Scope note

Playback already resamples: `audio` mixes at 44100 and the AIFF wrapper states the sample's own rate, so applying a pitch is a change to the rate written into that wrapper, not new DSP. Keep the disk's stated rate as the base and the note as a multiplier, so a wrong model is one line to correct.
