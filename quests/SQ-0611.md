## Fixed 2026-08-03 — commit 282caee6

### The bug
`zvm-cli --plain` produced `> In the Wings   Score: 0  Moves: 0` — status welded
onto the prompt line, reading as though the prompt were showing a room, with the
player's typing stranded below it.

Cause is timing, not placement: a game writes its prompt last and with no
trailing newline, and the host only learns the turn is over at the input request
— by which point the prompt is already out. So the status can only follow it
unless the prompt is held back.

### Why it went in the shared crate (user's call, and correct)
Both hosts had independently grown HALF the answer:
- gvm-cli: `plain_at_line_start` → tracked position, inserted a newline, but the
  status still landed *after* the prompt.
- zvm-cli: nothing at all.

That is precisely the drift SQ-0605 exists to stop, and I had walked past it once
already — I wrote the gvm-cli comment "a status bar welded to the end of `>` is
worse than a bare prompt above it" and then left zvm-cli alone on the grounds of
matching its existing piped convention. Wrong call.

`cli_host::LineHold` is now the one mechanism in two configurations:
- always a line-position tracker (`at_line_start`)
- in plain mode also a holder (`feed` withholds the unterminated tail;
  `release` hands it back)

gvm-cli's piped path is unchanged because without holding it takes exactly the
old newline-inserting branch.

### The same bug, one layer up
Fixing it exposed `/status` doing the identical thing: it answered *after* the
prompt had been released, so its answer welded onto the prompt line. `LineHold`
now remembers the last released tail (`last_prompt()`), so a host answer starts a
fresh line and puts the prompt back — the player sees `>` again and knows it is
still their turn. Verified on a cooked pty:

```
 In the Wings                          Score: 0  Moves: 3
>/status

 In the Wings                          Score: 0  Moves: 3
>wait
```

### Scope decision
Holding is **plain mode only**. Piped output is what the test harnesses and
scripted use read; it stays byte-identical (5 Z-machine + 5 Glulx stories), as
does TTY output under a pty (4 games). Piped mode therefore still shows the
status after the prompt — arguably also wrong, but changing it breaks byte-compat
for anyone scripting against it, and no one has asked.

### Verified
Zero escapes still in plain mode. Gate 0 errors, 64 == 64. Clippy clean.
Falsified 3 ways; the primary one reproduces the reported symptom exactly and
fails both CLI-level tests plus 4 in cli-host.

### Cosmetic detail, accepted
Interactively there is one blank line between the echoed `/status` and its answer:
the terminal echoes the user's Enter, and the host adds its own newline because it
cannot see that echo. Getting rid of it would mean modelling when the terminal
echoes; it reads as a separator, so it stays.
