--- note 2026-08-09T18:17:28Z ---

Inherited measurements from SQ-0706's investigation — already done, do not repeat.

THE GAME (65 KB, NO resource blorb, 0 pictures declared) boots clean: no fault, menu renders. The menu is NOT inert — it is keyed by each item's LOWERCASE INITIAL and nothing else:

    i -> Instructions   ("You are George Raft, an employee at a small space trading company...")
    s -> Start game     (title + "Copyright Att Scoddams 1982 / (Type 'about' for help)")
    r -> Reset computer ("As good as reset...") — and `pending_input` flips Char -> LINE, i.e. the game proper begins
    l -> Load game      (no output without a save)

Uppercase `I`, Enter, space, Esc, arrows (129-132), mouse codes (253/254), digits and y/n are all ignored with no output. So "nothing is selectable" was discoverability, not a defect, and the engine drives this game correctly.

THE REAL DEFECT, reported by the user once past the menu: after the ">" prompt each typed character gets a linefeed, and the first character starts one line BELOW the ">".

WHERE IT IS NOT: zvm performs no input echo at all — there is no echo path in `exec.rs`. This is app-side.

PRIME SUSPECT, already measured, verify before anything else: the model publishes **TWO windows both flagged `primary=true` at the identical (0,0) 640x400 rect**, and `classify_windows` takes the first as `story` and files the second one under CHROME. A second primary buffer is not chrome. If the prompt and the echo are mirrored from different windows, that is exactly a one-line offset — which is the reported symptom.

Note this is v6 with no graphics at all, so it exercises the text path in isolation — a useful property for a test, and one no other fixture in the corpus has.
