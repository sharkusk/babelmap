Design decisions (user, 2026-07-15):

1. SCOPE = stub only. The first 1-2 cells out of the corner are diagonal, then hand off to the EXISTING orthogonal lane router. Router, crossing model, and box stride are all UNTOUCHED. (The full 45-degree stair between rooms stays deferred per the 2026-06-22 diagonals spec.)
2. The corner ARROWS (↗↖↘↙ on the box corner cell, via corner_anchor map.rs:258 / diagonal_arrow) REMAIN as-is. The new diagonal glyphs are used AFTER the arrow, on the OUTSIDE of the box border.
3. Motivation is not just cosmetic: this ENABLES THE 4 CORNER SLOTS as connector attachment points. Today box_edge_anchor (map.rs:1273) deliberately keeps anchors off corners (v_max = BOX_H/2 - 1), so a Left/Right side has only 3 usable cells (rows 1-3). Corner slots materially raise the per-room slot budget.
4. This quest SUPERSEDES SQ-0184 (U+2571/2572), now discarded.

Geometry findings (verified against unicodedata, not recall):
- U+1FBA0 upper-centre<->middle-left; U+1FBA1 upper-centre<->middle-right; U+1FBA2 middle-left<->lower-centre; U+1FBA3 middle-right<->lower-centre.
- EVERY endpoint is an edge MIDPOINT, never a cell corner. So these bridge a v-attachment (upper/lower centre, where │ attaches) to an h-attachment (middle left/right, where ─ attaches) — exactly why they join a diagonal into an h/v path cleanly, and why U+2571/2572 (corner-to-corner) cannot.
- Corollary: U+2571/2572 and U+1FBAx live on DIFFERENT sub-grids (corner vs midpoint) and cannot connect to each other.
- Chaining: "U+1FBA3 then U+1FBA0" (L->R) ascends 1 row per 2 cols = true visual 45deg on a 1:2 terminal cell. Mirror "U+1FBA1 then U+1FBA2" descends. A pair spans lower-centre -> upper-centre (both v-attach); cutting a chain mid-pair ends on an h-attach.

BLOCKER to fix: symbols.rs is_wide_estimate (:404-435) blanket-rejects 0x1F000..=0x1FFFF as "Emoji, Mahjong, etc.", which swallows all of U+1FBA0-U+1FBAF. These are NARROW box-drawing glyphs. Hardcoded preset defaults bypass the gate, but style.toml OVERRIDES would be silently rejected — violating the standing "every UI element must be themeable" rule. Carve the 1FBA0-1FBAF range out of that reject list.

FONT RISK: U+1FBAx is Unicode 13 "Symbols for Legacy Computing" — much thinner font coverage than the U+2500 box-drawing block. Keep the existing corner arrows as the default; ship the diagonals so a terminal without the font isn't broken.

Gutter is >=2 wide (MIN_GUTTER) so the corner region is usually free, but overlap_stats (:1797) is the audit that will tell us. If it flags, options: (a) keep the stub to 1 cell, (b) only emit the diagonal when the corner gutter cell is unoccupied (check the accumulated cell_map first), (c) fall back to today's orthogonal stub.

ALSO REQUIRED:
- symbols.rs: add the 4 diagonal slots to PathGlyphs (:37), Default (:112), EVERY preset arm (:269 light/heavy/dotted — PartialEq tests at :520/:540 will catch omissions), and apply_override keys (:473). - Keep the arrows-only look as the DEFAULT preset (font-coverage risk); diagonals opt-in.

GEOMETRY CORRECTION (my earlier compacted note was WRONG and drove a wrong formula): the 🮣🮠 pair spans ONE column per row, not two. Chained pairs OVERLAP by a column (pair k at row cy+k*sy, cols cx+k*sx and cx+(k+1)*sx, resuming at (cx+(k+1)*sx, cy+(k+1)*sy)). That is a 63 degree climb. A true visual 45 is NOT expressible: every half-diagonal spans half a cell across and a full cell down, and there is no shallow variant in the block. So diagonal_col_gap(row_gap) = row_gap (was 2*(row_gap+1)-1, based on the false 45 premise).

OPEN — user asks: "when the rooms can't be perfectly diagonally aligned it looks like we lose the diagonal lines from the corners. is that by design?" ANSWER: no, it is a guard, not a decision. diagonal_chain returns None when n = min(|dy|,|dx|)-1 < 1. For NON-adjacent diagonals the chain targets first_interior = the corner LATTICE pixel, which sits only ONE row out of the box corner inside a 2-row MIN_GUTTER gap => n=0 => no chain => the render falls back to an orthogonal dogleg (`↗─┘`).

R1(0,1) -NE-> R2(2,0) routes as [(0,2),(1,1),(3,1),(4,0)]: (0,2)->(1,1) is a diagonal step, (3,1)->(4,0) is a diagonal step, with an H(0) run between. diag_corners correctly picks up BOTH corners. So the remaining work is renderer-side: (1) draw a diagonal step at the ARRIVAL end too, (2) give the chain room to develop at each end (an H-channel floor for diag_corners, mirroring the existing col floor — the corner-to-lattice hop needs >= 2 rows), (3) note 🮠 alone joins a horizontal run from the WEST to a vertical going north (its middle-left IS a horizontal attachment point), so a 1-cell diagonal corner glyph may be the right handoff in tight gaps rather than a full pair.

--- note 2026-07-15T14:29:22Z ---

Corner-sharing question resolved (user challenged my vague "3+ connectors at a corner" note — they were largely right, and the correction is worth keeping).

CORRECTED: "3+" is impossible. A room has at most ONE edge per direction, so at most one OUTGOING diagonal per corner. The ceiling is 2: one departure + one arrival.

FURTHER: an UNDISTORTED map cannot collide at a corner at all. An undistorted NE edge into R2 requires the origin to be SW-ADJACENT to R2; an undistorted SW edge out of R2 targets that same SW-adjacent cell. So both necessarily involve the same room, and back_edge_idx collapses them into ONE reciprocal connector. => A corner collision REQUIRES at least one distorted diagonal edge.

That case is real, though, and renders visibly garbled. Repro (verified, then removed as scratch):
  R2 (2,2); R1 (1,3) SW-adjacent; R3 (0,4).  add_edge(1, NE, 2); add_edge(2, SW, 3);
  => conn 1->2 arr=(28,4) and conn 2->3 dep=(28,4) — the SAME pixel (R2's SW corner),
     and both claim the same corner LATTICE cell (3,5).
  Render shows overlapping chains: row 19 "🮣🮠🮠", row 20 "┘🮠" — two chains overwriting.

R2's SW edge here points at a cell R1 already occupies, i.e. it is distorted — which is exactly the precondition derived above. Distorted edges are first-class in this codebase (mark_distorted, colors.connector_distorted) and common in real IF maps, so this is worth fixing, but it is NOT a flaw in the corner-arrival design.

Note overlap_stats/connector_ownership use the ORTHOGONAL reading (diag=None) and so would not flag a half-diagonal chain collision at all — any fix needs its own detection, or diag_cells need to participate in ownership.

Not yet decided: whether a distorted diagonal should yield the corner (fall back to a side slot) when the corner is already claimed, or whether the two should share it deliberately.
