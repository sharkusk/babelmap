--- note 2026-07-15T07:00:38Z ---

Design decisions (user, 2026-07-15):

1. SCOPE = stub only. The first 1-2 cells out of the corner are diagonal, then hand off to the EXISTING orthogonal lane router. Router, crossing model, and box stride are all UNTOUCHED. (The full 45-degree stair between rooms stays deferred per the 2026-06-22 diagonals spec.)
2. The corner ARROWS (↗↖↘↙ on the box corner cell, via corner_anchor map.rs:258 / diagonal_arrow) REMAIN as-is. The new diagonal glyphs are used AFTER the arrow, on the OUTSIDE of the box border.
3. Motivation is not just cosmetic: this ENABLES THE 4 CORNER SLOTS as connector attachment points. Today box_edge_anchor (map.rs:1273) deliberately keeps anchors off corners (v_max = BOX_H/2 - 1), so a Left/Right side has only 3 usable cells (rows 1-3). Corner slots materially raise the per-room slot budget.
4. This quest SUPERSEDES SQ-0184 (U+2571/2572), now discarded.

Geometry findings (verified against unicodedata, not recall):
- U+1FBA0 upper-centre<->middle-left; U+1FBA1 upper-centre<->middle-right; U+1FBA2 middle-left<->lower-centre; U+1FBA3 middle-right<->lower-centre.
- EVERY endpoint is an edge MIDPOINT, never a cell corner. So these bridge a v-attachment (upper/lower centre, where │ attaches) to an h-attachment (middle left/right, where ─ attaches) — exactly why they join a diagonal into an h/v path cleanly, and why U+2571/2572 (corner-to-corner) cannot.
- Corollary: U+2571/2572 and U+1FBAx live on DIFFERENT sub-grids (corner vs midpoint) and cannot connect to each other.
- Chaining: "U+1FBA3 then U+1FBA0" (L->R) ascends 1 row per 2 cols = true visual 45deg on a 1:2 terminal cell. Mirror "U+1FBA1 then U+1FBA2" descends. A pair spans lower-centre -> upper-centre (both v-attach); cutting a chain mid-pair ends on an h-attach.

BLOCKER to fix: symbols.rs is_wide_estimate (:404-435) blanket-rejects 0x1F000..=0x1FFFF as "Emoji, Mahjong, etc.", which swallows all of U+1FBA0-U+1FBAF. These are NARROW box-drawing glyphs. Hardcoded preset defaults bypass the gate, but style.toml OVERRIDES would be silently rejected — violating the standing "every UI element must be themeable" rule. Carve the 1FBA0-1FBAF range out of that reject list.

FONT RISK: U+1FBAx is Unicode 13 "Symbols for Legacy Computing" — much thinner font coverage than the U+2500 box-drawing block. Keep the existing corner arrows as the default; ship the diagonals so a terminal without the font isn't broken.

--- note 2026-07-15T07:01:51Z ---

Implementation approach (traced 2026-07-15, ready to build):

WHERE THE CHANGE GOES — plot_connector (app/src/render/map.rs:855). It already synthesizes the cell run locally: dep_anchor (corner_anchor for diagonals, :877) + attach_bridge (:888) -> inner_v. So a diagonal stub can be inserted THERE without touching route_lanes/assign_lanes at all. Router stays untouched, as decided.

CURRENT DEPARTURE GEOMETRY (the thing to work with):
- NE -> corner_anchor = (bx+BOX_W-1, by) = top-right corner cell; the ↗ arrow replaces ╮ there (stays).
- side_for collapses NE->Top / SE->Bottom / NW->Top / SW->Bottom (router.rs:70). So conn.exit = Top for NE.
- attach_bridge(anchor, interior, Top) => turn = (anchor.0, interior.1): the bridge runs STRAIGHT UP the corner's own column, THEN steps east. So today the first cells out of an NE corner are vertical on column bx+10, not diagonal.

GLYPH PLUMBING — do NOT try to express a diagonal in the existing 4-bit mask. glyph_for (:767) is driven by DIR_N/E/S/W bits and dir_bit (:1317) would misfile a (+1,+1) step as East (there's a debug_assert at :924 requiring orthogonal bridges). Instead give ConnectorPlot an explicit per-cell glyph override list (e.g. diag_cells: Vec<((i32,i32), char)>) painted directly in render_lane_connectors (:1046) alongside the mask-driven cells. This keeps the mask-OR crossing model and overlap_stats semantics untouched.

OPEN RISK to resolve during build: a diagonal stub moves up-AND-right, leaving the column the router reserved and entering the vertical gutter channel — cells assign_lanes never allocated. Gutter is >=2 wide (MIN_GUTTER) so the corner region is usually free, but overlap_stats (:1797) is the audit that will tell us. If it flags, options: (a) keep the stub to 1 cell, (b) only emit the diagonal when the corner gutter cell is unoccupied (check the accumulated cell_map first), (c) fall back to today's orthogonal stub.

ALSO REQUIRED:
- symbols.rs: add the 4 diagonal slots to PathGlyphs (:37), Default (:112), EVERY preset arm (:269 light/heavy/dotted — PartialEq tests at :520/:540 will catch omissions), and apply_override keys (:473). Note PathGlyphs is Copy and map.rs:1013 rebuilds it with ..*path, so new fields flow through automatically.
- symbols.rs is_wide_estimate (:431): carve U+1FBA0..=U+1FBAF out of the 0x1F000..=0x1FFFF reject range or overrides are silently dropped.
- Keep the arrows-only look as the DEFAULT preset (font-coverage risk); diagonals opt-in.

PRE-EXISTING INCONSISTENCY worth knowing (not caused by this): Zoom::steps() says the Boxes stride is 19x11, but Boxes rendering actually uses boxes_axes (:225) with a NON-uniform, lane-count-dependent stride (BOX_W 11 + channel_width, min gutter 2). cell_to_screen/screen_to_cell (:308/:335, hit-testing) still use the 19x11 figure; room_screen_rects (:348) correctly uses the axes tables.

So all three PathGlyphs presets (light/heavy/dotted) share the same 4 chars, exactly mirroring how "dotted" already falls back to light corners for turns. No per-preset glyph hunting.
