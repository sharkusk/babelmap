--- note 2026-08-12T07:32:41Z ---

USER 2026-08-12: *"if i select the fmvpoker.eg1 the colors and graphics are different than the blorb"*. Measured while answering — two separate causes, and the second is a real gap.

    FMVPOKER.EG1   byte-identical to zork0.eg1   503 entries, 396 with data, ids 1..504
    fmvpoker.blb   2213 Pict resources, ids 1..2709

**`fmvpoker.blb` IS Zork Zero's Blorb** — the same 2213-resource profile SQ-0713 recorded for `Zork0.blb` (2106 PNG + 107 Rect). So this is two renditions of one artwork set, and:

1. **Colours differ legitimately.** EGA draws from the 16-colour hardware palette (SQ-0794); the Blorb carries MCGA's per-picture palettes. Same art, different colour capability — that is what choosing a rendition means, and it is working as designed.

2. **GRAPHICS differ because the native archive is a strict subset.** Every native archive stops at **id 504**; the Blorb reaches **2709**. SQ-0713 measured that 1000–2709 block as Zork Zero's **graphical map and minigame UI** — 1250 tiles at 21x21, 180 at 27x11, 160 at 45x40, plus compass needles and EXIT / SHOW MOVES / UNDO / RESTART buttons — stored 3–6 times over in different colour schemes, and matching **nothing** in any of the five archives (all three PC files and both Amiga sources stop at 504). It has a third input nobody has identified.

**SO TIER 3 CURRENTLY TRADES ~1700 PICTURES FOR A COLOUR CHOICE, SILENTLY.** A user who picks `.eg1` for Zork Zero or fmvpoker gets EGA colours and loses the map and UI art. Nothing says so.

**FIX OPTIONS, none chosen — this needs a decision before code:**

- **(a) Composite: native first, Blorb for ids the archive lacks.** Keeps the rendition's look for the art it has, keeps the game working. Cost: the frame becomes a mixture of two colour treatments, which may look worse than either alone — EGA tiles beside MCGA-derived ones. Also quietly contradicts SQ-0734's "a named archive wins outright", which was written when the alternative was *no art*.
- **(b) Refuse and explain.** If the named archive cannot serve every id the story draws, say so up front rather than after the map appears blank. Honest, but makes tier 3 useless for exactly the title it was demonstrated on.
- **(c) Warn and proceed.** Draw what the archive has, tell the user what is missing. Cheapest, and consistent with the project's existing preference for loud degradation over silent.

**MEASURE BEFORE CHOOSING:** does Zork Zero actually *draw* ids above 504 during play, or are they reachable only through the map/minigame screens? If the latter, the loss is bounded and (c) is plainly right. If the game draws them in the ordinary frame, (a) or (b) is forced. Nobody has checked.

**ALSO WORTH RESOLVING:** SQ-0713 left the 1000–2709 block's provenance open. Now that the Blorb is known to be an **MCGA conversion** (SQ-0795), and no PC archive carries those ids, the third source is still unaccounted for. Candidates: a later re-release, a Mac archive, or art generated by whoever built the Blorb. Identifying it would say whether a native rendition *could* ever be complete.

RELATED: SQ-0798 (multi-part archives — a different completeness gap, where the fix is clear), SQ-0734 (the resolution policy this may amend), SQ-0713 (where the 1000–2709 block was catalogued).

**PREMISE WRONG — discarded 2026-08-12. The user refuted it from play, and the answer was already on SQ-0713.**

> "map works fine in native mode. i thought you already investigated that difference and found those extra blorb images were pre-renders of the palettes"

Both halves correct.

**SQ-0713 correction #3 (2026-08-09) established it:** the Blorb's 1000–2709 block is **the same artwork stored 3–6 times over in different colour schemes**. Measured colour-blind — hashing palette *indices* rather than RGB — the block collapses hard:

    size    images  distinct pixels  distinct shapes
    21x21     1250      1000              219
    27x11      180       180               36
    45x40      160       156               49
    62x9        70        70               22

and was visually confirmed: ids 1016-1023 and 1700-1707 are the identical line-art icon set in grey and in orange; 1160-1166 the same EXIT / SHOW MOVES / UNDO / RESTART buttons twice; 1141-1822 one arch in five border colours.

**WHY THE BLORB NEEDS THEM AND THE NATIVE PATH DOES NOT:** a Blorb resource is a PNG, which carries its own colours — the format has no adaptive-palette concept, so every recolour permutation had to be baked out as a separate id. The native path recolours at draw time: the game sets a palette and redraws the same stored shape, which is the adaptive path (`PicEntry::has_own_palette` / `rgba_with`, and the adaptive set SQ-0794's lane worked with). **One stored shape plus N palettes replaces N stored pictures.**

So the id-count gap is an artifact of the Blorb's format, not missing artwork. Nothing is lost by choosing a native rendition, and the user's map rendering correctly in native mode is the direct proof.

Nobody has checked."* — and then presented the gap as established anyway. The check was one play session, and the answer was already written down on SQ-0713 from three days earlier. **Read the related quest before filing the consequence.**

The regeneration mechanism is ordinary adaptive palettes, not a remap — which is what makes it work.
