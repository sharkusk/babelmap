--- note 2026-08-14T20:00:03Z ---

MEASURED off `masterpieces/Masterpieces-HFS.img` (294 MB, extracted from the hybrid CD's third partition; the CD itself is `masterpieces/Classic Text Adventure Masterpieces of Infocom (USA).bin`, MODE1/2352):

```
MDB signature 'BD', volume name 'Masterpieces', 770 root entries
drNmAlBlks  64,998  x drAlBlkSiz 10,240  =  665,579,520 bytes ALLOCATED
drFreeBks   34,958                       =  357,969,920 bytes FREE
used                30,040               =  307,609,600 bytes USED
drAlBlSt    19 (512-byte units) = byte 9,728
used data therefore ends at 307,619,328; the dump is 307,992,064 — 372,736 bytes SPARE
```

So every allocated block is present and only trailing FREE space is missing. The volume is complete and should mount. `zvm-cli` currently answers `Z-machine version 0 is not supported`, i.e. the mount was declined and the file fell through to being read as a raw story.

THE FIX IS ABOUT WHICH QUANTITY IS CHECKED. A bound of "nominal volume size must fit inside the file" is the wrong test for any HFS volume that does not occupy its whole container — and on a **hybrid CD that is the normal case**, because the Apple_HFS partition is sized for the disc and shares it with the ISO9660 side. Here the partition map claims 634.8 MB of a disc whose total user payload is 308 MB, which is impossible on its face and is not a sign of damage. The right check is that every block a reader actually FOLLOWS is inside the file — catalogue, extents overflow, and each file's own extents — with a truncated tail tolerated. Read `crates/blorb/src/hfs.rs` and find what actually rejects it before changing anything; my reading of the symptom is not a reading of the code.

Guard hard against the opposite error: a genuinely truncated volume, where a file's extents point past the end, must still be refused rather than yielding half a story. `stories/Zork Zero Disk.image` and `stories/InfocomMasterpieces.img` are the intact controls — both must keep mounting unchanged, the latter still offering its 33 stories.

FIXTURE CAUTION: do NOT copy the 294 MB image into `stories/`. Several suites sweep every file in that directory (`art_build_pairing`, `real_media_releases`, the ProDOS census, the picker scan), and a 294 MB member would be read repeatedly and slow the whole gate. Point the test at `masterpieces/` and skip cleanly when absent, exactly as the `stories/` cases do — CI has neither directory.

WORTH KNOWING: this unlocks nothing that is otherwise unreachable. `stories/InfocomMasterpieces.img` is the same Macintosh collection at 12 MB and already mounts with 33 stories, including a Journey at r26/s890316 we have from no other source. What the CD adds is the documentation and the PC side. So the value here is the CORRECTNESS of the bound, not the content behind it.

--- note 2026-08-14T20:04:53Z ---

WIDENED, because extracting a 294 MB partition by hand to work around a bounds check is the wrong shape. Read the CD directly. The two halves belong in one quest: reading the disc is pointless without the bound fix, and the bound fix's only new fixture is the disc.

DETECTION IS BY CONTENT, no `.cue` required — measured on `masterpieces/Classic Text Adventure Masterpieces of Infocom (USA).bin`:

```
every sector (0, 1, 16, 150514): sync = 00 ff ff ff ff ff ff ff ff ff ff 00, mode byte = 1
size 354,011,280 / 2352 = 150,515 exactly
```

That is the canonical MODE1/2352 signature, so the `.bin` self-describes and no file pairing is needed. The chain:

1. Sniff raw 2352-byte sectors (sync pattern + whole-number sector count).
2. User data is 2048 bytes at offset 16 of each sector.
3. `ER` at logical sector 0 = Apple driver descriptor; block size and count follow at +2 and +4 (measured: 512 and 1,300,492).
4. Walk the Apple Partition Map at that block size. Measured here: `Apple_partition_map` (3 blocks), `ISO9660_system` (509), and `Masterpieces` / `Apple_HFS` at start block 513, 1,299,979 blocks.
5. Hand the Apple_HFS partition's byte offset to the existing HFS reader.

ARCHITECTURALLY this is a WRAPPER, not a new reader — the same shape `volume_at` already uses to choose between a bare volume and a 2IMG header, and `hfs.rs` uses to unwrap DiskCopy 4.2 (which SQ-0863 noted is private with five constants and would need a home if shared). A raw-CD unwrap plus an APM is one more transform ahead of the same filesystem.

Two extras worth deciding rather than assuming:
- A plain 2048-byte `.iso` of a hybrid disc has the APM but no sync pattern. Supporting it is nearly free once the APM walk exists; say whether you did.
- The ISO9660 side of this disc holds the PC release — 216 files under `PC/`, every game's `.DAT` plus Arthur's four artwork archives. Reading THAT is a separate capability and is NOT in scope; do not start it.

Everything in the earlier note still stands: the used/free measurement, the guard that a genuinely truncated volume must still be refused, the intact controls, and the caution against putting a 294 MB fixture in `stories/`.
