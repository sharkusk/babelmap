--- note 2026-08-10T16:37:43Z ---

RESEARCHED under SQ-0762, 2026-08-10. Recommendation was "worth a time-boxed experiment, not now-work" — filed here so the findings survive that quest closing.

WHY IT MATTERS: the pty harness (SQ-0762) reads the bytes we EMIT. libghostty would tell us how Ghostty PARSES AND RESOLVES them — the layer that has defeated every investigation into defects correct in our model and wrong on the user's screen.

THE FOUR QUESTIONS, answered:

1. **What it exposes.** `libghostty-vt` is the relevant piece: parser plus terminal state, exposed as STATE not pixels (`vt/render.h`: row iterators, per-cell grapheme/style/resolved fg+bg/dirty). The GUI-surface API is a separate, explicitly unstable surface we would not touch.

2. **Kitty graphics — yes, and this flipped in our favour during 2026.** Issue #12111 originally said no; superseded by PR #12147, merged 2026-04-06 (v1.4.0), adding `vt/kitty_graphics.h`: raw pixel buffer plus a **placement iterator** giving image id, z-order, cell span, viewport-relative position and layer. Demonstrated by ghostling PR #13, a full kitty renderer in ~270 LoC. For a harness this is BETTER than a framebuffer — assert on resolved geometry rather than pixel-diffing, which is both more stable and more diagnostic.

3. **Toolchain.** Rust bindings exist (`libghostty-vt` / `-sys`, `Uzaaft/libghostty-rs`). Needs Zig 0.16.x on PATH. No GPU or GUI toolchain; inherently headless.

4. **Licence.** MIT (crates MIT OR Apache-2.0). Would stay dev-only regardless.

WHY NOT NOW: pre-1.0 with breaking changes promised, and a four-month-old image API. **The deciding fact is Windows** — a third-party product ships `libghostty-vt` on Windows x64 MSVC, but the Rust crate documents only Linux and macOS, and this project must build and test on all three ([[cross-platform-requirement]]). Resolve that before committing to it.

WHAT MAKES IT CHEAP WHEN TAKEN UP: SQ-0762's harness was deliberately split so a libghostty back end slots in behind `decode_capture` and reuses the pty driver unchanged. The experiment is therefore "swap the decoder, re-run the existing assertions", not a new harness.

FIRST TARGET IF IT PROCEEDS: SQ-0763 — an intro splash still placed over 2045 cells of a later frame, with zero `a=d` deletes in a 4.4 MB capture. Our own decoder infers that from the wire; libghostty would resolve it the way Ghostty does and settle whether the user actually sees those pixels.

--- note 2026-08-10T16:41:12Z ---

USER DECISION 2026-08-10, and it resolves the blocker recorded above:

> "We can also treat the libghostty harness as a debug-only tool since both our dev platforms support it. Any issues found need to be written into unit tests that repro on all three platforms (outside of libghostty.)"

So the Windows question — the single fact that made this "not now" — is answered by scope rather than by porting. libghostty is a **developer-machine investigation tool**, not part of the committed suite:

- It may be macOS/Linux only. Both dev platforms have it; [[cross-platform-requirement]] is not violated because nothing shipped or gated depends on it.
- It must NOT become a dependency of the app, of any crate, or of the test gate. Nothing in `cargo test -p blorb -p zvm -p gvm -p scott -p app` may require Zig or libghostty to be present, and the gate must pass identically on a machine without them.
- **Every defect it finds gets a committed regression test that reproduces WITHOUT it**, on all three platforms. libghostty's role is to *locate* a defect that our own harnesses cannot see; the proof that it is fixed and stays fixed lives in an ordinary test.

That last point is what makes this safe, and it matches how SQ-0762's pty harness already earned its place: it found that Journey's fill overrun reaches the terminal as SGR spans rather than a placement rect, and that finding is now pinned by ordinary cell-buffer assertions. Same pattern — a sharper instrument feeding conventional tests.

STATUS CHANGE: no longer blocked. The remaining work is the experiment itself — swap a libghostty back end in behind `decode_capture` (SQ-0762 split the harness for exactly this) and re-run the existing assertions. First target stays SQ-0763: the intro splash still placed over 2045 cells of a later frame with zero `a=d` deletes, which our decoder infers from the wire and libghostty would resolve the way Ghostty does.

--- note 2026-08-11T15:09:34Z ---

TOOLCHAIN GATE RUN 2026-08-11. libghostty-vt is NOT viable on this machine; pivoting to a pure-Rust port. All measured, not recalled.

WHAT KILLED libghostty-vt HERE:
1. crates.io `libghostty-vt` 0.2.1's `-sys` build.rs git-clones ghostty at pinned commit a887df42, whose build.zig gates on `minimum_zig_version = 0.15.2` EXACTLY (zig 0.16.0 fails the gate outright: std.Build API drift, `readFileAlloc` signature).
2. zig 0.15.2 cannot link ANYTHING on this machine — a trivial hello-world dies with the same undefined-symbol wall (`__availability_version_check`, `_abort`, `_bzero`, `_getenv`...). Host is macOS 26.5.2; zig 0.15.2 predates that OS line. `SDKROOT="$(xcrun --show-sdk-path)"` made no difference. zig 0.16.0 builds and runs hello-world fine, so the toolchain is not at fault — the pin is.
3. Upstream HAS moved: `libghostty-rs` master (rev 46a68c63) pins ghostty ab0b9da9, which declares `minimum_zig_version = 0.16.0` — unreleased, reachable as a rev-pinned git dep. That got past the version gate.
4. But `zig build` then failed fetching ~16 pinned dependency tarballs from deps.files.ghostty.org: `TlsInitializationFailed` on every one. Cause: DNS returns AAAA, this host has NO global IPv6 address, and zig's std.http.Client has no Happy-Eyeballs/IPv4 fallback. Verified: plain `curl` → 200 in 0.16s; `curl -6` → timeout at 8s. Reproduced with the Claude sandbox DISABLED, so it is the real network, not a sandbox artifact. Two attempts, then time-boxed.
5. Side-finding worth keeping: even the scoped `zig build -Demit-lib-vt=true -Demit-xcframework=false -Dapp-runtime=none` fetches ghostty's ENTIRE third-party graph — sentry, breakpad, spirv-cross, glslang, dcimgui, freetype, libpng, oniguruma, zlib, wuffs, vaxis, libxev, z2d, zf. A headless VT core costs a full GUI dependency set. Not a lightweight build even when it works.
6. No prebuilt escape hatch locally: Homebrew's ghostty ships no libghostty-vt artifact, and there is no ghostty pkg-config module.

THE FALLBACK, IF LITERAL-GHOSTTY GROUND TRUTH IS EVER NEEDED (user's idea, and it is sound): `libghostty-vt-sys` has a `pkg-config` feature — with it enabled and GHOSTTY_SOURCE_DIR unset, build.rs probes for an installed `libghostty-vt-static` and SKIPS ZIG ENTIRELY. So a GitHub Actions matrix (macos-latest + ubuntu-latest, IPv4-only runners, so no fetch wall) can build the static lib + headers + generated .pc, publish them as release assets, and dev machines link the prebuilt via PKG_CONFIG_PATH in seconds. Costs: platform matrix, a publishing tag separate from user-facing babelmap releases, rebuilds when the pin moves, and C-API skew risk against the checked-in bindings (pre-1.0, no compat promise).

PIVOT — `qwertty-term-vt` 0.4.0 (github.com/joshka/qwertty-term), Ghostty's terminal core PORTED TO PURE RUST. Verified by reading the crate source:
  - src/kitty/{command,exec,image,render,storage,unicode}.rs — `render::resolve_placements`, `RenderImagePlacement`, `storage::Placement`, `unicode::PlacementIterator`; resolves BOTH pin-anchored and virtual (U=1) placements, and virtual-with-unicode-placeholders IS babelmap's path.
  - ONE runtime dependency: base64. No zig, no clone, no build script.
  - 1619 unit tests in src, plus a `parser_vte_differential` suite and a unicode cross-check.
  - MIT OR Apache-2.0, edition 2024 (fine on rustc 1.97.1).
  - Pure Rust ⇒ builds on WINDOWS, which collapses the original design's awkwardness: this can be an ordinary dev-dependency whose findings become committed tests on all three platforms, instead of a dev-machine-only tool whose findings must be re-expressed by hand.
CAVEAT: it is a port, so the oracle is "Ghostty's algorithm as reimplemented", not Ghostty's own code. Sufficient for our questions (does this placement cover these cells; is that splash still resolved); the Actions route above is the escalation if literal fidelity is ever required.

USER DECISION 2026-08-11: pivot to qwertty-term-vt; keep the GitHub Actions plan documented as the fallback.

--- note 2026-08-11T15:23:39Z ---

GATE PASSED 2026-08-11 with qwertty-term-vt 0.4.0. Measured, not recalled.

COST: 3 packages total in the lockfile (probe + qwertty-term-vt + base64). No build script (`build = false`), no zig, no C, no external toolchain. Clean release build of probe+deps 2.92s wall. Zero warnings. Parsed a real 3.7 MB babelmap capture in 78 ms.

THE API, as actually compiled and run (Lane B builds from this):
  - `Terminal::new(Options { cols, rows, max_scrollback, ..Default::default() })`; pixel size is NOT a ctor arg — set the public fields `t.width_px`/`t.height_px`, then `TerminalGeometry::new(cols, rows, width_px, height_px)`. Cell size is implied (width_px/cols), never passed.
  - Feed: `Stream::new(TerminalHandler::new(t))`, `stream.feed(bytes)`, take it back via `stream.handler.terminal`. One-shot 3.7 MB feed == 64 KiB chunks, byte-identical.
  - `resolve_placements(&screen.kitty_images, &screen.pages, &geo, 0)`; `t.screen()` returns the ACTIVE screen, so babelmap's ?1049 alt screen needs no special handling.
  - `snapshot_window(0)` gives owned rows/cells — `cell.ch`, `cell.style.fg/bg` as `SnapshotColor::{Default,Palette,Rgb}`. No lifetimes to fight.
  - `storage.placements` exposes `Location::{Virtual,Pin}` + the AUTHORED z; `kitty::unicode::placement_iterator` gives exact CELL width/height plus decoded image_id/placement_id.

SHAPES THAT WILL BITE LANE B:
  - A virtual placement resolves to ONE `RenderImagePlacement` PER ROW (a 40x21 image → 21 entries). Aggregate by image_id to recover a rect.
  - `RenderImagePlacement` carries NO placement id and NO virtual flag, and hardcodes `z = -1` for virtual (render.rs:373) — the transmit's authored `z=` is discarded. Read `storage.placements[key].z` if the authored value matters.
  - Cell-rect via `dest_width.div_ceil(cell_w)` under-reports when aspect-fit shrinks the image inside its cell box. Prefer `placement_iterator`'s exact cell width/height.
  - `Pin::up` is `pub(crate)`, so an out-of-crate caller cannot reconstruct a scrollback-offset window; you can only walk from `pages.get_top_left(Tag::Screen)`. Equivalent for babelmap (alt screen, no scrollback), not in general.

AGREEMENT WITH OUR OWN DECODER, on a real Journey ADF capture (117x64, 8x18px cells, kitty negotiated, 897 APC _G commands): 5 of 6 placements match EXACTLY on rows and columns. Backgrounds agree cell-for-cell across all 64 rows, including the two cases the harness exists to separate (#222222 rows 4..52 cols 2..46 = paint-not-image in both; #000000 rows 1/53..61/63 = paint-not-image in both). Note the two decoders name images differently: ours by the LOW 24 BITS (the fg colour), qwertty by the full 32-bit `i=` value; `full = low24 | (high_byte << 24)`.

PROTOCOL COVERAGE VERIFIED BY RUNNING: `a=d,d=I` deletes image+placements (2→0); placement replacement via re-transmit updates stored geometry; scrolling decrements grid_row and culls out-of-window; chunked 689-part base64 RGBA (f=24 and f=32, t=d) reassembles a 2.1 MB image intact. NOT tested: PNG f=100, t=f/t=t file transfers, animation a=a, the other d= selectors, and pin-anchored placements against real babelmap bytes (babelmap emitted only U=1 here).

GAPS: one story, one screen, one size (Journey ADF r30 at 117x64). Hybrid only. The oracle is Ghostty's algorithm as ported (tracking ghostty 2da015cd6, 297-entry diacritic tables matching kitty's published list) — not Ghostty itself.

--- note 2026-08-12T03:18:53Z ---

WHAT SHIPPED, and why the quest's original title is no longer what it delivered: libghostty-vt itself was evaluated and REJECTED on measured grounds (the toolchain-gate note above — zig 0.15.2 cannot link on macOS 26.5.2, and ghostty's own fetcher has no IPv4 fallback on this host). The deliverable is the pivot: a placement oracle built on `qwertty-term-vt` 0.4.0, Ghostty's core ported to pure Rust — `crates/app/tests/pty_stream/oracle.rs` plus the `raster.rs` side-by-side renderer, slotted in behind `decode_capture` exactly as SQ-0762 split the harness for.

IT EARNED ITS PLACE IMMEDIATELY: it found SQ-0772 on its first real capture, and it caught a first-cut regression that trimmed a row off Zork Zero's banner — a defect no cell-buffer test would have seen. That is the layer this quest existed to reach.

THE GITHUB ACTIONS FALLBACK REMAINS DOCUMENTED, not built: `libghostty-vt-sys`'s `pkg-config` feature skips zig entirely against a prebuilt static lib, so a macos+ubuntu matrix could publish literal-Ghostty ground truth as release assets. That escalation is only needed if the port's fidelity is ever the thing in question — see `docs/architecture.md` for the oracle's stated caveats (the id-encoding mismatch between the two decoders, the SQ-0772 image-coverage gap).

GAPS carried forward rather than closed: coverage is one story, one screen, one size (Journey ADF r30 at 117x64), hybrid only; PNG f=100, t=f/t=t file transfers, animation a=a and pin-anchored placements against real babelmap bytes are untested because babelmap emitted only U=1 there.
