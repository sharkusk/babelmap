RESEARCHED under SQ-0762, 2026-08-10. Recommendation was "worth a time-boxed experiment, not now-work" — filed here so the findings survive that quest closing.

WHY IT MATTERS: the pty harness (SQ-0762) reads the bytes we EMIT. libghostty would tell us how Ghostty PARSES AND RESOLVES them — the layer that has defeated every investigation into defects correct in our model and wrong on the user's screen.

THE FOUR QUESTIONS, answered:

1. **What it exposes.** `libghostty-vt` is the relevant piece: parser plus terminal state, exposed as STATE not pixels (`vt/render.h`: row iterators, per-cell grapheme/style/resolved fg+bg/dirty). The GUI-surface API is a separate, explicitly unstable surface we would not touch.

2. **Kitty graphics — yes, and this flipped in our favour during 2026.** Issue #12111 originally said no; superseded by PR #12147, merged 2026-04-06 (v1.4.0), adding `vt/kitty_graphics.h`: raw pixel buffer plus a **placement iterator** giving image id, z-order, cell span, viewport-relative position and layer. Demonstrated by ghostling PR #13, a full kitty renderer in ~270 LoC. For a harness this is BETTER than a framebuffer — assert on resolved geometry rather than pixel-diffing, which is both more stable and more diagnostic.

3. **Toolchain.** Rust bindings exist (`libghostty-vt` / `-sys`, `Uzaaft/libghostty-rs`). Needs Zig 0.16.x on PATH. No GPU or GUI toolchain; inherently headless.

4. **Licence.** MIT (crates MIT OR Apache-2.0). Would stay dev-only regardless.

WHY NOT NOW: pre-1.0 with breaking changes promised, and a four-month-old image API. **The deciding fact is Windows** — a third-party product ships `libghostty-vt` on Windows x64 MSVC, but the Rust crate documents only Linux and macOS, and this project must build and test on all three ([[cross-platform-requirement]]). Resolve that before committing to it.

WHAT MAKES IT CHEAP WHEN TAKEN UP: SQ-0762's harness was deliberately split so a libghostty back end slots in behind `decode_capture` and reuses the pty driver unchanged. The experiment is therefore "swap the decoder, re-run the existing assertions", not a new harness.

FIRST TARGET IF IT PROCEEDS: SQ-0763 — an intro splash still placed over 2045 cells of a later frame, with zero `a=d` deletes in a 4.4 MB capture. Our own decoder infers that from the wire; libghostty would resolve it the way Ghostty does and settle whether the user actually sees those pixels.
