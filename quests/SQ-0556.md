--- note 2026-07-29T16:11:22Z ---

Reported by the SQ-0531 lane, deliberately NOT fixed there — the lane judged that guessing here was exactly the failure mode the project rules warn against, and I agree.

`GlulxSession::restore_game_save` returns the error `Glulx has no game-save (.qzl) format`, so a Glulx in-game `@save` cannot be loaded back through the saves manager (the host "Restore State" path). It still restores correctly through the GAME's own `@restore`.

PRE-EXISTING, NOT A REGRESSION: the old bare `.qzl` failed identically. SQ-0531 changed nothing about this. It is however more jarring now, because after the unification every other engine's `.babelmap` loads from the manager, so Glulx is the one visible hole.

WHY IT IS NOT A ONE-LINER. The two Glulx byte shapes are genuinely different and SQ-0531 pinned that with a test:
  - `@save`  -> `save_quetzal()`  = bare `IFhd` + `CMem` + `Stks` + `MAll`
  - host state -> `save_state()`  = the above plus `GReg` + `Glk `
`restore_quetzal` deliberately preserves the LIVE Glk model (per Glulx spec §1.8.5) rather than reinstating a serialized one. Feeding bare Quetzal into a cold-boot Glk window set is what the host path would have to do, and window ids referenced from the restored RAM may simply not exist in that fresh window set — which is a corrupt-session bug, not an error message.

Possible directions when picked up (unvalidated):
  1. On host-load of an `"ingame"`-trigger Glulx archive, boot the story fresh, let it establish its Glk windows, and only then apply the Quetzal — accepting that any window the game created after the save point is gone.
  2. Have Glulx `@save` seal the richer `save_state()` shape too, so the archive always carries `GReg`+`Glk `, and keep the bare form only for the interchange copy. Costs a format decision.
  3. Detect and refuse with a clear, specific message instead of the current generic one — the cheap honest option if neither of the above proves safe.

Standing gap is already documented in `docs/persistence.md` as of SQ-0531, so the docs are not lying about it in the meantime.

--- note 2026-07-29T16:25:19Z ---

REQUIREMENT CLARIFIED BY THE USER 2026-07-29: **`@save` must behave the same for ALL formats — Z-machine, Glulx, Scott, and any future engine added.**

This reframes the quest. It is not "Glulx has a rough edge we might smooth"; it is "uniform in-game-save semantics is the spec, and Glulx is the one engine violating it." Treat engine-neutral behaviour as the acceptance criterion, and treat it as binding on any engine added later — a new engine is not done until its `@save` archive behaves like the others.

Read the requirement as user-visible BEHAVIOUR being uniform, not bytes being identical: on every engine, `@save` writes a `.babelmap` archive, that archive appears in the saves manager, and it can be restored BOTH through the game's own `@restore` AND through the host restore path. The per-engine byte shape underneath may legitimately differ (the Z-machine's descriptor-PC Quetzal convention is real, per Quetzal §5.8) — what must not differ is what the user can do with the save.

CURRENT STATE, verified in code 2026-07-29:
  - Scott      — `scott_session.rs:268` `restore_game_save` works; one byte shape for both triggers. CONFORMS.
  - Z-machine  — `session.rs:2011` implements it. CONFORMS.
  - Glulx      — `glulx_session.rs:1073` hard-fails: `Err(BadSave("Glulx has no game-save (.qzl) format"))`. VIOLATES.
Note that Glulx's HOST path already works — `restore_state` at `glulx_session.rs:1066` restores fine and calls `refresh_screen()`. The refusal is specific to the bare `@save` bytes, which is what makes this look tractable.

DIRECTION THIS POINTS AT (option 2 from the earlier note is now the favoured one): have the Glulx `@save` archive seal the RICHER `save_state()` shape, so the archive is host-loadable like every other engine's. `save_state()` is a superset of `save_quetzal()` — the bare form is `IFhd+CMem+Stks+MAll`, the host form adds `GReg`+`Glk `. Since the archive already records `Meta::trigger`, the restore side can dispatch on it.

MUST BE VERIFIED, NOT ASSUMED, before implementing:
  1. Does Glulx's in-game `restore_quetzal` TOLERATE the extra `GReg`/`Glk ` chunks being present? It deliberately preserves the LIVE Glk model per Glulx spec §1.8.5, so it must ignore rather than apply them.
  2. Would a FOREIGN Glulx interpreter tolerate those chunks in an extracted `game.glksave`? Check the Glulx save-format spec on unknown-chunk handling before relying on the extract-it-out story. If foreign tolerance is not guaranteed, seal BOTH shapes in the archive rather than picking one.
  3. Whether restoring into a cold-boot Glk window set is safe — the original hazard: window ids referenced from restored RAM may not exist in a freshly booted window set. This is the thing the previous lane refused to guess at, and it remains the real risk.

Do not close this by merely improving the error message; that was listed as the cheap fallback and the user's requirement rules it out as a solution.

See the standing rule recorded in memory as `uniform-save-semantics-across-engines`.

--- note 2026-07-29T16:30:29Z ---

SPEC RESEARCH DONE 2026-07-29 — fetched from authoritative sources, not memory. Two of the three open verification questions are now ANSWERED, which materially de-risks the implementation.

**Q2 — will a foreign interpreter tolerate extra chunks in an extracted `game.glksave`? YES.**
Glulx spec §1.8: the Glulx save-game format "is a variant of Quetzal, the standard Z-machine save file format", so Quetzal's rules carry over. Quetzal §8.9, verbatim: *"Indeed, skipping is the expected procedure for dealing with any unknown or unexpected chunk."* Quetzal §7.17 explicitly sanctions this kind of extension: *"These extensions add no overhead to interpreters which choose not to handle them, except for larger save files and more chunks to skip when reading files written on another program."*
=> Sealing the richer `save_state()` shape (adding `GReg` + `Glk `) into the Glulx `@save` archive does NOT break interchange. A conforming Glulx interpreter skips the chunks it doesn't know. There is no need to seal both shapes; seal the superset.

**Q3 — is restoring into a cold-boot Glk window set safe? REFRAMED, and less scary than it looked.**
Glulx §1.8.5 lists what is deliberately NOT saved, verbatim: *"Glk library state. This includes Glk opaque objects (windows, filerefs, streams). It also includes I/O state such as the current output stream, contents of windows, and cursor positions."* Also unsaved: protected-memory range settings, RNG state, I/O system mode and string-decoding table address.
=> A STANDARD Glulx restore ALWAYS lands in whatever Glk state currently exists — that is the spec-sanctioned normal case, not an edge case, and games are written expecting it. So restoring bare Quetzal into a freshly booted window set is not inherently unsafe. The real remaining hazard is narrower and is babelmap-specific: our non-standard `Glk ` chunk reinstating a STALE window model over a live one. That is what needs care, not the bare path.

Also confirmed from §1.8: chunk set is `IFhd` (associated story file, first 128 bytes of memory), `CMem` (compressed dynamic memory), `UMem` (uncompressed alternative), `Stks`, `MAll` (heap — *"If the heap is not active, the 'MAll' chunk can contain 0,0 or it may be omitted"*, i.e. optional). `GReg` and `Glk ` are NOT standard Glulx chunks — they are babelmap's own extension, exactly the sort §7.17 permits.

**Q1 remains open and is a CODE question, not a spec one:** does Glulx's in-game `restore_quetzal` tolerate `GReg`/`Glk ` chunks being present — ignoring rather than applying them? It must preserve the LIVE Glk model per §1.8.5. The lane must establish this by reading and testing, not by assuming.

--- note 2026-07-29T16:49:52Z ---

Landed on branch worktree-agent-ad213b66c19cbac54, commit 03ddb3d1. Set to confirm (save/persistence per the standing rule), though it is test-verified AND real-game smoked.

MANUAL SMOKE FOR THE USER: run a Glulx story (e.g. Adventure/advent.blb or Counterfeit Monkey), type SAVE in-game and name a slot, play on a few turns, then open the saves manager (Ctrl+L) and press Enter on that slot. Expected: it loads (it used to say 'Glulx has no game-save (.qzl) format'), your windows/status line stay as they are, and your NEXT typed command is acted on rather than swallowed.

Q1 ANSWERED: restore_quetzal already TOLERATES GReg/Glk chunks. Evidence in code: restore_quetzal -> restore_vm_core looks up only CMem/UMem, Stks, MAll; nothing anywhere in that path reads GReg or 'Glk '. Matches Quetzal 8.9 ('skipping is the expected procedure'). Now pinned by gvm test restore_quetzal_skips_greg_and_glk_chunks_and_never_reinstates_a_stale_window_model, which feeds it a full save_state() blob AFTER splitting a second window into the live model and asserts the live tree survives.

DESIGN DECISION - the quest's favoured direction was REJECTED, with reasons. Sealing the richer save_state() into the @save archive would put a serialized window tree (Glk chunk) in the file, which is exactly the stale-window-model hazard the quest flagged; and it does not even work, because restore_state applies GReg's pc/sp without popping @save's call stub. The bare IFhd/CMem/Stks/MAll shape is the right thing to seal precisely because it carries nothing a restore could snap a stale layout back from. So NO format change: CURRENT_FORMAT_VERSION stays 5, the sealed bytes are byte-identical to before, no freeze-test/inventory/version-history churn.

THE NON-OBVIOUS BUG THIS UNCOVERED: a host restore arrives while the session is parked inside a glk_select belonging to the run being left, and 1.8.5 keeps that suspension out of the save file. Left in place, Machine::step short-circuits on it and never reaches the restored PC, and the player's next command is swallowed answering it. Real Adventure prints 'Ok.' (the save-verb tail) instead of moving. New gvm API Machine::abandon_pending_input retires it. Verified by mutation: deleting that one call makes both the synthetic and the real-game test fail.

BONUS, UNTESTED BY ME: a bare Glulx .qzl carried in from gvm-cli now host-loads too (same restore_from_file path).

POSSIBLE FOLLOW-UP, deliberately NOT done (no user request): persist_files::is_game_save only recognises .qzl, so a bare interchange file named .glksave is treated as an archive and fails to load. Worth a separate quest if anyone hits it.
