--- note 2026-08-12T06:09:09Z ---

MEASURED, 2026-08-11, on real media in `stories/`. EGA and CGA archives are NOT 320-wide archives with a different palette — they store the same artwork in a 640-wide picture space with pixels half as wide:

    file          hdr flags   picture space   picture 1
    zork0.mg1        0x30          320         320x200
    zork0.eg1        0x38          640         640x200
    zork0.cg1        0x38          640         640x200
    zork0.pic        0x06          320         320x200
    arthur.eg1       0x38          640         584x196
    journey.eg1      0x39          640         220x127
    FMVPOKER.EG1     0x38          640         640x200   (byte-identical to zork0.eg1)

The declaration is header byte 1 (`gh.flags`) bit 3, and three independent witnesses agree on it: Frotz `src/curses/ux_pic.c:126` (`x_scale = (flags & 0x08) ? 640 : 320`), Spatterlight bocfel's `hw_screenwidth`/`pixelwidth` table in `z6/find_graphics_files.cpp` (EGA/CGA -> 640 wide, pixelwidth 0.5; VGA/Amiga/Blorb -> 320, 1.0; MacBW -> 480; Apple II -> 140, 2.0), and this corpus. Now exposed as `blorb::infocom_pics::InfocomPics::picture_space_width()` and pinned by `each_rendition_declares_its_picture_space`.

WHY IT CANNOT BE SCALED INTO PLACE TODAY. `crates/app/src/session.rs` applies `V6_ART_SCALE`, ONE uniform integer, to both axes of both the picture-dimension table and the screen. A 640x200 EGA plate on the 640x400 unit screen needs scale (1, 2) — non-square — which that rule cannot express.

WHAT IT ACTUALLY WANTS, and why this is a profile rather than a scale factor: EGA ran 640x200 with an 8x8 character cell, which is still 80x25 characters. So the EGA rendition wants a 640x200 SCREEN on an 8x8 cell, not 640x400 art on an 8x16 one. That is a sixth knob of `InterpreterProfile` (`v6_font_cell`, currently pinned at (8,16) for both profiles against `zvm::screen::V6_FONT_WIDTH/HEIGHT`) plus everything downstream in the render path — hence a real piece of work, and hence out of SQ-0734's scope.

SHIPPED BEHAVIOUR IN THE MEANTIME, chosen deliberately and documented in `docs/features/v6-graphics.md`: `PictureOverride::std_window()` supplies (320,200) for a 320-wide archive (Amiga `Pic.data`, MCGA `.MG1`) — so those land pixel-for-pixel where the Blorb's art did, doubled onto 640x400 — and returns `None` for a 640-wide one. `None` is Blorb §11's own answer for art that declares no resolution: drawn at actual size, one image pixel per screen pixel. Measured: fmvpoker boots clean with `FMVPOKER.EG1` (no fault, same 6-item Layered root, same 640x400 native extent) and its art occupies 640x200 of the 640x400 screen. Not the intended EGA presentation; not broken either. `a_320_wide_rendition_supplies_the_standard_window_and_a_640_wide_one_defers` pins the deferral so it stays a decision rather than becoming an accident.

Consequence worth noting for whoever picks this up: MCGA is the DOS rendition that works correctly today, so `pictures = "zork0.mg1"` is the one to recommend to a user who wants DOS art now.

--- note 2026-08-12T06:39:05Z ---

IMPLEMENTED 2026-08-11 (ddc410b4, worktree branch — not merged). One correction to this quest's own premise, which is why it came in far smaller than it was scoped.

**The font cell did NOT need to move, and `InterpreterProfile` did not need a new variant.** EGA's 640x200 on an 8x8 cell is 80x25 characters — the SAME character grid the existing 640x400 unit screen already lays out on its 8x16 cell. Halving both axes buys an identical grid with half the vertical precision for window and cursor coordinates, at the price of making `V6_FONT_WIDTH`/`V6_FONT_HEIGHT` runtime state across ~40 sites in zvm's screen model, its location heuristics and the app render path. `v6_font_cell` stays (8, 16) for every profile, now with the reasoning recorded on it.

What genuinely differs is the ART DENSITY, and that belongs to the archive, not the machine — this quest's own `for_art_flavour` doc already says MCGA/EGA/CGA are "three video cards, one machine, and that machine is the IBM PC", and a profile variant would have contradicted it. So:

- `PictSource::art_scale() -> Option<(u32, u32)>`: 320-wide picture space -> (2, 2), 640-wide -> **(1, 2)**. `None` for a Blorb, which keeps the uniform rule.
- `PictureOverride::std_window()` now answers `Some((320, 200))` for EVERY loaded archive. The deferral test `a_320_wide_rendition_supplies_the_standard_window_and_a_640_wide_one_defers` is replaced by `every_rendition_supplies_the_same_standard_window`.
- `GameSession::art_scale` is a pair; `new_with_trace` keeps its 9-arg signature and delegates to a new `new_with_art_scale` with `None`, so all 150 existing call sites (84 files) are untouched and provably identical.

MEASURED CONFIRMATION, real media in `stories/`, unit-space dims under (1, 2):

    arthur.mg1 vs arthur.eg1   125/125 identical   (uniform (2,2): 5/125)
    zork0.mg1  vs zork0.eg1    446/503 identical   (uniform (2,2): 20/503)
    zork0.mg1  vs zork0.cg1    295/503 identical   (uniform (2,2): 20/503)

picture 1 is exact in all three. Arthur at 125/125 is the decisive case; the residue elsewhere is separately drawn artwork, not a scaling error. Bocfel's final blit (`draw_image.cpp:251`) reduces to `gscreenw * H / 320` for both `pixelwidth` values, which is the same claim arrived at independently.
