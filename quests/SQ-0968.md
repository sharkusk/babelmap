--- note 2026-08-21T16:13:25Z ---

## An instrument that showed a defect the bytes prove was already fixed

The SQ-0948 lane reports that `pty_capture --png` "composites a band's transparency onto something stale and showed the left block as still present after it was gone from the emitted bytes." The lane only got past it by decoding the kitty APC payloads back to RGBA by hand and reading the actual pixels — which is what finally showed a THIRD left-flank band still carrying the fill.

That makes this the worst kind of harness defect: it does not fail, it lies, and it lies in the direction of "your fix did not work". A reader who trusts it re-fixes something that is already correct.

## Why it matters more here than it would elsewhere

CLAUDE.md's whole render-testing doctrine is a ladder — cell buffers, then the emitted stream, then the placement oracle — with each rung reached for when the one below cannot explain the symptom. `--png` sits at the top of that ladder as the thing you LOOK at when the numbers are exhausted. Its own module (`tests/pty_stream/raster.rs`) already carries a caveat that it is honest about layout, art placement and colour and about nothing else, and SQ-0932 added a warning that better type made it MORE tempting to read as a screenshot. This is a different failure from either: not "do not over-read it", but "it can be wrong about the thing it is for".

## Shape of the investigation

The composite is built from bands, and a band ships with alpha (or, since SQ-0944, without it on half-blocks). If the raster path composites a band over whatever the previous frame left in that region rather than over a defined ground, a stale placement survives visually after the stream stopped carrying it. Suspects: the frame-shared `chrome_scaled` cache, the `chrome_bands` cache (keyed on the band's own native footprint plus, since SQ-0944, `band_ground`), and whether the PNG path clears its target between frames at all.

Whatever the cause, the fix must leave the ladder's ordering intact: the emitted stream is the ground truth this instrument is supposed to VISUALISE, so where they disagree the bytes win, and the picture should be derived from them rather than accumulated across frames.

Worth adding a case that would have caught it: render two frames where the second removes a placement the first had, and assert the second PNG does not contain it.

--- note 2026-08-21T20:36:49Z ---

## Resolved: the reported symptom did not reproduce; an adjacent real defect did

**The Shogun specimen exonerates the instrument.** Captured `stories/shogun-r322-s890706.z6` (r322 / s890706, IBM PC) at 117x40, 8x18 cells, two turns in (`cr` off the boot menu, then `look`) — the SQ-0948 frame exactly. Under the reported left block at device (74,54) the band's own texels read `[0,0,0,0]` and the picture draws the terminal default. With SQ-0948's two source hunks reverse-applied and nothing else changed, the same texels read opaque white and the picture draws the block. `--png` tracked the emitted bytes in both directions. The third left-flank band that lane found by hand really was still carrying the fill — which this quest's own note records. The suspects listed here (`chrome_scaled`, `chrome_bands`, "does the PNG path clear its target") are all clear: the harness holds no frame buffer and builds every canvas from scratch.

**What the audit did find: the composite order was a coin flip.** `raster::render_with` sorted draws by `z` alone and leaned on stability to keep "the order the resolver reported them in" — but that order comes out of `ImageStorage::placements`, a `HashMap`, so `resolve_placements` returns a fresh random permutation on every call. Ten renders of one hand-authored stream inside ONE process split six/four between the two orderings of a pair of overlapping placements. The losing half is exactly the reported shape: a superseded image on top with the live one's transparency blended into it.

Fixed by sorting on `(z, image id, dest_y, dest_x, src_y, src_x)`. The tie-break is the protocol's own, read off the document: "if two images with the same z-index overlap then the image with the lower id is considered to have the lower z-index" (kitty graphics protocol, "Controlling displayed image layout"); same z AND same id is undefined there, hence the position tail so the picture stays a function of the bytes.

Three cases in `pty_oracle.rs`'s `raster` module (hand-authored, portable, no fixture): `overlapping_placements_at_one_z_stack_by_image_id`, `the_same_bytes_always_draw_the_same_picture` (four overlapping placements, eight renders, byte-identical — a broken sort passes about one run in 10^9), and `art_the_next_frame_painted_over_is_not_in_the_picture`, the case this quest asked for. Falsified: with the old sort restored, over five runs the determinism case failed all five and the ordering case three of five.

Commit `20510551`. `docs/architecture.md`'s rasteriser section now carries both the ordering rule and the negative finding, so the next reader does not distrust the instrument for the wrong reason.
