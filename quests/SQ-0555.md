--- note 2026-07-29T15:58:25Z ---

Found by the Lane A frameless work (SQ-0549 / SQ-0491), reported rather than fixed because the fix is out of that quest's scope.

`draw_painted_screen` maps each run's COLUMN at native 1:1 — `col = (x - 1) / 8` — so a painted overlay is placed at the same cell index it occupied on the game's native screen, regardless of how wide the terminal pane actually is. At the native width (80 cols) this is correct. On a wider pane the overlay drifts relative to the content it is supposed to sit on, because the underlying content IS laid out to the pane width while the overlay is not.

Concrete symptom: Journey's 1-cell vertical divider lands INSIDE the picture column at around 120 cols. This is PRE-EXISTING and was not introduced by the frameless fix — it was equally misplaced before, it just used to land over prose instead of over art, where nobody noticed.

Rows are not affected in the same way; this is specifically the column axis.

WHY IT WASN'T FIXED IN LANE A: the fix means proportional column mapping across EVERY painted screen, not just Journey's. That is a behaviour change for all v6 titles at once, and it breaks `painted_screen_floods_only_full_width_reverse_rows`, which passes `native_w = 0` — so the test suite encodes the 1:1 assumption in at least one place that would have to be reworked deliberately.

Suggested approach when picked up: scale the column by the ratio of pane width to native width where a native width is known, and decide explicitly what `native_w = 0` should mean (probably "no scaling", preserving today's behaviour) rather than letting it fall through to a divide-by-zero guard. Verify against Journey at 80/100/120/138 cols, and against the Shogun and Zork Zero painted menus, which are the other consumers.

Related: the user runs a ~138x51 pane, so they are in the drifting regime, not the correct-at-80 one.

--- note 2026-07-29T21:48:23Z ---

STILL REPRODUCIBLE 2026-07-29 — but FRAMELESS-ONLY, which is why it looks fixed.

The user reported not seeing it with Journey any more. Checked rather than closed, and the reason is mode: their `~/.babelmap/config.toml` sets `v6_render = "hybrid"` (also the built-in default, `config.rs:638`). The drift lives in the FRAMELESS path. In hybrid they will never see it.

The mechanism is unchanged. `crates/app/src/render/screen.rs:2155` still maps run columns at native 1:1:
    let col = (t.x.max(1) - 1) / 8;
No scaling by pane width, exactly as the original note described.

EMPIRICAL PROBE (headless Journey, frameless, `honor_game_colours = true`, 40 rows). Counting per column how many rows are blank while BOTH neighbours have ink — i.e. a vertical line cutting through the halfblock picture:

    w= 80  worst interior-blank columns: [(22,1), (56,1), (68,1)]
    w=100  worst interior-blank columns: [(22,1), (56,1), (68,1)]
    w=120  worst interior-blank columns: [(29,9), (22,1), (56,1), (68,1)]
    w=138  worst interior-blank columns: [(29,9), (22,1), (56,1), (68,1)]

Column 29 is blank across NINE consecutive rows at 120 and 138 and absent at 80/100. The 1-row hits at 22/56/68 occur at every width and are picture content, not artifacts. Journey's picture window is 232px wide = 29 cols, so the divider is stamped at native col 29 — correct at the native 80-col width, inside the picture once the column scales up.

Note the threshold: clean at 100, broken at 120. Whatever makes the picture column scale only kicks in past some width, so a fix needs checking at several widths, not just one wide one.

Hybrid probed at the same four widths for comparison: no fixed-column artifact — its gaps sit at varying columns and do not repeat down a column.

WHY THE SUITE IS GREEN: `journey_frameless_shows_picture_column_and_pins_menu_to_the_bottom` (`crates/app/tests/v6_journey_menu.rs:961`) only renders 80x25 and 80x40 — both at the NATIVE width, where the 1:1 mapping is correct by construction. No test exercises a wider-than-native pane. Any fix should add one; the probe above is a ready-made oracle (assert no column is interior-blank for many consecutive rows).

The user runs a ~138-col pane, so if they ever switch to frameless they WILL hit this.
