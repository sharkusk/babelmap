## Two unrelated failures, one shared property: macOS passes, so nothing run locally sees them

`gh run list` shows **failure on at least the last five pushes**, back to 2026-08-20 23:27. This is not caused by any one recent merge. On the latest run (32458994729): windows-latest fails `cargo test`, ubuntu-latest passes `cargo test` and fails `cargo clippy`, macos-latest passes both.

## 1. LINUX — a toolchain skew, not our code

Five clippy errors, all from lints that DO NOT EXIST on the local toolchain:

    clippy::chunks_exact_to_as_chunks   crates/blorb/src/bpal.rs:50
                                        crates/blorb/src/fat12.rs:290
                                        crates/blorb/src/fat12.rs:518
                                        crates/blorb/src/infocom_pics.rs:1577
    clippy::manual_slice_fill           crates/zvm/src/screen.rs:202

The lint help URLs say `rust-1.98.0`. Locally:

    rustc 1.97.1 (8bab26f4f 2026-07-14)
    clippy 0.1.97
    (no rust-toolchain pin — `ls rust-toolchain*` finds nothing)

So CI floats to stable and the working copy lags. **`cargo clippy --workspace --all-targets -- -D warnings` passing locally is not evidence that CI's clippy passes**, and CLAUDE.md presents the clippy gate as though it were. This is structurally the same blind spot the file already documents for `cargo nextest` versus `cargo test` (SQ-0905): a gate that cannot observe the failure mode it is supposed to guard.

Two candidate fixes, and they trade differently:

  - **Pin `rust-toolchain.toml`.** Local and CI then agree by construction, and the gate means what it says. Cost: new lints arrive only when the pin moves, deliberately.
  - **Keep floating, and keep the working copy current.** No policy change; relies on someone running `rustup update`, which is exactly the kind of discipline that fails silently.

The first is the one that makes the gate honest. Note the fixes themselves are mechanical (`as_chunks::<N>().0`, `slice.fill(...)`) — but **`as_chunks` stability must be checked against the pinned version before using it**, or the fix for CI breaks the local build.

## 2. WINDOWS — a portable module importing a unix-only one

    error[E0432]: unresolved import `crate::pty_stream::driver`
      crates/app/tests/suites/pty_oracle.rs:138, :319, :552
    error: could not compile `app` (test "pty") due to 3 previous errors

`pty_stream/mod.rs` documents the split explicitly — "`driver` (unix only)", with `decode`, `oracle` and `raster` portable — and `pty_oracle.rs`'s own header says its `protocol` half is "PORTABLE, always runs, no fixture, no pty". `mod real_capture` is correctly `#[cfg(unix)]`. But `mod protocol` (138), `mod emitter` (319) and `mod raster` (552) each `use crate::pty_stream::driver` and are not gated.

**What they actually use is two CONSTANTS** — `driver::ANSWERED_FG` and `driver::ANSWERED_BG`, the colours the harness answers the OSC 10/11 queries with. Everything genuinely unix-only (`Spec`, `Key`, `run`, `stories_dir`) is used only inside the gated `real_capture`.

So the fix is not to gate three more modules — that would delete portable coverage on Windows for no reason. **Move the two constants somewhere portable** (`pty_stream/mod.rs`), since they are the harness's *answers*, which the oracle needs to interpret a stream on any platform. `driver` can keep referring to them.

This also means the intended design is right and only the placement is wrong, which is worth stating: the split between portable and pty-bound was deliberate and documented, and one import crossed it.
