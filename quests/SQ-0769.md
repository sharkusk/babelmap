--- note 2026-08-11T00:16:20Z ---

USER 2026-08-10, on the beta.5 build:

> "when we start amiga adf shogun it looks like a bunch of keypresses get sent to the game that causes the intro graphic to skip and a bunch of 'restore a saved position?' messages (along with a beep)"
> "maybe some terminal escapes?"

Their hypothesis is plausible and specific, and there is a strong reason to take it seriously: **at boot babelmap sends a burst of capability queries and the terminal answers them.** SQ-0762 measured the exact exchange — `ratatui-image`'s `Picker::from_query_stdio` sends the kitty capability APC, DA1, `CSI 16 t`, `CSI 14/18 t`, OSC 10, OSC 11, `CSI 6n`, `CSI ?u`, `CSI 5n`, and the terminal replies with things like `ESC[?62;c`, `ESC[6;18;8t`, `ESC]11;rgb:0000/0000/0000BEL`. If any of those replies arrive after input handling starts and are not consumed as responses, their bytes are read as keystrokes. A reply such as `ESC[?62;c` would deliver `?`, `6`, `2`, `;`, `c` to the game — which is exactly the shape of "a bunch of keypresses", and `c` is plausibly what triggers a restore prompt.

WHY SHOGUN OFF THE FLOPPY SPECIFICALLY, and this must be measured rather than assumed: the ADF path mounts a filesystem and decodes a native picture archive before the first frame, which changes the timing between the capability queries and the first read. A race that other titles win by a margin could be lost here. Note the beep and the *repeated* restore prompts suggest several bytes arriving, not one.

MEASURE IT WITH THE HARNESS WE ALREADY HAVE. SQ-0762's pty harness (`cargo run -p app --example pty_capture`) drives the real binary and captures the emitted stream; it also answers the capability queries itself, so it can be made to answer them LATE, or to answer with a longer reply, and see whether the game consumes them. `crates/app/tests/pty_stream/driver.rs` is where the answering lives. That turns "maybe some terminal escapes" into a yes or no in one run.

FIXTURE: `stories/James Clavell's Shogun.adf` (release 295 / serial 890321 — see `crates/app/tests/real_media_releases.rs`). Compare against `stories/shogun-r322-s890706.z6` under the Amiga profile: if the bare file does NOT show it, the difference is the mount's timing, not the profile.

FIRST QUESTIONS: is input handling armed before the query responses are drained? Does the response drain have a timeout that the ADF mount's work pushes past? Are responses matched to their queries, or is the input buffer simply flushed at a point that the mount delays?

--- note 2026-08-11T01:09:34Z ---

REOPENED — reproduced exactly, and the earlier "no longer happening" was the race being won by luck. The title in this quest's heading is wrong: it is not Shogun, and it is **not ADF-specific**. User 2026-08-10:

> "i was able to repro with sherlock. if i start the game from the cover view, it skips past the intro text and shows this on the first input line: `0;rgb:ffff/ffff/ffff11;rgb:2828/2c2c/3434`"

**That string identifies the culprit beyond doubt.** It is the payload of the OSC colour queries:

    ESC]10;rgb:ffff/ffff/ffff    <- foreground (OSC 10) response
    ESC]11;rgb:2828/2c2c/3434    <- background (OSC 11) response

The `ESC]1` prefix is consumed and everything after it is delivered to the game as ordinary keystrokes: `0;rgb:ffff/ffff/ffff` followed by `11;rgb:2828/2c2c/3434`. That is the "bunch of keypresses" — the digits and semicolons skip the intro's keypress waits, and one of them answers the restore prompt, hence the beep and the stacked "restore a saved position?" messages first reported.

**THE TRIGGER IS STARTING A GAME FROM THE COVER VIEW / PICKER**, not the disk image and not any particular story. Both earlier sightings (Arthur, "Shogun") were launched that way. The picker has already initialised the terminal; booting a story then re-runs the capability probe (`ratatui-image`'s `Picker::from_query_stdio`, whose full query set SQ-0762 enumerated: kitty APC, DA1, `CSI 16 t`, `CSI 14/18 t`, OSC 10, OSC 11, `CSI 6n`, `CSI ?u`, `CSI 5n`) while input handling is already live — so the replies race the game's first read instead of being drained as responses.

That also explains the intermittency: whether the reply arrives before or after input handling is armed is a timing question, so it reproduces sometimes and not others, on whatever title happens to lose.

REPRO: open the picker (cover/gallery view), start `sherlock`. Compare launching the same story directly from the command line — if that is clean, the defect is the *second* probe, and the fix is either to probe once for the process lifetime or to drain and match responses rather than letting unmatched bytes fall through to the input stream.

RELEASE IMPACT: this is in the v0.1.0-beta.5 draft. Corrupted input on a picker launch is a poor first impression, and the draft is not yet published — worth deciding whether to hold it.

MEASURE WITH THE EXISTING HARNESS: SQ-0762's pty harness answers these queries itself (`crates/app/tests/pty_stream/driver.rs`), so it can answer them late, or answer during a picker-launched boot, and assert that no response byte reaches the game's input. That gives a regression test that reproduces without a real terminal — which matters, because this cannot be caught by any buffer-level harness.
