--- note 2026-08-14T21:13:45Z ---

THE DISTINCTION THIS QUEST RESTS ON, and it must not blur:

**Colour arrives with Version 5.** `set_colour` is v5+, and so are the `$2C`/`$2D` default-colour header bytes. So a **v1–v4** story has no colour concept at all — it never sets, never reads, never branches. (The user asked about "v3"; the real boundary is v1–v4, since v4 is equally pre-colour.)

- For **v5/v6** games that never call `set_colour`, what we do today is already right and is NOT cosmetic: the default pair is something the story can read and is what an inherited colour resolves to. SQ-0846 is the proof — Zork Zero on the Macintosh never calls `set_colour` at all, so the machine's white page under black ink IS the screen's meaning. Every value there is sourced from Infocom's own code: `mac/xzip.lst`'s `SetColor := (zWHITE*256) + zBLACK; { Mac defaults: white under black }`, `zboot.asm`'s 9 and 2 for the Apple, `st/stx1.s` for the ST. **Do not touch that path.**
- For **v1–v4** there is no such fact. Anything painted is the interpreter's presentation.

THE SOURCING PROBLEM, which is why this is a separate field and not an extension of `default_colours()`:

Infocom's **v3 interpreters had no colour support**, so there is no equivalent line to quote. "What Zork I looked like on a C64" is the MACHINE's text mode — the KERNAL's light blue on dark blue — not anything Infocom wrote. That is genuinely weaker provenance than everything else in the profile table.

**And do not simply reuse `default_colours()` for v1–v4.** The Amiga's 12/9 came from Infocom's v5-era interpreter; assuming the v3 ZIP made the same choice is exactly the kind of plausible-but-unsourced inference this project keeps getting caught by. If the v3 interpreter's behaviour can be sourced, source it; if only the hardware default can be, say so and name it as hardware.

THE DESIGN, agreed with the user:

- A **separate field** beside `default_colours()`, so a future reader can tell which values are Infocom's and which are ours. Two different kinds of claim, two different fields.
- **Sourced or declined**, per machine — the same standard as the rest of the table. A machine whose period look cannot be sourced simply has none, exactly as `AppleIIgs::std_window` and `IbmPc::interpreter_number` decline.
- **Default ON in babelmap**, which paints a pane it owns and where the medium was chosen deliberately — opening Zork I off an `.adf` and having it look like an Amiga is the point.
- **Default OFF in `zvm-cli`**, which writes into a terminal belonging to the user — the same reasoning that makes `IbmPc::default_colours` return `None` so that "default" means what the player actually sees.
- A **config key** either way, so the look can be declined without also losing game-set colours. Check how it composes with `honor_game_colours`, `--no-game-colours` (SQ-0855), `NO_COLOR`, and SQ-0860's monochrome-artwork force-off — it is a fourth thing in that neighbourhood and must not fight them.

SCHEDULING: build this AFTER SQ-0872 centralises the machine table, not before. The period look is a column in that table; adding it first means doing it twice and in the wrong crate.

--- note 2026-08-14T21:18:00Z ---

SOURCING METHOD — the user's, and better than the "documented hardware defaults" fallback in my previous note. Prefer this.

**Boot the original disk images in an emulator and observe.** The corpus now holds self-booting media for most of these machines, and self-booting means the disk carries INFOCOM'S OWN INTERPRETER — so what you see is not "a C64's text mode" but what Infocom's v3 interpreter chose to do on that machine. That is exactly the source I said did not exist in code, and it exists in behaviour.

Media already in `stories/` that boot:
- `Planetfall r29 (clean copy from retail disk).dsk` — Apple II, RWTS boot code, v3 (SQ-0868)
- `TRINITY1.D64` / `TRINITY2.D64`, `Hitchhikers_Guide_to_the_Galaxy_The_1984_Infocom.d64` — Commodore, v4 and v3 (SQ-0869)
- The Apple `.po`/`.2mg` images carry `INFOCOM.SYSTEM` and `INFOCOM`
- `.adf` Amiga floppies, `.st` Atari compilations, `Zork Zero Disk.image` and `InfocomMasterpieces.img` for the Mac

THREE CAVEATS, without which the evidence is not trustworthy:

1. **Name the emulator AND its palette.** VICE alone ships Pepto, Colodore and its own default, and they disagree visibly on the same pixels. A screenshot with no provenance is unreproducible, and this project pins values for years.
2. **Capture raw — no CRT shader, no scanlines, no NTSC composite.** Those change colours substantially. The Apple II is the extreme case: its text was commonly green or amber phosphor on one monitor and white on another, so part of "the Apple II look" is a MONITOR choice rather than a machine fact. Say which you are recording.
3. **Cross-check two independent emulators where possible.** Agreement on the RGB is strong evidence. **Disagreement is itself the finding** — and probably means declining rather than picking a side, per this quest's rule that a machine whose period look cannot be sourced simply has none.

Record for each machine: emulator, version, palette setting, video standard (PAL/NTSC where it applies), the disk booted, and the observed foreground/background as RGB. That provenance goes in the code beside the values, matching the standard the rest of the profile table already meets (`st/stx1.s`, `zboot.asm`, `mac/xzip.lst`).

Note this also gives a way to CHECK the v5+ values we already ship: booting the Macintosh Zork Zero should show white under black, and the Amiga floppies their 12/9. If an emulator contradicts a value we sourced from Infocom's assembly, that is worth knowing loudly.

FIRST DATA POINT — Commodore 64, from the user, by this quest's own preferred method.

An emulator screenshot of `stories/Hitchhikers_Guide_to_the_Galaxy_The_1984_Infocom.d64` booted and played to the first prompt (Bedroom, "It is pitch black."). Measured off the PNG rather than eyeballed — the image contains EXACTLY three colours and nothing else:

  page                        #6C6C6C   (108,108,108)   91,570 px
  ink                         #FFFFFF                    5,535 px
  cursor + reversed status    #000000                    2,255 px

The third is not a third default: black is the status line's reverse video and the cursor, which is §8.2 behaviour. The pair this quest wants is **page #6C6C6C, ink #FFFFFF**.

`#6C6C6C` is a plausible exact match for VIC-II colour 12 (grey) in at least one common palette, but PROVENANCE IS STILL MISSING and caveat 1 of the note above forbids recording it without: emulator name, version, palette setting (Pepto / Colodore / VICE default disagree visibly), and PAL vs NTSC. Ask the user for those before this goes into the table. The screenshot is 368x270, which is a cropped border-inclusive frame rather than the bare 320x200, so the capture settings are not inferable from the file.

NOT USABLE AS A SECOND DATA POINT: a photograph of Bureaucracy running on a real C128 (interpreter 7) was also supplied. Measured: page black `(16,0,0)`-dominant, ink clustering `(0,80,128)`..`(80,176,208)` — i.e. green at ~85% of blue, so cyan-leaning and NOT §8.3.1's blue. It is good enough to REFUTE something (see below) and not good enough to source a constant: caveat 2 rules out CRT capture outright, and a photographed CRT plus JPEG cannot separate the VDC's cyan from its light blue. Ask for a C128 emulator capture of `TRINITY1.D64` instead — Trinity is the C128 release (confirmed below), so it is the exact analogue of the C64 capture already in hand.

WHAT THE C128 PHOTO DOES SETTLE, and it is worth acting on independently of this quest: `zvm::interpreter::MACHINES`'s Commodore 128 row declines `default_colours` on the stated ground that "the machine's famous light-blue-on-blue boot screen is the hardware's reputation rather than the interpreter's evidence" (SQ-0869). The photo shows blue-ish ink on a BLACK page. Whatever the pair turns out to be, that sentence is now false and should be rewritten.

CONFIRMED WHILE CHECKING: `stories/TRINITY1.D64` really does carry a **C128** interpreter, not a C64 one — `STA $FF00` x43 (MMU configuration register) and `STA $D506` (MMU RAM configuration), both C128-only. So the corpus already holds bootable media for interpreter 7 as well as 8.

DEAD END, recorded so nobody repeats it: the C128 constant cannot be read out of that disk statically. Across both 175 KB images there are ZERO stores to the VDC ($D600/$D601), zero PETSCII colour codes sent through the five `JSR $FFD2` sites, and no `$D021`/`$D020` writes. Only the boot/loader is stored plainly — its message table sits at offsets 428..9800 ("The story is loading ...", "Insert Side * of the STORY disk into Drive #1.") — and the interpreter proper is not plainly present. TRINITY2.D64 has no plain 6502 at all. Emulator observation is the route, exactly as this quest already says.

ONE DESIGN POINT CONFIRMED BY THE MEASUREMENT: the C64's page is a mid-grey, and §8.3.1's numbers 2..9 contain no grey at all (the greys are 10..12 and `clamp_default_colour` accepts those only when `version == 6`). So this genuinely cannot be expressed as a `default_colours` pair for any C64 game, all of which are pre-v6 — which is independent confirmation that the separate field this quest specifies is the right shape, and that reusing `default_colours()` would have silently clamped the C64's page to black.

SECOND DATA POINT — Commodore 128 (interpreter 7), from the user, VICE.

`vice-screen-2026081500331205.png`, 856x288, Trinity booted to the first prompt (Palace Gate). Trinity is v4, so pre-colour — the case this quest is about. Measured off the PNG; the frame contains EXACTLY two colours:

  page   #000000                  230,408 px
  ink    #55FFFF  (85,255,255)     16,120 px

The status bar is those same two reversed (cyan ground, black characters), so as with the C64 there is no third default — reverse video is §8.2 behaviour.

`#55FFFF` is exactly RGBI **light cyan**: the VDC drives four digital bits and the primary+intensity encoding puts every channel at 0, 85, 170 or 255, so 85/255/255 is a canonical entry rather than a near miss. **This makes interpreter 7 markedly better sourced than interpreter 8** — the VIC-II's palette is analogue-derived, which is exactly why Pepto, Colodore and VICE's default disagree on the C64's grey, while the VDC's RGBI leaves far less room for emulators to differ. The C64 value still needs its palette named; this one is close to palette-independent.

IT ALSO VINDICATES THE CRT PHOTO, and the way it does is worth keeping. The photo of the same machine measured green at ~0.85 x blue, which was enough to say "cyan-leaning, NOT §8.3.1's blue" and not enough to name a value. The emulator gives G = B = 255 exactly. So the photo pointed the right way and the CRT plus JPEG shifted the magnitude — which is caveat 2 working as written, not an argument for relaxing it.

STILL OUTSTANDING FOR THE RECORD (caveat 1): VICE **version** for both captures, the VDC palette setting for this one, and the VIC-II palette setting plus PAL/NTSC for the C64 one. Caveat 3's second independent emulator is outstanding for both.

THE TWO COMMODORE ROWS, as measured:

  7  Commodore 128   page #000000   ink #55FFFF   (VICE, Trinity, v4)
  8  Commodore 64    page #6C6C6C   ink #FFFFFF   (VICE?, Hitchhiker's, v3)

And note they are NOT the same, which is itself a finding: the same publisher's interpreter on two closely related machines chose a black page with cyan ink on one and a grey page with white ink on the other. Anything that assumed "the Commodore look" was one thing would have been wrong.
