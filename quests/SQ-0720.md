Everything needed to start, measured 2026-08-09 against `stories/Zork0.blb`.

BPal LAYOUT (not in the Blorb spec — a converter extension; `crates/blorb/src/lib.rs:141` already names it and deliberately skips it). 462336 bytes = 38528 triples of big-endian u32:

    (background_picture_id, adaptive_picture_id, prebaked_variant_id)

- field0: 224 distinct ids in 1..504 — the non-adaptive picture whose palette is current.
- field1: 172 distinct ids in 9..485 — verified EQUAL to the `APal` set.
- field2: 1710 distinct ids in 1000..2709 — exactly the mystery high-id block.
- Complete table: every field0 value has exactly 172 entries, one per adaptive picture. Each adaptive picture has 10-20 distinct variants.

So the high-id block is the converter pre-baking Blorb §11.3 for every (background, adaptive) pair — the same computation `graphics.rs` performs at runtime by splicing the live PLTE into the adaptive picture. Zork Zero declares `Reso` std 320x200 with 503 entries; Arthur has APal/BPal too (12 and 4824 bytes), Journey has an empty APal, Shogun and Lurking have neither.

SPOT CHECK: 40 random triples, reconstructing each by replacing the adaptive picture's PLTE with the background picture's and comparing RGB output to the baked variant — **39 exact matches, 1 mismatch, 0 skips**. That is strong independent evidence the adaptive path is right.

THE OUTLIER: `background=503, adaptive=18, variant=1520` — 132 differing bytes of 5400 (44 pixels of a 45x40 image, 2.4%). Picture 503 is NOT in APal, so the obvious "the background was itself adaptive" explanation does not apply. Worth understanding before trusting the oracle wholesale: it is either a converter quirk or a real edge case in our splice (duplicate palette entries and index collisions are the first thing to check).
