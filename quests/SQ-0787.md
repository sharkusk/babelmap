FOUND 2026-08-11 by the SQ-0784 lane, reported as out-of-scope rather than acted on. Its words:

> "restoring that Save State does **not** bring back scopa's blue card panels or its dealt cards — the baize survives but the panel rectangles do not, which is why my reproduction shows the bridges against green rather than against the panels. That is a display-list/paint-ground restore-fidelity question, not a flood question."

The archive is the user's own scopa Save State, taken at the end of a game (the same one that reproduced SQ-0784). On restore the green baize comes back and the blue card panels do not — so *some* paint ground is restored and some is lost, which is more diagnostic than a wholesale failure.

WHY THIS IS THE INTERESTING KIND OF RESTORE BUG. CLAUDE.md's persistence rule is "persist the recipe, not the result": a Quetzal save carries no screen state by design because the standard assumes the *story* repaints, while a host Save State swaps memory under a game that never learns it happened — so everything the screen needs is ours to carry. A ground that comes back partially says the display list is being restored but something in it is not being replayed, rather than that nothing was saved. Compare `v6_restore_palette_replay.rs`, which is the established pattern for exactly this class.

REPRODUCTION IS ALREADY SOLVED, and cheaply — the SQ-0784 lane worked out a headless restore recipe that needs no `--restore` flag, because `auto_load` defaults to true:

    mkdir -p $S/home/saves/scopa.z6.save
    cp ~/.babelmap/saves/scopa.z6.save/default.babelmap $S/home/saves/scopa.z6.save/
    cargo build -p app --bins --examples
    cargo run -q -p app --example pty_capture -- \
        --story stories/scopa.z6 --user-dir $S/home \
        --size 117x64 --keys wait:4000 --png $S/scopa.png

Two gotchas it paid for and recorded: `pty_capture --user-dir` **overwrites** the per-game `config.toml` with `show_map = false`, so per-game overrides must arrive via `--arg --config <path>`; and `cargo build -p app --example pty_capture` does **not** rebuild `target/debug/babelmap`, which the example actually runs — a stale binary reports "no change" and costs a cycle.

TESTING RULE THAT APPLIES HERE, from CLAUDE.md: restore tests must **perturb before asserting**. Asserting the frame immediately after a restore is precisely when everything still looks correct; the defect surfaces one action later when the game repaints, changes palette, splits or resizes. Restore, make a move, then assert. Cover restoring into a *different* terminal size and a different graphics backend — neither is visible to a same-session round-trip and both are common in the field.

NOT YET ESTABLISHED, and worth settling before any fix: whether this is scopa-specific or reaches the whole v6 corpus. Zork Zero, Shogun, Arthur and Journey all keep painted grounds under their chrome, and a display-list replay gap would show in all of them. Establish the scope first — a per-title fix to a general defect is how the hybrid/raster divergences in this codebase started.

--- note 2026-08-12T05:34:27Z ---

HYPOTHESIS CORRECTION 2026-08-11 — **the primary hypothesis on this quest is probably WRONG, and SQ-0788's lane supplied the reason.**

This quest's note says the leading explanation is SQ-0753/0763's missing `a=d` kitty deletes: we never delete an image placement, so menu artwork survives. That reasoning assumed scopa's screen is composed of placements.

**It is not.** SQ-0788 established by measurement that scopa takes the **raster arm** — no Buffer window plus a painted ground means hybrid falls through (see `v6_scopa_hybrid_no_story.rs`), and the entire 640x400 screen ships as **one full-frame image**. There are no per-element placements to delete, so no `a=d` is expected or needed, and the placement-lifetime family is not implicated here at all.

**THE BETTER LEAD, from the same lane, in its words:**

> "restoring the scopa save renders stale main-menu artwork. That is a separate defect and I left it alone — but note it has the same smell, a cached raster frame outliving its inputs, so it may well be a cousin of this one."

SQ-0788's root cause was `v6_raster_gen` (`crates/app/src/render/screen.rs:2801`) — a `u64` key folding every raster input, which `GraphicsRender::v6_wants_build` (`graphics.rs:728`) uses to skip the entire rebuild, resize and encode. Its defect was that the **painted ground rode beside the window tree and the key never looked at it**, so a ground-only change left the key unmoved and the previously uploaded frame stayed on screen.

**A restore is the same shape of event.** It swaps the entire game state underneath a renderer that never learns it happened — exactly what CLAUDE.md warns about ("a host Save State swaps memory under a game that never learns it happened"). If the key does not move across a restore, `v6_wants_build` returns false and the pre-restore frame — the main menu — stays uploaded. That is precisely the reported symptom, and it needs no placement involvement whatsoever.

FIRST MEASUREMENT, now much cheaper than the placement-oracle route this quest previously called for: **dump `v6_raster_gen` immediately before and immediately after a restore.** If the key is unchanged, the mechanism is settled in one comparison and the fix is the same shape as SQ-0788's — fold whatever the restore changes into the key. Note SQ-0788 fixed the painted-ground input specifically; a restore may move inputs the key still does not read.

CAUTION, and it is the reason this is not simply a repeat of SQ-0788: do not assume the fix is another input added to the key. A restore might legitimately leave every keyed input equal while the screen must still be rebuilt, in which case the right answer is to force a rebuild on restore rather than to widen the key. Establish which before writing code.

CLAUDE.md's rule still governs the tests: **perturb before asserting** — the frame immediately after a restore is exactly when everything still looks correct — and cover restoring into a different terminal size and a different graphics backend. `v6_restore_palette_replay.rs` is the pattern.

Fixing SQ-0753's missing deletes changes nothing here, confirmed by capturing the same restore before and after that fix.

SO THE STALE MENU IS BAKED INTO A FRESHLY BUILT CANVAS, which narrows it a lot and rules out `v6_raster_gen` as well: the key DID move, the rebuild DID happen, `v6_wants_build` said yes, and the canvas it built still contains the menu. WHY THAT IS EXACTLY WHAT YOU WOULD EXPECT, and where to look: `auto_load` restores AFTER the story has already booted to its main menu and painted it. The Save State swaps VM memory under a game that never learns it happened (CLAUDE.md's own warning), so the game issues no repaint; the painted ground still holds the menu's pixels; the restored screen's text draws over them. The fix is on the restore path — reset/replace the painted ground (and whatever else rides beside the window tree) from the archive rather than leaving the pre-restore surface standing — not on the render path.

Reproduce in one command, no --restore flag needed:
    cargo run -q -p app --example pty_capture -- --story stories/scopa.z6 \

FIXED 2026-08-12, commit 2e96d745, and the corpus sweep the quest asked for is now MEASURED rather than assumed.

THE FIX, on the restore path exactly as the note above predicted. The ground now travels in the archive as `pictures/ground.png` (`GameSession::paint_ground_png`), and `engine_helpers::apply_v6_pictures` — the one funnel every restore site already shares — calls the new `GameSession::load_paint_ground` UNCONDITIONALLY. The unconditional half is the load-bearing one: an archive with no ground RESETS the ground rather than leaving the pre-restore surface standing. Pixels rather than a recipe, with the justification CLAUDE.md requires: the ground's inputs are an unbounded stream of `erase_window` fills (which is why SQ-0706 made it a surface and not a list of rects), so there is no bounded recipe to store. Native pixels, so the archive stays backend- and terminal-neutral. Additive ZIP entry — no `format_version` bump, because nothing is omitted for it and an older build simply ignores it.

WHICH v6 TITLES ACTUALLY PAINT A GROUND — measured by booting each and driving 25 turns:

  scopa.z6        yes (its whole table is erase fills)
  shogun          YES — a 548x368 backdrop, one keypress into the boot, never repainted
  fmvpoker        yes
  zork0           no
  arthur          no
  journey (r83)   no
  advent.z6       no
  mysterious01    no
