--- note 2026-08-12T04:10:23Z ---

FOUND 2026-08-11 by the SQ-0784 lane, reported as out-of-scope rather than acted on. Its words:

> "restoring that Save State does **not** bring back scopa's blue card panels or its dealt cards — the baize survives but the panel rectangles do not, which is why my reproduction shows the bridges against green rather than against the panels. That is a display-list/paint-ground restore-fidelity question, not a flood question."

The archive is the user's own scopa Save State, taken at the end of a game (the same one that reproduced SQ-0784). On restore the green baize comes back and the blue card panels do not — so *some* paint ground is restored and some is lost, which is more diagnostic than a wholesale failure.

WHY THIS IS THE INTERESTING KIND OF RESTORE BUG. CLAUDE.md's persistence rule is "persist the recipe, not the result": a Quetzal save carries no screen state by design because the standard assumes the *story* repaints, while a host Save State swaps memory under a game that never learns it happened — so everything the screen needs is ours to carry. A ground that comes back partially says the display list is being restored but something in it is not being replayed, rather than that nothing was saved. Compare `v6_restore_palette_replay.rs`, which is the established pattern for exactly this class.

REPRODUCTION IS ALREADY SOLVED, and cheaply — the SQ-0784 lane worked out a headless restore recipe that needs no `--restore` flag, because `auto_load` defaults to true:

    mkdir -p $S/home/saves/scopa.z6.save
    cp ~/.babelmap/saves/scopa.z6.save/default.babelmap $S/home/saves/scopa.z6.save/
    cargo build -p app --bins --examples
    cargo run -q -p app --example pty_capture -- \
        --story stories/scopa.z6 --user-dir $S/home \
        --size 117x64 --keys wait:4000 --png $S/scopa.png

Two gotchas it paid for and recorded: `pty_capture --user-dir` **overwrites** the per-game `config.toml` with `show_map = false`, so per-game overrides must arrive via `--arg --config <path>`; and `cargo build -p app --example pty_capture` does **not** rebuild `target/debug/babelmap`, which the example actually runs — a stale binary reports "no change" and costs a cycle.

TESTING RULE THAT APPLIES HERE, from CLAUDE.md: restore tests must **perturb before asserting**. Asserting the frame immediately after a restore is precisely when everything still looks correct; the defect surfaces one action later when the game repaints, changes palette, splits or resizes. Restore, make a move, then assert. Cover restoring into a *different* terminal size and a different graphics backend — neither is visible to a same-session round-trip and both are common in the field.

NOT YET ESTABLISHED, and worth settling before any fix: whether this is scopa-specific or reaches the whole v6 corpus. Zork Zero, Shogun, Arthur and Journey all keep painted grounds under their chrome, and a display-list replay gap would show in all of them. Establish the scope first — a per-title fix to a general defect is how the hybrid/raster divergences in this codebase started.
