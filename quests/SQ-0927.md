## The observation

`stories/shogun-r322-s890706.z6` at its main menu, 117x64 pane, kitty backend
(pty capture, VERDICT: KITTY). The credits panel and the START/RESTORE/QUIT box
are solid **black rectangles** floating on a **theme-grey** pane. Nothing on the
real machine looks like that.

## Every candidate for the black, measured and eliminated

- **Window pages.** All six of Shogun's windows report `bg=None`. `fill_pages_where`
  skips any window whose bg is not `packed_explicit`, so it paints nothing here.
- **Run backgrounds.** Every `PxText` on the frame is `fg=0x00000000
  bg=0x00000000` — fully inherited, nothing named.
- **Artwork.** `build_graphics_canvas` holds ONLY the two ornament flanks:
  `rgba(34,34,34,255)` ground and `rgba(204,170,102,255)` gold, 36,800 opaque
  pixels of 256,000. The credits box, the menu box and the surround are all
  `rgba(0,0,0,0)`.
- **The machine.** A bare `.z6` names no medium, so `InterpreterProfile::resolve`
  falls through to **IBM PC**, which declines `default_colours` deliberately and
  has no `v6_screen_page`. No machine pair, so `v6_host_pair` falls back to the
  host and `v6_machine_page` is a no-op.

So the game contributes **no colour at all** to this frame, and both grounds are
lanthorn's own.

## The two answers

    theme[transcript  ]  fg=White  bg=None     (Provenance::Default)
    theme[upper_window]  fg=White  bg=Black    (Provenance::Default)
    theme[status_bar  ]  fg=White  bg=Black    (Provenance::Default)

`transcript` inherits the `text` role, which sets no background — so the pane is
**unpainted** and the terminal's own shows through (#1D1F21 in the user's
Ghostty). `upper_window` inherits `chrome`, which `Roles::from_scheme` falls back
to as hard-coded white-on-BLACK. The black is not paint the game asked for; it is
the chrome role, emitted as SGR cell backgrounds — the capture's background map
shows `#000000[10..106]` on rows 5..15 and 28..31, spans of CELLS, not a
placement.

So: **grey is the absence of paint, black is the chrome role**, and on one screen
they disagree about what "nobody named a colour" means.

## Why it does not show elsewhere

Boot the same game off `stories/James Clavell's Shogun.adf` and both grounds
become `#424242` — the Amiga's `default_colours` bg 12, which its row flags
`v6_screen_page: yes` ("the machine's default pair IS the Version 6 screen").
`v6_machine_page` then overrides the `upper_window` selector too, so the
disagreement is invisible. Measured: lanthorn off the floppy is 78.8% `#424242`
against the real Amiga capture's 85.4% `#3A3C3A` (`machine-screenshots/amiga-shogun-main.png`,
release 295 — the same release the floppy carries). Same register, this emulator
renders it darker, exactly as SQ-0873 recorded.

## Why the rule is defensible and still wrong here

A solid black ground under a **v3 status line** is right — that is chrome, one row,
and it wants to read as a bar. On a **v6** frame the "upper window" is the game's
whole presentation surface, so the same rule paints a rectangle the size of the
credits panel and leaves the pane around it bare. Two conventions meeting, not a
typo.

## Suggested shape, NOT yet agreed — discuss first

Narrow it to the case that is wrong: on a v6 frame with **no machine pair**,
chrome text cells should take the same ground the pane has rather than the
`chrome` role's black. v3 status lines keep today's behaviour untouched.

Open questions the user wants to settle before anything is written:

1. **Should the pane get a ground instead?** The opposite fix — give the v6 pane
   the chrome black so the panels stop floating — is also coherent, and it is
   closer to what a real IBM EGA screen probably looked like. We have no capture
   to say (see below), and it would be a much more visible change.
2. **Where does the rule live?** A selector default, a `v6_machine_page`-style
   layer, or at the draw site. The first two are theme-visible and a user's
   `style.toml` must still win either way (SQ-0847's rule).
3. **Does this touch `honor_game_colours = false`?** Both baselines have to be
   pinned (CLAUDE.md), and in that mode there is no game pair to inherit at all.
4. **Zork Zero, Arthur, Journey and advent are all on this path too** off their
   bare files. Any change has to be measured on the whole v6 corpus in both
   colour modes, not on Shogun alone.

## The corpus gap behind all of it

There is **no IBM/DOS capture in `machine-screenshots/`** — the same gap SQ-0873
left open for interpreter 5 and 6. We cannot currently falsify a claim about what
an EGA Shogun's screen ground was, which is exactly the kind of question internal
measurement cannot answer (CLAUDE.md). Worth asking the user for one before
choosing between (1) and its opposite.

Not caused by SQ-0903: the identical frame captured on the pre-change baseline
(`31f1c3cf`) is the same picture.

## THIS QUEST AS FILED WAS WRONG. The app was correct; the instrument was not.

Rewriting rather than deleting, because the investigation is worth keeping and
because the remaining question is real, just much narrower.

**What was actually happening (SQ-0929, fixed in 6ed26471).** The pty harness
answered the OSC 11 probe with `rgb:0000/0000/0000` while its rasteriser filled
unpainted cells with the emulator palette's entry 0, `#1D1F21`. lanthorn asks the
terminal for its background at startup and seeds the `chrome` role from the answer
(`seed_scheme_from_terminal` → `Roles::from_scheme`, `chrome: fg(scheme.foreground)
.bg(scheme.background)`), so it painted its chrome cells `#000000` **correctly,
following what it was told**, and the surround came out `#1D1F21`. The seam existed
only inside the harness.

Proved two ways. Making the harness answer `#1d1f21` instead, with no change to
lanthorn: `#000000` 14.7% → gone, `#1D1F21` 68.3% → 83.0%. And the emitted SGR is
**16 × `48;2;0;0;0` against 2 × ANSI `40`** — truecolour, i.e. `Color::Rgb(0,0,0)`
seeded from the probe, not the hard-coded `Color::Black` fallback.

**My error, recorded so it is not repeated.** I measured
`theme.get("upper_window")` through `ColorScheme::terminal_default()` in a scout
probe — the FALLBACK constructor — saw `bg=Some(Black)`, and generalised to the
real run, which takes `from_scheme`. A theme value read outside `reload_style` is
not the theme the app renders with.

## WHAT SURVIVES, and it is a deliberate decision rather than a defect

`Roles::terminal_default()` hard-codes `chrome: white on BLACK` while `text`
carries no background at all. That branch is taken only when **no scheme is
configured AND the terminal answered neither OSC 10 nor 11**.

**SQ-0510 already fixed the visible half of this** — the Anchorhead report, a black
status band on a non-black terminal — by handing the startup probe to the theme.
It KEPT the hard-coded band for the unanswered case, and pinned it:
`upper_window_terminal_bg::an_unanswered_probe_keeps_the_hard_coded_fallback_band`.

So the user's rule — *"the chrome background should not be different than the
terminal background unless it is colored by the game"* — is **already satisfied on
every path where the terminal tells us anything at all**. The only divergence is
when it tells us nothing.

## The trade-off, measured

Dropping `.bg(Color::Black)` from `terminal_default()`'s chrome fails **13 tests**,
and they are not incidental:

    reload::reload_keeps_todays_behaviour_when_the_terminal_answers_nothing_or_half
    theme::resolve::an_unanswered_probe_leaves_the_terminal_default_roles_alone
    upper_window_terminal_bg::an_unanswered_probe_keeps_the_hard_coded_fallback_band
    upper_window_terminal_bg::a_half_answered_probe_is_skipped_whole
    v6_advent_status::advent_hybrid_bar_is_solid_{honoring_game_colours,theme_only}
    v6_advent_status::the_status_bar_is_one_row_at_any_pane_scale
    v6_advent_status::the_boot_popup_does_not_blank_the_rows_behind_it
    v6_journey_menu::journey_hybrid_{menu_full_black_panel_dividers_continuous,
                                     tall_pane_divider_reaches_menu,
                                     tall_pane_panel_fill_reaches_the_divider}
    v6_amiga_global_colour_pair::the_ibm_pc_profile_renders_in_the_host_theme_exactly_as_before
    render::command_band::band_is_opaque

Every one exercises the fallback path, because render tests build state with
`ColorScheme::terminal_default()`. What they encode is **a v6 chrome grid reads as
a solid band**, and `bg = None` costs that. Note `status_bar` and `help_bar` carry
REVERSED in their registry deltas and stay solid either way — it is `upper_window`,
which has no such delta, that goes transparent.

## The actual question, for whenever this is picked up

When the terminal tells us NOTHING, is the honest answer a guessed black or a
deferred `None`? `None` is not a guess — it means "the terminal's own", which is
the rule exactly. Black is a guess that happens to keep bars solid.

Not obvious, decided once already by SQ-0510, and worth 13 tests' worth of
deliberation rather than a drive-by. Options if it is taken up: accept
non-solid chrome grids on unanswering terminals; give `upper_window` its own
registry delta that produces solidity without inventing a colour; or narrow the
fallback to v6 chrome only. Reverted for now — the tree carries the SQ-0929 fix
alone.

## THE 13 FAILURES ARE THREE DIFFERENT THINGS, and lumping them was lazy

The user asked the right question: *"wouldn't bars also be solid even with None,
since they should reverse the terminal's own?"* Yes — for bars that reverse.
Reading an actual failure instead of asserting one shows none of the 13 is a
reversed bar going transparent, and the previous note's "it is `upper_window`
that goes transparent" was wrong.

**Kind 1 — game chrome that was solid only because of the invented black.**
`v6_advent_status::advent_hybrid_bar_is_solid_*`,
`the_status_bar_is_one_row_at_any_pane_scale`, `the_boot_popup_...`, and the three
`v6_journey_menu` panel/divider cases.

The advent failure reads:

    assertion failed: the bar occupies one row only (honor=false)
      left:  [0, 1, ..., 24]      <- every row
      right: [0]

The predicate is `every cell in the row shares bar_bg`, so it is not measuring
SOLID, it is measuring DISTINGUISHABLE FROM THE PAGE. And the suite says why three
lines below itself: *"advent's runs carry no reverse bit, so the reverse-only flood
rule (SQ-0515) skipped them entirely."* advent's bar is solid by a full-width FLOOD
in the chrome colour, not by reverse video. Make that colour "the terminal's own"
and the flood equals the page.

**Which is arguably the rule working, not breaking.** advent names no colour and
sets no reverse bit. By the user's rule its bar SHOULD be the terminal's ground —
and on the machine it would be, since SQ-0928 puts an IBM PC screen at blue under
white for every window that names nothing, bar included. These tests encode a band
the game never asked for. They should be re-examined, not preserved.

**Kind 2 — lanthorn's OWN UI, which is not covered by the rule at all.**
`render::command_band::band_is_opaque` paints the buffer red-on-green and asserts
the band overwrites it. That is an overlay of ours, drawn through `dialog.background`
and `panel.*`, and wanting it opaque is our design decision about our own chrome,
not a claim about any game. It inherits an opaque ground from the `chrome` role
today purely by accident of the role chain.

**This is the real shape of the fix, and it is better than "strip chrome's bg".**
Split the two: lanthorn's own surfaces carry an opaque ground of their own, and the
`chrome` role stops inventing one for the game's windows. Then kind 1 becomes
correct behaviour, kind 2 keeps its opacity for a stated reason instead of by
inheritance, and the rule is satisfied without a global strip.

**Kind 3 — tests that pin SQ-0510's decision directly.**
`upper_window_terminal_bg::an_unanswered_probe_keeps_the_hard_coded_fallback_band`,
`a_half_answered_probe_is_skipped_whole`,
`theme::resolve::an_unanswered_probe_leaves_the_terminal_default_roles_alone`,
`reload::reload_keeps_todays_behaviour_when_the_terminal_answers_nothing_or_half`,
and `v6_amiga_global_colour_pair::the_ibm_pc_profile_renders_in_the_host_theme_exactly_as_before`.

These are the only ones that are genuinely a decision to overturn rather than a
consequence to fix. Five tests, not thirteen.

## Revised recommendation

Not "accept non-solid chrome grids" and not "narrow the fallback to v6" — both were
guesses at a problem I had mischaracterised. Do this instead:

1. Give lanthorn's own overlays (command band, dialogs) an opaque ground that does
   not depend on the `chrome` role inheriting one.
2. Drop `.bg(Color::Black)` from `Roles::terminal_default()`'s chrome.
3. Re-examine kind 1's assertions on their merits — a bar the game did not ask for
   probably should not be a band, and SQ-0928 says the machine agrees.
4. Rewrite kind 3's five, which are the deliberate part, with SQ-0510's reasoning
   revisited in the note rather than silently inverted.

Still reverted; the tree carries only SQ-0929's harness fix.

## IMPLEMENTED, MEASURED, AND REVERTED. Recommend closing as already-fixed.

Third narrowing, and this one ends it. The plan in the previous note is wrong in
its second step, for a reason no amount of reading would have found.

## What the attempt established

**Step 1 turned out to need no new machinery.** `Color::Reset` — "set the
background TO the terminal's default" — is both opaque and deferring, which is
exactly the primitive the plan wanted. Changing `Roles::terminal_default`'s
chrome from `Color::Black` to `Color::Reset` fixed
`render::command_band::band_is_opaque` on its own: the band needs to SET a
background because `Style::patch` leaves `bg` alone when the patch has none, and
`Reset` sets one. No `surface` role, no re-parenting. 13 failures → 12.

**The user's rule is already satisfied in production, and this is the finding.**

    from_scheme:  text:   fg(fg)          <- no background: the terminal's default
                  chrome: fg(fg).bg(bg)   <- the terminal's own background

On every terminal that answers OSC 10/11, a chrome band is ALREADY the same
colour as the page. The black exists only on the fallback, and only there can the
rule be violated at all. SQ-0510 did the work; what is left is the case where the
terminal tells us nothing.

**Four of the twelve rewrote cleanly** — the probe pins and the IBM PC render
case. They pin "the fallback is skipped whole", which is untouched; only what it
falls back TO moved.

**Advent's four rewrote BETTER than they were.** They inferred the bar's height
from a background colour; `v6_cell_map` publishes the strip the ring reserved, so
the height can be asked for directly. The popup case was measuring "is this a box
or a flood" by comparing two backgrounds, when its own failure message showed text
from behind the popup surviving on the same row — the property, directly visible.

## AND THEN JOURNEY'S THREE, WHICH ARE THE ANSWER

`journey_hybrid_menu_full_black_panel_dividers_continuous`,
`..._tall_pane_divider_reaches_menu`, `..._tall_pane_panel_fill_reaches_the_divider`
use **`Color::Reset` as the tell for "a cell nothing drew"**:

    // A `Reset` background is the tell: that is a cell nothing drew.
    assert_ne!(buf.cell((x, y)).unwrap().bg, Color::Reset, ...)

That distinction is load-bearing — it is how the flank work (SQ-0883 and the
panel-fill quests) tells a cell the panel covered from a cell it missed. On the
answered path it survives, because `chrome.bg` is a concrete `Rgb`. Make the
FALLBACK `Reset` and the two become indistinguishable, and three real regression
cases lose their instrument.

So the fallback's black is doing work: it is a **concrete stand-in** for "the
terminal's background, whatever it is", exactly as the answered path supplies a
concrete colour. Its only flaw is being the wrong concrete colour on a non-black
terminal that answered nothing. `Reset` is not a better guess — it is a different
KIND of value, and one the renderer's own tests read as "unpainted".

`None` is worse still: not opaque, so lanthorn's overlays stop covering what they
cover.

## Recommendation

Close as fixed by SQ-0510, and document the fallback rather than change it. The
residual violation is real but confined to terminals answering neither OSC 10 nor
11 — where we cannot know the background, so every available value is a guess and
the current guess at least preserves the painted/unpainted distinction the render
tests depend on.

If it is ever picked up again, the shape that could work is a THIRD state: a
concrete colour that is also flagged as "provisional", so the renderer's tests can
still tell painted from unpainted while the value defers on screen. That is a new
concept in `Resolved`, not a change to a constant, and it would want a better
motivation than a path most users never take.

Reverted; the tree is green at 5677/5677 with none of this in it.
