--- note 2026-08-19T19:48:18Z ---

## The observation

`stories/shogun-r322-s890706.z6` at its main menu, 117x64 pane, kitty backend
(pty capture, VERDICT: KITTY). The credits panel and the START/RESTORE/QUIT box
are solid **black rectangles** floating on a **theme-grey** pane. Nothing on the
real machine looks like that.

## Every candidate for the black, measured and eliminated

- **Window pages.** All six of Shogun's windows report `bg=None`. `fill_pages_where`
  skips any window whose bg is not `packed_explicit`, so it paints nothing here.
- **Run backgrounds.** Every `PxText` on the frame is `fg=0x00000000
  bg=0x00000000` — fully inherited, nothing named.
- **Artwork.** `build_graphics_canvas` holds ONLY the two ornament flanks:
  `rgba(34,34,34,255)` ground and `rgba(204,170,102,255)` gold, 36,800 opaque
  pixels of 256,000. The credits box, the menu box and the surround are all
  `rgba(0,0,0,0)`.
- **The machine.** A bare `.z6` names no medium, so `InterpreterProfile::resolve`
  falls through to **IBM PC**, which declines `default_colours` deliberately and
  has no `v6_screen_page`. No machine pair, so `v6_host_pair` falls back to the
  host and `v6_machine_page` is a no-op.

So the game contributes **no colour at all** to this frame, and both grounds are
lanthorn's own.

## The two answers

    theme[transcript  ]  fg=White  bg=None     (Provenance::Default)
    theme[upper_window]  fg=White  bg=Black    (Provenance::Default)
    theme[status_bar  ]  fg=White  bg=Black    (Provenance::Default)

`transcript` inherits the `text` role, which sets no background — so the pane is
**unpainted** and the terminal's own shows through (#1D1F21 in the user's
Ghostty). `upper_window` inherits `chrome`, which `Roles::from_scheme` falls back
to as hard-coded white-on-BLACK. The black is not paint the game asked for; it is
the chrome role, emitted as SGR cell backgrounds — the capture's background map
shows `#000000[10..106]` on rows 5..15 and 28..31, spans of CELLS, not a
placement.

So: **grey is the absence of paint, black is the chrome role**, and on one screen
they disagree about what "nobody named a colour" means.

## Why it does not show elsewhere

Boot the same game off `stories/James Clavell's Shogun.adf` and both grounds
become `#424242` — the Amiga's `default_colours` bg 12, which its row flags
`v6_screen_page: yes` ("the machine's default pair IS the Version 6 screen").
`v6_machine_page` then overrides the `upper_window` selector too, so the
disagreement is invisible. Measured: lanthorn off the floppy is 78.8% `#424242`
against the real Amiga capture's 85.4% `#3A3C3A` (`machine-screenshots/amiga-shogun-main.png`,
release 295 — the same release the floppy carries). Same register, this emulator
renders it darker, exactly as SQ-0873 recorded.

## Why the rule is defensible and still wrong here

A solid black ground under a **v3 status line** is right — that is chrome, one row,
and it wants to read as a bar. On a **v6** frame the "upper window" is the game's
whole presentation surface, so the same rule paints a rectangle the size of the
credits panel and leaves the pane around it bare. Two conventions meeting, not a
typo.

## Suggested shape, NOT yet agreed — discuss first

Narrow it to the case that is wrong: on a v6 frame with **no machine pair**,
chrome text cells should take the same ground the pane has rather than the
`chrome` role's black. v3 status lines keep today's behaviour untouched.

Open questions the user wants to settle before anything is written:

1. **Should the pane get a ground instead?** The opposite fix — give the v6 pane
   the chrome black so the panels stop floating — is also coherent, and it is
   closer to what a real IBM EGA screen probably looked like. We have no capture
   to say (see below), and it would be a much more visible change.
2. **Where does the rule live?** A selector default, a `v6_machine_page`-style
   layer, or at the draw site. The first two are theme-visible and a user's
   `style.toml` must still win either way (SQ-0847's rule).
3. **Does this touch `honor_game_colours = false`?** Both baselines have to be
   pinned (CLAUDE.md), and in that mode there is no game pair to inherit at all.
4. **Zork Zero, Arthur, Journey and advent are all on this path too** off their
   bare files. Any change has to be measured on the whole v6 corpus in both
   colour modes, not on Shogun alone.

## The corpus gap behind all of it

There is **no IBM/DOS capture in `machine-screenshots/`** — the same gap SQ-0873
left open for interpreter 5 and 6. We cannot currently falsify a claim about what
an EGA Shogun's screen ground was, which is exactly the kind of question internal
measurement cannot answer (CLAUDE.md). Worth asking the user for one before
choosing between (1) and its opposite.

Not caused by SQ-0903: the identical frame captured on the pre-change baseline
(`31f1c3cf`) is the same picture.

SUPERSEDED IN PART BY SQ-0928, which should be decided first.

That quest has evidence — three DOS captures plus a screen-op trace — that the IBM
PC interpreter's default page is **blue 6 under white 9**. If interpreter 6 gains
a pair, `v6_machine_page` lays it under BOTH grounds this quest is about, and the
two-answers split disappears on exactly the frames where it shows.

So this quest may reduce to a regression test rather than a change. Do not
implement the "chrome text cells take the pane's ground" fix until SQ-0928 is
settled — it would be the wrong repair if the real defect is that the machine had
a pair all along and we declined it.

What survives regardless, and is worth keeping whatever SQ-0928 decides: the
`chrome` role's black and the `text` role's absent background are two different
answers to "nobody named a colour", and a v6 frame is where they meet. If a
machine WITH a pair covers it, the disagreement is merely hidden, not resolved —
it would reappear on any future machine that declines one.
