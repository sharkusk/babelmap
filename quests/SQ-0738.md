--- note 2026-08-09T23:09:28Z ---

ROOT-CAUSED 2026-08-09, measured end to end. NOT a click-mapping bug, and NOT the scopa (SQ-0706) shape. The fix is OUT OF THE RENDER LANE — it is in zvm — so nothing was committed for this quest.

THE VM RECEIVES THE CLICK. Traced with screen_trace on the menu frame:
    @read_mouse(array=0x07e2) -> y=314 x=199 buttons=0x0001
The game reads the coordinates every time, then redraws its menu and waits again. So input delivery works and the header/read_mouse plumbing is correct.

HYBRID AND RASTER DO NOT DIFFER. Since SQ-0729, fmvpoker's menu frame takes `picture_takeover` in BOTH modes, so both render the same raster composite and record the SAME click map — measured byte-identical:
    V6ClickMap { pane 0,0, cell 8x16, img_x 16, img_y 0, img_w 768, img_h 480, native 640x400, text_rows: None }
That map is an exact inverse of the letterbox (768 = 96 cells x 8px, centred in a 100-cell pane). Nothing is wrong with it.

THE GAME'S OWN HIT RECTANGLES, swept by brute force (save_state, restore, set_mouse, submit_char(254), 1px steps, "did the model change"):
    y band (all five items): 316..333 inclusive, 1-based native pixels
    x runs at y=322:  (23,151) (201,346) (395,428) (477,534) (580,616)
                      PLAY     CHANGE     SAVE      RESTORE   QUIT
Those are precisely the game's own set_cursor operands: window 2 is at 1-based (23,236), and its five @set_cursor(row=80, col=0/178/372/454/557, window=2) give absolute lefts 23/201/395/477/580 and an absolute text top of 236+80-1 = 315 (the game tests y > 315, hence 316).

WHERE WE DRAW IT. `v6_layout::buffer_line_rects` stacks a secondary prose window's lines from the window's origin, one 16px row each. The menu is model line 4 of window 2 (y_px 235), so the composite draws it at 0-based native rows 299..315 — 1-based 300..315. The game's band starts at 316. ZERO OVERLAP: the label is drawn exactly one text row above where the game placed it.

END-TO-END DEMONSTRATION (hybrid, 100x30 pane, 8x16 cell, honor=true). Clicking column 39, which is inside "CHANGE CURRENT BET" horizontally:
    cell (39,22) -> game pixel (251,301)  drawn-on-label=true   ACTED=false
    cell (39,23) -> game pixel (251,314)  drawn-on-label=true   ACTED=false
    cell (39,24) -> game pixel (251,327)  drawn-on-label=false  ACTED=TRUE
The two rows that CARRY the label do nothing; the row immediately BELOW it — where nothing is drawn — is the one that works. That is the user's report exactly.

WHY THE 15px IS LOST, and where. zvm `Machine::v6_take_declared_indent` (crates/zvm/src/cpu/exec.rs:3555) converts the declared cursor to text cells by FLOORING:
    (col.saturating_sub(1).saturating_sub(left_margin) / V6_FONT_WIDTH,
     row.saturating_sub(1) / V6_FONT_HEIGHT)
For row=80 that is 79/16 = 4, discarding the 15px remainder, and `ZWindow::push_prose` then pads the buffer out to line 4. The model publishes only `lines: Vec<String>` for this window (`px_runs` is EMPTY — confirmed by dumping the model), so the renderer has a line index and no way to recover the pixel row. The renderer cannot fix this: line*16 IS the model's own statement of where the run is.

TWO CANDIDATE FIXES, both in the concurrent agent's lane:
(a) ROUND instead of floor: (row - 1 + V6_FONT_HEIGHT/2) / V6_FONT_HEIGHT gives line 5 -> 0-based y 315 -> 1-based 316..331, fully inside the measured accept band 316..333. One expression, exact for this game, and bounded at +/-8px for any other. Note the same floor costs the COLUMN 1px ((178-1)/8 = 22 -> x 199 vs the game's 200); harmless at cell granularity.
(b) The general fix: a diverted prose window should shadow its runs at pixel coordinates the way the primary window already does (`ZWindow::streamed` -> `BufferWindow::px_runs`), and the composite should paint them with `draw_story_canvas_runs` instead of stacking `lines`. Then no residue is lost at all and the same defect cannot recur for any other placed run.

BLAST RADIUS to check for either: advent.z6 is the only other title that takes the divert (SQ-0729's measurement), and the app tests `fmvpoker_menu_labels_keep_their_columns_*` pin MENU_LINE = 4 today — that constant moves to 5 under (a).

NOT THE CAUSE, ruled out by measurement: the click map, the hybrid ring/letterbox transform, SQ-0563's cell granularity (the labels are 4-18 cells wide), and any (x,y)/(y,x) swap (`set_mouse` was called as (y_px, x_px) throughout).

SHARED CAUSE WITH SQ-0739? No. 0739 is the story window MOVING to window 2, so its plate belongs to neither half of the hybrid split; 0738 is window 2's declared pixel ROW being quantized away while it is diverted. Both are consequences of fmvpoker running a second prose window, but they have no code in common and neither fix touches the other.
