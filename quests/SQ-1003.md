--- note 2026-08-22T05:18:29Z ---

ROOT CAUSE — `crates/app/src/render/inline_image.rs`. `InlineImageRender` holds two caches:

- `cache: HashMap<(src_ptr, cols, rows, row, page), (Arc, Protocol)>`
- `fitted: HashMap<(src_ptr, cols, rows), (Arc, DynamicImage)>`

Both are keyed in **cells**. Neither carries the **cell's pixel size**, which is read from `picker.font_size()` at the miss (`box_w = cols * fw`, `box_h = rows * fh`, `strip_y = row * fh`) and is the single input that decides how the picture is resampled. So after a font-size change every key is unchanged and both caches hit, serving a `fitted` image and per-row strips resampled for the OLD cell — placed into the same cell rect at the new size. `cols`/`rows` come from `fitted_cells` (native pixels rounded UP to whole cells) and only sometimes move with the font, which is exactly the reported "some sizes".

Restarting the game rebuilds the pictures behind fresh `Arc`s, so every pointer key misses and the corruption vanishes — the user's own observation, and the thing that rules out geometry.

SQ-0988 ALREADY FIXED THIS FOR THE OTHER CACHE. `main.rs:1981` calls `graphics_render.invalidate_cell_geometry()` when `refresh_cell_size` reports a move, and `draw_chrome_band` folds `(cw, ch)` into its freshness hash directly. `InlineImageRender` is a sibling field on `AppState`, owned by neither, and got neither.

FIX: fold the cell size into both keys, rather than adding a second thing for a resize site to remember — the chrome-band hash is the precedent.
