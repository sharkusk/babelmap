--- note 2026-08-09T21:22:47Z ---

USER DIRECTIVE 2026-08-09, and it adds a requirement this quest did not have: "we should select the amiga as the interpreter when running from an adf."

So loading from an ADF is not merely a container question — it also selects an interpreter PROFILE. That is a behavioural change, not a cosmetic one.

WHAT ALREADY EXISTS (verified in the tree, 2026-08-09):
- **Interpreter selection is already plumbed.** `Machine::interpreter_number: Option<u8>` (`crates/zvm/src/cpu/exec.rs:346`), setter `set_interpreter_number` (line 862), applied into **header byte 0x1E** by `init_header_caps` (`crates/zvm/src/screen.rs:1091`) at every `init_caps`, so it survives `@restart`. Default is `None` = auto, following Frotz's rule: **6 (IBM PC) for v6, else 1 (DEC-20)**. Existing unit tests pin both the default and the override.
- **It already changes behaviour.** `crates/zvm/src/cpu/exec.rs:4052` branches on `self.mem.read_byte(0x1E) == 6`. So switching a v6 story from IBM PC to Amiga will change what the game does — which is the point (authenticity) and also the risk (every v6 title currently renders against the IBM-PC answer). Any change here needs the full corpus re-checked, not just the ADF path.
- **The native Amiga picture codec is done** — SQ-0713 landed `crates/blorb/src/infocom_pics.rs`, and the flavour it decodes (big-endian Huffman + RLE + per-line XOR) is exactly the flavour on these disks. 383 of 388 Zork Zero pictures decode byte-exact.

WHAT DOES NOT EXIST:
- Reading an ADF at all. The OFS/FFS filesystem walk was done by hand in Python during the investigation session and is NOT in the codebase. What it needs: 880 KB image, 512-byte blocks, bootblock `DOS\0` with bit 0 of byte 3 selecting OFS vs FFS; scan blocks for file headers (type word 2, secondary type 0xFFFFFFFD = ST_FILE, name length at BSIZE-80, name following, byte size at BSIZE-188); OFS data blocks carry a 24-byte header (type 8, header_key, seq, size, next) with 488 bytes of payload, FFS blocks are raw. Verified against the real Zork Zero disks: Disk0 is a plain AmigaDOS boot disk, Disk1 holds `Story.data` (the z6), `Pic.data` (the picture archive), the interpreter binary, and saved games.
- Choosing WHICH files to use from a mounted image. `Story.data` and `Pic.data` are the Infocom convention, but the names are not guaranteed and there is no manifest to trust — the disk's own `.info` sidecar lists names but also lists `Icon.data`, a file that does not exist (it is a save-icon template; see SQ-0713's notes).
- Any resolution policy tying a native picture archive to a story — that is SQ-0734.

VERIFY, DO NOT ASSUME: the interpreter number for Amiga comes from the ZMSD's interpreter-number table (§11.1.3). Read it from the standard rather than recalling it — CLAUDE.md is explicit that spec constants come from authoritative sources, and a wrong number here would be silently wrong rather than loudly wrong.

ALSO WORTH DECIDING: which story versions this applies to. Infocom's Amiga releases span v3-v6 while zvm runs v3-v8, so an ADF containing a modern v8 story would be anachronistic. Probably harmless, but the rule should be stated rather than emergent.

--- note 2026-08-09T21:32:51Z ---

The deferred second half of this quest — selecting the Amiga interpreter profile — has grown a rule, recorded in full on SQ-0734: the user wants the interpreter number inferred from the FLAVOUR of the art in play, with an explicit setting overriding it. An ADF implies Amiga; a named `.EG1` implies IBM PC; an explicit interpreter setting beats both; the existing Frotz default (6 for v6, else 1) is the fallback.

The first agent on this quest is scoped to mounting and file selection ONLY and has been told to stop and report rather than reach for the interpreter number, because 0x1E is not inert — `crates/zvm/src/cpu/exec.rs:4052` branches on it being 6, which is what every v6 story gets today. Do the profile work as its own change, with the whole v6 corpus re-checked, and read SQ-0734's note first.
