--- note 2026-08-09T21:22:47Z ---

USER DIRECTIVE 2026-08-09, and it adds a requirement this quest did not have: "we should select the amiga as the interpreter when running from an adf."

So loading from an ADF is not merely a container question — it also selects an interpreter PROFILE. That is a behavioural change, not a cosmetic one.

WHAT ALREADY EXISTS (verified in the tree, 2026-08-09):
- **Interpreter selection is already plumbed.** `Machine::interpreter_number: Option<u8>` (`crates/zvm/src/cpu/exec.rs:346`), setter `set_interpreter_number` (line 862), applied into **header byte 0x1E** by `init_header_caps` (`crates/zvm/src/screen.rs:1091`) at every `init_caps`, so it survives `@restart`. Default is `None` = auto, following Frotz's rule: **6 (IBM PC) for v6, else 1 (DEC-20)**. Existing unit tests pin both the default and the override.
- **It already changes behaviour.** `crates/zvm/src/cpu/exec.rs:4052` branches on `self.mem.read_byte(0x1E) == 6`. So switching a v6 story from IBM PC to Amiga will change what the game does — which is the point (authenticity) and also the risk (every v6 title currently renders against the IBM-PC answer). Any change here needs the full corpus re-checked, not just the ADF path.
- **The native Amiga picture codec is done** — SQ-0713 landed `crates/blorb/src/infocom_pics.rs`, and the flavour it decodes (big-endian Huffman + RLE + per-line XOR) is exactly the flavour on these disks. 383 of 388 Zork Zero pictures decode byte-exact.

WHAT DOES NOT EXIST:
- Reading an ADF at all. The OFS/FFS filesystem walk was done by hand in Python during the investigation session and is NOT in the codebase. What it needs: 880 KB image, 512-byte blocks, bootblock `DOS\0` with bit 0 of byte 3 selecting OFS vs FFS; scan blocks for file headers (type word 2, secondary type 0xFFFFFFFD = ST_FILE, name length at BSIZE-80, name following, byte size at BSIZE-188); OFS data blocks carry a 24-byte header (type 8, header_key, seq, size, next) with 488 bytes of payload, FFS blocks are raw. Verified against the real Zork Zero disks: Disk0 is a plain AmigaDOS boot disk, Disk1 holds `Story.data` (the z6), `Pic.data` (the picture archive), the interpreter binary, and saved games.
- Choosing WHICH files to use from a mounted image. `Story.data` and `Pic.data` are the Infocom convention, but the names are not guaranteed and there is no manifest to trust — the disk's own `.info` sidecar lists names but also lists `Icon.data`, a file that does not exist (it is a save-icon template; see SQ-0713's notes).
- Any resolution policy tying a native picture archive to a story — that is SQ-0734.

VERIFY, DO NOT ASSUME: the interpreter number for Amiga comes from the ZMSD's interpreter-number table (§11.1.3). Read it from the standard rather than recalling it — CLAUDE.md is explicit that spec constants come from authoritative sources, and a wrong number here would be silently wrong rather than loudly wrong.

ALSO WORTH DECIDING: which story versions this applies to. Infocom's Amiga releases span v3-v6 while zvm runs v3-v8, so an ADF containing a modern v8 story would be anachronistic. Probably harmless, but the rule should be stated rather than emergent.

--- note 2026-08-09T22:10:02Z ---

SCOPE OF "THE AMIGA PROFILE", traced in the code 2026-08-09 after the user tried setting interpreter-number 4 by hand and reported: scaling unchanged; without it the story fg/bg is the terminal default; with it the story bg is light grey and the text white (poor contrast) while input text is black.

**The core finding: "the Amiga profile" is a BUNDLE of at least six independent knobs, and only one of them is currently settable.** That is why setting 0x1E alone produced an incoherent machine — a byte that changes what games *do* without changing the machine it implies.

1. **Art scale / standard window — NOT keyed on the interpreter number at all.** `session.rs:800` keys `art_scale` on `v6_screen_px.is_some()`, i.e. the Blorb `Reso` chunk. Byte 0x1E is not consulted. This is why setting 4 changed no scaling, and it is SQ-0736. The profile must SUPPLY a standard window (Amiga v6 = 320x200 art on a 640x400 screen) so the existing x2 rule fires, rather than special-casing ADFs.
2. **Interpreter number (0x1E)** — already wired end to end: `Machine::interpreter_number`, `Config::set_interpreter_number`, a picker at `input.rs:3750`, applied by `init_header_caps`. Needs auto-selection from the source (SQ-0734's rule).
3. **Default colours ($2C/$2D) — currently the TERMINAL'S colours, deliberately.** zvm's own defaults are `DEFAULT_BG_COLOUR = 2` (black) / `DEFAULT_FG_COLOUR = 9` (white) (`screen.rs:1194`), but `loop_tick.rs:192` overwrites them every tick from `state.term_default_colors`. That is exactly the user's "without setting it, the story fg/bg is terminal default", and it is right for a terminal-native experience. For a profile claiming to BE an Amiga it is arguably wrong: the game should be told the Amiga's defaults, not the user's terminal's. This is a real design decision, not a bug — flag it rather than silently changing it.
4. **Colour number → RGB mapping.** The light-grey-on-white the user sees is very likely the GAME's own choice: Zork Zero branches on the interpreter and picks an Amiga colour scheme, and "light grey" is standard colour 10 (v6-only, `screen.rs:1247`). We resolve standard numbers through ZMSD §8.3.1's true-colour table, which is correct for the standard but is not the Amiga's actual palette. If we claim to be an Amiga, those numbers arguably should resolve to Amiga colours — and the contrast the user is seeing is the gap between the two. **Verify any Amiga palette against an authoritative source; do not reconstruct it from memory** (CLAUDE.md).
5. **Input-line colours.** "input text is black" while the story is white-on-grey suggests the input surface does not follow the game's foreground. Needs its own measurement; may be independent of the profile.
6. **Font cell metrics** — 8x16 for v6 already, documented in `docs/features/v6-graphics.md`. Probably nothing to do, but it belongs in the bundle so the profile is complete rather than partial.

**RECOMMENDATION: build the profile as one named thing** (a struct or enum selecting screen geometry, standard window, default colours, colour palette and interpreter number together), then let the SOURCE choose it — ADF → Amiga, a named `.EG1` → IBM PC, explicit setting overrides. Wiring these knobs one at a time is what produced the incoherent state the user just hit.

**BLAST RADIUS unchanged and still the main risk:** `exec.rs:4052` branches on `read_byte(0x1E) == 6`, which every v6 story gets today. Any change here needs the full v6 corpus re-checked frame-by-frame.

--- note 2026-08-09T22:17:04Z ---

APPROVED by the user 2026-08-09: build the interpreter profile as one named bundle. Their framing, which is the key to doing this safely: **"we basically already have the ibm pc version wired today (default)"**.

So this is not "add Amiga behaviour" — it is **name what already exists, then add a sibling**:

- **`IbmPc`** = today's behaviour, exactly. Interpreter number 6 for v6 / 1 otherwise (Frotz's rule), the Blorb `Reso` standard window driving `art_scale`, terminal-sourced default colours via `loop_tick.rs:192`, ZMSD §8.3.1 colour resolution, 8x16 v6 cell.
- **`Amiga`** = the sibling. Standard window 320x200 (so the existing x2 rule fires and SQ-0736 dissolves), interpreter number per ZMSD §11.1.3, Amiga default colours, Amiga palette.

**THE REGRESSION GATE FALLS OUT OF THAT FRAMING, and it should be stated as an acceptance criterion:** with `IbmPc` selected, the entire v6 corpus must be **byte-identical** to today — Zork Zero, Arthur, Shogun, Journey, advent, scopa, mysterious01, fmvpoker, across both `honor_game_colours` modes and every render path. If it is not, the profile has been defined wrongly, not the corpus. That converts the "0x1E branches at `exec.rs:4052` and every v6 story sees 6" blast radius from a hazard into a checkable property.

TWO SUB-DECISIONS I flagged as the user's; taking them as approved under "let's do the amiga profile suggestions", with the reasoning recorded so they are easy to reverse:
- **The Amiga profile reports Amiga default colours, not the terminal's.** Reporting the host terminal's colours is right for a terminal-native experience and is what `IbmPc` keeps; a profile whose whole purpose is to present as an Amiga should not tell the game about the user's terminal.
- **The Amiga profile resolves standard colour numbers through the Amiga palette**, not ZMSD §8.3.1's true-colour table.

Both make the result more authentic and potentially less readable in a modern terminal — which is exactly what the user saw when they set 0x1E by hand and got white on light grey. The escape hatch already exists and needs no new setting: **`honor_game_colours` still governs whether the game's colour choices are honoured at all**, so a user who dislikes the authentic palette turns it off and gets their theme. Compose with that rather than adding a knob.

**VERIFY, DO NOT RECALL:** the interpreter number for Amiga (ZMSD §11.1.3) and the Amiga palette itself both need an authoritative source. CLAUDE.md is explicit, and a wrong value here is silently wrong — the game simply behaves as a different machine.

Still open, deliberately not decided: the input line rendering black while the story is white-on-grey (knob 5 in the previous note). Measure it before assuming it belongs to the profile at all.
