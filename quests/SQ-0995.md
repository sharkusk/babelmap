## The mechanism, verified in code

`kitty_place_rows` (`crates/app/src/render/graphics.rs:2634`) encodes the image id into EVERY placeholder cell: the low 24 bits as the foreground `Color::Rgb(id_r, id_g, id_b)`, the high byte as the third diacritic. `render_kitty_virtual` (:1346) sets `entry.id` from a `canvas_hash` lookup, and a miss allocates a NEW id.

So the id is a per-cell value, and changing it dirties the entire grid:

- **Canvas unchanged** -> same id -> placeholders byte-identical -> ratatui's diff emits nothing. This is the case the design is good at, and it already works.
- **One pixel changes** -> new hash -> new id -> all `w*h` placeholder cells differ in their fg colour -> the diff emits every one. At 458x144 that is 65,952 cells, ~380 KB, on top of the (now compressed, ~50 KB) image.

The existing `sent: Vec<(u64, u32)>` LRU only helps a game that flips between a FEW FIXED canvases — advent.blb's toolbar alternating resting/pressed re-places an id the terminal already holds. Novel or evolving content always takes a new id, so an animating v6 frame pays the full repaint every time.

**This means SQ-0977's "the cells cost more than the images" is the per-CHANGE cost, not a cold-start artifact.**

## The fix the mechanism points at

Re-transmit to the SAME id instead of allocating a new one. The kitty protocol allows replacing the data behind an existing id; if the id is stable the placeholders never change, the diff emits zero cells, and the whole per-frame cost collapses to the compressed image.

Things to establish rather than assume:
- Whether a terminal updates an existing placement in place when the data behind its id is replaced, or whether the placement must be re-issued (and if so, whether re-issuing costs the cells again).
- What happens to a still-displaying placement mid-transmit — a torn or blanked frame would be worse than the bytes.
- Whether the `sent` LRU still earns its place, or becomes dead once ids are stable per window.
- The interaction with SQ-0637's delete-on-resize: ids currently churn on resize by design, since the r x c grid is baked into the transmission.

## What NOT to do

Do not drop virtual placements for direct (`a=p`) placements to save the cells. That would cost the HiDPI correctness SQ-0520 pinned — ratatui-image's placement omits `r`/`c`, and on displays rendering images at device pixels while reporting cell metrics in logical points (Ghostty/macOS 2x) the image covered only part of the window and mouse clicks mapped to the wrong game pixels — and it would give up ratatui's occlusion and z-order handling, since with virtual placements the cells ARE the image.

The cell model is right. It is the id churn that stops it paying off.

## Done, measured, and one thing the framing got wrong

Commit 5dbe01eb on branch `worktree-agent-a896564ee97342b13` (not merged, not pushed). Gate: `5919 tests run: 5919 passed`, grep count 0; clippy clean.

### What the protocol says about replacing data at an existing id

*"When re-transmitting image data for a specific id, the existing image and all its placements must be deleted. The new data replaces the old image data but is not actually displayed until a placement for it is created."*

That reads like a blocker and is not one, because our transmit is `a=T,U=1,r,c` — transmit AND display in one command. It replaces the data and re-creates the window's virtual placement with the same r×c in the same breath, so the placeholder cells never stop resolving and never need re-emitting. Ghostty is looser still: `ImageStorage::add_image` replaces the image and leaves placements alone, bumping a generation stamp that drives its repaint.

**Mid-transmit is safe.** A chunked transmit accumulates and commits only on the final chunk (`load_and_add_image`: `if t.more_chunks { … return }`), so the old picture stays on screen for the whole of the new one's journey. No tear, no blank.

**One thing had to change on the wire: `p=1`.** `p=0` means "assign me an internal placement id", and since Ghostty does NOT delete placements on re-transmit, an unnamed placement would leave one dead duplicate behind per animated frame. A named (external) placement is replaced in the map. The cells still encode placement 0, which resolves as "the first virtual placement of this image" — the only one.

### The `sent` LRU is gone, and the measurement is why

It cannot coexist with a stable id: an id you might place is an id in every cell. And it never earned its place — a cache HIT swapped the id back and repainted the whole grid anyway. golden_baton.blb at 230×64, the frame that walks back into an already-drawn room: **zero bytes of image transmitted, 39,859 bytes emitted.** It is now 4,107 with a 2,620-byte re-upload. The half of SQ-0564 that survives is the content hash (a repaint onto identical pixels still transmits nothing). A window now holds exactly ONE image in the terminal however long it animates — tighter than the cap, with no eviction to get wrong.

### SQ-0637 kept verbatim

Resize still churns the id (the r×c grid is baked into the transmission) and still deletes what it abandons, in the same batch as the replacement, ahead of it. Window close still deletes. `queue_kitty_deletes` now frees one id instead of a cache generation, and skips an entry that never transmitted.

### THE FRAMING WAS WRONG ABOUT WHERE THIS LIVES — see the follow-up

`render_kitty_virtual` is **not on the v6 path at all**. Journey r83, Zork Zero r393, Shogun r322 and Arthur r74 all emit ZERO ids from lanthorn's own `0x00B0_xxxx` range under a pty: v6 art goes through `WinNode::Layered` → chrome ring or raster composite, and both are placed by `ratatui-image`. The path this quest fixed serves Glulx graphics windows (advent.blb's toolbar) and Scott room pictures.

So "an animating v6 frame pays it every time" is true of the DEFECT and false of this CODE — the same id churn exists one layer down, on the `ratatui-image` placements, where the frames are far larger. Filed as SQ-0996.
