MEASURED on `stories/Planetfall r29 (clean copy from retail disk).dsk` (143,360 bytes, now in the corpus). Re-derive rather than trusting these numbers — my probes have been wrong twice today — but this is the shape:

- **Boot sector** opens `01 A5 27 C9 09 D0 16 A5 2B` — DOS 3.3 / RWTS style, NOT ProDOS's `01 38 B0 03 4C`.
- **No DOS 3.3 VTOC** at track 17 sector 0 (release byte 0, tracks 26, sectors 99 — noise).
- **No ProDOS volume directory** at block 2 in physical order OR de-interleaved. So it is genuinely filesystem-less, unlike the `.dsk` sets SQ-0864 handled, which turned out to be ProDOS volumes in DOS-order interleave.
- **Sector order is DOS 3.3 LOGICAL interleave**: `[0,7,14,6,13,5,12,4,11,3,10,2,9,1,8,15]`. Three other orders were tried and rejected.
- **Story at track 3, sector 0** — offset 12,288 after de-interleaving. v3, release 29, serial 840118, declared length 109,052.
- **Verified**: the story's own header checksum `$842E` matches a computed sum over `0x40..109052` ONLY under that interleave. Physical order gives `529D`, DOS→ProDOS `97D5`, ProDOS→DOS `3F20`. That checksum is the oracle — a reader that gets the interleave wrong produces a plausible-looking story with a wrong checksum, so it must be verified rather than assumed.

WHY THIS MATTERS BEYOND ONE GAME: it is the first **non-v6 Apple disk** in the corpus. `zvm-cli` declines v6 by design, so every Apple format we support today (`.2mg`, `.dsk`, `.po`) can be MOUNTED but never PLAYED through the CLI, because Arthur, Journey, Shogun and Zork Zero are all v6. Planetfall closes that hole for whichever path reads it. The same gap still stands for HFS, where `Zork Zero Disk.image` is our only Macintosh disk and is also v6.
