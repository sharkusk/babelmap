--- note 2026-08-09T18:22:59Z ---

MEASURED 2026-08-09 while closing SQ-0697's second half. Shogun's title screen in RASTER mode shows the frozen banner and the menu correctly and NO prose at all — "You may choose to:" never appears. Rendered the composite to PNG to confirm.

CAUSE, measured: `v6_layout::story_clear_native` shrinks the story window's box edge-by-edge until no edge row/column carries an opaque chrome pixel. Shogun's story box is (46,336) 548x64 — four rows — and window 2 (the menu) sits INSIDE it at (234,336) 169x48 with an erase fill, which lands on the paint ground. The shrink therefore eats the top three rows:

    story_clear_native = Some((46, 384, 548, 16))     -- one row of four

and `build_main_text(state, 68, 1)` on a one-row box returns `lines: []`, `viewport_rows: 0` (`RasterMetrics { total_rows: 10, viewport_rows: 0, max_scroll: 10, first_visible_row: 10 }`). So the box collapses to one row and that row then renders nothing. `build_main_text(state, 68, 4)` — the box the game actually declared — returns the right thing: ["Release 322 / Pix 322 / Serial number 890706", "IBM Interpreter version 6.65", "You may choose to:"].

TWO DEFECTS, either of which alone would hide the prose:
1. `story_clear_native` treats a chrome window painted OVER the story as if it bordered it. Insetting past bordering frame art is the function's purpose and is right (Zork Zero's frame, Arthur's plate); a menu window that overlaps the story box is the game deliberately drawing on top of window 0, and both coexist on a real interpreter — the prompt at x=47, the menu at x=235, same rows.
2. A one-row story box yields ZERO visible transcript rows. Even after (1), a genuinely tiny box should show its one line rather than nothing.

NOT a regression from the SQ-0697 freeze, and not from SQ-0715/0717/0721: the raster arm is untouched by all of them, and before the freeze the same shrink applied to the same box. Shogun's title has never shown prose in raster.

SCOPE NOTE: deliberately left undone by the SQ-0697 agent. The reported bug, the approved design and the corpus were all about where the RESUMED transcript lands, which is now correct in hybrid, frameless and the cell fallback. Fixing (1) means changing what `story_clear_native` counts as an obstruction, which is load-bearing for Zork Zero's hints/InvisiClues screens, scopa and Journey — a guess there is exactly the kind of render-geometry change the standing rule says to check with the user first.

--- note 2026-08-09T19:11:34Z ---

FIXED 2026-08-09 (commit 9c48ce29, worktree branch worktree-agent-a5638a57fe9a3fae0). Both defects the earlier note named, plus two more the fix exposed.

DEFECT 1 (the obstruction rule). `story_clear_native` shrinks the story window until no edge touches an opaque pixel. Its purpose — seating prose inside bordering frame ART — is right; the input was wrong, because rasterized chrome TEXT is opaque too. Measured, declared box vs. what the shrink returned:
    Shogun   (46,336) 548x64  ->  548x16  (1 row)   [ART ONLY: 548x64]
    Journey  (240,0) 392x304  ->  392x0             [ART ONLY: 392x304]
Journey is a fourth witness nobody had filed: its raster has never carried prose either, and for the same reason — the SQ-0504 screen-wide pure-reverse gap fill (triggered by ONE reversed divider cell on each of nineteen rows) floods straight across window 0's text panel.

The corpus fear in the earlier note did not materialise. `story_clear_native` is only called on the raster path in production (`story_viewport`, the hybrid-side caller, is dead — hybrid uses `story_viewport_box`, the DECLARED box, since SQ-0549). Measured before/after on Zork Zero (gameplay + hints), scopa, Arthur (all 8 intro frames), advent: identical. Only Shogun and Journey move, and both move from "no prose" to "prose".

FIX: the raster path measures the box against art + grounds (`build_graphics_canvas` + the same `grounds` closure that composes paint ground and window pages onto the real canvas), never the chrome text.

CONSEQUENCE, and the second half: with the box back to four rows, the flat `fill_cell` story-page fill erased Shogun's menu. Window 0's page belongs UNDER what other windows printed into its box. `fill_story_page_under_chrome_text` spares the rects the game's own `px_texts` runs and non-blank grid cells occupy. Deliberately NOT "every opaque pixel": SQ-0504's gap fill is a host device for closing bare cells in a bar, not something the game drew, and sparing it would leave Journey's panel entirely grey with grey ink on it.

DEFECT 2 (a one-row box renders zero rows) is fixed by defect 1 for Shogun — the box is four rows again, viewport_rows 3. The general "a genuinely tiny box should show its one line" case is NOT addressed: `build_main_text` still reserves one row of the box for the input line, so a genuine 1-row story window still reports viewport_rows 0. No game in the corpus now hits it. Filing that as a separate concern rather than guessing at it.

DEFECT 3, found while fixing: `build_main_text` ignored the screen-clear anchor. The cell path top-anchors post-clear output (`window_wrapped_rows` / `anchor_row_at`, SQ-0305/0640); raster bottom-stuck, so the newly-four-row box redrew ["Release 322 / Pix 322 / Serial number 890706", "IBM Interpreter version 6.65", "You may choose to:"] — the tail of the banner the SQ-0697 freeze had just retired as paint up top — across the menu. `build_main_text` now records each source line's wrapped-row start and pins the same way. After: ["You may choose to:"], and the raster composite matches Shogun's own hybrid layout exactly.

Tests: crates/app/tests/v6_raster_text_loss.rs — 10 cases, both honor_game_colours modes, covering Shogun (prose present, menu survives the page fill, top-anchored), advent, fmvpoker and Journey. Each change falsified separately with the reported symptom. Gate 0 / 95 binaries / 95 results / 0 SKIP; clippy clean.

FOR THE USER'S EYE (why Confirm, not done): Journey's raster panel now shows its prose as light ink on the host's dark page, sitting inside the light-grey screen the SQ-0504 gap fill paints. It is readable and it is the same story-page rule every other v6 game gets, but Journey's screen is the game asking for a light background overall, so the dark panel may read as wrong. Not touched here — it is a colour-resolution question, not a text-loss one.
