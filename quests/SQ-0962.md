## The report

Point lanthorn at any of `treasures/The Lost Treasures of Infocom - Disk N - ….dc42` and it **launches straight into the first game found** instead of offering a chooser. The user's reading was "single-disk multi-game is broken in lanthorn, we need to add support for it".

## MEASURED, and the diagnosis is narrower than that — support exists

Mounted each volume and asked it directly:

    Disk 1 - Beyond Zork, Lurking Horror      detect=true  stories()=4
        Beyond Zork / Lurking Horror / Trash/Lurking Horror / Trash/The Lurking Horror
        story() tiebreak -> "Beyond Zork"
    Disk 4 - Enchanter … Zork III             detect=true  stories()=6
        Enchanter / Sorcerer / Spellbreaker / Zork I / Zork II / Zork III
        story() tiebreak -> "Spellbreaker"
    Disk 5 - Zork Zero                        detect=true  stories()=1
        story() tiebreak -> "Story.data"

**The `blorb` layer enumerates these volumes correctly.** So this is not missing support and nothing needs adding at that level. Note Disk 5 has ONE story, so launching straight in is CORRECT there — any fix must keep that.

Single-disk multi-game is also plumbed through the app already, so "add support" would duplicate what exists:

  - `StoryEntry.meta.disk_entry: Option<String>` threads a chosen story through the picker, the launch-options dialog and the save key (`story_key_at_from`, `pictures_for`, `lo.disk_entry`).
  - `picker::dedupe_within_a_volume` exists SPECIFICALLY for a volume holding several games, and prefers the deepest path so `PC/ZORK1/DATA/ZORK1.DAT` beats `PC/DATA/ZORK1.DAT` — it would fold this press's `Trash/Lurking Horror` duplicates the same way.
  - SQ-0859 already fixed a bug about exactly this shape (a story chosen off a compilation being handed its disk-mate's fetched metadata).

So the defect is that the **launch path does not reach the chooser for this press** — a story is selected by `story()`'s tiebreak and started. "Launches the first game found" matches the tiebreak output above: Beyond Zork on disk 1, Spellbreaker on disk 4.

## Where to look

The question is what the direct-launch path (`lanthorn <path>`) does differently from the browser, which the user reports DOES list games correctly for the `.adf` press. Compare against `crates/app/tests/suites/disk_story_rows.rs` and `disk_set_rows.rs`, which pin the browser's answer.

Worth checking whether the two presses differ in a way a heuristic keys on: the ADF volumes hold their stories in SUBDIRECTORIES (`Zork/Zork1.Data`, `Spellbreaker/Story.Data`) while the DiskCopy volumes hold them at TOP LEVEL (`Beyond Zork`, `Zork I`). If something distinguishes "a disk with a game on it" from "a disk of games" by path depth, that is the first suspect.

## Related, not the same

  - **SQ-0961** — `zvm-cli` lists only the platter's games where lanthorn lists the collection. Different front-end, different code path, same family ("enumeration is not reaching the user").
  - **SQ-0961's second note** — `disk_set::members` returns **0** for this DiskCopy press because its naming has the index in the middle with no common suffix. That is a SEPARATE defect on the same fixture and does not explain this one: these volumes each hold their games themselves, so no grouping is needed to enumerate them.

Do not conflate the three. This one is about a single volume's chooser.
