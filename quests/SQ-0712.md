--- note 2026-08-09T16:32:49Z ---

ROOT CAUSE FOUND AND SPEC-VERIFIED 2026-08-09; the fix is a one-liner but does NOT land alone. Not a design question — do not treat it as one.

WHAT THE GAME DOES (mysterious01, screen ops, turn after answering 'n'):
  @erase_window(all(unsplit))
  @split_window(260)
  @set_window(upper)
  @draw_picture(number=1, window=1, y=1, x=1)   … + set_cursors + picture 32
  @set_window(lower)                            … and narrates here
It never calls @move_window on window 0. It does not have to.

THE SPEC. ZMSD sect.8.8.4.1, verbatim (fetched from inform-fiction.org/zmachine/standards/z1point1/sect08.html, not memory): "The split_screen opcode tiles windows 0 and 1 together to fill the screen, so that window 1 has the given height and is placed at the top left, while window 0 is PLACED JUST BELOW IT (with its height suitably shortened, possibly making it disappear altogether if window 1 occupies the whole screen)."

zvm's v6 split (cpu/exec.rs VAR:0x0A) shortens window 0's HEIGHT but leaves its ORIGIN at (1,1) — a deliberate choice recorded in the comment there for SQ-0497. That is the whole bug: after split_window(260) win1 is 640x260 at (1,1) and win0 is 640x140 at (1,1), exactly the reporter's dump.

THE FIX (tried, verified, then REVERTED — see below): in the v6 arm, also set windows[0].x_coord = 1, y_coord = rows + 1, x_size = screen_w. mysterious01 then gives win0 640x140 at (1,261); rendered to PNG, the prose sits below the artwork instead of over it. Zork Zero's split_window(400) title splash is unaffected (win0 goes to (1,401) with height 0 — the spec's own "disappear altogether" — and the game re-places it with its own move_window on the next screen). Two regression tests were written and falsified cleanly:
  "the story window must sit BELOW the picture window the split put at the top — win0 (1,1) 640x140 overlaps win1 (1,1) 640x260"

WHY IT WAS REVERTED — advent.z6. Its Inform 6 v6 library READS WINDOW 0'S POST-SPLIT GEOMETRY BACK and positions its own window 7 from it:
  @split_window(20)
  @get_wind_prop(win=0, prop=1) -> 1     (x_coord)
  @get_wind_prop(win=0, prop=0) -> 21    (y_coord — 21 only WITH the fix; 1 today)
  @move_window(win=7, y=21, x=1)
So the game itself corroborates the spec reading. But once window 0 stops overlapping window 1, four v6_advent_status cases fail, and one is a real visual regression, not a stale baseline. Measured, frameless cell dump, 80x25, after "look" at End Of Road:
  BEFORE fix:  row 0 "At End Of Road    Score: 36    Moves: 3"   <- the status bar
               rows 1-3 the room description
  AFTER fix:   NO status bar at all; row 2 "At End Of Road", rows 3-4 the prose
The bar disappears. draw_anchored_status_band takes runs with native row < story.y_px/16; with the story correctly at y=20 that bound becomes 1 and advent's bar rows fall outside it. In other words the frameless/hybrid status-band renderer was compensating for the overlapping geometry, and correcting the geometry exposes it.

DISPOSITION. The engine change is right and ready; it needs a matching fix in crates/app/src/render/screen.rs (draw_anchored_status_band's band bound, and the help-panel opacity + frameless-bar cases that follow from it). That file was being worked in concurrently by the SQ-0710/0711 agent this session, so the two halves must not be attempted in parallel. Land them together, in one pass, with the advent frameless/hybrid dumps re-checked by eye before re-baselining any v6_advent_status expectation — three of the four failures are consequences of the fourth and must not be blanket-updated.
