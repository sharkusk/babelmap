--- note 2026-08-10T02:28:01Z ---

SYMPTOM (user, 2026-08-09, hybrid, after SQ-0739's frame fix landed): choosing "CHANGE CURRENT BET" leaves the bottom panel blank — no prompt, no money lines, and the digits typed are never echoed. Typing a number and pressing Enter still applies the new bet and the game continues, so the INPUT works and only its display is lost. The user then found the same on "QUIT": blank panel, and pressing `y` exits. Not bet-specific — it is every read that fmvpoker performs through window 2.

That last point is the useful discriminator: the trigger is "window 2 becomes the v6 input window", not anything about the bet screen's content.

MEASURED MECHANISM (carried over from SQ-0739's closing section, still current):
zvm's divert rule is `prose_window() && !copy_to_transcript() && current != v6_input_window`. The instant window 2 becomes the input window it stops being diverted and is published as the PRIMARY Buffer, whose `lines` are empty by construction (a primary window's prose is the host transcript). But the prompt was printed into window 2's `prose` buffer while it was still diverted, and that buffer is dropped on the switch. In the same instant window 0 stops being a Buffer, so its `px_runs` shadow — carrying "Current Bet:" / "10" / "Total Winnings:" / "1000" at (76,247), (76,265), (420,247), (420,265) — is dropped too.

At the bet frame: window 2 publishes `lines: []`, window 0 publishes `px_texts: []`, and the host transcript is unchanged from the menu frame. The model carries no text for that screen from either window, so the composite has nothing to draw.

    menu frame:  story=(0,0,640,400)     story_gfx=(0,0,640,400)   path=raster
    bet frame:   story=(22,235,594,156)  story_gfx=(0,0,640,400)   path=hybrid-ring

OPEN QUESTION for whoever takes this — the echo is a THIRD loss, and it may have a different cause than the two drops above. The typed digits are host-side input, not game prose, so they should reach the screen even with both buffers empty. Check whether SQ-0739's new `story_plate_escapes_story_window` takeover arm is now suppressing story-text drawing on this frame: a full-picture takeover that paints the plate and skips `draw_story_text` would explain a panel that is blank rather than merely missing the game's own lines. If so, the takeover needs to keep drawing the story text (and the input line) inside the story window's box. Measure before assuming — this is a hypothesis, not a finding.

Both buffer losses are in the session/zvm publish path; the echo may be in render. Fixes must hold in BOTH honor_game_colours modes and must not move any other title's `v6_path_log`.

FIXED 2026-08-09 (commit 30dcde56, worktree agent-abab44c143b324752; merged main 651622a7 cleanly). Status left at `confirm` — the user should look at the bet and quit screens.

MEASURED, before touching production code, with a headless probe over the real bet and quit frames (both honor_game_colours modes):

  menu frame:  current=0 input=0  win0 primary Buffer px_runs=[(76,247 "Current Bet:"),(76,265 "10"),(420,247 "Total Winnings:"),(420,265 "1000")]  win2 secondary Buffer, 8 lines (menu + hint)
  bet  frame:  current=2 input=2  win0 published as a GRID, px_texts=[]      win2 published as the PRIMARY Buffer, lines=[]
  zvm state at the bet frame: win0.streamed still holds all four money runs; win2.prose still holds ["","","","","","Enter the new bet: "]. NOTHING was lost in the engine — both buffers were dropped by the app's PUBLISH path.

All three losses have ONE cause: `prose_idx`/the divert rule let the READ decide which window is the transcript. zvm diverts a prose window's text to its own buffer when `prose_window() && !copy_to_transcript() && current != v6_input_window`. fmvpoker prints "Enter the new bet: " into window 2 (attribute 2 CLEAR) while input_window is still 0, then reads through window 2 — and that read re-designated it.

  1. PROMPT: window 2 republished as the primary Buffer, whose `lines` are empty by construction (a primary window's prose is the host transcript). The prompt printed a moment earlier stayed in win2.prose and was never published.
  2. MONEY LINES: window 0's `streamed` shadow publishes as `px_runs` ONLY on the primary-Buffer branch. Window 0 stopped being primary, took the Grid branch, and published `px_texts: win.texts` — which is empty for a window that streams.
  3. ECHO — the SQ-0746 hypothesis (SQ-0739's `story_plate_escapes_story_window` takeover arm suppressing story text) is WRONG. Measured: the takeover arm was never involved. The host draws its live input line in the STORY window, the story window was now the panel, and the panel had NO text box at all. `story_clear_native` measures the story box against a canvas that includes the game's own painted ground, and fmvpoker `erase_window`s window 2 right before printing the prompt — 92664 of 92664 pixels of the story box opaque — so the box insetted to (99,313,440,0), `story_clear` came back None, and `build_v6_raster_canvas` took its "the picture owns the screen" branch: plate only, no `draw_story_text`, hence no prose AND no input line. The whole panel measured as ONE flat colour (92664 px of pure white).

FIX. The game's own ZMSD 8.8.3.1 attribute 2 decides which window is the transcript; the window the game reads through is the FALLBACK, applying only when no prose window declares attribute 2 — which is the case SQ-0585 needed it for. Corpus-measured: advent sets attribute 2 on window 7, the very window it reads through, so the fallback has never been what protected it; no corpus title (zork0, arthur, shogun, journey, advent, scopa, mysterious01, fmvpoker) ever reads through a window whose prose is diverted. One predicate, `Machine::v6_diverts_prose`, is now read by zvm's print path AND by the app's `prose_idx`, which had its own copy of the question and could contradict the engine that filled the model. With window 0 the story window again, losses 1 and 2 disappear and loss 3's erased-panel story box is never consulted.

ECHO: `BufferWindow::reads_input` publishes which window the player is typing into, and `draw_secondary_prose` continues that window's own last line with the live input plus a caret — the echo follows the READ, not the story window.

NOT the takeover arm, so SQ-0739's third `picture_takeover` arm is left in place with its corpus guard; it simply no longer has to fire for fmvpoker (the story window stops moving, so the plate stops escaping). `fmvpoker_bet_entry_keeps_its_frame` keeps its byte-identical-above-the-panel assertion and had its premises rewritten to the new, stronger fact.

Panel lines: []`; `"Current Bet:" is still on window 0's glass at (76,247) ... Runs: []  left: None  right: Some("Current Bet:")`; `premise: ... window 0 stays the story window  left: (22, 235, 594, 156)  right: (0, 0, 640, 400)`.
  * reverting the echo arm: `typing "25" at the bet prompt changed NOTHING on the screen. The digits are the host's own input line, and with them invisible the player has no feedback at all that the game is listening (SQ-0746).`

NO PATH MOVED. v6_path_log over 8 frames x 8 titles x both honor modes is byte-identical before and after (arthur ["raster", ring x7], journey [ring,"raster",ring x6], zork0 [ring x8], mysterious01 [ring x8], advent [ring,menu-takeover,ring x6], shogun ["raster",menu-takeover,ring x6], scopa [painted,"raster" x7], fmvpoker [ring,"raster" x7]); fmvpoker's bet and quit frames are ["raster","raster"] before and after.
