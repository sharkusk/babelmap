  Noticed while smoke-testing the debug inspector — the memory pane's fixed 72-char rows (16 bytes hex + 16 ASCII) get clipped in the half-width pane, hiding the ASCII text unless the pane is ~72+ cols wide.

--- note 2026-07-19T18:18:41Z ---

Root cause: memory_hex (crates/app/src/session.rs) formats fixed 16-byte rows → "{:06x}  {:<48}{ascii}" = 72 chars. draw_memory (render/debug_panel.rs) clips to the memory pane, which is window_rects()[0] = region.width/2. So ASCII (cols 56–72) survives only when the half-pane content width ≳72. Fix: responsive bytes-per-row = fit to pane width (8+4·bpr ≤ content_width; keep bpr ∈ {1,2,4,8,16} to preserve the 16-aligned mem_addr grid, and advance step_memory by bpr not a fixed 16). Complication: the pane width is only known at render (draw_frame's `state` is &AppState, immutable), while rows are generated in refresh/step_memory/goto_memory (which have dbg but not width) — needs the width threaded/stored on the panel (set at render, used next regen; one-frame lag on resize is acceptable). Alternatively store per-byte (value, decoded glyph) in the snapshot and lay out rows at render time (keeps the engine-specific ZSCII/unicode decode in session).
