SURVEY — `stories/zork-zero-disk.sit`, measured 2026-08-13. **This is the first v6 fixture for a platform other than PC and Amiga, and it is a THREE-LAYER container chain.**

## The chain

```
zork-zero-disk.sit   595544   StuffIt classic: magic 'SIT!' at 0x00, 'rLau' at 0x0A, 1 entry, "Zork Zero"
  └─ Zork Zero/Zork Zero Disk.image   838484   DiskCopy 4.2
       └─ HFS volume, 819200 bytes
            └─ Zork Zero story: v6 r296 s881019, found at volume offset 59904 (block 117)
```

**DiskCopy 4.2 header** (84 bytes, then data): 64-byte Pascal disk name (`\x0eZork Zero Disk`), data size u32BE at `0x40` = 819200, tag size at `0x44` = 19200 (**12 tag bytes per 512-byte sector × 1600 sectors** — the tags follow the data and are NOT part of the volume), encoding `0x01`, format `0x22`, magic `0x0100` at `0x52`. Getting the tag region wrong shifts everything.

**Filesystem is HFS, not MFS** — signature at volume offset 1024 is `0x4244` (`BD`), where MFS would be `0xD2D7`. HFS means a B-tree catalog: **the most work of any filesystem in this corpus**, and nothing at all like the FAT12 family that covers DOS, Atari ST and (nearly) everything else.

## THE RELEASE — and it is not like the others

**Macintosh Zork Zero is v6 release 296, serial 881019.** Every other Zork Zero in the corpus is **r393 / 890714** (DOS 360K, DOS 720K, DOS Lost Treasures). The Mac build is from October 1988; the DOS one from July 1989 — an appreciably earlier build, not a repackaging. Given SQ-0755 (Journey r83 narrates through window 0, r30 through window 2), a 97-release gap should be assumed to differ in behaviour until proven otherwise. Name the exact medium and release in every finding about it.

## Two things this changes

1. **A StuffIt decompressor is a genuine dependency question, and the first one in this whole area.** Every other container here — FAT12 for DOS/ST, AmigaDOS for `.adf`, ProDOS for `.2mg`, DiskCopy for Mac — is a hand-rollable parser, which is why `blorb` reads `.adf` at zero dependency cost. StuffIt is compression, not a filesystem, and implementing it is a different order of work. Options worth weighing: require the user to unpack `.sit` themselves and support the bare `.image` (cheap, and covers this fixture today); or take a dependency in `app` only, never in `blorb`, since the zero-dep rule protects the VM crates rather than the TUI. **Do not put a decompressor in `blorb`.**
2. **`hdiutil attach` REFUSES this image** — macOS dropped HFS-standard read support after 10.14, so there is no shortcut via the host OS. Whatever reads this has to be ours.

## Methodological note worth keeping

I could not parse HFS at all, and still located the story: a scan of every 512-byte boundary for a plausible Z-machine header (version 1-8, sane release, six ASCII digits of serial, dictionary below high-memory base) returned **exactly one** candidate across the whole 800K volume — no false positives. That is the fourth independent vindication of the content-first approach `blorb::adf::Adf` established, and the strongest: it worked with **zero** filesystem knowledge. For a first cut, a block scan may be enough to make Mac disks playable long before an HFS catalog reader exists.
