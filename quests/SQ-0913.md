## Cause found, and it was the same mechanism as SQ-0909

The user's symptom, given 2026-08-18: *"sometimes when i quit a game the game story text is still shown, and the terminal prompt ends up in the middle of it."* That is specific enough to name the bug, and it is not really OS-specific — it is GAME-specific, which is why it looked like Linux-only.

`ScreenView::leave()` read:

```rust
if self.is_tty && self.active_rows > 0 { … } else { String::new() }
```

so it did nothing at all when nothing had been pinned. Two things go wrong there:

1. **The cursor is never moved.** When no region was set — a v5 game with no upper window, and after SQ-0909 any one-row-status game too — the cursor is sitting wherever the game left its `>` prompt, mid-screen and mid-paragraph. Returning without moving it hands the shell that spot, so the next shell prompt is drawn INTO the story text. Exactly the report.
2. **The region reset is skipped on a gate that cannot answer the question.** `active_rows` records what THIS view pinned; a region established by any path it did not record survives the gate. And `CSI r` is a no-op when no region is set, so gating it saves nothing.

Fixed in 1bcea805: reset unconditionally, then either park at the bottom row (if rows were pinned, where the text filled the screen beneath them) or emit a fresh line (if not, so the shell starts below the story).

**SQ-0909 made this commoner, not rarer** — a one-row status bar no longer pins, so `was_pinned` is false for most games now. Had the two been done separately, this fix would have arrived after a regression rather than before it.

## Also fixed: two exits that skipped the guard entirely

`std::process::exit` runs no destructors, so a `TerminalGuard`'s `Drop` never fires. Two `process::exit(1)` calls sit past the guard's arming in `main` (the story-load error path and the restart path's) and left raw mode and the block cursor behind. Both now go through `cli_host::restore_and_exit`.

## Left at `confirm` deliberately

The diagnosis fits the reported symptom exactly and the mechanism is proved, but the report is from a Linux terminal this session cannot reproduce on, and "the terminal is not reset" has more than one possible cause — a stale region, lost echo, a block cursor left behind, a tinted page background. If anything remains after this, the next thing to ask is WHICH of those, because each is a different fix.
