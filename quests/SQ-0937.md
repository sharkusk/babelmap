## The asymmetry

`render/screen.rs`, in the ring's in-box run packing. SQ-0892 made the ROW
box-relative, for a reason it states well — a run placed by device pixel drifts away
from the very text it overlays as soon as a terminal row stops being one native 16px
text row:

    let row = viewport.y + (t.y.max(1) - 1) / 16 - vp_native.1 / 16;

The COLUMN never got the same treatment and is still absolute:

    let run_col = |t| area.x + ((scale.off_x + px * scale.s) / cw).round();

and a few lines down, any run whose column lands outside the viewport is DROPPED:

    if row < viewport.y || row >= viewport.bottom() || col < viewport.x || col >= viewport.right() { continue; }

`run_col`'s own neighbouring comment already identifies the rate mismatch: "a run is
POSITIONED through the ring scale but its characters then advance ONE TERMINAL COLUMN
each, and the two rates coincide only where a column is one native 8px text cell."

## Reproduced

Macintosh press (`stories/Zork Zero Disk.image`, r296/881019), InvisiClues menu, pane
136x50, captured through `cargo run -p app --example pty_capture` (the Ghostty path —
a cell-buffer harness cannot see this correctly, see SQ-0934's notes).

The menu's LEFT column of topics prints at native x=87 against a story box whose left
edge is x=86. It rounds to `viewport.x - 1` and is discarded. The RIGHT column at
native x=320 is far enough in to survive, so the frame shows GENERAL QUESTIONS / AS A
LAST RESORT / FOR YOUR AMUSEMENT as glyphs and nothing at all where PROLOGUE / GREAT
HALL AREA / EAST WING belong. The user also reports "disconnected reversed cells after
the menu items" at other pane sizes — the same rounding one column the other way.

## Why only the Macintosh shows it

Release r296 KEEPS its primary buffer for the hint screen, so its menu runs are chrome
runs inside the story box and take this packing path. Blorb r393 and Amiga r366
withdraw the buffer, so SQ-0934 promotes the menu grid to the story surface and
`render_node` draws it as cells — never touching this code. Same screen, two roads,
and only one has the bug.

## Proposed fix

Count columns from the story box's own left edge, exactly as SQ-0892 counts rows from
its top:

    let col = viewport.x + (px - vp_native.0) / 8;

A run at the box's first column IS the viewport's first column, by construction, and
cannot disagree with the box.

## Why it was not folded into SQ-0934

It changes positioning for EVERY in-box run, including Macintosh gameplay chrome, and
SQ-0898's blank-run logic is built on the current rate — so it needs its own
falsification rather than riding along. Cover both `honor_game_colours` modes and
sweep pane sizes; the defect is a rounding boundary and appears at some sizes only.
