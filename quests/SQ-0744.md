--- note 2026-08-10T02:20:16Z ---

MEASURED 2026-08-09 by extracting `Pic.data` from each ADF in `stories/` with a throwaway OFS reader and comparing headers. The archives are NOT all one format:

    game      header (first 16 bytes)                              byte1  count@4  byte8 (record size)
    Zork Zero 01 06 0d 91 01 ef 00 00 0e 00 0f a7 01 00 00 0a        6      495      14
    Journey   01 06 03 b2 00 86 00 00 0e 00 78 f7 01 00 00 01        6      134      14
    Arthur    01 06 04 a7 00 a9 00 00 0e 00 7c 7c 01 00 00 1d        6      169      14
    Shogun    01 02 00 00 00 30 00 00 10 00 8a b5 01 00 00 01        2       48      16

**Shogun declares byte1 = 2 and a directory record size of 16**, where the other three declare 6 and 14. SQ-0713's reader treats record size 14 as the marker of the Amiga flavour and rejects anything else, so Shogun's entire archive is dropped and the game boots with no art — the user's "not showing any graphics at all, so no title screen".

The file itself is intact: 216832 bytes read cleanly out of the image, and forcing a 14-byte walk over it yields exactly one plausible record (id 1, 320x200) before the ids stop incrementing — the signature of reading a 16-byte layout with the wrong stride, not of a corrupt file.

WHAT TO DETERMINE, and **from the authoritative source, not by inference**: SQ-0713 got the format from Infocom's own released interpreter source (`github.com/erkyrath/infocom-zcode-terps` — prose spec at the top of `mac/gfx.c`, `EF_*` flags and `LBYTES` in `amiga/gfx.c`, palette trailer in `mac/gfx.p`). Byte 1 looks like a format VERSION and byte 8 the record size; that source should say what a version-2 record contains and whether the compression differs too. Do not assume the extra two bytes are padding and reuse the v6 field offsets.

Cross-check when it works: Shogun's Blorb (`stories/Shogun.blb`) has its own pictures, so the same oracle technique SQ-0713 used for Zork Zero — decode natively, compare byte-exact against the Blorb's PNGs for shared ids — applies here and is the right proof. Note Shogun.blb is small (191084 bytes) versus Zork Zero's 1036226, so the overlap may be partial; report the match count either way.

ALSO WORTH KNOWING for whoever does this: the user has added Beyond Zork, Zork I/II/III and Zork Undiscovered ADFs too. Those are text games and mostly carry no picture archive, but they are free coverage for the ADF mount and the story-identification rule, and worth a pass.

FIXED 2026-08-09, branch worktree-agent-a5da21b60ec327e6a, commit faa550fc (merged with main at 22ba133d, clippy follow-up 95887fce). Not pushed.

FORMAT, FROM THE AUTHORITATIVE SOURCE — and byte 1 is NOT a version number.
`InitGFX` in Infocom's own `amiga/gfx.c` (github.com/erkyrath/infocom-zcode-terps) reads the 16-byte header field by field:

    0    gh.fileID       byte  ("not used on Amiga")
    1    gh.flags        byte  the HF_* set
    2-4  gh.huffOff      word, DOUBLED to a byte offset
    4-6  gh.nPics
    6-8  gh.ngPics
    8    gh.dirEntryLen  byte

    #define HF_GDIR 1  /* file has a global directory */
    #define HF_EHUFF 2 /* dir entries include Huff ptrs (may be 0) */
    #define HF_GHUFF 4 /* file header includes global Huff ptr */
    #define HF_NOPAL 8 /* no palettes exist (Apple II) */

`ReadGFXEntry` then copies 8 bytes (picID/picX/picY/eFlags), 3-byte dataOff, 3-byte palOff, and:

    if (BAND (gh.flags, HF_EHUFF+HF_GHUFF) == HF_EHUFF)
        { ge.huffOff = 0; doCopy (pEnt, (UBYTE *)(&ge.huffOff) + 2, 2); ge.huffOff *= 2; }
    else    ge.huffOff = gh.huffOff;

So the "version 2 / 16-byte" flavour is HF_EHUFF WITHOUT HF_GHUFF: every picture names its OWN 256-byte Huffman tree in a further word (stored in words, doubled), making the record 14+2 = 16. Zork Zero/Journey/Arthur declare 6 = HF_EHUFF|HF_GHUFF, which takes the else branch and shares the one global tree at gh.huffOff — 14-byte records. The extra two bytes are NOT padding and the v6 field offsets are otherwise unchanged. Nothing else differs: same Huffman+RLE+XOR codec, same 3+3 LBYTES blob header, same palette record (count byte, count*3 RGB from colour index 2, then a 0x10 stipple count and 16 stipple bytes — verified against every Shogun palette: the palOff-to-dataOff gap is exactly 4n+18 for all 42).

MEASURED CAUSE. `parse` compared data[8] against a hard 14 and returned UnsupportedContainer otherwise, so `Adf::pictures()` was None, `PictSource::resolve` fell through to a Blorb that does not exist beside a disk image, `all_pict_dims()` was empty and `pictures_canvas` was `[]` after boot. Shogun's header: `01 02 00 00 00 30 00 00 10 00 8a b5 01 00 00 01` — flags 2, global huffOff 0 (correctly unused), nPics 48, dirEntryLen 16, directory ends at 784, and the first per-entry tree offset is 784. All 48 records parse; 42 carry pixels and all 42 decode.

THE FIX (crates/blorb/src/infocom_pics.rs only, ~60 lines): derive the expected record size from the header flags and require data[8] to match; resolve each entry's tree offset at parse time (global or its own) into a private PicEntry field; `huff_tree(off)` takes the offset. Validation strengthened rather than loosened — record size must match flags, every tree of a pixel-bearing EF_PHUFF entry must sit past the directory and inside the file, and ids must ascend (ReadGFXEntry binary-searches the directory, so they must). That ascending check is what still keeps a PC .MG1 out now that two sizes are legal.

ORACLE vs Shogun.blb (Infocom's own converter, same standard as SQ-0713's 383/388): of the 39 pictures both sources carry, **34 are byte-exact** — 15 at identical dimensions, 19 as the smaller window the Blorb kept (18 dropped the last scanline, 185 rows -> 184; picture 3 kept the leftmost 23 of 320 columns). The 6 size-only records (ids 2, 45, 46, 47, 48, 49) are id for id the Blorb's 6 Rect resources — the same 1:1 correspondence SQ-0713 found for Zork Zero's 107. Native-only: ids 4, 21, 35. Blorb-only: 59, 61, 62.

The five that differ, all explained and none a decode defect:
- **16, 25**: pixels IDENTICAL (index map is a clean permutation). The Blorb's PLTE quantises the Amiga's 4-bit channels as n<<4 where native (and every other picture in this same Blorb) uses n*0x11. Max channel delta 14 — below the 17 one 4-bit step costs, so no colour actually differs. Only these two pictures in the file use that convention.
- **37**: 1310 of 34965 pixels (3.7%) genuinely disagree. Native paints a region flat colour 3; the Blorb has detail there and an extra palette entry (44ee22) inserted at index 8 to hold it, shifting its indices 8..15 by one. The other 96.3% match modulo the same quantisation.
- **42**: 3 of 49 pixels of a 7x7 icon — white in the Blorb, 0099ee blue natively.
- **50**: the Blorb keeps a 320x29 band of a 320x200 picture and paints 18 pixels the native archive marks transparent. Native wins, exactly as for Zork Zero's ids 5-8.

SQ-0743 CORRESPONDENCE ON THIS FLAVOUR: it holds, in its degenerate form. All 42 pixel-bearing records name their own palette, so `adaptive_pictures()` is EMPTY — and `Shogun.blb` carries no APal chunk at all (0 entries). Zero = zero. The mechanism is per-picture as SQ-0743 insisted, not archive-wide: the same reader gives Zork Zero 172, Arthur 1, Journey 0, Shogun 0.

FOUND, NOT FIXED (candidates for follow-up quests):
1. Picture 37's 1310-pixel disagreement and 42's 3 pixels are content-level differences a dimension diff cannot see — the same class of thing as the SQ-0713 note about Zork Zero's truncated compass rose. Worth a human eye before claiming which source is right.
2. The Blorb's per-picture colour quantisation is inconsistent (n*0x11 for 37 of 39 pictures, n<<4 for ids 16 and 25). Harmless — under 17 — but it means a byte-equality oracle against this Blorb can never be 39/39.
3. Blorb ids 59, 61, 62 have no native counterpart and native 4, 21, 35 have no Blorb counterpart; the id sets are not a subset relation either way. Unexplained, same shape as Zork Zero's unexplained 1000-2709 block.
4. `parse` still rejects EF_MONO, EF_IFF and the non-Huffman raw-RLE path. Shogun's flags histogram is {0: 6, 2: 34, 3: 8} — nothing exotic — so still no fixture for those.
5. HF_GDIR and HF_NOPAL are read but not acted on; no release we have sets either.
