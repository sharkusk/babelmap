DISCUSSED AND SCOPED 2026-07-29 (with the user). Decision: **YES — unify on a single save format.** `@save` writes a full `.babelmap` archive exactly as a host Save State does; the two are differentiated only by a recorded trigger. Restore keeps dual support so a `.qzl` carried in from another interpreter still loads.

## Why this is much smaller than the quest title suggests

There are NOT two save formats today — there are two CONTAINERS around identical bytes. Verified in-tree:
  - `crates/app/src/persist_files.rs:305` — `save_game(path, machine)` writes `machine.save_quetzal()`
  - `crates/app/src/archive.rs:976` — the archive's `EngineSave` is `machine.save_quetzal()`
Same call. So the inner `game.qzl` is byte-identical either way; unification changes only what wraps it. `handle_save_as` (`crates/app/src/ingame_io.rs:70`) already has both writers side by side in one `if ingame { … } else { … }` — this is largely deleting the branch.

The restore half is ALREADY done: `archive::read_quetzal_from_file` (`crates/app/src/archive.rs:941`) extracts `game.qzl` from a `.babelmap` or returns raw bytes for a plain `.qzl`.

Verified the inner save really is interchange-grade by unzipping a real archive from the user's disk (`zork1-r88-s840726.z3.save/default.babelmap`): `FORM`/`IFZS` with `IFhd` 13 / `CMem` 212 / `Stks` 78. Genuine standard Quetzal — unzip and Frotz reads it.

Size is a non-issue, measured on the user's actual saves: largest archive 122 KB (Shogun, v6 with picture canvases), most 2-14 KB, while Counterfeit Monkey's BARE `.qzl` is 50 KB. Frequent save-scumming costs nothing.

Also: both kinds already live in the SAME directory (`<story>.save/default.babelmap` beside `<story>.save/2026-07-28-0457.qzl`), so no relocation is needed. An earlier worry about "two homes" was wrong.

## The one real asymmetry, and why we accept it

Quetzal's PC convention is definitionally "inside a save instruction" — fetched from the spec, not memory (inform-fiction.org/zmachine/standards/quetzal, §5.8):
  §5.8.1 (v3 and below): "the save instruction takes a branch … The saved PC points to the one or two bytes which describe this branch."
  §5.8.2 (v4 and above): "the save instruction stores a value … The saved PC points to the single byte describing where to store the result."

A host Save State is taken BETWEEN turns, so its PC points mid-`read`, with no save instruction to branch/store into. The file is structurally valid Quetzal but a foreign interpreter would treat the bytes at that PC as a save instruction's operand and mis-store. `@save`-written archives are unaffected — their PC is at a real save opcode, so they extract and restore anywhere.

Retrofitting the standard convention onto host saves was considered and REJECTED. Every route is brittle or corrupting: pointing the PC at a plausible store byte resumes into arbitrary game code; injecting a synthetic `save` opcode ships those bytes inside CMem (a diff against the pristine story) so a foreign interpreter executes them and falls through to garbage; pointing at the GAME's own save instruction depends on locating it and on the following routine being a simple print-and-return, which breaks per-title. Conforming properly would mean only saving when a `save` instruction is executing — i.e. only when the game offers to save — which destroys BOTH properties the host Save State exists for: save-anywhere, and engine-neutrality (Glulx has no Quetzal save-opcode convention; Scott has no native save format at all, already special-cased at `ingame_io.rs:79`). Trading the feature for the file format is the wrong trade.

## Work outline

1. `ingame_io.rs::handle_save_as` — collapse the `if ingame` writer branch so BOTH paths call the archive writer `save_named(...)`. Preserve the surrounding in-game behaviour that is NOT about format: the `ingame_resume_save = Some(true)` flag-hop that resumes the VM, and the re-open-dialog-on-empty-name / on-error retry.
2. `meta.json` — add `trigger: "ingame" | "hoststate"`. Pre-release, breaking the sidecar/meta shape is fine (no back-compat shims, no old-save smokes).
3. In-game restore picker — widen its file glob from `.qzl` to include `.babelmap`, keeping foreign `.qzl` support. This is the user-visible half of "restore supports both".
4. Engine tagging — the unified writer must keep `engine.txt` / `save_ext()` correct (Glulx -> `glksave`, Z-machine -> `qzl`) and must not regress Scott, whose bytes come from `session.save_state()` rather than a native format.
5. Portability surfacing — mark which saves are portable in the saves list, driven off the new `trigger` field. Cheap, and it keeps us honest instead of silently implying every archive extracts cleanly.
6. DECISION STILL OPEN (flag to the user, do not assume): today `handle_save_as` does `if !ingame { state.unsaved_progress = false; }`. Now that an in-game `@save` captures the full archive, should it also clear `unsaved_progress`? Arguably yes — it is no longer a lesser save. Confirm before changing.

## Tests

Both triggers write an archive; the inner `game.qzl` stays byte-identical to `machine.save_quetzal()`; `trigger` round-trips through meta; in-game `@restore` of a `.babelmap` works; in-game `@restore` of a FOREIGN raw `.qzl` still works (the interchange path must not regress); host Save State restore unaffected; Glulx and Scott both still save and restore under the unified writer.

## Docs

User-facing saves documentation must be updated in the same effort. Note the standing terminology: "Save State / Restore State" is the emulator-style host snapshot; "@save/@restore" is the game's own Quetzal path. The SQ-0518 doc line saying in-game restores cannot bring back scrollback/inline art becomes STALE once `@save` writes the full archive — it must be revised, not left to contradict the new behaviour.
