## scott-cli is the only host where a session cannot be preserved

Found while wiring SQ-0918's save listing into the CLIs: there was nothing to wire it into. `scott-cli` has no save, no restore, no prompt, no `--data-dir`.

### The header is accurate but easy to misread

`crates/scott-cli/src/main.rs:7` says Scott is line-only "and no in-game save protocol, so the whole host loop is: describe → prompt → read a line → step → print." Both halves are true, and they conflate two different things:

- **No game-native save format** — correct, and `persist_files.rs:161` says the same.
- **Therefore the host cannot save** — does not follow.

The `scott` VM already has `snapshot()` (`vm.rs:234`) and `restore()` (`vm.rs:259`), and **the TUI already uses them**: `scott_session.rs:301` builds an `EngineSave` from `vm.snapshot()` and restores through `vm.restore()`. Classic ScottFree also offers SAVE GAME / LOAD GAME as *interpreter* commands rather than game ones, so there is precedent for a host doing this.

So this is a gap, not a limitation, and it leaves the three CLIs inconsistent in the one way that loses work.

### Sized

Small; every piece exists.

- `/save <name>` and `/restore <name>` host commands, on the `/status` precedent already in scott-cli's read loop (`main.rs:290`) — the loop that recognises a host command and goes round again is already written.
- `--data-dir`, then `cli_host::game_dir` for the directory.
- `cli_host::{existing_saves, save_list_line, pick_save, overwrite_warning, is_yes}` — all landed under SQ-0918, so scott-cli gets the listing, the number-picking and the overwrite guard for free.
- `vm.snapshot()` / `vm.restore()` for the bytes.

Perhaps 60–80 lines.

### One design point to settle FIRST, because it touches the other two

`cli_host::resolve_save_input` hard-codes a **`.qzl`** extension. That is Quetzal, and a Scott snapshot is not Quetzal — writing `cellar.qzl` for one would be a lie, and worse, it would make a Scott save indistinguishable by name from a Z-machine one in a shared data dir.

So the helper needs an extension parameter (or a sibling), which means touching both existing call sites in `zvm-cli` and `gvm-cli`. Deliberately not done as a drive-by under SQ-0918. `existing_saves` reads the same extension and would need the same treatment, as would the round-trip test that asserts the two are inverses.

Suggested: `.sav` for Scott, and keep `.qzl` where it is genuinely Quetzal.

### Also worth deciding

Whether scott-cli's own header comment should be reworded once this lands — as written it reads like a statement that saving is impossible, which is what made this invisible.

--- note 2026-08-19T18:16:02Z ---

DONE. scott-cli saves and restores; the shared helpers now carry an extension.

THE DESIGN POINT THIS QUEST SAID TO SETTLE FIRST, settled the way it suggested.
`cli_host::resolve_save_input` and `existing_saves` take an `ext`, and there are
two named constants rather than string literals at the call sites, because the
extension is a **claim about the bytes** and not a filename convention:

    QUETZAL_EXT = "qzl"   the Z-machine's own standard format; gvm-cli too
    SCOTT_EXT   = "sav"   scott::Vm::snapshot — item locations, flags,
                          counters, the lamp. Nothing Quetzal about it.

Both existing call sites in zvm-cli and gvm-cli were updated as this quest
predicted. Two more in gvm-cli went with them and were NOT strictly required:
`game_auto_save_path` and `seed_saved_games` each hard-coded "qzl" and have to
agree with `existing_saves` — making the extension a parameter is precisely what
lets them drift, so they take the constant now.

`each_hosts_extension_lists_and_resolves_only_its_own` is the case the quest's
worry deserves: same typed name, two different files; a name typed WITH the other
host's extension is not stripped of it (`cellar.qzl` asked of the Scott host is
`cellar.qzl.sav`, not a Quetzal save it has no business opening); and the
resolve/list inverse — the SQ-0925 property — still holds *within* each extension.
Falsified by setting SCOTT_EXT to "qzl": four cases fail across two crates.

SCOTT-CLI, and it came in around the size predicted. `/save [name]` and
`/restore [name]` (alias `/load`), plus `--data-dir`. A `HostCommand` enum parsed
by `host_command`, on the `/status` precedent that was already there; the inner
read loop now dispatches on it and only a game command leaves the loop, so EOF
stays `None` and the SQ-0604/0605 hang cannot come back. Reads the filename
through `read_command`, not stdin directly, so the raw-mode editor, the piped echo
and the EOF rule are the ones every other line of input already gets.

ONE THING NOT IN THE SIZING, and it would have been a real defect. **A restore has
to redraw the room.** The outer loop prints the room block only when it CHANGES,
and it cannot see a change made from inside the input loop — so without an
explicit redraw the player is silently teleported and the next thing they see is a
bare prompt. `do_restore` returns whether the VM actually moved, and the caller
prints the block and records it in `last_block` so the outer loop does not then
print it twice. `a_host_save_and_restore_survive_a_move` asserts on the text AFTER
"Restored from", which is what makes that assertion mean anything.

FREE FROM `Vm::restore`, worth knowing: it checks the item count against the
loaded database before writing anything, so another adventure's `.sav` is refused
rather than half-applied. Verified against a real second game (`stories/adv01.dat`
into tiny_cave) and pinned with a synthetic mismatched snapshot.

TESTS: 3 unit cases in cli-host/scott-cli plus 4 end-to-end through the real
binary in `scott-cli/tests/play.rs` — round trip, restore-by-number, the overwrite
guard, and `an_unslashed_save_still_reaches_the_game`, which is the one that keeps
the feature honest: bare `save` and `restore` are ordinary things to type at a
Scott prompt and the host must not swallow them. Manual smoke: GET LAMP → /save →
DROP LAMP → /restore 1 puts the lamp back in inventory, and the path is
`<dir>/tiny_cave.dat.save/deep.sav`.

THE HEADER IS REWORDED, which this quest asked about last and is arguably the most
valuable line of the change: it now says outright that "no save protocol of its
own" and "the host cannot save" are two different statements, and names ScottFree's
own SAVE GAME / LOAD GAME as the precedent. That conflation is what hid this.

Docs: a new subsection under "Saving from the command line" in
docs/features/interpreter.md. README untouched — it tracks the released build and
this is post-0.2.0; the CHANGELOG's Unreleased section carries it.

Gate: 5675/5675, clippy clean.
