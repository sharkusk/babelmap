## Three separate things, found in one run of `cargo run -p app --example gallery`

### 1. The missing-glyph fallback is a RANGE, and it should be a capability question

`crates/app/tests/pty_stream/gallery.rs`'s `Face::draw` falls back to the bitmap master only for `is_structural(ch)`, which is:

    fn is_structural(ch: char) -> bool { matches!(ch, '\\u{2500}'..='\\u{259F}') }

Box Drawing (2500–257F) and Block Elements (2580–259F). The map's arrows are **outside** it — `↑` U+2191 and `↓` U+2193 are in Arrows, `▲▼◀▶` U+25B2/25BC/25C0/25B6 are in Geometric Shapes — so they go to fontdue, which returns `.notdef`, and `zork1-map.png` drew a tofu box at both ends of every connector under Monaco.

The durable fix is not to widen the range. **Ask the face whether it has the glyph** (`fontdue::Font::lookup_glyph_index(ch)` returns 0 for missing) and fall back to `app::render::bitfont` when it does not. That covers every face a user might pass to `--font`, including ones nobody has thought of, and it keeps the deliberate part of the current rule: structural glyphs stay with the bitmap master EVEN WHEN the face has them, because a text face draws them with gaps at the cell seams and the bitmap's cells tile exactly.

Confirmed by re-rendering with a Nerd Font: the tofu disappears because that face HAS the glyphs — which fixes the symptom on this machine and leaves the mechanism broken everywhere else.

### 2. The default font list should lead with something that has the coverage

`FONT_CANDIDATES` today is Menlo, Monaco, Andale Mono, DejaVu Sans Mono, Liberation Mono. The user asked for **JetBrains Mono Nerd Font Mono**, verified present at
`/Users/marcuskellerman/Library/Fonts/JetBrainsMonoNerdFontMono-Regular.ttf`, and it renders the map correctly. A Nerd Font is a good default *for this tool* precisely because its coverage is enormous — but note that with (1) fixed, coverage stops being load-bearing and this becomes a taste decision rather than a correctness one.

Nerd Fonts installed on this machine, for reference: 0xProto, FiraCode, IosevkaTerm, JetBrainsMono, ProggyClean, SauceCodePro, Symbols.

### 3. Every v6 shot is at a NON-INTEGER scale, so its art is resampled

`zork0-dos` is 117x40 cells at 8x18 = 936x720 device against a 640x400 native screen — roughly 1.46x, so every edge in the pillars and banner is interpolated. Choosing pane sizes whose device box lands on a whole multiple would make the art pixel-crisp: 2x of 640x400 wants 1280x800 device, i.e. **160 cols at 8px** and about **45 rows at 18px** for kitty, or **128x40** at the half-block picker's 10x20.

Prefer choosing the SIZE over turning on the pixel lock (SQ-0936). With a pane that yields exactly 2.0, locked and free scaling agree, so the shot stays a picture of DEFAULT behaviour while being crisp — no divergence between what the gallery shows and what a user gets out of the box.

Caveat that stops this being one global number: presses differ in native size. Arthur's DOS press is **560x384**, not 640x400 (the fixture CLAUDE.md's boot warning is written about), so a single pane size cannot be integral for every shot. The manifest already carries per-shot `size`, so this is a per-shot calculation, not a constant.

## A question this raises but does not answer

The user asked whether a font "more representative of these games" would be better. Worth deciding deliberately rather than drifting: **the gallery's job is what lanthorn looks like in YOUR terminal**, not what a 1989 machine looked like. lanthorn's own raster path already uses Uni-VGA 8x16, the DOS face, and that is in the product. A period face in the gallery would make these renders read as machine captures — the exact hazard `docs/superpowers/plans/2026-08-20-website.md` warns about under "Do not claim typography from generated renders", which notes the temptation went UP after SQ-0932 made the pictures better. Period-authentic type belongs in `machine-screenshots/`, where the frames are real.

If a DOS-flavoured variant is wanted for the site's `/machines` page specifically, that argues for a **per-shot `font` field** in the manifest — which does not exist today; `--font` is global.

## OPEN QUESTION on the font choice — JetBrainsMono is the worst measured face for half-block sample squareness

This quest chose 'JetBrainsMono Nerd Font Mono' for gallery shots, on glyph coverage (the map arrows are tofu on most faces). That reason still stands. But if the shots are meant to show the half-blocks backend at its best, the choice works against it.

A half-block sample is `cell_width` wide by `cell_height / 2` tall, so square samples — equal resolution on both axes — need a cell aspect of exactly 1:2 (w:h). Measured from font metrics on this machine (adv/em from hmtx, line as ascent - descent + lineGap from hhea):

  FiraCode Nerd Font              0.615 / 1.231 = 2.000   (exact)
  0xProto Nerd Font Mono          0.620 / 1.200 = 1.935
  SauceCodePro Nerd Font Mono     0.600 / 1.257 = 2.095
  ProggyClean Nerd Font Mono      0.438 / 0.812 = 1.857
  JetBrainsMono Nerd Font Mono    0.600 / 1.320 = 2.200
  Monaco                          0.600 / 1.333 = 2.222
  IosevkaTerm Nerd Font Mono      0.500 / 1.250 = 2.500

More decisive than the em ratio is how often the ROUNDED cell lands on exactly 2.000, since a cell is round(adv*px) x round(line*px) and the two round at different rates. Over 6..24 px/em: FiraCode hits it at 10 of 19 sizes (5x10, 6x12, 7x14, 8x16, 9x18, 10x20, 11x22, 13x26, 14x28, 15x30 — the historical terminal cells); JetBrainsMono hits it ONCE, at 4x8 / 6px, and is 10-29% off everywhere usable.

So gallery shots taken in JetBrainsMono sample the artwork ~10% coarser vertically than horizontally, at every size anyone would pick.

## The question to settle

Whether the gallery wants glyph coverage (JetBrainsMono, current) or square half-block samples (FiraCode at a sweet-spot size). It may not be either/or: check whether FiraCode Nerd Font covers the map arrows — if it does, it wins on both counts and the trade disappears. If it does not, the shots showing MAP output and the shots showing half-blocks ART may simply want different faces, which the manifest could carry per-shot.

Note also that Ghostty's `adjust-cell-height` / `adjust-cell-width` can force the ratio for any font, so a third option is keeping JetBrainsMono and correcting the cell (about -9% height).

## The measurement, so nobody redoes it by hand

Reproducible with no dependencies — parse the sfnt table directory, then head(+18) for unitsPerEm, hhea(+4) for ascender/descender/lineGap, hmtx(+0) for the first advance width. Cell aspect is (asc - desc + gap) / advance. Caveat: terminals may take line height from OS/2 rather than hhea and usually add their own line spacing, so this ranks candidates rather than predicting an exact cell — which is why SQ-0986 proposes reporting the cell lanthorn ACTUALLY got.

## RESOLVED — user confirms Fira Code has all the glyphs, so the trade disappears

The open question above asked whether FiraCode Nerd Font covers the map arrows. It does. That makes it strictly better than JetBrainsMono for this purpose:

- Glyph coverage: equal (both cover the arrows), which was the ONLY reason JetBrainsMono was chosen.
- Cell aspect: FiraCode is 0.615/1.231 = 2.000 exactly; JetBrainsMono is 2.200. A half-block sample is cell_width wide by cell_height/2 tall, so 1:2 is what makes a sample square.

**Use 'FiraCode Nerd Font Mono' and pin a sweet-spot size.** Because a cell is round(adv*px) by round(line*px), the ROUNDED ratio matters more than the design ratio. FiraCode lands on exactly 2.000 at ten sizes in 6..24 px/em, giving cells 5x10, 6x12, 7x14, 8x16, 9x18, 10x20, 11x22, 13x26, 14x28, 15x30 — the historical terminal cells. Pick one of those rather than a point size chosen by eye, or the shots sample the artwork unevenly for no reason. (JetBrainsMono hits 2.000 exactly once in that whole range, at 4x8.)

Integer scaling — the other half of this quest — composes with that: an exact 2.000 cell plus an integer magnification is the whole point, since it is the combination where one art pixel lands on a whole number of samples on both axes.
