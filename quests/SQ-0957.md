## "Not sure if other graphics formats also have this feature" — they ALL do, and this is the finding

`blorb::infocom_pics` parses a transparent index for every flavour, and its own documentation records which archives use it, from two witnesses (the Apple II's `pic.asm` and Frotz's `bcpic.c`):

  - **PC EGA archives really do use the flag word's top nibble, naming colours 1, 2, 3, 7, 8 and 9** — six different transparent indices, not one.
  - **Apple II uses it too, naming colours 1, 2, 3 and 4** (Arthur). Same nibble, shifted 4 rather than 12 because the field is one byte wide.
  - **Amiga/Mac leave the nibble zero throughout**, which is colour 0 — `amiga/gfx.c` says so in prose ("picture uses color 0").
  - **CGA/two-colour** byte-per-pixel art uses 0 = transparent, 2 = white, 3 = black.

So this is NOT a CGA feature and the quest should not be scoped to one. CGA is merely where it is most VISIBLE, because a two-colour plate is mostly stencil — but an EGA plate naming colour 9 as transparent has exactly the same dependency on the ground, and there are more of those.

`Picture::rgba_with` drops the transparent index to alpha 0 (`let a = if Some(i) == self.transparent { 0 } else { 255 }`), so the picture arrives at the compositor as a hole. Everything downstream then resolves that hole against whatever the ground is AT THAT MOMENT: `v6_layout::flatten_onto_page` for the raster composite, `fill_story_page_clear` and `fill_window_pages` for the hybrid canvas, `inline_image::flatten_onto` for story floats, and the SQ-0944 band ground for half-blocks.

## The defect

Zork Zero has an in-game `color` command. When it changes the pair, every already-resolved hole is still showing the OLD ground, because nothing downstream is keyed on the ground.

## Where to look, and the precedent for the fix

There is already a generation counter for the neighbouring problem — `PictSource::palette_gen`, bumped when a non-adaptive draw establishes a different Current Palette (§11.3), with adaptive decodes cached per `(resnum, palette_gen)` so a palette change re-decodes them. **A colour change is the same shape and has no equivalent.** Suspect in particular:

  - the raster composite's cache: `v6_wants_build(gen, area)` reuses a ready composite when `r.gen == gen` and the area matches. If the ground is not in `gen`, a `color` change cannot invalidate it.
  - the hybrid band cache: `chrome_bands` is keyed on a hash of the band's own native footprint. SQ-0944 had to add `band_ground` to that hash for exactly this reason — a band flattened onto the old ground must re-encode — so that half of the pattern is already in place and is the model to copy.
  - `chrome_scaled`, the frame-shared scaled canvas.

## Interaction with SQ-0956 — check this before assuming a conflict

SQ-0956 makes a TWO-COLOUR rendition decline the story's colours (a two-colour display has two pixel states and cannot represent a named pair), so on the CGA plates specifically the `color` command should end up inert. That is not this quest being wrong — it means the reproducer the user found is the one case that may stop reproducing, while the EGA, MCGA, Apple II and Amiga renditions, where colours ARE honoured and six transparent indices are in use, keep it. **Reproduce this on a colour rendition, not on `.cg1`.**

If the two ever seem to disagree, SQ-0956 is the one with the machine capture behind it.

## USER COULD NOT REPRODUCE IT OUTSIDE CGA — tried Amiga, Mac colour, Mac B&W, EGA

That negative result contradicts the prediction in the note above (six EGA transparent indices should have shown the same dependency), so the prediction was wrong about the MECHANISM, and the correct reading is almost certainly this:

**It is not a stale cache. It is `declines_game_colours` freezing the ground.**

Today, a two-colour rendition that reaches the rule gets `honor_game_colours = false`, **pinned one-run** (SQ-0646/0807). With honour off, the story's own `@set_colour` — which is what Zork Zero's in-game `color` command issues — is ignored outright. So the ground never moves, and the transparent pixels resolved against it never move either. Everywhere else honour is on, the colour change flows through, the holes re-resolve, and there is nothing to see. That is exactly the distribution the user measured: CGA and nowhere else.

Which means the caches are probably fine, and `palette_gen`'s missing sibling may not need to exist at all. The suspects listed above (`v6_wants_build`'s `gen`, `chrome_bands`, `chrome_scaled`) should be CHECKED rather than assumed guilty — SQ-0944 already put the ground into the band hash, which is one of the three.

## Do not close this yet — re-test after SQ-0956

SQ-0956 changes exactly this rule: a two-colour archive will state its own pair (CGA: bg 2 black under fg 9 white) instead of falling through to no ground. Once that lands, re-run the user's reproducer. Three outcomes, and they want different things:

  1. The symptom is gone because the ground is now correct and static — close this as subsumed.
  2. The symptom moves (holes now resolve to black but still do not follow a `color` change) — then the question below is live.
  3. Some third rendition starts showing it — then the cache hypothesis is back, and the note above lists where to look.

## THE OPEN QUESTION SQ-0956 CREATES, which needs the user

After SQ-0956, a two-colour rendition declines the story's colours, so Zork Zero's `color` command becomes **inert on the `.cg1` plates**. The machine capture supports that for the PAGE — `machine-screenshots/dos-zorkzero-cga.png` is black where the story asked for white, so the page is plainly not the story's to set.

But it may not be the whole truth for the INK. CGA's two-colour graphics mode has a *selectable* foreground register, and the capture's ink is colour 7 (light grey) rather than the pure white `CGA_PALETTE` slot 1 states — which is itself a hint that the foreground was a choice someone made. If `color` on a real CGA machine changed the ink and not the page, then "decline everything" is half right and the correct rule is narrower still.

There is no capture of a colour-changed CGA screen to settle it. Worth one more emulator run — `color`, pick a different pair, screenshot — before anyone writes code for this.

--- note 2026-08-21T04:32:08Z ---

## THE EMULATOR ANSWERED THE OPEN QUESTION — and it is a swap, not a colour

User went back to the DOS emulator in CGA mode:

  - Zork Zero's `color` command there offers **only a swap of the two colours**, black and light grey. It cannot name arbitrary colours.
  - **With the light-grey background the artwork comes out WASHED OUT on the real machine too.**

Both matter, and the second is the more useful.

### What it settles

A two-colour display is not "no colours at all" — the phrasing SQ-0956's note and `declines_game_colours`' prose both use. It is **two states and one bit of choice.** So "the story's pair is unrepresentable" is very slightly too strong: arbitrary colours are unrepresentable, a polarity is not.

### What it does NOT change

The default page is still not the story's to set. `machine-screenshots/dos-zorkzero-cga.png` is black where Zork Zero asks for white, so at boot the machine plainly ignores the story's pair rather than mapping it to the nearer polarity. SQ-0956's ground stands untouched.

### And the washed-out observation is the design argument, from the machine

The `.cg1` plates are light line work authored for a black ground. Swapping to the light-grey background degrades them on the REAL machine, not just for us. So black is not merely what the capture happens to show — it is the state the artwork was drawn for, and the swap is a player option that makes the game worse. That is worth knowing before anyone spends effort making the swap faithful: it is a cosmetic nicety with a known-bad outcome, which is why this stays deferred rather than being promoted off the back of new evidence.

### Scope, if this is ever taken up

Narrow: a two-colour rendition should let a story `@set_colour` select the POLARITY of its two states and nothing else. Everything about re-resolving transparent pixels then follows for free, because the ground genuinely changed — no new generation counter, no cache work. The three suspects listed earlier (`v6_wants_build`'s `gen`, `chrome_bands`, `chrome_scaled`) should still be checked rather than assumed innocent, but the evidence now says they were never the cause.

The 0956 lane has been told explicitly not to implement the swap, and not to pin "a colour change is a no-op on a two-colour display" as a claim about the machine.

## Re-tested after SQ-0956's REOPENED fix (commit 3c432e5b) — cause gone, reproducer not driveable

SQ-0956 no longer declines colours for a two-colour rendition, so the diagnosis in the note above ("it is `declines_game_colours` freezing the ground") no longer applies: the colour flag is set, `@set_colour` reaches the model, and the ground moves.

**Pinned in `v6_cga_stencil_page::a_story_colour_change_moves_the_ground_the_plate_stands_on`**: on the 360K CGA press, the raster composite's ground is `#000000` (194,659 px) at boot and `#ADADAD` (175,575 px) after the pair is swapped, and the plate's transparent holes move with it. So the three suspects listed earlier — `v6_wants_build`'s `gen`, `chrome_bands`, `chrome_scaled` — are cleared: nothing keeps a stale copy of the page.

**What could NOT be driven, and is why this stays open.** The swap is applied at the model where the opcode applies it, not through Zork Zero's own `color` menu. That menu is graphical — no prose reaches the transcript, `pending_input` goes to `Char` and stays there — and every key sequence tried (`n`, `y`, digits, Enter, arrows) either dismissed it or left it up, so a headless walk would be pinning a guess at a keybinding rather than a colour rule. The user's eye is what can settle whether `color` now behaves.

**Also measured, and it is the reason the mechanism had to change rather than the ground**: Zork Zero r393 checks the colour flag before doing ANY colour work. With `honor_game_colours = false` the `color` command emits no `@set_colour` at all (screen trace, empty both at boot and after the command), so under the old decline the swap could not have been implemented at any layer. Two states is a bit the story has to be able to spend.

## CORRECTION — this IS verifiable. The claim that it needs the user's eye was wrong.

The SQ-0956 lane reported that its reproducer "needs the user's eye" because "no headless harness drives it", and I relayed that. The user corrected both of us: **`pty_capture` is a HEADED harness.** It runs the real `lanthorn` binary under a real pty, answers the terminal queries, sends real keystrokes, and resolves the frame that came back. A graphical menu is exactly as drivable there as any other screen.

What the lane actually hit was not a capability limit — it was not knowing the key sequence ("every key sequence tried either dismissed it or left it up"). That is a navigation problem with a fixture, not a reason to hand the quest to a human.

## So this quest is actionable, and here is the equipment

  - `cargo run -p app --example pty_capture -- --story ... --keys ... --out ... --png ...` drives and captures. Keys accept `text:...` for a literal string, `wait:MS`, `cr`, `ctrl+X`.
  - **The `expect` mechanism from SQ-0942 is how you find the right sequence.** The gallery manifest requires every shot to name something that must be on the resolved screen, and it exists precisely because two blank keypresses once picked *Ballyhoo* off a neighbouring disk under a caption about Zork Zero. Use the same idea here: assert the `color` menu is actually up before asserting anything about what it did.
  - The pty must answer the kitty queries convincingly or the capture silently measures the half-block backend; `pty_capture` exits 3 and says so. For THIS quest half-blocks may be the better backend anyway, since the ground is what is under test and half-blocks paints it into cells.

## What to assert, now that SQ-0956 has landed the card

SQ-0956 reports the ground now moves — pinned on the composite at `#000000` -> `#ADADAD`, with the holes following. So the case is: capture the frame, drive `color` to the swap, capture again, and assert **both** that the ground flipped AND that the plate's transparent regions flipped with it. The second is the actual quest; the first is only the premise.

The washed-out swapped state is expected and correct — it is what the real machine shows, because the `.cg1` plates are light line work authored for a black ground. Do not "fix" that.

## The general lesson, worth keeping

This repo has three render-testing layers and a standing rule about escalating between them. "Headless" is not one of the axes: the cell harness, the pty stream and the placement oracle are all automated, and the pty layer drives the real binary. Reaching for "the user must look at it" should be reserved for things no instrument can resolve — feel, timing, audio — and a menu's ground colour is not one of them.

## SECOND CORRECTION — `color` is not a graphical menu. It is two y/n questions.

The user again, and it matters more than the first correction: the SQ-0956 lane described the reproducer as "Zork Zero's *graphical* `color` menu", and everything that followed — "no headless harness drives it", "every key sequence tried either dismissed it or left it up", "needs the user's eye" — followed from that premise. It is wrong. `color` asks **two y/n questions**.

So the drive is `text:color`, `cr`, `y`/`n`, `cr`, `y`/`n`, `cr`. No menu navigation, no arrow keys, no dismissal problem.

## Which means the CHEAPEST layer probably suffices

Two questions asked in prose means transcript prose, so this may not need the pty at all — a cell-buffer harness can drive `read_line` and assert on the resolved buffer, which is faster to write, faster to run, and deterministic. Escalate to `pty_capture` only if the ground turns out to be one of the things a cell harness cannot see (CLAUDE.md's rule: the cell layer is blind to a defect that is correct in the model and wrong on screen — and "the ground under a placement" is exactly such a thing, so the escalation may still be needed for the ASSERTION even if the DRIVE is cheap).

## And the lane's own observation is now a clue rather than a dead end

It reported "no transcript prose" when it tried. If `color` asks two questions, prose is exactly what there should have been — so the harness was probably reading the wrong window. Zork Zero is v6 and lays out several; SQ-0934 established that on some presses the prose arrives in a withdrawn primary buffer while the visible text is a Grid promoted to the story surface. A harness that reads only the primary Buffer would see nothing on precisely those presses.

**Start by finding where the two questions are printed**, not by finding a key sequence. `/dump-windows` or `ring_scout` will say which window carries them on the 360K CGA press, and that answer probably explains the whole difficulty.

## Standing correction to the record

Two claims in this quest's history turned out to rest on the same false premise — that the reproducer was a graphical menu — and both pointed at "a human must look". Neither survived contact with what the command actually does. Worth remembering before writing "needs the user's eye" again: check what the thing being driven IS first.
