--- note 2026-08-15T15:04:12Z ---

MEASURED by the SQ-0888 diagnostic lane, 2026-08-15.

`stories/Shogun.po` is a **DiskCopy 4.2** image, not a bare ProDOS volume. `blorb::prodos` declines it — correctly, and by design. The defect is that the refusal is not fatal anywhere downstream: the 838 KB file is then handed to the story loader as an ordinary story, and its **byte 0 — the DiskCopy format's name-length field, `0x06` — is read as the Z-machine version byte**. Six is a legal version, so nothing rejects it. babelmap opens the entire disk image as a v6 story, pairs it with `Shogun.blb` (which is sitting in the same directory and passes the release/serial pairing check for a *different* file), and runs until it reports "story ended without asking for input."

Every layer behaves reasonably in isolation, which is why this survives: the mounter declines, the version byte is legal, the art pairing succeeds against a real archive. Only the composition is wrong.

WHAT TO FIX — the general case, not this file. A medium that a mounter recognises-then-declines must not silently degrade into "treat the container as a story". The decline carries information ("this IS a DiskCopy image, and I cannot mount it") that is currently discarded and replaced with a guess. Two candidate shapes, and the choice wants a look at how the other mounters report:
  - the loader distinguishes "no mounter claimed this" from "a mounter claimed it and failed", and only the first falls through to bare-story handling;
  - or the mounters gain DiskCopy 4.2 support, which fixes this file but not the class.

The first is the one that stops the next such file. Prefer it, or do both.

A FALSIFIABLE CHECK: the story that DOES run for the Apple press is the five-volume 5.25-inch set `stories/shogun_s1.dsk`…`s5.dsk` (ProDOS volumes SHOGUN.1…SHOGUN.5), reassembling to **release 311 / serial 890510**, checksum `$E200`, art `SHOGUN.D1`. So a test can assert both halves against real fixtures: the `.dsk` set mounts and reports r311/s890510, and `Shogun.po` is refused with a diagnostic naming DiskCopy — rather than booting. Both fixtures are gitignored, so skip vacuously.

WORTH CHECKING IN THE SAME EFFORT: how many other `.po`/`.dsk`/`.2mg` files in `stories/` are DiskCopy-wrapped and quietly doing this. The symptom is silent — a story that "ends without asking for input" reads as a game bug, not a loader bug — so there may be more of these than anyone has noticed. Nobody has counted.

Do NOT confuse with SQ-0883 (Journey `.po` drawing vertical bands instead of art in hybrid): that one mounts and renders, and is a render-path defect.

--- note 2026-08-15T15:09:11Z ---

CORRECTION 2026-08-15 — the note above gets the premise WRONG. Read this one first.

**The ProDOS decline is not a defect. It is deliberate, documented and tested.** `crates/blorb/src/prodos.rs:51` says so in as many words — "`Shogun.po` is not one of them and its name is the point… it is a DiskCopy 4.2 image… and this reader does not unwrap that, so it is declined whatever it is called" — and `only_the_prodos_images_in_the_corpus_look_like_prodos` asserts the decline, deliberately, as a standing test. `.po` support is real: `Arthur.po`, `Journey.po` and `ZorkZero.po` are all exactly 819,200 bytes of bare volume and open fine (SQ-0863). Measured, all four:

| file | size | first 4 bytes | DC42 magic @0x52 |
|---|---|---|---|
| Arthur.po | 819,200 | `0138b003` | — |
| Journey.po | 819,200 | `0138b003` | — |
| ZorkZero.po | 819,200 | `0138b003` | — |
| **Shogun.po** | **838,484** | `0653484f` | **`0100`** |

838,484 = 84-byte header + 819,200 volume + 19,200 tag bytes, exactly. So one file wears a `.po` extension over a different container; nothing about `.po` is broken.

**What IS real is only the downstream half**, and it reproduces:

    target/debug/babelmap "stories/Shogun.po"
    babelmap: loaded resources from stories/Shogun.blb (sidecar) (0 sounds, 48 images)
    babelmap: story ended without asking for input.
    (exit 0)

Every mounter declines the file — `blorb::medium::DiskImage::detect` returns `None` and `app::assets::mount_across` short-circuits — and then the path is handed to the story loader **anyway**, where byte 0 (the DiskCopy name-length `0x06`) is a legal Z-machine version, so an 838 KB disk image runs as a v6 story, pairs with a sidecar archive meant for a different file, and exits **0**.

SO THE QUEST IS NARROWER AND SHARPER than the first note claimed. Not "teach ProDOS about DiskCopy" — that refactor is separately noted in `prodos.rs` as known, optional, and unnecessary because the Apple artwork is already reachable off `shogun_s1.dsk`…`s5`. The defect is that **"no mounter claimed this" is not distinguished from "this is a story file"**, so a container nobody could open degrades into a bogus story instead of an error. A file that failed to open should say so and exit non-zero.

Cheapest correct fix to evaluate first: refuse to load as a story any file that a mounter *recognised and declined*, or that simply fails a sanity check no real story would fail (838 KB with a 19,200-byte tag trailer is not a Z-machine story of any version). The version byte alone is far too weak a gate — six of the 256 possible byte values are legal versions, so ~2.3% of arbitrary containers pass it.

Falsifiable: `stories/Shogun.po` must exit non-zero with a diagnostic naming what it actually is, while `Arthur.po`, `Journey.po` and `ZorkZero.po` continue to mount and run. All four are gitignored — skip vacuously.

STILL UNCOUNTED, and the reason this is worth more than one file: how many other containers in the corpus pass the same weak gate and present as "story ended without asking for input", which reads as a game bug rather than a loader bug. Nobody has swept for it.

--- note 2026-08-15T15:11:21Z ---

SCOPE CORRECTED AGAIN 2026-08-15, and this supersedes the emphasis of both notes above. There are **two** pieces of work here, and the earlier notes only saw the first.

My framing of "give Z-code a positive identity check" was the wrong emphasis on its own: it would make `Shogun.po` fail *cleanly* instead of failing *silently*, which is an improvement that still leaves the game unplayable. The image is not unreadable. MEASURED:

    file offset 1108 (= 84 + 1024):  0000 0300 f6 "SHOGUN     "     storage type $F, name len 6
    Journey.po offset 1024 (bare):   0000 0300 fb "JOURNEY.3.5"     storage type $F, name len 11

Structurally identical ProDOS volume directory headers. And the DiskCopy header states its own geometry exactly: `dataSize` @0x40 = `0x000C8000` = 819,200 (the same 800K as the three bare `.po` files), `tagSize` @0x44 = `0x00004B00` = 19,200, and 84 + 819,200 + 19,200 = 838,484 = the file size to the byte. An ordinary 800K ProDOS volume is sitting 84 bytes in, intact.

**PIECE 1 — support it (the one that gets the game running).** `crates/blorb/src/hfs.rs` already carries the whole DiskCopy 4.2 layer for Macintosh images: `DISKCOPY_HEADER: usize = 84` (:109), `volume_offset` (:548) and `diskcopy_volume_len` (:578), all currently private. `prodos.rs` already tries multiple volume placements — its `volume_at` "takes the declared length when there is one, then the block count, then whatever follows the header" — so adding the DiskCopy placement is joining two mechanisms that both exist, not writing a decoder. `prodos.rs:54` predicted precisely this: "*[`crate::hfs`] has the unwrap for its Macintosh images and sharing it here is a small refactor nobody has done*."

Note the existing test `only_the_prodos_images_in_the_corpus_look_like_prodos` currently asserts `Shogun.po` is **declined** and its doc calls that the point. Piece 1 inverts that expectation deliberately — update the test and its prose together, and keep the other half of its claim (a DOS 3.3 `Planetfall` dump is still declined) intact.

**PIECE 2 — stop the silent fallthrough (the one that generalises).** Independent of whether Shogun.po ever mounts, `hints::extract_story` makes Z-code the untested else-branch: Blorb proves itself by magic, Glulx by `Glul`, Scott by content sniff, and **everything else is assumed to be a Z-machine story** — its own doc says "the historical pass-through… Never errors for a non-Blorb input." The only gate left is `parse_header`'s `3..=8` on byte 0, which ~2.3% of arbitrary bytes pass. That is why an 838 KB disk image ran, paired with a sidecar meant for another file, and exited **0** with "story ended without asking for input" — a message that reads as a game bug and sends the reader looking in entirely the wrong place.

Piece 2 is the one worth doing even after Piece 1, because the next unsupported container will land in the same else-branch. Still uncounted: how many other files in the corpus already do.

SUGGESTED ORDER: Piece 1 (small, unblocks the Apple Shogun press), then Piece 2 (broader, needs a sweep to size). They can share a lane; they must not share a commit.
