MEASURED by the SQ-0888 lane, 2026-08-15, and it is the finding that decided that quest's fix.

Fixture: `stories/shogun_s1.dsk` — the five-volume Apple II press, **release 311 / serial 890510**. Repro, fresh user dir with `v6_render = "raster"`:

    cargo run -q -p app --example pty_capture -- --story stories/shogun_s1.dsk --user-dir <ud> \
      --size 100x40 --keys "wait:3500,space,wait:2500,cr,wait:4500" --png out.png

Result: ONE 784x537 placement at rows 4..33 — the ship drawn correctly at raster's proportions — and **not one word of the prose**. Window 6 (z=17) composites above window 0, so the story window's text is buried under the graphics window's canvas.

WHY THIS MATTERS BEYOND ONE FRAME: the SQ-0888 diagnosis recorded "raster is correct" on this scene, and that phrasing was load-bearing — one of the two candidate fixes was to take the raster composite. It would have traded a squashed picture for a blank story window. Raster is correct about the SHIP; it is wrong about the text, and nobody had looked at the text because the reported symptom was about the art. **A mode described as "correct" on a frame was only ever checked for the thing that was broken.** Worth remembering the next time raster is used as the oracle for a hybrid defect.

SCOPE: pre-existing, and NOT caused by SQ-0888's fix (`b6b70f3e`), which changed hybrid only — hybrid on this frame now shows the ship beside crisp wrapped prose. So the two modes have swapped places here: hybrid is right and raster is wrong.

WHAT TO ESTABLISH FIRST:
  - Is this z-order the game's own declaration or our composite's? Shogun r311 puts the room art in window 6 at z=17 and window 0 at z=5 (the SQ-0888 body carries the full display list from a host Save State's `display.json`). If the game really does declare graphics above text, the question becomes what a real Apple IIgs did with that — the original presumably showed both, so either the hardware composited differently or window 6's canvas is not opaque where the text sits.
  - Whether transparency is the answer: if window 6's canvas has transparent pixels outside the ship's own rect, the defect is that we composite it as opaque rather than that we order it wrongly. Check the canvas's alpha before assuming a z-order fix.
  - Whether other v6 titles stack a graphics window above window 0 anywhere. SQ-0888's sweep found the window-6 idiom is Shogun r311's alone among the Apple presses (`zork_zero_1.dsk` r383, `journey_s1.dsk` r77, `Arthur.po` r63 never set a margin and put no chrome-graphics pixels inside window 0's box), but that sweep was about margins, not z-order, and covered opening scenes only.

DO NOT fix this by reordering globally without the above — z-order is stated per window by the story, and a blanket "text above graphics" rule would break every title that legitimately paints art over its text.

Related: SQ-0888 (`b6b70f3e`) fixed the hybrid half of this scene; SQ-0890 is the Shogun credits screen's duplicate-text collision. Different screens, different paths.
