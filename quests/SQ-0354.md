--- note 2026-07-15T20:39:41Z ---

User addition (2026-07-15): Right arrow at the END of the line, when a suggestion is showing, must ACCEPT the suggestion (fish/zsh autosuggest style) rather than move the cursor. Anywhere else in the line, Right moves the cursor as normal.

So Right is context-dependent and the two behaviours must be designed together, not bolted on:
  - cursor at end + suggestion present -> accept the suggested text
  - otherwise                          -> move cursor right one char

Note the existing suggestion model already distinguishes preview from applied: state.suggestion_active is false after typing (the candidate at suggestion_idx is only a PREVIEW shown in brackets) and true once a Tab press has applied it. Accept-on-Right should apply the previewed candidate the same way Tab does, so the two paths agree.

--- note 2026-07-15T20:49:33Z ---

Investigation before starting (2026-07-15). The user's "this should apply to dialog input boxes too — good to have a common implementation" reshapes this quest. Facts on the ground:

- crates/app/src/text_field.rs ALREADY EXISTS: `TextField { value: String, cursor: usize }` with insert/backspace/delete/left/right/home/end/set/char_len (183 lines).
- DIALOGS ALREADY USE IT (render/dialog.rs, render/text_entry_dialog.rs), so dialog input boxes ALREADY HAVE arrow-key cursor movement. This quest is not needed for them.
- The MAIN input line is the odd one out: `AppState.input` is a bare `String` with only push_input_char/backspace — NO CURSOR AT ALL. That is the actual gap.
- => The "common implementation" the user wants = migrate AppState.input from String to TextField. BLAST RADIUS: ~60 touch sites across 7 files (loop_tick.rs, reset.rs, state.rs, main.rs, input.rs, render/transcript.rs, render/verbmenu.rs).

- SUGGESTIONS ARE MAIN-LINE ONLY. TextField carries no suggestion state; state.suggestions/suggestion_idx/suggestion_active live on AppState. So "autocomplete in dialogs" is NOT a matter of sharing a matcher — the suggestion machinery does not exist for dialogs at all. Making it common means lifting suggestions into the shared layer (TextField, or a wrapper owning TextField + suggestions) and letting each dialog supply its own candidate source.

Suggested order:
 1. Migrate AppState.input -> TextField. Pure refactor, no behaviour change, big diff. Gives the main line a cursor and puts both surfaces on one type.
 2. Right-at-end accepts the suggestion (see the note above) — needs cursor + suggestions together, so it lands after 1.
 3. Mouse click -> cursor index. Needs the input line's screen rect; check render/transcript.rs for where the prompt is drawn.
 4. OPTIONAL/SEPARATE: lift suggestions into the shared layer so dialogs can opt in with their own candidate source. This is the part that actually delivers "autocomplete in dialogs" and is arguably its own quest.

SQ-0353 (substring matching) is DONE and independent (bf4d649) — slash_suggestions is a free function taking (token, names, limit), so any future dialog suggestion source can call it unchanged.
