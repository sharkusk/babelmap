## REOPENED — closed too early on 2026-08-20

SQ-0935 unified the PAGE (it comes from the machine's measured RGB now, for v1–v6)
and I marked this done off the back of it. That was wrong: the page was only one of
the places a section 8.3.1 number gets resolved, and the others still go through the
app's ColorScheme. Measured on the frame SQ-0935 was verified with — Shogun r322,
licensed IBM PC, 114x44, via `examples/pty_capture`:

    our status bar ground   #FFFFFF   (colour 9 -> theme white; right by luck)
    our status bar INK      #006BB5   (colour 6 -> theme blue;  WRONG)
    the machine's blue                #0000AA

## The game's own set_colour is the path that is still wrong

Traced with `set_trace_screen`, which is how SQ-0928 established the DOS facts.
Shogun issues 14 `@set_colour` calls, all on window 1, its status window, and what
it asks for DEPENDS ON THE PAIR WE REPORT:

    licensed IBM PC:   @set_colour(fg=std6, bg=std9, window=1)
    no machine pair:   @set_colour(fg=std2, bg=std9, window=1)

So the chain works exactly as SQ-0935 intended — we report the machine's pair, the
game reads it and reverses it for its status bar, and the result is authentic DOS
blue-on-white. The defect is the last step: `std6` is resolved to the THEME's blue
rather than the machine's, so the right colour NUMBER lands in the wrong shade.

This is the general form and it is why the quest exists: **on a licensed launch,
every section 8.3.1 number should resolve through the MACHINE's colours, wherever
the number comes from — the header pair, a period look, or the game's own
`set_colour`.** Fixing only the page fixed only the one that bypasses numbers
entirely.

## A SECOND defect, found in the same measurement: the IBM PC's ink is wrong

`zvm::interpreter`'s IBM PC row states `ink: (0xAA, 0xAA, 0xAA)` — EGA palette
entry 7, which is LIGHT GREY. Measured on the real machine, `dos-shogun.png`'s
body text is `#FDFFFF` / `#FCFEFF`, i.e. bright white, and 59% of its text pixels
are above `#C8C8C8`. EGA entry 15 is white; entry 7 is light grey; section 8.3.1
calls colour 9 "white". So the row should almost certainly say `#FFFFFF`.

I put that value there myself, in commit e7a7b8ab earlier the same day, when
switching the row from capture measurements to EGA_PALETTE entries — entry 1 for
the page was right and entry 7 for the ink was not.

CAVEAT WORTH KEEPING, because it is the one thing that argues the other way:
`dos-hitchhiker.png` measures ink `#A0A0A0`, light grey, and that capture is a v3
story on a CGA display. So grey may be genuinely right for a v1–v4 CGA frame and
white right for a v6 EGA one — DOS's default text attribute is 7, while a game
naming colour 9 gets 15. If so the single `ink` field cannot serve both and the
question is whether the table needs to distinguish the adapter. Do not "fix" the
row to white without deciding that, or `dos-hitchhiker.png` stops matching.
