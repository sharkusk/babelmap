--- note 2026-08-12T21:28:45Z ---

Design settled before filing — do not re-derive.

MECHANISM IS GRANULARITY, NOT A PROTOCOL FEATURE. Neither kitty nor iterm2 has an
op to patch pixels into an already-transmitted image. (Kitty's animation-frame
composition, `a=f` with an offset, technically could — but it is kitty-only, recent,
not exposed by ratatui-image, and UNVERIFIED against virtual placements. Do not
build on it without measuring first.) The portable form of "update only the dirty
region" is: upload a SMALLER image over just those cells.

WHY IT IS CHEAP HERE. `chrome_bands` is already keyed by `(slot, x, y, w, h)` in
cells, already hashes each band's content, already skips re-encode on a hit, and
already handles delete/retain per key. The graphics layer needs no new idea. The
change lives in `decompose_chrome_strips` (`render/screen.rs:1050`) — which RECTS it
emits. Estimated a day, low risk.

THE SEAM QUESTION IS ALREADY ANSWERED. Every band crops its sub-rect from ONE
scaled canvas (`chrome_scaled`, SQ-0514), so N tiles are byte-identical to the
single strip they replace. No resampling boundary, no ceil-vs-round trap.

DO NOT BUILD A PATCH-OVER-BASE LAYER. Virtual placements name an image per CELL, so
a patch dropped over a base image does work. It costs more than it saves: the band's
placement rewrites every cell of its rect each frame (so a patch is clobbered unless
the strip tracks which sub-rects are overridden — that bookkeeping IS tiling, plus a
layer), and patches accumulate, each resident, needing a re-flatten policy. Tiling
has no drift: one image owns a cell, permanently.

GRANULARITY IS BACKEND-CONDITIONAL, and `decompose_chrome_strips` knows the picker:
  kitty / iterm2 — tile. First-frame cost is one extra control block per tile plus a
    rounded-up last chunk each: fractions of a percent, identical pixel payload.
  sixel — DO NOT tile. Every sixel image carries its own palette definition, so N
    tiles means N palettes where there was one. A real first-frame regression.
  halfblocks — irrelevant; ratatui's own cell diff already gives it dirty-region
    updates for free.

ESTIMATED WIN (arithmetic off the SQ-0817 capture, not measured): banner 115 cells
wide, compass rect 45 unit px ≈ 65 device px ≈ 8 cells at the captured 8x18 cell.
8-cell tiles → 2 of 15 re-send → ~86 KB against 618 KB, ~7x.

TEST IT WITH WHAT EXISTS: `uploaded_targets()` already answers "which bands actually
sent pixels this frame". Change one tile's pixels; assert exactly one Upload and
N-1 Reuse. Also assert the partition is exact — no gaps, no overlap, every tile >= 1
cell.

TWO COSTS TO WEIGH. A frame that changes the WHOLE strip now sends N images instead
of one (per-image framing; small, but it is the case a palette change hits). And
more resident images means more terminal LRU pressure — the failure SQ-0753 was
about. The deletes handle that correctly now, but finer tiling makes the lifecycle
matter more, not less.

FRAMING FOR THE DECISION: with SQ-0817 fixed, nothing blinks — this is a BANDWIDTH
and CPU question now, not a correctness one. The payoff is responsiveness on a slow
pipe (over ssh, 4.9 MB for a boot animation is snappy vs sluggish); on a local
terminal it may never be noticed. User is deciding whether to do it at all.
