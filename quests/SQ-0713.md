Format cracked from real media (2026-08-09). User extracted the original Amiga Zork Zero disks; `Pic.data` renamed to `stories/zork0.pic` (218880 bytes, dated 1989-03-23). Parsed directly — everything below is measured, not recalled.

CONTAINER
- 16-byte header. Byte 0 = 0x01, almost certainly the part number (so more picture files likely exist on the other disks). Word at offset 4 = 0x01ef = 495 = picture count. Remaining header words (0x0d91, 0x0e00, 0x0fa7, 0x000a) not yet identified. No magic signature — the file cannot be identified by content alone; validate by parsing the directory and sanity-checking the count and dimensions.
- Directory: 495 x 14-byte big-endian records starting at 0x10, ending 0x1b22. Record = id(2), width(2), height(2), flags(2), data offset(3), palette offset(3). ids run 1..485 with gaps; 462 have real dims, 33 are all-zero placeholders. flags seen: 0 and 3.
- Palette: 20 distinct palettes, shared by many pictures (palette offset 0 = none). Layout is count byte, count x 3 RGB bytes, then a second count byte and that many index-remap bytes — 14 colours + 16 remap = 60 bytes in the two sampled. Every channel byte is a multiple of 0x11, confirming 12-bit Amiga RGB expanded to 8-bit. This is direct confirmation from original media of the earlier inference that the .blb files were converted from the Amiga releases.
- Pixel data: NOT decoded. Each blob starts with what looks like a 3-byte length. Infocom's picture compression is the actual work of this quest; the container above is the easy half.

WHY THIS QUEST IS WORTH MORE THAN PREVIOUSLY THOUGHT
Cross-checked the native directory against Zork0.blb (2213 Pict resources: 2106 PNG + 107 Rect):
- 74 pictures have real art in the native file and appear in the Blorb ONLY as `Rect` placeholders. All 74 native-only ids are exactly Rect ids — a perfect match, so the Blorb author had no source for them and stubbed them. Those 74 pictures are recoverable ONLY from native media. This overturns the earlier read that native support buys nothing for Zork Zero.
- The other 33 Rects correspond to the 33 all-zero native entries (genuinely absent everywhere).
- 5 shared ids disagree on dimensions: 5 (native 320x200 vs blorb 320x34), 6 (320x200 vs 320x39), 7 (320x200 vs 320x39), 8 (320x200 vs 320x29), 33 (150x158 vs 150x156). Worth understanding before trusting either source — ids 5-8 are in the range we were fighting over for the boot animation and side bars.
- The Blorb carries ids 497-504 and a large 1000-2709 block with nothing corresponding in this file. Either a second Amiga picture file exists on the other disks (consistent with the part-number byte), or that block came from a different release. Ask the user to check the extracted disks before concluding.

NAMING
AmigaOS has no extension convention (`.info` is just the Workbench icon sidecar), and every Infocom Amiga release names its archive `Pic.data`, so names collide across games. Convention adopted: rename to the story stem, `<stem>.pic`, matching `blorb::resolve_resource_blorb`'s existing same-stem sibling rule. Since there is no magic number, a native reader must validate by cross-checking the parsed picture table against what the story expects, or it will happily draw Arthur's plates into Zork Zero.

Codec cracked and implemented (2026-08-09). crates/blorb/src/infocom_pics.rs, commit d8f30d45.

FORMAT — from Infocom's OWN interpreter sources (github.com/erkyrath/infocom-zcode-terps), not inference. mac/gfx.c carries a prose spec of the compression at the top of the file; amiga/gfx.c has the EF_* entry-flag defines and the LBYTES length prefixes; mac/gfx.p has the palette trailer. Amiga/Mac Pic.data is a COMPLETELY different codec from the PC .MG1/.EG1/.CG1 files (those are little-endian LZW). Decode, in reverse order:
  3. Flat 256-byte Huffman tree, MSB-first bits. Node n (even): child for a clear bit is tree[n], set bit tree[n+1]. Value <128 = internal node id, DOUBLE it for the index. Value >=128 = leaf carrying symbol value-128.
  2. RLE: symbol 0..15 = emit that colour index and remember it; 16..127 = emit the remembered colour (symbol-15) MORE times.
  1. XOR: every scanline is XORed with the line above it (row 0 against a virtual zero row).
Blob header is 6 bytes = two 3-byte big-endian counts: minSize (compressed byte count, excludes the 6) then midSize (SYMBOL count out of the Huffman stage — this is the mystery second value from the earlier note; it is the olen loop counter, not a length).
Global Huffman tree offset = header word at offset 2, DOUBLED (0x0d91*2 = 6946 = exactly the end of the directory here). Header byte 8 = 14 = the directory record size, and is the field that distinguishes Amiga/Mac (14, big-endian) from the PC flavours.
Flags: 3 = EF_TRANS|EF_PHUFF (transparent + Huffman-coded). Every picture with data in zork0.pic is exactly 3.
PALETTE: the stored RGB triples occupy colour indices starting at 2, NOT 0 — indices 0 and 1 are reserved (0 = transparent). A 14-colour palette fills 2..15. Confirmed against the Blorb PLTEs, which are the native table shifted by two with black in 0 and 1. The count-plus-N bytes after the triples are gp.stips, a STIPPLE-PATTERN id per colour for rendering on a 1-bit screen — NOT a colour remap. This kills the inference in correction #3 that a remap table could regenerate the Blorb's 1000-2709 recolour block from native art; there is no remap mechanism in the format. That block's provenance is still unexplained.

ORACLE RESULT — 383/383 byte-exact. 388 native pictures have real pixel data; all 388 also exist as PNGs in Zork0.blb. 383 decode pixel-for-pixel identically. The only 5 failures are precisely the 5 known dimension-mismatch ids (5,6,7,8,33), and there the NATIVE file wins: it holds the full 320x200 decorative frames (red-and-brown pillared border, green bamboo-and-vine border, and for 33 the full 150x158 'Ceremonial Object / Four Fantastic Flies of Famathria' plate) where the Blorb keeps only a cropped top band or, for id 8, a solid rectangle. Those five are a real recovery.

CORRECTION #4 — THE '74 RECOVERABLE PICTURES' CLAIM IS WRONG. Retract it. The native directory has 388 entries with pixel data and 107 entries with NO data offset (flags 0). Those 107 map exactly onto the Blorb's 107 Rect resources — a perfect 1:1 match, not 33. The earlier note counted the 74 that have nonzero WIDTH as 'real art', but width without a data offset is a size-only placeholder: a picture the game draws as a solid rectangle. Whoever built the Blorb stubbed nothing; the placeholders are placeholders in the original Amiga media too. Net native-only recovery for Zork Zero is the 5 dimension-mismatch pictures, not 74.

Tests: a hand-built one-picture archive (no fixture needed) plus a real-media smoke over zork0.pic that pins all 388 decodes with an FNV-1a hash and skips vacuously when stories/ is absent. **THE TWO EDITIONS SPLIT THE ADAPTERS, AND NEITHER SHIPPED ALL THREE:**

    720K (3.5")   MCGA + CGA, no EGA
    360K (5.25")  CGA + EGA, no MCGA

Consistent with the hardware timeline — MCGA/VGA arrived with the PS/2 line and its 3.5" drives, while EGA machines were the older 5.25" generation. CGA is on both because it was the floor. This also explains the earlier finding that the 720K `INSTALL.EXE` offers only "CGA" and "MCGA/VGA" picture files while the binaries plainly know `.eg1`: the interpreter is edition-independent, the *media* are not.

PRACTICAL CONSEQUENCE: a user's DOS art depends on which physical edition they own, and a complete PC corpus needs both. Our `stories/` happens to hold all three for Zork Zero because the files were collected separately rather than from one box.
