--- note 2026-08-09T17:04:40Z ---

Format cracked from real media (2026-08-09). User extracted the original Amiga Zork Zero disks; `Pic.data` renamed to `stories/zork0.pic` (218880 bytes, dated 1989-03-23). Parsed directly — everything below is measured, not recalled.

CONTAINER
- 16-byte header. Byte 0 = 0x01, almost certainly the part number (so more picture files likely exist on the other disks). Word at offset 4 = 0x01ef = 495 = picture count. Remaining header words (0x0d91, 0x0e00, 0x0fa7, 0x000a) not yet identified. No magic signature — the file cannot be identified by content alone; validate by parsing the directory and sanity-checking the count and dimensions.
- Directory: 495 x 14-byte big-endian records starting at 0x10, ending 0x1b22. Record = id(2), width(2), height(2), flags(2), data offset(3), palette offset(3). ids run 1..485 with gaps; 462 have real dims, 33 are all-zero placeholders. flags seen: 0 and 3.
- Palette: 20 distinct palettes, shared by many pictures (palette offset 0 = none). Layout is count byte, count x 3 RGB bytes, then a second count byte and that many index-remap bytes — 14 colours + 16 remap = 60 bytes in the two sampled. Every channel byte is a multiple of 0x11, confirming 12-bit Amiga RGB expanded to 8-bit. This is direct confirmation from original media of the earlier inference that the .blb files were converted from the Amiga releases.
- Pixel data: NOT decoded. Each blob starts with what looks like a 3-byte length. Infocom's picture compression is the actual work of this quest; the container above is the easy half.

WHY THIS QUEST IS WORTH MORE THAN PREVIOUSLY THOUGHT
Cross-checked the native directory against Zork0.blb (2213 Pict resources: 2106 PNG + 107 Rect):
- 74 pictures have real art in the native file and appear in the Blorb ONLY as `Rect` placeholders. All 74 native-only ids are exactly Rect ids — a perfect match, so the Blorb author had no source for them and stubbed them. Those 74 pictures are recoverable ONLY from native media. This overturns the earlier read that native support buys nothing for Zork Zero.
- The other 33 Rects correspond to the 33 all-zero native entries (genuinely absent everywhere).
- 5 shared ids disagree on dimensions: 5 (native 320x200 vs blorb 320x34), 6 (320x200 vs 320x39), 7 (320x200 vs 320x39), 8 (320x200 vs 320x29), 33 (150x158 vs 150x156). Worth understanding before trusting either source — ids 5-8 are in the range we were fighting over for the boot animation and side bars.
- The Blorb carries ids 497-504 and a large 1000-2709 block with nothing corresponding in this file. Either a second Amiga picture file exists on the other disks (consistent with the part-number byte), or that block came from a different release. Ask the user to check the extracted disks before concluding.

NAMING
AmigaOS has no extension convention (`.info` is just the Workbench icon sidecar), and every Infocom Amiga release names its archive `Pic.data`, so names collide across games. Convention adopted: rename to the story stem, `<stem>.pic`, matching `blorb::resolve_resource_blorb`'s existing same-stem sibling rule. Since there is no magic number, a native reader must validate by cross-checking the parsed picture table against what the story expects, or it will happily draw Arthur's plates into Zork Zero.

Correction to the previous note (2026-08-09): the Icon.data lead is DEAD. Parsed both ADFs' filesystems directly (OFS, 1760 blocks each) and enumerated every file-header block. Disk0 is a plain AmigaDOS boot disk (5 dirs, 16 system files). Disk1 holds 13 files and **none of them is Icon.data** — only its 413-byte `Icon.data.info` icon sidecar. My earlier `strings` hit came from the disk's hidden 67-byte `.info` manifest, which reads exactly:

    Story.data / Zork Zero / Pic.data / Icon.data / bine2 / bine

So the release DOES include Icon.data and this 2-disk image is INCOMPLETE. Deleted-file traces: exactly two orphaned OFS data blocks survive (seq 2 and seq 3, next=0, so the file ended there), carrying 1-bit bitmap data and totalling ~1.1 KB. Whatever that deleted file was, it is far too small to be a picture archive, and the first block is overwritten, so it is not recoverable.

Provenance of the Blorb's unexplained ids, measured by testing whether each PNG's PLTE is pure 12-bit Amiga (every channel byte a multiple of 0x11):
- ids < 500: 390 of 391 pure Amiga. This is the range native `Pic.data` covers.
- ids 1000-2709 (1710 pictures, 304 KB, mostly small tiles — 1250 at 21x21, 180 at 27x11, 160 at 45x40, 70 at 62x9): 971 pure Amiga, 630 with no PLTE at all (greyscale/truecolour), ~109 other.

So that block is still largely Amiga-sourced — it is NOT evidence the Blorb was built from DOS media. There is another Amiga source file we do not have, and Icon.data at ~1 KB cannot be it. Before this quest can deliver full native coverage for Zork Zero, someone needs a more complete Amiga dump than this two-disk pair. Native `Pic.data` alone still delivers the 74 pictures the Blorb only stubs as `Rect`, which remains the concrete payoff.

--- note 2026-08-09T17:22:46Z ---

Correction #2 (2026-08-09) — `Icon.data` is a PHANTOM, and the disk image is COMPLETE. Retract the "this 2-disk image is INCOMPLETE" conclusion from the previous note.

Decoded the Workbench icons as DiskObject structures. `Icon.data.info`, `bine.info` and `bine2.info` are all 413 bytes, all type PROJECT with ToolTypes, all a 53x20 icon; `bine.info` and `bine2.info` are byte-identical to each other, and `Icon.data.info` differs from them at only 14 byte offsets (position and render fields). Meanwhile `bine` and `bine2` are real 31232-byte files that both contain the string `890323` — and `Story.data` is version 6, release 366, **serial 890323**. They are SAVED GAMES left on the disk.

So `Icon.data.info` is the TEMPLATE icon the Amiga interpreter copies when it writes a save file, giving each save a double-clickable Workbench icon. The base file `Icon.data` never has to exist — an Amiga `.info` is a standalone sidecar, and its only job here is to carry the icon imagery under a known name. That is why Arthur's Amiga disk shows the identical pattern (user confirmed: `Icon.data.info` present, `Icon.data` absent). It is not damage, not a bad extraction, and there is no third disk to hunt for.

Consequence for this quest: `Icon.data` is NOT a picture source and must not be chased. The Blorb's ids 1000-2709 remain unexplained by any file on this media.

Also tested and REFUTED the "the Blorb stores multiple versions of each image" hypothesis: pairing id X with id X+1000 across all 396 low ids gives only 115 dimension matches and **zero** byte-identical pairs — e.g. id 1 is 320x200 while 1001 is 45x40, and 1001-1008 are all 45x40 room icons. The 1000+ block is different CONTENT (1250 tiles at 21x21, 180 at 27x11, 160 at 45x40), not a re-encoding. The Blorb does alias images across ids — 136 distinct images appear under more than one id, 266 ids total — but that is reuse, not versioning, and the Blorb resource index has no alternate-version mechanism in any case.
