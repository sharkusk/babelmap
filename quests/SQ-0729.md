--- note 2026-08-09T19:11:04Z ---

RASTER HALF FIXED 2026-08-09 (commit 9c48ce29, worktree branch worktree-agent-a5638a57fe9a3fae0). The HYBRID half is UNTOUCHED and still open.

VERDICT on the "one cause behind all three?" question: TWO causes across the three quests, not one and not three.
- SQ-0727 (advent) + SQ-0728 (Shogun) share a root cause: the raster path used "is this pixel opaque?" as a proxy for "is there artwork here?", and rasterized glyphs are opaque. Two call sites, one mistake.
- SQ-0729 (fmvpoker) is a different mistake: `story_prose_box` measured window 0's plate by its BOUNDING BOX.

ROOT CAUSE HERE, measured. fmvpoker's poker table is a 640x400 picture that is mostly HOLE — 42830 of 256000 pixels opaque (16.7%), and only 4.0% of the middle half. SQ-0714 correctly classifies it as a backdrop and puts it on window 0's canvas; SQ-0707's `story_prose_box` then yields the whole screen to any window-0 plate whose bbox leaves no wrappable margin strip. A hollow frame's bbox is the whole screen, so `story_prose_box` returned None, `build_v6_raster_canvas` took its plate-owns-the-screen early return, and NOT ONE line of text was drawn. `raster_metrics` was None on every frame.

FIX: `story_prose_box` now measures the largest rectangle of the clear interior that the plate painted no pixel of (histogram/monotone-stack largest-rectangle sweep over the plate's alpha mask), replacing the bbox + four-margin-strips rule. Measured after:
  fmvpoker title frame  -> (24,54) 586x172
  fmvpoker menu frame   -> (22,234) 594x158   (exactly the frame's interior)
  Arthur graveyard plate-> (0,0) 28x400, below the 8-column floor -> still None, plate still owns the screen
  Journey title (100% opaque win-0 picture) -> None, unchanged
PNG after: the banner, "Press 'i' for more information…", "Current Bet: / 10", "Total Winnings: / 1000" all render inside the blue frame, cards still drawn.

STILL OPEN HERE (hybrid, not mine): (1) no graphics at all in hybrid — the page is white and not one picture is drawn; (2) the menu labels concatenate (PLAY CURRENT BETCHANGE CURRENT BETSAVERESTOREQUIT). Note for whoever takes it: at the frame where those labels appear, the window at native (22,235) 594x156 is published as a NON-PRIMARY `WinNode::Buffer` whose `lines[0]` is ALREADY the concatenated string "PLAY CURRENT BETCHANGE CURRENT BETSAVERESTOREQUIT" — so the runs are being flattened into buffer lines before any render code sees them, not collapsed by the cell mapper. That also means `build_chrome_canvas` never draws it in raster at all (it renders Graphics and Grid, never a chrome Buffer); one frame later the same window becomes an empty `Grid 74x9`, so the labels are lost on both paths for that reason too. Worth measuring before assuming it is the same column-mapping bug as SQ-0727.

HYBRID HALF FIXED 2026-08-09 (commit cb907e2c, worktree branch agent-aac7ced4754cd20eb).

DEFECT 1 — no graphics at all in hybrid. ROOT CAUSE, measured. Hybrid uploads art as bands AROUND the story viewport, so a story window covering the whole screen leaves `chrome_bands` with nothing to carve and NO art behind it can be shown, whatever its shape. `picture_takeover` exists to route exactly those frames to the composite, but it asked whether the art FILLED the screen — an 8x8 sample grid, every point required painted. fmvpoker paints a 640x400 table into full-screen window 0 and prints its title inside it, and that table is a FRAME: 42830 of 256000 pixels opaque (16.7%), the middle a hole. It missed at every sample point that mattered, so hybrid kept its empty ring and drew nothing.

FIX: the rule now also fires when the art ENCLOSES the screen — painted pixels within one native text row of all four edges, probed edge strip by edge strip. Corpus-measured per frame (hybrid path log, before vs after): exactly one game moves, fmvpoker, and only from the frame where its plate exists.
  zork0 hybrid-ring x4 (window 0 inset 86,78 468x320 -> covers_screen false)
  arthur raster,ring,ring,ring (intro plate 89.4% painted, already fired)
  shogun raster,menu-takeover,ring,ring (window 0 inset)
  journey ring,raster,ring,ring (title 100% opaque, already fired)
  advent ring,menu-takeover,ring,ring (no graphics at all)
  scopa painted-takeover x4 (no story window)
  mysterious01 hybrid-ring x4 (plate bbox 0,191 512x192 — reaches neither top nor right edge)
  fmvpoker ring,raster,raster,raster  <- the only change
Pinned as a per-frame path table in `fmvpoker_is_the_only_title_this_moves`, because hybrid is the shipped default and a title that stops taking the ring renders as a pixel image instead of crisp cells.

DEFECT 2 — the concatenated menu. VERDICT: MODEL-SIDE, in zvm, and NOT fixable in the render lane. The previous agent's finding is confirmed and traced one level deeper. At that frame the window is a non-primary `WinNode::Buffer` whose `lines[0]` is already "PLAY CURRENT BETCHANGE CURRENT BETSAVERESTOREQUIT". I probed the zvm window behind it: `win.texts` is EMPTY and `win.streamed` is EMPTY too. So the positions are not merely unpublished by session.rs — they were never recorded. A v6 window in flowing-prose mode streams through `ZWindow::push_prose`, which appends to `prose` lines and keeps no cursor x. The columns are lost inside the VM before any render code sees them. Fixing it means teaching zvm to shadow a secondary prose window's runs the way it already shadows the primary's (`streamed`/`retire_streamed`), which is a VM-core change and belongs to a zvm lane. Pinned as a premise assertion in the new test so a later fix there is noticed rather than silently changing what the file guards.

DEFECT 2's RENDER-SIDE HALF, fixed here. `build_chrome_canvas` draws Graphics and Grid windows and never a secondary prose Buffer, so the menu row AND the "Select an option with your mouse or by typing the first letter." hint were absent from the composite entirely. That is almost certainly the "no text hints" the user reported in raster. New `draw_secondary_prose` stacks such a window's lines from its own origin, one 16px row each; `chrome_text_rects` spares them so the story page fill cannot erase them; `v6_raster_gen` hashes the lines so the cached composite cannot outlive them. It sits beside `build_chrome_canvas` rather than inside it because the ink is honor_game_colours-gated and that function is not — painting fmvpoker's declared black regardless put black glyphs on the host's black page, caught by the theme-only half of the pair. Without this, routing hybrid to the composite would have LOST the menu row hybrid used to show (garbled), so the two halves had to land together.

PNG after (raster composite, which is now also what hybrid ships for this frame): the blue frame whole, "FROBOZZ MAGIC VIDEOPOKER / by Zach Matley / Release 60 ... / Press 'i' for more information... / Current Bet: 10 / Total Winnings: 1000" inside it, and the bottom box carrying the menu row and the hint line.

FREE OBSERVATION on the pre-existing frame clipping (not investigated, per instruction): in the raster composite the frame's top-centre TAB is cut off at y=0 — the tab that carries the "Double Fanucci" title — while the sides and bottom are complete. The art itself is not oversized: the plate is 640x400 in a 640x400 screen, painted bbox exactly (0,0,640,400). So whatever clips it is a placement/offset question at the top edge, not a size mismatch. The user reports frameless shows the frame whole including the title, which makes frameless the reference for whoever picks that up.

STILL OPEN AFTER THIS COMMIT: (1) the menu-label concatenation, zvm-side as above; (2) the pre-existing top-of-frame clipping, which the user confirmed predates 9c48ce29.

ADJACENT, UNREPORTED, NOT FIXED: mysterious01 has the same shape as defect 1 — full-screen story window with a plate behind it (38.4% painted) — so hybrid shows none of its art either. It does not qualify under the enclosure rule (its plate is a band across the lower half and reaches neither the top edge nor the right one), so this commit deliberately leaves it alone. Its raster composite renders correctly, so the honest general rule ("any art behind a full-screen story window is unshowable by the ring") would fix it too, at the cost of moving a second title from crisp cells to a pixel image. That is a user-visible tradeoff on a game nobody complained about, so it was not taken.
