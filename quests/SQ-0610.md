## Why

Status information reaches a plain-mode reader only at the moment the game chose to
write it, and then scrolls away. A sighted user re-reads a pinned status line for free;
a screen-reader user has to scroll back through the transcript to answer "where am I,
what's my score?".

## Options (undecided)

- A command the CLI intercepts before the engine sees it (`status`, `/status`) that
  prints the current status text. Cheapest, but risks shadowing a game verb.
- Emit the status line before each input prompt in plain mode. No new syntax, always
  current, but repeats on every turn — likely too chatty for a reader.
- A key the input layer intercepts. Fits the raw-mode path but not the cooked one that
  plain mode wants ([[SQ-0606]]).

The data is available in all three engines already: zvm-cli reads it for its pinned
line, gvm-cli tracks grid windows in its cell buffer, and a Scott game's status is
prose the game itself prints.

Worth deciding with a real user rather than from here — the right answer depends on how
noisy a reader finds per-turn repetition, which is the whole question.

## Shipped 2026-08-03 — commit ed7223b8

Chose **option 1** (a command the CLI intercepts) from the three the quest left
open, with the stated risk engineered away rather than accepted.

### The shadowing problem, solved by the slash
The note's objection to option 1 was "risks shadowing a game verb". `/status`
does not: no interactive-fiction parser assigns meaning to a leading `/`, and
babelmap's own TUI already spells host commands that way, so the vocabulary is
not new to the product. Verified both directions — `status` still reaches the
game (Ballyhoo: `[I don't know the word "status."]`), `/status` does not.

Option 2 (status before every prompt) was the one the note said needed a real
user, because it turns on how noisy per-turn repetition is. That question is
untouched — option 1 only adds capability and forecloses nothing.

### Implementation
- `cli_host::input::is_status_request` — exact match after trim, case-insensitive.
  Never a prefix: `/status now` must reach the game.
- `ScreenView::status_now(&machine)` (zvm-cli) and
  `TerminalBackend::grids_plain_now()` (gvm-cli) — both deliberately bypass the
  streaming dedupe, since the player asked *because* nothing changed. scott-cli
  uses `vm.room_block()` directly.
- Each CLI loops its line read until a non-status line arrives. zvm-cli does NOT
  re-read after a timed-input abort — the interrupt has already run and the game
  is owed its answer.

### Verified
`/status` x3 with no turn between: 5 status lines for 2 turns (zvm/Ballyhoo),
4 for 1 (scott/adv01). Piped output byte-identical to the previous build across
11 stories. Falsified twice (prefix matching; routing the answer through the
dedupe).

### Known limitation, documented in the help and in interpreter.md
`/status` is a **line** command. At a `char` prompt ("press any key") the input
layer takes it as a keypress — and on piped input a char request eats the whole
line. Chasing this cost real time during verification: repeated `/status` in
Counterfeit Monkey looked like it was being dropped, and instrumenting the read
showed a Glk char request had swallowed the line. Not a bug in the interception.
