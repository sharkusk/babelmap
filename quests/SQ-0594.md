--- note 2026-08-03T04:03:14Z ---

## Measured, not inferred

Booted CM headlessly twice — cold with no VFS, then warm with whatever the cold run
produced:

```
cold boot (no cache):      5.142s
  vfs_dirty after boot:    true
  vfs_bytes after boot:    52 bytes
  vfs_bytes after 3 turns: 52 bytes (dirty=true)
warm boot (cache fed back): 5.118s   <-- 100% of cold
```

Those 52 bytes decode to the GVFS header plus ONE file entry:

```
GVFS \0\0\0\1  \0\0\0\1  \0\0\0\x20  "_Counterfeit_Monkey-startup-data"  \0\0\0\0
                ^1 file   ^32-char name                                   ^0 bytes
```

So CM opens its cache file and it ends up **zero length**. Nothing is cached, every
boot recomputes, and feeding the file back changes nothing — which matches the user's
memory that startup used to get faster after the first run and no longer does.

## What is NOT the cause

- The write path IS wired: `exec.rs:3147` routes `StreamKind::File` output to
  `Model::file_stream_write`, which writes straight into `self.files` (5 call sites).
  I briefly concluded otherwise from a bad grep — wrong, corrected.
- The open modes match Glk §6.1: 0x01 truncates, 0x02 fails when absent, 0x03 keeps
  and seeks 0, 0x05 appends at len. A truncating open (0x01) is what leaves the empty
  entry, and that is correct behaviour on its own.

## Next step

Instrument the Glk layer: count bytes passed to `file_stream_write` for that filename
during boot, and log every fileref open with its mode. Three outcomes to tell apart —
CM never writes (it is declining, so find what it checks first), CM writes and a later
truncating open discards it (an ordering bug), or CM writes somewhere we do not
persist. The 5s recompute happens during boot, so the trace has to cover the boot run
itself, not just the turns after it.

--- note 2026-08-03T04:20:02Z ---

## RETRACTED — the cache works, my harness was wrong

The user spotted `_Counterfeit_Monkey-startup-data.qzl` (41 KB) in the save dir. That is
the real cache, and it IS loaded at boot:

```
GlulxSession::new     (no seeding):  5.143s
GlulxSession::new_in  (seeded):      0.769s   <-- 6.7x faster
```

CM caches its startup state as a SAVED GAME, not as a Glk data file. Saved-game filerefs
bypass the VFS entirely and become host `.qzl` conduits, and `seed_saved_games`
(glulx_session.rs:205, SQ-0301) scans the save dir for `*.qzl` before boot so
`glk_fileref_does_file_exist` reports the cache present and CM restores it.

**My measurement was invalid.** The probe called `GlulxSession::new`, which does not seed
— only `new_in` does. So CM could never see its saved state, always recomputed, and the
"cold == warm" result was an artifact of a harness that structurally could not exercise
the path. Everything built on it was wrong: the "cache is written empty" conclusion, the
0-byte-file evidence, and the dismissal of the user's "maybe it depends on a game-save"
hypothesis — which was right, and which I contradicted using a boot trace that could not
have shown it.

The empty `_Counterfeit_Monkey-startup-data` entry in `default.glkvfs` is unrelated: a
separate Data-usage file CM opens with mode 0x01 and never writes. Harmless, and NOT the
cache.

Same lesson as SQ-0590 and the SQ-0588 wiring miss, a third time: the test exercised the
mechanism and skipped the wiring, and passed convincingly while proving nothing.

No defect found. Closing.
