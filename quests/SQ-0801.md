--- note 2026-08-12T07:39:51Z ---

USER 2026-08-12, playing fmvpoker with `pictures = "FMVPOKER.EG1"`:

> "there is a rendering problem with the cards with the ega graphics. specifically the card outline is missing from the top left and bottom right of each numbered card (where the number's background is painting over the card). it looks like the numbers should have transparent backgrounds, but we are not honoring that."

Note `FMVPOKER.EG1` is byte-identical to `zork0.eg1`, and `fmvpoker.blb` is Zork Zero's Blorb — so this is one artwork set seen through two renditions. The Blorb path is correct; EGA is not.

**MEASURED: EGA IS THE ONLY RENDITION WITH NON-UNIFORM TRANSPARENCY.** Per-picture flag words across the four sources, pictures with data only:

    zork0.mg1   396 pics   ALL EF_TRANS, transparent index 0        (flag word 1)
    zork0.cg1   396 pics   ALL EF_TRANS, index 0                    (flag word 9  = TRANS|MONO)
    zork0.pic   388 pics   ALL EF_TRANS, index 0                    (flag word 3  = TRANS|PHUFF)
    zork0.eg1   396 pics   only 264 EF_TRANS
                           132 with flags = 0 — NO transparency at all
                           119 transparent on index 1  (flag 0x1001)
                             5 on index 2              (0x2001)
                             4 on index 3              (0x3001)

Every other source is uniformly "index 0 drops out". **EGA is the only one that uses a non-zero transparent index, and the only one where some pictures are deliberately opaque.** So EGA exercises a path no other rendition does, which is why nothing caught this earlier.

**OUR DECODE MATCHES THE DOS INTERPRETER — verified, not assumed.** Frotz `src/dos/bcpic.c:343-352`, verbatim:

    /* Bit 0 of "flags" indicates that the picture uses a transparent
       colour, the top four bits tell us which colour it is. For CGA
       and MCGA pictures this is always 0; for EGA pictures it can be
       any colour between 0 and 15. */
    transparent = 0xff;
    if (pic_flags & 1)
        transparent = pic_flags >> 12;

`infocom_pics.rs:809` does exactly this: `transparent: (e.flags & EF_TRANS != 0).then_some((e.flags >> 12) as u8)`. And `Picture::rgba_with` (`:405-412`) sets `a = 0` for that index. Both look right on inspection.

**SO THE DEFECT IS DOWNSTREAM OF THE DECODE, OR THE PICTURES ARE GENUINELY OPAQUE. Two candidates, and the measurement that separates them is the first job:**

1. **Alpha is lost between `rgba_with` and the screen.** The Blorb path draws PNGs that carry their own alpha and renders correctly; the native path builds RGBA with `a = 0` and may be composited, uploaded or flattened somewhere that discards it. If so this is our bug and affects every transparent native picture — it is merely *visible* on EGA because EGA is the only rendition whose transparency is not index 0. (Note a picture that is transparent on index 0 can look fine even if alpha is dropped, whenever index 0 is also black against a black ground — which would have hidden this for MCGA, CGA and Amiga alike.)
2. **The card-number pictures are among the 132 with `flags = 0`**, i.e. genuinely opaque in the original media, and the real EGA release looked the same. Then there is nothing to fix and the honest answer is that the EGA rendition differs from the Blorb because the Blorb is MCGA-derived.

**FIRST MEASUREMENT, in order:**
- **Identify the card-number picture ids** that fmvpoker draws, and read their flag words in `zork0.eg1`. That alone decides between (1) and (2).
- If they carry `EF_TRANS` with index 1/2/3, follow one such picture from `rgba_with` to the emitted bytes and find where alpha dies. The emitted-stream harness (`crates/app/tests/pty_stream/`) and the placement oracle exist for exactly this — per CLAUDE.md they distinguish an image PLACEMENT from a background PAINTED into cells, which look identical on screen.

**IF IT IS (1), THE BLAST RADIUS IS LARGER THAN FMVPOKER**: every native archive marks essentially every picture transparent, so a dropped alpha affects Zork Zero, Arthur, Journey and Shogun under any native rendition — and would have been invisible until EGA made it show.

--- note 2026-08-12T08:06:03Z ---

INVESTIGATED — CANDIDATE 2: THERE IS NO DEFECT. The EGA rendition is faithful; the original looked like this too.

**The decisive measurement.** fmvpoker draws these ids (display list, window 0, one hand in): backdrop 99, card back 100, card body 101, pips 105/107/116/120/122/131 (26x12), and the rank plates 133/134/135/138/140 (36x11) + 144/145/146/149/151 (34x11). Their flag words in FMVPOKER.EG1 (= zork0.eg1):

    id  99  640x200  flags 0x0001  EF_TRANS, colour 0
    id 100   96x64   flags 0x1001  EF_TRANS, colour 1
    id 101   96x64   flags 0x1001  EF_TRANS, colour 1
    ids 105..151 (pips + rank plates)  flags 0x0000  NO TRANSPARENCY

**The rank plates are among the 132 deliberately opaque EGA pictures.** Their background is colour 7 — the same light grey as the card face — and the game draws each plate at its card's OWN origin. An opaque 36x11 plate at (0,0) of a 96x64 card therefore covers the card's rounded red border: the top edge for 36 of 96 columns and the left edge for 11 of 64 rows. Exactly the reported symptom, and it is the artwork doing it.

Infocom's own interpreter agrees, not just Frotz: terps/apple/yzip/rel.15/pic.asm ZDSP101 — bit 0 of the flag word clear → `TRANSCLR = $FF` (no colour can match), else the flag word shifted right four bits. Same rule as bcpic.c and same as `infocom_pics.rs:809`.

**The game's draw ops are IDENTICAL in both renditions** — card 101 @(42,69) and plate 140 @(42,69) under FMVPOKER.EG1 and under fmvpoker.blb alike (a good independent check on `art_scale`: EGA 36x11 at (1,2) and MCGA 18x11 at (2,2) both cover the same 36x22 unit box). So nothing about our geometry differs; the Blorb keeps its corner only because MCGA picture 140 is 18x11 with a TRANSPARENT surround, while the EGA one is a solid tile.

**ALPHA IS NOT BEING DROPPED — the blast-radius candidate is refuted.** EGA is the only rendition naming a non-zero transparent colour, and fmvpoker's cards use it: picture 101 is transparent on colour 1, and all five cards' cut-away corners arrive at window 0's canvas with alpha 0 (measured on the live canvas at (41,68), (154,68), (267,68), (380,68), (493,68)). A non-zero index surviving end to end is the strongest available proof that the index-0 case every other rendition uses survives too, so Zork Zero / Arthur / Journey / Shogun are unaffected under every native rendition.

Reproduced through the REAL binary as well as the harness: `pty_capture --story stories/fmvpoker.z6 --arg --pictures --arg FMVPOKER.EG1` shows the same clipped corners; the Blorb capture shows intact cards.

**Committed on the worktree branch (c041762a) — tests only, no behaviour change:**
- `crates/blorb/src/infocom_pics.rs` — synthetic PC-archive unit test pinning both arms of the flag word: `flags = 0x1001` → transparent colour 1 (and only colour 1 gets alpha 0), `flags = 0` → no transparency, whole rectangle opaque. No fixture needed.
- `crates/app/tests/suites/v6_ega_transparency.rs` (+ mod line in the `v6_scopa` group) — real-media, skips vacuously: the non-zero transparent index reaches the canvas as alpha; the ten rank plates are opaque in the artwork, so a future "fix" that invents transparency for them has to argue with the format first.

Falsified: forcing the decode to `Some(0)` / ignoring `EF_TRANS` fails the blorb test with the wrong index; forcing `rgba_with` to alpha 255 fails the canvas test with the reported symptom.
