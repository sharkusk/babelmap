## Why this is not just tidiness

SQ-0904 gave every suite that already declared a `PALETTE` mutex the shared `app::V6_PALETTE_LOCK`. **A mutex only excludes the parties that take it.** A test that sets `zvm::screen::set_palette` without acquiring the lock can flip the palette in the middle of a lock-holder's test, and the lock-holder has no way to notice. So the remaining three are not "also worth guarding" — they defeat the guard for everyone in their binary.

MEASURED after the SQ-0904 sweep (`grep -c "zvm::screen::set_palette"` against `grep -c V6_PALETTE_LOCK`, per suite, resolved through each group binary's `mod` lines):

### `v6_zork0` group — the live hazard

| suite | set_palette | takes shared lock |
|---|---|---|
| v6_float_machine_page | 2 | **yes** |
| v6_float_margin_ground | 2 | **yes** |
| v6_mac_pillar_feet | 2 | **yes** |
| **v6_mac_input_echo** | 1 | **no** |
| **v6_macintosh_profile** | 1 | **no** |

Five palette users in one process, three of them politely serialised and two ignoring the lock entirely. This is the same shape as the failure SQ-0904 fixed — `arthurs_notices_…` read `#5A5A5A` where the Amiga's page is `#424242` — and it is not currently red only because nothing in this group happens to read a palette-dependent value while one of the two is writing.

### `v6_state` group — benign today, silent trap tomorrow

`v6_hardware_palette` sets the palette and is the ONLY palette user in its group, so it races nothing right now. Guard it anyway: the next suite added to that group collides with no warning, and the whole point of the shared lock is that a suite should not have to audit its binary-mates.

### `crates/zvm/tests/amiga_palette.rs` — check, do not assume

Its own header says *"Its own test binary on purpose. `zvm::screen::set_palette` is process-wide…"*, which is a real and correct isolation argument at the BINARY level. But it holds **four `#[test]`s** and sets the palette twice — `Palette::Amiga` at line 115, `Palette::Standard` at line 130 — and cargo test runs those four in parallel threads of that one process. Verify whether the two writes and every palette-dependent assertion sit inside a single test (fine) or are spread across tests (a race the file's own argument does not cover). `zvm` takes zero external dependencies, so any lock here is `std::sync::Mutex` and local to the test file.

## Verifying a fix

`cargo nextest run` **cannot** answer this — per-test processes make the race structurally invisible (CLAUDE.md now records this). Use CI's own command:

```sh
cargo test --workspace          # must exit 0
cargo test -p app --test v6_zork0
```

A single green run is weak evidence for a scheduling race, so make the change and confirm the reasoning holds rather than trusting one pass. The strongest check is mechanical: after the fix, every file calling `zvm::screen::set_palette` outside `crates/app/src/startup.rs` and `crates/zvm-cli/src/main.rs` (both production, single-threaded, one machine per run) should also reference a lock.

## The real answer, still

As SQ-0904 records: `standard_true_colour_in(n, palette)` would let callers resolve a colour without laundering it through process state, making the race impossible rather than excluded. A `zvm` API change, larger than this quest, and the thing that would retire the lock altogether.

## Done — two of the three files needed the lock, the third did not, and a case now enforces the rule

Commit 2dabe883. `cargo test --workspace` exit 0 (50 binaries, 5596 tests, matching nextest's 5596); clippy clean; gate 0.

### The app suites

| suite | set_palette in | fixed |
|---|---|---|
| `v6_mac_input_echo` | `mac_at_prompt` helper | all 4 cases guarded |
| `v6_macintosh_profile` | `launch` helper | all 8 cases guarded |
| `v6_hardware_palette` | `boot_named` only | the 5 cases that stand up a session |

`v6_hardware_palette`'s other two cases (`a_hardware_palette_archive_has_no_adaptive_pictures`, `a_cga_archive_reports_itself_monochrome_and_the_others_do_not`) take nothing: they parse `InfocomPics` and call `native()` and touch no process state at all. Its `boot()` helper — used by four of the five guarded cases — does NOT set the palette, and its assertions read `pictures_canvas`, which is archive pixels rather than anything `zvm::screen` resolves, so those cases are palette-independent in substance and guarded for the reason the quest gives: a suite should not have to audit its binary-mates.

### `crates/zvm/tests/amiga_palette.rs` — verified, and correct as it stood

The quest asked to check rather than assume, and the assumption was wrong in our favour. It holds **three** cases, not four. Both `set_palette` calls AND every assertion that reads the global — `palette()`, `standard_true_colour()`, `grey_rgb()`, all three of which resolve through `ACTIVE_PALETTE` — sit inside `the_palette_defaults_to_standard_and_moves_every_resolver_together`, which also restores Standard at the end. The other two cases use only `amiga_true_colour` and `zmsd_true_colour`, which are pure `match` tables reading no process state. Cargo's parallel threads have nothing to race over, so the file's binary-level isolation argument holds and no lock was added. The measurement is recorded in its header, with the condition that would break it (a case here that reads the global) named explicitly.

### The part that outlives the sweep

`crates/app/tests/suites/palette_lock_discipline.rs`, wired into the `engines` group. It reads `tests/suites/*.rs` and asserts that any file containing `zvm::screen::set_palette` also contains `V6_PALETTE_LOCK`, with `setters >= 25` as a non-vacuity floor so it cannot pass by matching the wrong string or looking in the wrong directory.

Source-level on purpose: there is no runtime signal available. An unguarded setter produces a green run until its scheduling happens to interleave, then produces a failure in a DIFFERENT suite, and `cargo nextest run` cannot observe it at all. Falsified by reverting `v6_macintosh_profile` to a private `static PALETTE: std::sync::Mutex<()>` — the exact SQ-0904 shape, which still compiles and still locks something — and the case names that file. The failure message carries the two lines to add.

CLAUDE.md's shared-process-race paragraph now points at it.

### Unchanged and still the real answer

`standard_true_colour_in(n, palette)` would let callers resolve a colour without laundering it through process state, making the race impossible rather than excluded, and would retire the lock and this discipline case together. A `zvm` API change, still larger than this quest.
