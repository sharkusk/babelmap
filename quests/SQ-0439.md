DESIGN COMPLETE — settled with the user 2026-08-12. Implement this; do not redesign it.

SHAPE: detect and SUGGEST, never act (see the previous note for why auto-peel was rejected).
A prompt offers three outcomes: PEEL / IGNORE / MARK FOR LATER.

"Mark for later" is NOT a list, a badge or a new command. It simply RE-ARMS the prompt for the
next crossing of that seam. The three options are then a gradient over one mechanism —
peel now / ask me again next time I come through / never ask about this seam — and the only
state is a per-seam flag with three values, persisted with the map as layer metadata already is.

TWO INDEPENDENT TRIGGERS, one prompt, one memory:

1. STRUCTURAL
   - GATE: the region on the far side of the seam is reachable ONLY through portal edges
     (in/out/up/down) — no in-plane path back. A cellar reached only by `down` qualifies; a
     balcony you can also walk to does not.
   - FLOOR: the region is >= 4 rooms. (User's number. It exists only to suppress trivial
     prompts.) Compute the region with `peel_region`, which already answers "the region on the
     far side of a portal seam" — so the suggestion cannot disagree with what the peel would do.
   - TIMING: prompt when the player steps back ACROSS the seam, not mid-exploration. You finish
     the cellar, climb the stairs, and THEN the map asks. If the player never comes back, they
     are never asked — deliberately conservative. There is NO "hasn't grown in K turns" fallback.

2. SEMANTIC (the user's addition)
   - Room name matches /\bmaze\b/i — word boundary, case-insensitive, so "Amazement" and
     "Amazed" do not trip it.
   - Fires on the TRANSITION into a matching room from a NON-matching one — one prompt per
     entrance, silence inside. Zork I's maze is ~15 rooms all named "Maze"; prompting in each is
     the nag failure this design exists to avoid. The transition is also exactly the seam a bare
     `peel-layer` cuts ("the passage you just walked in through", SQ-0552), so trigger and
     action agree by construction.
   - BYPASSES the floor and the timing rule. Those exist because structural evidence is weak at
     first contact; the name IS the evidence and is available immediately.

ACCEPTING A NAME-TRIGGERED PEEL ALSO SETS THE MAZE FLAG. A peel from the structural trigger
does NOT. (User's call: the player confirmed it is a maze by accepting a prompt that said so.)

MEMORY: an ignored seam stays ignored; a layer that was merged back is never re-suggested.
Persisted with the map.

PROMPT MECHANICS: the project's standing dialog conventions — shared chrome, Tab/Shift-Tab to
move focus, Enter activates, Esc cancels (Space is widget-reserved). Must not steal focus
mid-turn.

STILL OPEN (ask the user, do not assume): whether a layer already flagged as a maze is exempt
from the STRUCTURAL trigger. It was proposed and not contradicted, but not explicitly confirmed.

PREREQUISITE: SQ-0826 removes the old asymmetry-based detector (`tangles`/`offer_maze_layer`,
SQ-0666), which is the same detect-and-suggest idea on evidence that fires late, never, or on
an ordinary ring of rooms. Do not resurrect it, and do not build on `matrix::tangles`.

## The manual half: peel and merge anchored on a SELECTED room

The user's original complaint, verbatim: "the issue i've had with peeling is that the peel direction is not clear, especially since we need to specify the peel based on the edge direction. and if the edge is one way into the room we want to peel there is no direction to select."

**The diagnosis is that today's `peel-layer [direction]` is anchored on the room you are STANDING IN.** So to peel the area you are in you must name the direction pointing back OUT of it, which is inverted from how the player is thinking; and if you arrived through a one-way passage there is no direction to name at all — which is exactly why `peel_across(.., true)` had to exist as a separate path for the bare command (SQ-0552). Re-anchoring on a SELECTED room dissolves all of it. `state.selected_room` already exists and already carries `RenameRoom`, `EditNotes` and the room dock.

**Which side of the seam gets peeled: the side of the SELECTED ROOM. Always.** This is not a new rule — `peel_at_edge(from, dir)` already peels `from`'s OWN region. The room is the anchor; the edge is only the seam. No preview, no flip, no disambiguation UI.

**How the seam is chosen, in three tiers — no edge selection required:**

1. **Portal boundary.** `peel_region(selected)` walks out across compass edges and stops at portal edges (no grid offset — up/down/in/out). That is a floor, and it needs no input beyond which room was picked. The common case.
2. **The unique inbound bridge.** When the region is not portal-bounded, `planar_region` walks straight through and `peel_region` refuses `WholeLayer`. Then look at the bridges INCIDENT TO THE SELECTED ROOM, oriented as arrivals — passages from outside INTO it. Exactly one → cut it, and SAY what was cut. One-way inbound edges are included, which is precisely the case that previously had no direction to name.
3. **Pick-list.** More than one inbound bridge → offer them by name ("north, to Forest Path").

The user's ruling, verbatim: "auto-pick when unambiguous, ask only when not. and the pick-list should be based on paths coming into the selected room."

**Why edge selection is NOT needed, and this is the load-bearing observation:** a peel can only ever cut a BRIDGE. `peel_at_edge` refuses `NotASeam` when "its two ends stay connected by some other route, so cutting it separates nothing." So the set of legally cuttable edges is exactly the bridges out of the region — computable, usually tiny, often one. Pointing at an edge cannot select anything outside that set, so edge selection would buy ergonomics and nothing else. Deferred.

**Consequence of anchoring on the entrance:** selecting a room in the MIDDLE of a maze offers no inbound bridge, so it falls back to the portal-boundary peel or refuses. The user was told this explicitly and did not object. The anchor is the entrance room, not any room in the region.

## MERGE GENERALIZES; there is no `move-room`

The user spotted the redundancy: "we have the command merge already, so we should standardize on move or merge, probably don't need both."

The real gap found on inspection is one of GRANULARITY, not naming: `peel-layer` is region-granular (takes a region out, makes a layer) while `merge-layer [target]` is layer-granular (puts a WHOLE layer into its parent or a named one). They are therefore not inverses — there is no way to say "put just this room into that layer", and a peel that grabbed one room too many can only be fixed by merging the whole layer back and re-peeling.

So: `merge-layer` keeps its current meaning, AND merge also accepts the selected room or its region — "put this into that layer". Peel and merge then become true inverses at both granularities, and no new verb is introduced. Grid-position nudging was offered as an alternative meaning for `move-room` and was NOT chosen; it is not part of this quest.

## Prompt UI and persistence

* **Shared-chrome modal**, chosen over a non-blocking map-pane offer and over the room dock. Standing dialog conventions apply: Tab/Shift-Tab moves focus, Enter activates, Esc cancels, Space stays widget-reserved. It must not steal focus mid-turn.
* **Deferrals AND refusals persist** into the archive with the map. A restored game must not re-ask about a seam already declined. Consistent with "persist the recipe": these are player DECISIONS, not derived state, so they cannot be recomputed and must be carried.

## Reminders that still bind

* Every new UI element needs a `style.toml` selector (ColorScheme field + `style.rs` selector + render apply). The modal and any peelable-edge or seam affordance are new elements.
* SQ-0826 removed the old asymmetry-based detector (`tangles`/`offer_maze_layer`, SQ-0666). Do not resurrect it and do not build on `matrix::tangles`.
* Layers are still created and destroyed ONLY by explicit peel/merge. Detect-and-suggest preserves that invariant literally; auto-peel was considered and rejected.

DESIGN AMENDMENT — 2026-08-13, and it SUPERSEDES the "merge generalizes" paragraph in the note above. Read this as the final word on the peel/merge surface.

## The user's insight

Verbatim: "peel and merge are actually the same thing. the only difference is that merge needs the name of an existing layer. so, maybe we generalize peel to also allow selection of an existing layer (if more than one already exists), or 'new layer'."

Checked against the code and it holds. Both operations are "re-home a set of rooms onto a layer". The three apparent differences are narrower than they look:

* **The room set** — peel computes a region (portal-bounded, or cut at a bridge); merge takes a whole layer. Same shape either way: a set of rooms.
* **The target** — peel mints a new layer; merge names an existing one. That is a PARAMETER, which is the whole insight.
* **Position reconciliation** — the ONE real asymmetry. `merge_layer_into` calls `occupied_cells_in_layer(target)` and reconciles grid positions so rooms do not land on top of each other; peeling into a fresh layer cannot collide. The unified operation needs collision handling on the existing-layer branch only.

**Neither direction destroys topology, which is what makes the unification safe.** `peel_at_edge`'s doc says it "severs" the passage, but `region_with_cut` uses the cut only as a PREDICATE while walking — nothing is deleted, and the passage survives as a cross-layer connection.

## The refusals simplify, which is the tell that the model is right

* `WholeLayer` ("the region spans its whole layer") stops being an error whenever the target is an EXISTING layer — moving a whole layer's contents into another layer is exactly a merge. It refuses only against `new`, where it would be a no-op rename.
* `MainSource` ("main cannot be a merge source") becomes the more general and more accurate **"you cannot empty `MAIN_LAYER`"**. Moving a region out of main stays legal, as it already is.
* `NotASeam` and `LeavesLayer` attach to COMPUTING THE REGION, and are now visibly separate from the move itself — two concerns currently tangled in one function.
* `SelfMerge` (target == source layer) still refuses.

## DECISION: collapse to one verb — `move-region <new|layer>`

The user chose the full collapse over keeping both names as entry points and over adding a third name with aliases: **`peel-layer` and `merge-layer` are RETIRED.** Pre-release is the only time this is affordable, and it is affordable — verified: neither verb has a default keybinding in `config_template.rs`. The cost is one paragraph in `docs/features/mapping.md`, the two `CommandSpec` entries in `slash.rs` and their parser tests. The hits under `docs/superpowers/` are historical plan and spec records and MUST NOT be rewritten.

`move-region new` carves a fresh layer. `move-region main` folds back into main. **Bare `move-region` auto-picks when there is only one possible target and asks when there is not** — the same rule the user chose for seam selection, now applied to the target as well. So both the seam AND the destination follow "auto-pick when unambiguous, ask only when not".

Name chosen over `set-layer` and `move-rooms`. "Region" is already the term `docs/features/mapping.md` uses for what peel carves off, so it introduces no new vocabulary.

## What this does NOT change

The detector's prompt is unaffected. An auto-suggestion always means "separate this out", i.e. target = new, so the peel/ignore/mark-for-later prompt keeps exactly the shape settled above. The unification is about the MANUAL surface.

Supersedes: the previous note's "MERGE GENERALIZES; there is no `move-room`" section. The conclusion there (one operation, both granularities) survives; the surface described there (keep `merge-layer`, teach it regions) does not.

DESIGN AMENDMENT 2 — 2026-08-13. Two corrections/additions the user raised after the unification note. Both settled.

## (1) The seam tiers belong to the REGION step, not the `new` branch

**Correction to the earlier note, which scoped them to peeling.** Under the `move-region` unification the region is computed identically whatever the target is, so the three-tier seam selection — portal boundary → unique inbound bridge (auto-cut, and SAY what was cut) → pick-list of inbound bridges — applies to EVERY region computation, including a move to an existing layer. The user's words: "we still need a detector and prompt when moving a region to an existing layer for the non-obvious compass cases."

The "non-obvious compass case" is exactly the one where `planar_region` walks straight through in-plane edges and hands back the whole layer, so tiers 2 and 3 are the whole mechanism there.

## (2) The auto-suggest may propose an EXISTING layer as the destination

Previously recorded as "an auto-suggestion always means separate this out, i.e. target = new". **That is now wrong** — the user chose "both". The detector can also notice that a region belongs on a layer that already exists.

**Why this case exists at all, and it is the load-bearing fact:** new rooms are always discovered on the ACTIVE layer (the user corrected an earlier wrong claim of mine on exactly this point — new rooms do NOT go to `MAIN_LAYER`; `layout/incremental.rs` inherits the layer from the previous room). So the classic failure is: peel a cellar, keep exploring, and rooms that are in-plane neighbours of the cellar land on whatever layer was active instead — structurally part of a layer they are not on. That is a "non-obvious compass case" and it is detectable.

**THE HOME RULE (chosen over two stricter/looser alternatives):**

> A layer B is a candidate home for region R on layer A when R has COMPASS (grid-offset) edges into B. Rank candidates by edge count.

* **Portal edges NEVER nominate a home.** They are what separates layers in the first place, so a cellar reached by `down` must not be suggested as the home of the room above it. This is the rule's whole point and the thing an implementer is most likely to get wrong.
* Rejected — "only when A has no compass edge of its own": too strict, misses partially-attached regions.
* Rejected — "also weigh grid adjacency": layout position is derived by the router and can shift, so a suggestion could change without the map changing. Evidence must come from topology, not from layout.

## Consequence for the prompt shape

The prompt settled earlier had three outcomes (peel / ignore / mark-for-later). When a plausible existing home is found it gains a destination choice — offer the ranked candidate(s) alongside `new`. Still one modal, still shared chrome, Tab/Shift-Tab + Enter, Esc cancels. The three-value per-seam memory (peel now / ask again next crossing / never ask) is unchanged; a destination choice does not add a fourth memory state.

Manual and automatic flows keep their distinct rules: bare `move-region` AUTO-PICKS the target when only one is possible and asks otherwise, while the detector always prompts — it is detect-and-SUGGEST, and it may never act on its own.

`Mapper::take_suggestion() -> Option<LayerSuggestion>` is the app-facing hook. `Mapper::observe_inner` runs `on_arrival` on every real move (and only there — a self-loop and `observe_relocation` clear it), so the app needs no polling: after `apply_turn`, take it. Nothing in `app` calls it yet — that wiring plus the modal is Lane D.

Accepting = `move_region(graph, &suggestion.region, chosen_destination)`. A NAME-triggered accept must ALSO `set_layer_maze(landed, true)`; a structural one sets nothing. `trigger` is on the suggestion for exactly that.

Memory: `graph.seam_decision(key)` / `set_seam_decision(key, d)`. Setting `Armed` forgets the entry. Lane D writes `Deferred` for "mark for later" and `Ignored` for "never".

## Decisions taken inside the settled design

* **Timing is expressed as discovery order**: `seq(to) < seq(from)`. "Steps back across the seam" needed a mechanical test and `Room::seq` is the only thing that knows which side of a boundary came first. Conservative side effect: climbing out into a room you have never seen does not fire (it fires next time through).
* **The structural crossing must be Up/Down/In/Out**, not merely "no grid offset" — new `direction::is_portal`. `Unknown` is a passage whose direction was never learned, not a portal.
* **`move_region` onto an EXISTING layer records `Ignored` for every boundary passage**, both orientations. That is where "a layer merged back is never re-suggested" lives; it is in the mapper so no caller can skip it.
* **A suggestion with no legal destination is never made.** `destinations` mirrors `move_region`'s own refusals, so nothing offered can be turned down.
* **`region_is_whole_layer` moved out of `input.rs` into `layer::is_whole_layer`** (pub). The detector and the command must not be able to disagree about what a whole layer is. Two call sites in input.rs now delegate; no behaviour change.

## Persistence

`PersistState.seams: Vec<SeamRecord { from, dir, decision }>` — a flat list, because a room+direction pair cannot be a JSON object key. `from_json` calls `graph.restore_seam_decisions`, which drops entries naming a room the map no longer has (same hygiene as connections/`current`/`last_visited`). `rekey_room` re-keys them too, or a dismissed prompt would come back from the dead. `persist.rs` no longer builds a `Mapper` literal — use `Mapper::restored(graph)`.

## Nine falsifications, all reproduced

gate, floor, timing, maze exemption, `\bmaze\b` boundary, maze transition, portals-never-nominate-a-home, the memory (in-session and across a reload), and the merge-back silencing. Two notes worth keeping:

1. **The GATE was initially unfalsifiable** — my first balcony fixture was blocked by the whole-layer check in `destinations`, not by the gate, so removing the gate changed nothing. Fixed by giving the fixture a room outside the region. A negative test that passes for the wrong reason is worth exactly nothing; check WHICH rule is doing the work.
2. **An earlier timing formulation ("every region room has seq > seq(to)") strictly subsumed the gate**, making the gate dead code. `seq(to) < seq(from)` is independent of region membership and says the same thing more simply.
