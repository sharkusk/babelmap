--- note 2026-08-10T02:06:27Z ---

THE ARGUMENT, from measurements already taken this session.

Blorb signals adaptivity with a top-level `APal` chunk listing picture numbers whose own palette is a placeholder to be ignored in favour of the **Current Palette** — the palette of the most recently drawn non-adaptive picture (Blorb §11.3). `Zork0.blb` lists **172** such pictures (ids 9..485). `crates/app/src/graphics.rs` implements this, and SQ-0720's 38930-row oracle proves our implementation matches Infocom's own converter exactly.

**A native Infocom archive has no `APal` chunk — the format has no such concept.** What it has instead, measured directly from `stories/zork0.pic` (SQ-0713's format notes): each 14-byte directory record carries a **3-byte palette offset**, and **279 of 495 records have that offset set to zero**. A picture with no palette of its own cannot be drawn except through whatever palette is current. That is the same mechanism expressed differently — the native format's own way of saying "adaptive".

So if `PictSource`'s native path resolves each picture through its own palette bytes and treats "no palette" as something other than "use the current one", every adaptive picture off native media renders with wrong colours — which is exactly the user's report: drop caps and room icons now appear (SQ-0741) but the room icon comes out **yellow/green**.

WHY THIS MATTERS SEPARATELY FROM SQ-0740: the user attributed the wrong colour to the pending Amiga colour-register work. It may be that, but this would produce the identical symptom by a different route, and fixing the registers would leave it wrong. **Check this first — it is cheaper and more specific.**

FIRST MEASUREMENT: for the room icon Zork Zero draws inline, dump (a) its native directory record's palette offset, (b) the palette our native path actually resolved it through, and (c) the Current Palette at draw time. If (a) is zero and (b) is not (c), that is the whole defect.

CONSTRAINTS: the Blorb path must stay byte-identical — SQ-0720's oracle is the guard and must keep passing. Prefer feeding the native source into the SAME Current-Palette machinery `graphics.rs` already runs for `APal` rather than building a parallel native-only palette path; two mechanisms for one concept is how the hybrid/raster divergences in this codebase began.

RELATED: SQ-0740 (Amiga colour registers, which also recolour artwork on a real Amiga), SQ-0741 (the inline floats that made these pictures visible at all), SQ-0713 (the decoder and the format notes cited above).

--- note 2026-08-10T02:08:24Z ---

STRONG CORROBORATION, user 2026-08-09: **"as i progress throught the rooms in amiga's zork0, the compass direction colors get painted the wrong colors (i.e. bright blue)"**.

The *progressive* character of it is the fingerprint. An adaptive picture takes the palette of the most recently drawn non-adaptive picture. Zork Zero draws a new room illustration as you walk, each setting the Current Palette; the compass needles are adaptive (they are in the `APal` set, ids 9..485). So a compass whose colours **change as you move between rooms** is the adaptive-palette mechanism operating — and operating with the wrong palette. A static miscolouring would have been weaker evidence; a drifting one is close to diagnostic.

Note this is not "the compass should not change colour". On a real Amiga it changes deliberately — that is what adaptive palettes are FOR, so the compass matches the scene it sits beside. The defect is that it resolves to the wrong colours (bright blue), not that it varies.

That makes this quest, not SQ-0740, the likelier cause of every wrong-colour report from native media, and it should be done first. SQ-0740's colour-register semantics are real and separately justified (Infocom's own `set_color` moves registers 0/1 and recolours everything painted in those pens), but they would not produce a per-room drift keyed to which illustration was drawn last.

REFINES THE FIRST MEASUREMENT already recorded: take it across TWO rooms, not one. Dump the compass picture's native palette offset, the palette our native path resolved it through, and the Current Palette at draw time, in room A and then again in room B after moving. If the Current Palette changes between rooms while the palette we render the compass with does not — or changes to something that is not it — the resolution path is the defect and the fix is to feed the native source into the same Current-Palette machinery `graphics.rs` already runs for `APal`.

--- note 2026-08-10T02:10:35Z ---

REFINEMENT, user 2026-08-09: **"the original n/s/e/w compass colors are okay (other directions are off), but any newly painted directions get the wrong color"**.

So the compass pieces drawn EARLY are correct and the ones drawn LATER are not. That is more specific than "the compass drifts", and it splits the hypothesis in two — with a cheap test that distinguishes them.

**Reading A — we are adapting a picture that is not adaptive.** If the compass arrows carry their OWN palette in the native archive (non-zero palette offset in their directory record), they must be drawn through it and never through the Current Palette. Early arrows would then look right by luck — the Current Palette at boot still being the one they want — and every arrow drawn after a room illustration changed it would come out wrong. This is the reading the user's wording fits best, and it inverts the quest's original framing: the bug would be that we adapt too MUCH, not too little.

**Reading B — we are adapting correctly but sourcing the wrong palette.** If the arrows genuinely have palette offset 0, they are adaptive by the format's own convention, and the defect is which picture we treat as the Current Palette's source. Compare: the compass ROSE is drawn once with its own palette, and arrows drawn straight after take it and look right; once a room illustration lands, our "most recently drawn non-adaptive picture" becomes the room, and later arrows take the room's palette.

**THE TEST THAT SEPARATES THEM IS ONE LOOKUP: read the compass arrow pictures' palette offsets from `stories/zork0.pic`'s directory.** Non-zero → Reading A, and we must stop adapting them. Zero → Reading B, and the question becomes which picture sets the Current Palette. Do this before anything else; it is a few lines against a file already parsed by `blorb::infocom_pics`.

Worth noting for either reading: 279 of 495 native records have a zero palette offset and 216 do not, so the format plainly distinguishes the two cases, and the distinction is per-picture. Any fix must respect it per-picture rather than treating "native archive" as a mode.

Also note the user says the ORIGINAL n/s/e/w are fine while OTHER directions are off — the diagonals and up/down. Those are different picture ids from the cardinals, so their palette offsets may differ too; check the whole set, not one arrow.
