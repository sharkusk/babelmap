--- note 2026-08-10T02:56:46Z ---

MEASURED by SQ-0746's agent, reported as found-not-fixed:

`Machine::v6_input_window` is not written into the host archive. A Restore State taken while a game is waiting on a read through a secondary panel comes back with `input_window` 0, so `BufferWindow::reads_input` is false and the typed input is not echoed until the next read re-establishes it. Everything else on that frame restores correctly, and after SQ-0746 the restored panel does at least show its prompt where it previously came back blank.

Pre-existing since SQ-0585 — the divert rule already depended on this field before SQ-0746 made the echo depend on it too; SQ-0746 only made the consequence visible.

This is squarely the "persist the recipe, not the result" rule from CLAUDE.md: `v6_input_window` is an input to what the screen must show, and Quetzal saves no screen state by design, so carrying it is ours to do. Note the repo's restore-test convention when this is picked up — restore tests must PERTURB before asserting: restore, then make a move (here, type at the restored prompt), then assert. Asserting the frame immediately after the restore is exactly when everything still looks correct. Cover restoring into a different terminal size and a different graphics backend.

--- note 2026-08-10T23:20:39Z ---

Found but NOT fixed (out of scope for this quest): `GameSession::paint` (the "erase_window fill" painted ground, `Engine::paint_surface`) is not part of the `.babelmap` archive at all — no field in `ScreenDto`/`ArchiveContents`, no reconstruction in `restore_screen`/`load_pictures_png`/`load_display_list`. Confirmed empirically: after a real Save State round-trip of fmvpoker.z6 (save via `save_archive_meta_pics`, restore via `restore_state`+`restore_screen`+`load_pictures_png`), `Engine::paint_surface(&fresh)` returns `None` while the pre-save session's returns `Some`.

Consequence: `fill_story_page_under_chrome_text` (crates/app/src/render/v6_layout.rs) unconditionally paints the story's declared page over any pixel not covered by `chrome_text_rects` (the panel's own static printed lines) or by the painted ground. The live input-echo cell drawn by `draw_secondary_prose` (SQ-0746) is NOT part of `chrome_text_rects`, so on fmvpoker's bet panel specifically, after ANY v6 Host Save State restore, the panel's live typed-input echo is overpainted invisible by the page fill — regardless of whether `v6_input_window`/`reads_input` is correctly restored (verified both ways: the model's `reads_input` flag is correct post-restore, yet the full-pipeline composite still shows no echo). This is a second, independent cause of "no echo after restore" on top of SQ-0749's own defect, and it will still reproduce even with SQ-0749 fixed, until the game's next `erase_window` repaints the ground.

Root cause is architectural: `paint` accumulates host-side from `EraseFill` events during play and is never part of the archive's persisted "recipe" (screen.json / display.json / pictures). Fixing it would mean either persisting the painted-ground image/ops, or reconstructing it from the display list on restore. Left alone per this quest's "do exactly this and nothing more" scope; SQ-0749's own test (`crates/app/tests/v6_restore_input_window_echo.rs`) works around it by asserting through `draw_secondary_prose` in isolation (a blank canvas) rather than the full `build_v6_raster_canvas` pipeline, since the full pipeline is confounded by this separate gap for fmvpoker's specific panel.
