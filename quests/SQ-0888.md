--- note 2026-08-15T15:02:26Z ---

MEASURED, read-only diagnostic lane. Both defects reproduced and diagnosed; they are NOT the same bug as each other.

THE FIXTURE, NAMED EXACTLY. The Apple II press that runs is the FIVE-VOLUME 5.25-inch set `stories/shogun_s1.dsk` … `shogun_s5.dsk` (143,360 bytes each, DOS sector order, ProDOS volumes SHOGUN.1…SHOGUN.5), reassembled by `blorb::infocom_packed` into **Shogun release 311 / serial 890510**, header checksum `$E200`, 344,224 bytes. The game narrates it: "Release 311 / Pix 311 / Serial number 890510" and "Apple IIgs Interpreter version 6.65". Its art is `SHOGUN.D1`, Apple flavour, 55 entries, picture space 140x192, `art_scale` (4,2) → a 560x384 screen. Save directory `shogun-r311-s890510.save`.

**`stories/Shogun.po` IS NOT THAT PRESS AND DOES NOT RUN.** It is a DiskCopy 4.2 image (838,484 = 84-byte header + 819,200 data + 19,200 tag bytes, name field `06 "SHOGUN"`), which `blorb::prodos` declines by design — `MountedDisk::mount` answers `NotADiskImage` (documented at `crates/blorb/src/prodos.rs:52`). What babelmap then does with it is a SEPARATE HAZARD worth its own quest: the DiskCopy name-length byte `0x06` is read as the Z-machine VERSION byte, so the whole disk image is opened as a bogus Version 6 story, paired with `stories/Shogun.blb`, and dies instantly — measured final screen: "babelmap: loaded resources from stories/Shogun.blb (sidecar) (0 sounds, 48 images)" then "babelmap: story ended without asking for input." A wrapper we decline should be refused, not mistaken for a story.

── Q1: DEFECT 1 IS THE SAME BUG AS SQ-0886. Same cause, same fix. ─────────────

Captured at 100x40 (8x18 cells, kitty negotiated), map hidden, `--keys "wait:3500,space,wait:3000"`, on the build BEFORE SQ-0886's fix landed in the tree:

  APPLE II (`shogun_s1.dsk`, r311/s890510), hybrid: **ZERO kitty placements.** One 784x537 RGBA image is transmitted and no U+10EEEE placeholder cell is ever printed, so a real terminal draws no image at all (the oracle agrees: "a real terminal would draw no image on this screen"). The frame is all painted cells: `#000000` on cell rows 1..9 across cols 1..98 (the credits), `#000000` on rows 25..27 cols 25..45 (the menu box), terminal default everywhere else.
  AMIGA (`James Clavell's Shogun.adf`, r295/s890321), hybrid, same conditions: **ZERO kitty placements** likewise; `#000000` on cell rows 1..9 across cols 1..98, `#424242` (colour 12) on rows 10..37, menu box black at rows 10..12 cols 30..50.
  Both raster: one full-frame placement (Apple 784x537 at rows 4..33 cols 1..98; Amiga 784x490 at rows 5..32 cols 1..98). Correct.

SQ-0886's recorded number is the SAME measurement in device pixels: cell rows 1..9 at 18 px/row IS device rows 18..179, and cols 1..98 at 8 px IS 784 of 800 columns (the note said 761). So the ProDOS press fails identically; the only differences are cosmetic — the Apple machine's page resolves to the terminal default where the Amiga's is `#424242`, and the two builds park window 0 in different places (Apple win0 = (1,257) 560x96, Amiga win0 = (1,337) 640x64), which moves the menu box's rows.

The mechanism, confirmed in code: `has_menu` (screen.rs, the SQ-0484 gate) routes a menu takeover to the CELL path, and the cell path draws no art. The row-classifier compounds it — `decompose_chrome_strips` (screen.rs:5063) classes a full-width band row `Text` when its runs are not over opaque art, and Amiga picture 3 is a HOLLOW frame (320x200, 14% opaque, exactly 46 opaque columns on every row = the two ornate side panels), so the centred credits are never "over art" and each of their rows becomes a full-width Text strip that paints edge to edge over the panels' own columns. That is SQ-0886's "we are painting OVER them", made exact.

**AND THE IN-FLIGHT SQ-0886 FIX ALREADY FIXES THE PRODOS PRESS.** I rebuilt against the parallel lane's uncommitted `menu_over_art` edit and re-captured: the Apple credits screen now takes the composite — a single 784x537 placement at rows 4..33 cols 1..98, byte-for-byte the geometry raster produces — and the PNG shows the red/gold decoration strips top and bottom with the credits and the START/RESTORE/QUIT menu between, which is exactly what the user reports raster doing. The Amiga likewise now places 784x490 at rows 5..32. Defect 1 needs no separate fix; it needs SQ-0886 to land, and this press should be named in its regression test.

── Q2: DEFECT 2 IS SEPARATE AND UNFIXED. Root cause below. ────────────────────

Still reproduces with the SQ-0886 fix applied (verified). In play the Apple press draws its room illustration into a CHROME GRAPHICS WINDOW THAT OVERLAPS THE STORY WINDOW, and hybrid's ring only ever draws the pane MINUS the story viewport, so all but the top sliver is discarded.

The display list, read out of a host Save State (`display.json`) on the opening Bridge scene:
  win7 (1,1) 560x384 : Draw #3 @(0,0), Draw #3 @(0,352), Erase(0,64,560,320), Erase(0,0,560,32)   ← the two header/footer rules
  win6 (1,33) 560x352: Draw #4 @(0,0), Erase(0,32,560,320), **Draw #7 @(248,0)**                   ← the room illustration
  anchors: win6 origin (1,33) w=560 h=348; win7 origin (1,1)
And the v6 turn snapshot: win0 (story) pos=(1,65) size=560x320; win1 (status) (1,1) 560x32; win6 (1,33) 560x352 canvas z=17; win7 (1,1) 560x384 canvas z=5. There is NO `canvas win0` at all.

Picture 7 is 78x174 in Apple picture-space units; `art_scale` (4,2) makes it 312x348 unit px, drawn at win6-relative (248,0) = screen native x 249..561, y 33..381. The story window starts at native y=65. So **316 of the picture's 348 rows (90.8%) lie inside the story window's box and are dropped; the surviving 32 rows (9.2%) are what the top chrome band shows** — measured as 13 placements, all at terminal rows 3..5 (three rows, 54 px), cols 1..98, and nothing else on the frame. That is precisely the "squashed up at the top" the user reports. Raster composites the whole canvas and shows the ship correctly (`apple_game_raster.png`).

THE DIVERGENCE, WITH ANCHORS:
1. `crates/app/src/session.rs:2026` `is_win0_inline_float` — `if ev.window != 0 || !intent { return false; }`. The Amiga r295 draws the same ship into WINDOW 0 with a `set_margins`, so it becomes a `Story`/`MarginRight` transcript float and hybrid renders it as per-row bands beside wrapped text (measured on the Amiga: 25 placements of 392x18 at cols 41..89, one per row, plus two 64x630 side flanks — the frame is perfect). The Apple r311 draws into window 6, so the gate rejects it and no float exists.
2. `crates/app/src/render/v6_layout.rs:283` `classify_windows` — `story_gfx` is only a `Graphics` window with `g.win == 0`. win6 is therefore CHROME.
3. `crates/app/src/render/v6_layout.rs:1540` `chrome_bands` — returns exactly the four bands of pane-minus-viewport. Chrome art inside the viewport has nowhere to go. This is the actual loss.
4. `crates/app/src/render/screen.rs:3936` `picture_takeover` and its arms `art_paints_anything` (:3955) and `story_plate_escapes_story_window` (:3995) are the existing escape hatch to the composite — but every one of them interrogates `story_gfx` ONLY. A chrome window painting inside the story box is invisible to all three, so the frame keeps a ring that cannot show it. SQ-0739 wrote the mirror-image rule ("the escaping art is in neither place") for the plate escaping the window; this is the same failure from the other side.
5. `crates/app/src/render/screen.rs:3292` — the pixels ARE captured: `transcript.json` carries an entry at line index 3, `align: InlineUp`, `source: ContentSplash`, and `transcript-img/0003.png` is the exact 312x348 ship. `build_main_text` skips every `ContentSplash` on the stated assumption that "hybrid/raster draw the graphics window itself". Hybrid does not draw this one.

SMALLEST REPRO (fresh user dir, `show_map = false` in `<ud>/saves/shogun-r311-s890510.save/config.toml`):
  cargo run -q -p app --example pty_capture -- --story stories/shogun_s1.dsk --user-dir <ud> \
    --size 100x40 --keys "wait:3500,space,wait:2500,cr,wait:4500" --png out.png
  BAD (hybrid): 13 placements, every one at rows 3..5; prose runs full width from row 6.
  GOOD (raster, `v6_render = "raster"` in `<ud>/config.toml`): one 784x537 placement at rows 4..33, ship intact.
Beware two traps that cost me runs: the per-game sidecar is keyed `shogun-r311-s890510.save`, NOT `shogun_s1.dsk.save` (the pty driver writes the wrong one, so the map pane stays open and halves the pane), and a user dir that already holds a save AUTO-RESUMES, which silently skips the credits screen.

SUGGESTED SHAPE FOR A FIX LANE (not implemented, not tested): the narrow, in-house-precedent option is a fourth arm on `picture_takeover` — a CHROME graphics window with opaque pixels inside the story window's box has no ring to live in, so the frame takes the composite. It is the identical rule SQ-0886 has just applied to menus and SQ-0725/0739 to plates. Whether Shogun's in-game frame is better served by the composite (loses crisp text) or by generalising the float capture at `is_win0_inline_float` (keeps crisp text and the Amiga's handsome wrap, but changes engine-side classification and would need the `ContentSplash` skip revisited) is a judgement call I deliberately did not make.

--- note 2026-08-15T16:47:16Z ---

ANSWERED BY THE USER 2026-08-15 — this settles the open question in the note above.

**The image MOVES UP as new text arrives.** Their description of the original: the start screen shows the prose on the right with a `[more]` prompt and the ship on the right; as more text renders it wraps around the BOTTOM of the ship art, scrolling both the prose and the ship upwards together.

That is a true inline float — the art is anchored in the text flow, not pinned to the pane. It is NOT "text wraps beside a picture that stays put", which is what the merged fix (`b6b70f3e`) currently does with its fixed ring placement.

**SO CANDIDATE (b) IS CORRECT AND THE LANE'S AUTHENTICITY ARGUMENT WAS BACKWARDS.** It rejected the float because "a window-0 float scrolls with the prose… whereas window 6's canvas is persistent" — and scrolling with the prose is precisely what the original does. The persistence of window 6's canvas in our display model was never evidence about the screen.

**THE REFERENCE IMPLEMENTATION IS ALREADY IN THIS CODEBASE.** The Amiga press r295/s890321 renders this exact scene the described way today, and it is measured: 25 placements of 392x18 at cols 41..89, one per row, beside wrapped text, plus two 64x630 side flanks — "the frame is perfect" per the SQ-0888 diagnostic lane. So this is not a fix to be designed from a description; it is a fix to be made by routing Apple r311 down the path Amiga r295 already takes, with the two compared frame by frame.

The two presses state one layout two ways, and the lane's own instrumentation shows the margins nearly agree:

| press | draw | `win0` at that moment |
|---|---|---|
| Amiga r295/s890321 | `pic 7 → win 0` at (229,1), `out_chars=526`, `margin_after=Some(2)` | (47,33) 548x368 **L2 R328** |
| Apple r311/s890510 | `pic 7 → win 6` at (249,1), `out_chars=21`, `margin_after=None` | (1,65) 560x320 **L0 R320** |

Two differences to handle rather than assume away: the Apple draws into window 6 (the `ev.window != 0` gate at `session.rs:2026` rejects it), and it sets its margin BEFORE the draw, so `margin_after` is `None` where the Amiga's is `Some(2)` — the float's anchor has to be derived from the margin in force, not from a margin the draw event carries.

THE MERGED FIX IS A WAY-STATION, NOT THE DESTINATION. `b6b70f3e` took the art from a 3-row squashed sliver to the ship at raster's proportions beside crisp prose, and it is a better base than the original code. But its fixed placement is now known to be wrong, so the float work should SUBSUME it, not stack on top of it — including its `story_text_box` narrowing and its ceded-flank exclusion from `v6_border::recognize`, both of which exist to serve fixed placement and may not be needed once the art is a float. Do not leave two mechanisms fighting over the same columns.

Also in scope to re-check: SQ-0891 (raster loses the prose entirely on this frame — window 6 composites above window 0) becomes load-bearing, because a float changes what raster composites.
