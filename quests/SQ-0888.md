MEASURED, read-only diagnostic lane. Both defects reproduced and diagnosed; they are NOT the same bug as each other.

THE FIXTURE, NAMED EXACTLY. The Apple II press that runs is the FIVE-VOLUME 5.25-inch set `stories/shogun_s1.dsk` … `shogun_s5.dsk` (143,360 bytes each, DOS sector order, ProDOS volumes SHOGUN.1…SHOGUN.5), reassembled by `blorb::infocom_packed` into **Shogun release 311 / serial 890510**, header checksum `$E200`, 344,224 bytes. The game narrates it: "Release 311 / Pix 311 / Serial number 890510" and "Apple IIgs Interpreter version 6.65". Its art is `SHOGUN.D1`, Apple flavour, 55 entries, picture space 140x192, `art_scale` (4,2) → a 560x384 screen. Save directory `shogun-r311-s890510.save`.

**`stories/Shogun.po` IS NOT THAT PRESS AND DOES NOT RUN.** It is a DiskCopy 4.2 image (838,484 = 84-byte header + 819,200 data + 19,200 tag bytes, name field `06 "SHOGUN"`), which `blorb::prodos` declines by design — `MountedDisk::mount` answers `NotADiskImage` (documented at `crates/blorb/src/prodos.rs:52`). What babelmap then does with it is a SEPARATE HAZARD worth its own quest: the DiskCopy name-length byte `0x06` is read as the Z-machine VERSION byte, so the whole disk image is opened as a bogus Version 6 story, paired with `stories/Shogun.blb`, and dies instantly — measured final screen: "babelmap: loaded resources from stories/Shogun.blb (sidecar) (0 sounds, 48 images)" then "babelmap: story ended without asking for input." A wrapper we decline should be refused, not mistaken for a story.

FIXED AS THE FLOAT, 2026-08-15, commit 85a57b27. b6b70f3e's machinery REMOVED, not stacked on.

THE ONE FACT THE EARLIER NOTES GOT WRONG, and it made the fix easier rather than harder: the Apple does NOT set its margin before the draw. The opcode trace on the Bridge turn reads, in order:

    @set_window(win6)
    @draw_picture(number=7, window=6, y=1, x=249)
    @set_window(lower)
    @set_margins(left=0, right=320, win=0)

That is the SAME idiom as the Amiga's — draw, then reserve the column — differing only in that the set_margins names window 0 explicitly while window 6 is still current. `PictureEvent::margin_after` is `None` purely because exec.rs:3321 only attaches a set_margins issued on the same window as the draw (`ev.window as u16 == win`). No engine-side change was needed: the host reads window 0's live margins at drain time.

THE CHANGE. `is_win0_inline_float` became `win0_inline_float_x`, answering with the picture's x INSIDE WINDOW 0 (not `ev.x`, which is relative to whatever window painted it). A new arm `ceded_margin_float_x` handles `ev.window != 0` and asks three things: the painting window must CONTAIN window 0's box; window 0 must hold a nonzero left/right `set_margins` reservation in force; and the picture must lie ENTIRELY inside the column that reservation gave up, overlapping window 0 vertically. `apply_picture_event` also now reads WINDOW 0's margins rather than the drawing window's (it was named `win0_*` and read `ev.window` — identical for every window-0 draw, wrong for this one).

REMOVED: `v6_layout::story_text_box` (+57 lines) and both ceded-flank exclusions from `v6_border::recognize` in screen.rs. With the ship out of window 6's canvas, `story_text_box` answers `None` on every corpus frame — measured: chrome opaque pixels inside window 0's box went 0 on the Apple Bridge at boot and every turn after. Dead, so deleted rather than left fighting the float for the same columns.
