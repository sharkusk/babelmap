--- note 2026-07-29T01:50:17Z ---

Early diagnosis (unconfirmed — needs a headless probe of Arthur's actual px_texts before fixing).

The frameless cell path in render/screen.rs splits chrome grid runs at native row 4 (`const STATUS_BAND_ROWS: u16 = 4`):
  - rows 0..4  -> `draw_anchored_status_band()` — reflowed into left/center/right anchor groups and drawn at the TOP of the pane, consuming `rows_used` from the story area.
  - rows >= 4  -> `draw_painted_screen(&runs, STATUS_BAND_ROWS, ...)` — stamped ABSOLUTELY at `area.y + native_row`, no reflow.

Arthur paints its status bar at NATIVE ROW 12 (already documented in the hybrid menu-detection comment near screen.rs:507: "Arthur paints its status bar at row 12 above a story buffer starting at row 13"). Row 12 >= 4, so the anchored band finds nothing, and the painted-screen overlay stamps the bar at terminal row 12 — matching the user's "floating about 25% from the top".

The threshold is a native-row constant, but Arthur's status bar is not near the top of the native screen; it sits directly above the story window. Likely correct rule: treat a full-width grid run band that lies immediately ABOVE the story window's top row as the status band regardless of its absolute native row, rather than gating on row < 4. Note the hybrid path already computes `story_rows` (story window top/bottom in native rows) for menu detection — the same value is available on the cell path via `layout.story`.

CAUTION: do not guess the geometry. Probe Arthur headlessly first and dump the actual (native row, text, window w_px) of every chrome run plus the story window's y_px/h_px, and confirm the bar's row and width before changing the split rule. Verify against BOTH the anchored-band tests and the Shogun/Zork0 painted-menu tests, which depend on the row-4 split.
