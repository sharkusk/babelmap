--- note 2026-07-29T21:26:29Z ---

`[map.overrides]` is a real, working feature — `parse_style_toml` reads it at `crates/app/src/style.rs:410-418` into `symbols.overrides`, `SymbolSet::resolve` consumes it, and it is pinned by `style::tests::map_overrides_still_beat_the_preset` (a slot override beats the `box_style` preset). It is the mechanism SQ-0560 deliberately chose as the ONE way to override a single map glyph.

But it does not appear in `style.example.toml` at all. The only occurrences of the string in the tree are in `style.rs` (the doc comment and a test). So a user reading the file we ship — the file `theme::template::commented_template()` generates and `template.rs:398` pins byte-for-byte — has no way to discover it.

This is mildly ironic given SQ-0560's reasoning: we removed the `glyphs = { … }` sub-map on the grounds that `[map.overrides]` already covers the job, while `[map.overrides]` is itself invisible in the reference file. Anyone who had found the (non-working) `glyphs` sub-map in the old embedded template text is now left with nothing they can see.

WHY IT IS NOT A ONE-LINE FIX: the example file is generated from `REGISTRY` rows, one line per selector. `[map.overrides]` is not a selector — it is a free-form TABLE keyed by glyph slot name, so it has no registry row and cannot be emitted by the generic row path. It needs a special case in `theme/template.rs`, in the same spirit as the existing ones for `map.layer_cycle` (list-valued) and `map.diagonal_corners` (bool-valued) at `template.rs:133-143`.

Also needed: the set of valid slot names is not documented anywhere user-facing. `map_overrides_still_beat_the_preset` uses `"arrow.north"`, so the keys are dotted slot paths. Whatever gets emitted should show at least one real example and point at where the full slot list lives (or enumerate it if it is short).

Check while there: `docs/features/mapping.md` and `docs/features/customization.md:65` both mention the `[map.overrides]` table — confirm their described key syntax matches what the parser actually accepts, since that mismatch is exactly the SQ-0558 failure mode.
