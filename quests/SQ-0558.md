PROVEN EMPIRICALLY by a throwaway test through the live path (`parse_style_toml` -> `finalize_symbols`):

    [symbols] box_style = "double"  ->  box_style = "double"   (works)
    [map]     box_style = "double"  ->  box_style = "rounded"  (the DEFAULT — silently ignored)

`style.example.toml` is the shipped user-facing reference (pinned by `style.rs:716` `style_example_toml_parses_and_resolves_clean`). It documents all five glyph presets under `[map]` — lines 133-137:
    # box_style = "rounded"
    # arrow_set = "filled"
    # portal_icons = "ascii"
    # path_style = "light"
    # portal_path_style = "dotted"
But `parse_style_toml` (`crates/app/src/style.rs:385`) reads them from `root.get("symbols")` and nowhere else. A user who uncomments a line in the file we ship gets no effect and no warning.

The reason the example file looks that way: `crates/app/src/theme/registry.rs:244-249` defines `map.box_style`, `map.arrow_set`, `map.portal_icons`, `map.path_style`, `map.portal_path_style`, with the comment "Glyph-set presets (the old [symbols] section, merged in)". `theme/template.rs:175-178` generates the example file's inline hints from those rows. So the NEW registry-driven schema moved the presets to `map.*`, the generated example followed — but the runtime never did. `render/map.rs` still consumes `SymbolSet`, built from `SymbolConfig`, built from the `[symbols]` section. Nothing resolves `map.box_style` from the resolved `Theme` at runtime (grepped: no consumer outside registry.rs / template.rs / toml_schema.rs).

So there are two half-finished halves of a migration. Decide which section is canonical, then make code and docs agree:
  (a) Finish the migration — resolve the presets from the Theme's `map.*` glyph slots and retire the `[symbols]` parser. Matches the shipped example file, no doc churn, but touches the render path.
  (b) Revert the docs — move the five presets back under `[symbols]` in the registry/template so the generated example matches the parser. Smaller, but concedes the registry unification.
Whichever is chosen, ACCEPT BOTH SPELLINGS for a transitional period only if it costs little — note the standing pre-release rule says formats may break old files freely, so a clean break is allowed.

WHY THE TEST SUITE MISSED IT: `style_example_toml_parses_and_resolves_clean` only asserts the file PARSES and resolves without error. Every preset line in it is commented out, so nothing exercises whether an uncommented `[map] box_style` actually takes effect. A test that uncomments a preset and asserts the resolved `SymbolSet` changed would have caught this.

Sibling: SQ-0557 (`diagonal_corners` never parsed at all). Both are parser/doc-surface mismatches in the same area and are probably one lane — but they are distinct defects: SQ-0557 is a key that works in NO section, this one is keys that work in the section we do not document.
