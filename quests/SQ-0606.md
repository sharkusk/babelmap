## What screen readers need from a terminal app

Linear append-only output (no cursor repositioning / in-place redraw); no alternate
screen, so scrollback review works; the terminal's OWN line discipline for input, since
readers hook the terminal's echo to announce typed characters and to give the user
their familiar line editing; no blocking pager hiding content; side information present
in reading order, not just spatially.

## Measured state (2026-08-03)

|                          | zvm-cli | gvm-cli | scott-cli |
|--------------------------|--------:|--------:|----------:|
| lines                    |    2568 |    3341 |       244 |
| TTY-conditional sites    |      51 |      40 |         1 |
| escape sequences piped   |       0 |       0 |         0 |
| alternate screen         |      no |      no |        no |
| status text when piped   |     yes |  NO (see [[SQ-0607]]) | n/a (prose) |
| raw-mode input on a TTY  |     yes |     yes |       yes |
| [MORE] pager             | yes (TTY) |    no |        no |

The good news: a clean plain path ALREADY EXISTS in all three and is maintained,
because the test harnesses read it. No alternate screen anywhere — usually the hardest
thing to retrofit, already absent.

## The work

1. Make the plain path selectable on a TTY: a `--plain` (or `--screen-reader`) flag.
   Also honour `NO_COLOR` and `TERM=dumb` — grep found NO env handling of either in any
   CLI today (only `BABELMAP_DEBUG_TERM` in gvm-cli).
2. Cooked input comes free: the non-TTY branch already uses the terminal's `read_line`.
   Selecting plain mode should route input the same way (pass is_tty=false to the input
   layer), which restores the terminal's echo and line editing.
3. Keep `[MORE]` off in plain mode (already off when piped).
4. Fix [[SQ-0607]] first or status is missing for Glulx.

Mode resolution belongs in the shared crate — see [[SQ-0605]].

## Caveat

None of the screen-reader behaviour above was measured — I verified escape output,
input paths and TTY gating only. NVDA/Orca/VoiceOver specifics are established
terminal-accessibility practice, not something tested here. Cheap early validation:
have an interested user try zvm-cli with output redirected or piped through `less`,
which approximates plain mode closely.

## Shipped 2026-08-03 — commit 9fb4621d (after prerequisite SQ-0607, 394497f9)

### Delivered
- `--plain` / `--screen-reader` on all three CLIs; `TERM=dumb` selects it too.
- `NO_COLOR` honoured — see the deviation below.
- Cooked input in plain mode (free: `HostMode::raw_input` from SQ-0605).
- `[MORE]` suppressed in plain mode (zvm-cli; the other two have no pager).
- Help text on all three + a new "Plain text, for screen readers" section in
  docs/features/interpreter.md.

### Deviation from this quest's plan, deliberate
The note listed "honour NO_COLOR and TERM=dumb" together, implying both select
plain mode. Implemented differently: **NO_COLOR suppresses colour only**, mapping
onto the existing `--no-game-colours`. Per no-color.org the convention is that
software "prevents the addition of ANSI color" — it says nothing about cursor
addressing, and someone who sets NO_COLOR has not asked to lose their pinned
status line. `TERM=dumb` is the variable that means the terminal has no
vocabulary at all, so that one does select full plain mode.

Measured on a pty with beyondzork: default 13 escapes incl. `ESC[37;40m`;
NO_COLOR 6 escapes, colour gone but `ESC[2J`/`ESC[H`/`ESC[r` kept; TERM=dumb 0.

### Design notes
- `plain_from(argv, term)` / `no_color_from(env)` are pure and take the
  environment as a parameter; the env-reading wrappers are thin. Kept
  zvm-cli's `parse_game_colours` pure too and folded NO_COLOR in at the call
  site, so its unit test does not depend on the ambient environment.
- gvm-cli needed a reorder: `TerminalBackend::new` detected the TTY itself, so
  the mode is now resolved before the backend is constructed and the backend
  reads `HostMode::current().rich()`.
- scott-cli needed only to accept the flags in its strict parser.
- Bleeps deliberately still ring in plain mode: BEL is not an escape sequence and
  a game ringing it is saying something. Wired to `mode.stdout_tty()` (the device
  fact) rather than `rich`; identical in every non-plain case.

### Verified
- Zero escape sequences under `--plain` AND under `TERM=dumb`, on a pty, for all
  three CLIs — against 15 (zvm-cli) / 68 (gvm-cli) by default at the same size.
- `[MORE]`: 3 occurrences at 10 rows by default, 0 in plain.
- **Cooked pty** (ICANON + ECHO on — what a screen-reader user really has): all
  three run correctly with the terminal doing the echo, output linear and
  append-only. This needed a new harness; the existing `ptyrun.py` forces RAW
  discipline, which is precisely what plain mode hands back to the terminal.
- No regression: piped output identical across 4 Z-machine, 5 Glulx, 3 Scott;
  TTY output byte-identical under a pty for ballyhoo, beyondzork, CM, Coloratura.
- Gate 0 errors, 64 == 64. Clippy clean.
- Falsified 5 ways (3 unit, 2 behavioural) — all fail with the right symptom.

### A false alarm worth recording
gvm-cli + CM + plain on a cooked pty first looked like a hang (8 bytes out).
It was harness impatience — CM takes several seconds to boot and the drip-feed
was on a 0.7 s timer with a 1.5 s idle cutoff. At 2.5 s / 6 s it works perfectly.
No product bug. Check harness timing before believing a hang in a big game.

### Still NOT validated (unchanged from the original caveat)
No real screen reader was exercised. Escape output, input paths and TTY gating
are what was measured; NVDA/Orca/VoiceOver behaviour is not. This is stated in
docs/features/interpreter.md as a call for feedback rather than glossed over.
Cheapest next validation is still a real user on `--plain`.
