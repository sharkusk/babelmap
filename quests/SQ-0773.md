FINDING (research only; no code changed). The rule is a **sentinel colour probe**, not a gestalt.

## The rule, from the game's own source

`Kerkerkruip.materials/Extensions/Victor Gijsbers/Kerkerkruip Start and Finish.i7x` lines 30–53 (clone i7/kerkerkruip @ b341c3c1, section "Detecting whether or not the Gargoyle config file has been applied"):

```
[ DetectGargoyleConfigFile res;
	! Don't test the style in CocoaGlk because it will crash
	if ( ~~(+ CocoaGlk detection flag +) )
	{
		res = glk_style_measure( gg_mainwin, style_User2, stylehint_TextColor, gg_arguments );
	}
	return res && gg_arguments-->0 == $F400A1;
];
```

and the matching bait in `Kerkerkruip.materials/Kerkerkruip.ini` (shipped in the game's own zip; ours sits at `stories/Kerkerkruip.ini`):

```
# User2 colour - set the colour to 'Fashion Fuchsia' so that we can detect whether this config file has been applied
# (because why else would anyone ever set it to Fashion Fuchsia??)
tcolor	10	F400A1	ffffff
```

Constants verified against **glk.h from eblong.com** (not recall): `style_User2 = 10`, `stylehint_TextColor = 7`, selector `glk_style_measure = 0x00B3`; semantics per Glk 0.7.6 §5.5.2 ("returns FALSE (0) if the library cannot determine the attribute").

So the branch is **"was my Gargoyle config file applied?"** — it is not an interpreter-identity check, not a gestalt, not a capability probe. Any host that reports `0xF400A1` as the rendered foreground of `style_User2` in a text-buffer window passes.

## What it gates

`Kerkerkruip Start and Finish.i7x:60–84` — the *check screen reader rule*:
- **pass (GarGlk)**: no prompt at all; `main menu graphics flag` and `menu hyperlinks` force-enabled; screen reader mode off.
- **fail**: the game asks `"Kerkerkruip has a mode optimised for those using a screen reader. Enable...? Yes or No"` and, on **No**, enables graphics but leaves **menu hyperlinks disabled** — a permanent difference, not just a one-time prompt.

Also `Kerkerkruip.materials/Extensions/Kerkerkruip/Windows.i7x:150,154` — only on pass does it `place border border-12-window` / `border-13-window` (two 7px fixed-size *graphics* windows above the status window, opened only `if glulx graphics is supported`).

## What each interpreter answers

| host | `glk_style_measure(mainwin, 10, 7)` | detected | intro |
|---|---|---|---|
| Gargoyle **+ the shipped ini** | `1`, `0xF400A1` | GarGlk | no prompt, graphical menu + hyperlinks |
| Gargoyle **without** the ini | `1`, `0xFFFFFF` (built-in default) | — | prompt |
| Spatterlight | `1`, its theme colour for User2 | — | prompt |
| babelmap | `1` + `transcript` fg, or `0` when the theme leaves fg terminal-default | — | prompt |

Gargoyle chain verified in source: `garglk/config.cpp:834-854` parses `tcolor 10 …` into `gli_tstyles[10].fg`; `garglk/style.cpp:169-227` returns `style.fg` packed for `stylehint_TextColor`; `gli_tstyles` default User2 fg is `0xFFFFFF` (`config.cpp:119-130`), so **bare Gargoyle also fails** — the ini is the whole trigger.

Spatterlight: `garglk.ini` does not exist anywhere in angstsmurf/spatterlight; its Glk (`glkimp/`, a plain-C Glk 0.7.5, *not* a CocoaGlk fork) answers style_measure from the theme + game stylehints (`glkimp/stylehint.c`, `GlkController+GlkRequests.m:355-385`). **So the quest premise is half wrong: Spatterlight behaves the same as us, not like Gargoyle.** The likely explanation for the user's observation is that Kerkerkruip only ever asks **once** and persists the answer (see below), so an already-answered Spatterlight install never shows the prompt again.

## Reproduced here

`./target/debug/gvm-cli --screen-reader --data-dir <fresh> stories/Kerkerkruip.gblorb` → prints the screen-reader prompt. Glk call trace over the whole boot (via `Machine::trace_screen`) shows exactly one line before that text:

```
glk_style_measure(4, 10, 7, 1445490)
```

i.e. window 4 = `gg_mainwin`, style 10 = User2, hint 7 = TextColor. That is the probe, and the prompt is printed immediately after it.

The **CocoaGlk** probe (Interpreter Sniffing's bug-819 test) also runs and we pass it correctly — trace shows `window_open(0,…)→1`, `window_open(1,…)→2`, `get_parent(1)→3`, `get_arrangement(3,…)`, then both closed. `Glk::window_open` sets `p.key = nid` (the *new* window) per spec, and `exec.rs:0x0027` returns it, so we are not misidentified as CocoaGlk. Good — that guard would otherwise skip the style probe entirely.

## The interesting part: we already import the exact file the sentinel is testing for

`stories/Kerkerkruip.ini` **is** discovered and applied by babelmap today (SQ-0319). Verified directly:

```
path=…/stories/Kerkerkruip.ini matched=["Kerkerkruip.gblorb"]
buffer[10]=Some((Rgb(244, 0, 161), Rgb(255, 255, 255)))     # 0xF400A1 on white
summary: imported garglk config … 1 buffer + 0 grid style colours, link set,
         honor_game_colours=true, text margin 1×0 cells, borders off
glk_styles[0][10]=Style::new().fg(Color::Rgb(244, 0, 161)).bg(Color::Rgb(255,255,255))
theme_style_colours buffer=(None, None) grid=(None, None)     # <-- the gap
```

We **render** the fuchsia (`render/transcript.rs:1287` reads `scheme.glk_styles[0][glk]`, and `resolve_glk_channel` applies the slot in *both* `honor_game_colours` modes) but we **report** something else when the game measures it, because the only thing feeding the measure path drops the style class:

- `glk_backend.rs:1089` — `fn default_style_colours(&self, wintype, _style)` ignores `_style` and returns one pair per window type, sourced from
- `glk_backend.rs:113` — `theme_style_colours()`, which reads only `colors.transcript` and `theme.get("status_bar")` — never `colors.glk_styles`.

The `GlkBackend` trait doc (`gvm/src/glk.rs:600-607`) says "the colours the host actually renders **by default for style class `style`**", so the app impl contradicts its own contract. And **SQ-0319's own user-confirmed scope says**: *"Also answer Kerkerkruip's 0xF400A1 garglk-config style_measure sentinel truthfully once a scheme is applied."* That half of SQ-0319 shipped the import (commit 023bff6d) but never wired the measure path. This is the single reason we differ from Gargoyle.

The fix is one place — have `default_style_colours` consult `colors.glk_styles[wintype][style]` before the element base, and carry the per-style slots into the backend snapshot alongside `set_theme_colours`.

**Deliberately not taken here.** It is not a pure correctness fix: passing the sentinel also (a) suppresses an accessibility prompt in a *terminal* app whose users are exactly the screen-reader population Gargoyle's GUI users are not, (b) turns on `menu hyperlinks` permanently, and (c) opens the two Gargoyle-pixel-tuned graphics border strips. That is a product call, and `exec.rs:0x00B2`'s justification comment for `style_distinguish` ("the backend's default colours are per-window-type base colours, identical across style classes, so they can never make two styles distinguishable") goes stale the moment the answer becomes per-style. Filed as a follow-up.

## What else depends on this answer

`default_style_colours` is consulted **only** by `glk_style_measure`, and only for hints 7/8. Surveyed every Glulx fixture in `stories/` (24 blorbs) booted to first input with `trace_screen` on:

> Kerkerkruip.b10.gblorb and Kerkerkruip.gblorb: `glk_style_measure(4, 10, 7, …)` — **every other game: none.**

So nothing else in the corpus reads it at all. Two corollaries:
- The SQ-0315 rationale still quoted in four comments (`colors.rs:369`, `startup.rs:385`, `glulx_session.rs:337`, `gvm/glk.rs:606` — "Kerkerkruip's dark-background detection") is **mis-attributed**: Kerkerkruip never measures BackColor and never branches on a colour *value*, only on the sentinel. SQ-0315's own closing note already reached this conclusion; the comments were never updated.
- Changing the answer therefore cannot regress any other local fixture.

## Side evidence: the prompt is asked once, ever

`Kerkerkruip Persistent Data.i7x` stores the answers in the Glk file `KerkerkruipStorage`; the label table maps key 5 = main menu graphics, 7 = window panels, 8 = menu hyperlinks, 9 = sound, 10 = screen reader mode.

`stories/KerkerkruipStorage.glkdata` (written by an external interpreter, beside the story) decodes to `5 1 / 8 -1 / 10 -1 / 9 1 / 7 0` — **`8 -1` = menu hyperlinks disabled**, which is reachable *only* from the interactive "No" branch; the GarGlk branch would have written `8 1`. So whichever interpreter wrote that file also failed the sentinel.

babelmap persists the same state in its own VFS sidecar (`<data-dir>/Kerkerkruip.gblorb.save/default.glkvfs`, contents `5 1 / 8 -1 / 10 -1 / 6 0`) and correctly asks only on the first run — verified by two consecutive gvm-cli runs sharing a `--data-dir`: run 1 prompts, run 2 goes straight to the title screen. Note our VFS sidecar is *not* the `.glkdata` file beside the story, so babelmap and Gargoyle do not share the answer (by design, not a defect).
