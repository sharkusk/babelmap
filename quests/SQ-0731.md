--- note 2026-08-09T19:37:51Z ---

DIAGNOSED 2026-08-09 by headless probe on `stories/Facility.z8` (throwaway harness, since deleted). Six turns driven with look/north/south:

    version = 8
    every turn: upper_window_rows = 1, upper[0] = ""   <- the status line is ALWAYS EMPTY
    every turn: detect_location = None

The game splits a one-row upper window and never paints a single character into it. Meanwhile the room name is printed into the MAIN TEXT as a heading line:

    "...\n\n\nLobby\nThis entry chamber feels quite friendly. A large sign reads, \"WELCOME TO THE FACILITY.\"
     The main doors are to the south, and a doorway leads north.\n\n>"

and it reprints on every move, so movement is observable. This is the Inform 7 `Subheader` room-heading convention.

WHY DETECTION RETURNS NONE: `detect_location` (`crates/zvm/src/location.rs:797`) gates the whole v4+ ladder on `status_line_room_name(&machine.screen.upper, …)`. With an empty upper window there is no candidate name, so player-parent validation, `resolve_room_object`, StatusName and NameOnly are all unreachable, and the centered-title fallback finds nothing either. It returns None every turn, forever.

THE PRECEDENT IS ALREADY IN THE CODEBASE. `LocationMethod::RoomHeading` exists and is documented as "Glulx: the room was read from the Inform 7 `Subheader` room heading in the story buffer (name-based; no backing object). Trusted directly — not subject to the `NameOnly`-empty-graph gate." Facility.z8 is the same authoring convention arriving through the Z-machine instead of Glulx. So the work is most likely EXTENDING an existing, proven mechanism rather than inventing one — read how the Glulx path finds and validates a Subheader before designing anything.

LIKELY LANE PROBLEM, worth knowing before scheduling: `detect_location` is a pure function of `Machine`, and zvm's own output sink (`buffer_output()`) is a test convenience — the app supplies its own `Output` impl, so the story text a heading would be read from is probably only available app-side, in `session.rs`. If so this fix spans zvm and `crates/app/src/session.rs`, which was owned by another agent when this was filed. Check before starting.

DO NOT generalise from one game: a heading rung that fires whenever the upper window is empty could mint garbage rooms in games that legitimately print no status line and no headings. Whatever validation the Glulx path uses is the starting point, and the corpus (Zork Zero, Arthur, Journey, advent, the Mysterious titles, scopa) must keep detecting exactly as it does now.

--- note 2026-08-10T04:19:41Z ---

FIXED 2026-08-09 in the SQ-0752 lane (commit 68e5ad75) — SAME ROOT CAUSE, and the 2026-08-09 diagnosis in the note above is WRONG on its central fact. Re-measured on stories/Facility.z8 (v8, 209 objects, only 32 with short names): the upper window is NOT always empty. It is empty at boot only; from the first command on it reads ' Lobby', then ' Visitor Gallery' after north, tracking movement correctly. detect_location does NOT return None — it returns Some(NameOnly "Lobby") / Some(NameOnly "Visitor Gallery") every turn. So no new heading rung was needed and none was added; the RoomHeading-from-story-buffer work the old note recommended was not the answer. The candidate was found and then discarded downstream, in crates/app/src/session.rs apply_turn, which suppressed an unvalidated NameOnly until the map held an object-backed room. Nothing in Facility's object tree is named for any room (grep of the whole tree for 'Lobby'/'Visitor Gallery' returns nothing, and there are no player-object candidates at all), so that gate could never be satisfied and the map stayed empty forever — exactly the reported symptom. The gate now asks instead for CORROBORATION: an unbacked room may seed an empty map when the story ALSO printed that name as its own heading line, which Facility does ('Lobby\nThis entry chamber feels quite friendly...'). Facility now maps Lobby and Visitor Gallery and connects them; pinned by facility_maps_rooms_as_the_player_walks in crates/app/tests/nameonly_room_corroboration.rs (skips vacuously without the fixture). Falsified: with the corroboration clause reverted the test fails 'walking north out of the Lobby must map both rooms; got []'. The lane-spanning worry in the old note did not materialise — the fix is three lines in apply_turn and touches no story-buffer plumbing. Corpus check found no regressions (zork1, enchanter, anchor, LostPig, trinity all unchanged). Left at confirm for user verification.
