USER REQUEST 2026-08-11: "our scrollbar is a bit fat so text that ends up next to it is very close. is it possible to make a skinnier scrollbar, and auto-hide in the story pane when we are not actively scrolling?"

RECONNAISSANCE (read-only, done at filing time — do not re-derive):

**WHY IT IS FAT.** Every scrollable surface goes through ONE function, `draw_scrollbar` in `crates/app/src/render/scroll.rs`, which renders ratatui's `Scrollbar` with its DEFAULT symbols — thumb `█` (full block), track `│`. A full block fills the whole cell, so neighbouring text has no visual gutter. ratatui exposes `.thumb_symbol()` and `.track_symbol()`, so a thin pair (`▐` U+2590 right half block, or `▕` U+2595 right one-eighth block) makes it a rule hugging the pane edge. One change, every surface consistent.

Call sites, all via that one helper: `picker_ui.rs` (x3), `render/{hints_panel,history,command_band,saves,palette,config_screen,filebrowser}.rs`, and the story pane at `render/transcript.rs:2401`.

**AUTO-HIDE IS CHEAP HERE, and the reason is worth knowing.** The story pane draws its bar at `x = area.right() - 1 + right_margin`, width 1 — i.e. in the MARGIN BAND, outside the text area, because SQ-0345 pushed it past the right text margin so only text is inset. **So showing/hiding it cannot reflow a single character.** That removes the usual objection to auto-hiding scrollbars. Confirm the same is true of any other surface before auto-hiding it there; the modals reserve a 1-column gutter from their content width (`content.width.saturating_sub(1)`) and WOULD reflow, which is a good reason to keep them always-on.

**THE FRAME PUMP ALREADY EXISTS.** `crates/app/src/anim.rs` provides clock-backed `Tween`s that "the run loop advances each frame", already used for smooth transcript scroll. So a visibility window can request frames until it expires, and a fade is as cheap as a pop.

DESIGN POINTS TO SETTLE:
  - **Scope of "skinny"**: apply to every surface (consistency) but auto-hide ONLY in the story pane, per the request. Modals benefit from a persistent bar and would reflow anyway.
  - **What counts as "actively scrolling"**: wheel, PgUp/PgDn, and the scroll keys — probably NOT new text arriving, or the bar would flash on every turn. State that choice explicitly in the implementation.
  - **STYLEABILITY IS MANDATORY** (CLAUDE.md): a `scrollbar` colour selector already exists in the theme; the glyph pair and the hide delay both need to be settable from `style.toml`/`config.toml` rather than hard-coded, with the template updated. Never hard-code a style.
  - Both `honor_game_colours` modes need pinning if any test asserts colour.

OFFER TO THE USER at implementation time: the SQ-0775 rasteriser can render the candidate glyph pairs (full block vs half block vs one-eighth block, thumb and track) as PNGs so the choice is made by eye rather than by description. That is exactly the kind of decision a picture settles.
