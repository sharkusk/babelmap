--- note 2026-08-13T20:58:24Z ---

THE RULE, from the user 2026-08-13: "please keep the functionality consistent for all disk image formats."

So: **whatever a front-end can DETECT, it can OPEN — and every capability a disk gives us (stories, pictures, hints) works the same way whichever format the disk is.** A format is added in ONE place and every caller gains it at once.

## The defect, measured on main at `ee03cf71`

Format handling is a per-call-site `if/else` chain over formats, duplicated three times and complete in none:

```
crates/app/src/graphics.rs:303   if looks_like_adf … else if looks_like_hfs …      (pictures)
crates/app/src/hints.rs:697      if looks_like_adf … else if looks_like_hfs …      (story + hints)
crates/zvm-cli/src/media.rs:67   Adf ONLY  — looks_like_image() == detect() == Adf
```

`zvm-cli` therefore mounts an Amiga floppy and refuses a Macintosh one, even though `blorb::hfs` has read that disk since SQ-0837 and `blorb::medium::DiskImage::detect` already recognises both. Its `looks_like_image` doc comment says outright that this front-end "must not claim an image it cannot open" until `story_candidates` grows an HFS arm — an honest guard around a real hole, not a mistake.

**How it happened, for the record:** SQ-0834 (CLI wiring) and SQ-0837 (the HFS reader) were dispatched IN PARALLEL by the coordinator. SQ-0834's brief told it to wire "what `blorb` offers today" and explicitly not to pre-abstract for formats that had not landed; SQ-0837 added HFS beside it. Both lanes were correct inside their own scope and neither owned the join. That is a scheduling artifact, not a technical obstacle — and it is exactly the failure mode a per-call-site chain guarantees will recur.

## What this quest must produce

ONE mount path in `blorb`, beside `medium::DiskImage::detect`, that answers: is this an image, mount it, what stories are on it, what pictures, what hints. Every existing chain then asks it instead of restating the policy. `blorb::medium` already holds `DiskImage {Adf, Hfs}` with `detect`, `label` and `interpreter_number`, and SQ-0839 established the pattern of putting shared policy there rather than duplicating it — this is the same move for mounting.

The success test is concrete: **adding the next format should be one arm in one file.** Three are already queued behind this — DOS/ST FAT12 (SQ-0833), ProDOS (SQ-0836) — and the corpus survey in SQ-0833 shows why the current shape will not survive them.

`blorb` takes ZERO external dependencies. Do not add one, and do not let this become a rewrite of `adf.rs` or `hfs.rs` — their readers are correct and gated; this is about the seam above them.

## Do not paper over the v6 asymmetry

`zvm-cli` refuses v6 outright, so a mounted Zork Zero will mount cleanly and then be declined at load — as the five graphical Amiga floppies already are. That is the CLI's own limitation and is NOT an inconsistency between formats. The message a user sees should be the v6 refusal, not a disk error. Do not "fix" it by making the CLI claim it cannot open v6 media.

--- note 2026-08-13T20:58:51Z ---

SHAPE CONFIRMED by the user, 2026-08-13: "we should have a standard api in our blorb crate for disk images."

So this is not merely "route the CLI to HFS as well" — it is a **standard disk-image API in `blorb`** that every format implements and every caller consumes. The per-call-site `if/else` chains are the symptom; the missing abstraction is the defect.

The API has to cover everything a mounted disk is asked for today, or the chains will simply survive underneath it:

* **detect** — is this an image, and which format (`medium::DiskImage::detect` already does this for `Adf` and `Hfs`)
* **mount** — turn bytes into a volume, with a format-neutral error
* **stories** — every story on the volume, identified by CONTENT rather than by name; the corpus makes this non-negotiable, since every Atari ST story is called `STORY.DAT` and five of nine Amiga floppies call theirs `Story.data`
* **pictures** — the Infocom art archive, if the disk carries one (`graphics.rs:303`)
* **hints** — `hints.rs:697`, which also wants the story bytes and the medium back
* **label** and **interpreter_number** — already on `medium::DiskImage` from SQ-0839; fold them in rather than leaving a second vocabulary beside the new one

Whether that is a trait with a boxed volume or an enum that dispatches is the lane's call — `blorb` is zero-dependency and hand-rolled throughout, so the simpler of the two probably wins. What matters is the property: **one place names the formats, and adding the next one is a single arm.**

Queued behind this and waiting on exactly that property: DOS/ST FAT12 (SQ-0833) and ProDOS (SQ-0836). The SQ-0833 survey shows why the current shape will not survive them — four OEM strings, two geometries, two file extensions, root-only and subdirectoried layouts, and a `2IMG` length field that reads zero.
