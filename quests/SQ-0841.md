--- note 2026-08-13T21:54:38Z ---

EVIDENCE — two headless pty captures of the SAME frame, 2026-08-13, main `36965ba2`. `Zork Zero Disk.image` (Macintosh, v6 **r296 / s881019**), 120x40 cells at 8x18, kitty, map hidden, one `cr` past the title.

```sh
cargo run -p app --example pty_capture -- --story "stories/Zork Zero Disk.image" \
    --size 120x40 --keys wait:2500,cr,wait:1200 --png colour.png
# …and the same with:  --arg --pictures --arg Pic.data
```

Tall placements emitted, colour against monochrome:

```
CPic.data (colour)   rows  8..37  cols   1..16   (16 cols x 30 rows)   LEFT pillar
CPic.data (colour)   rows  8..37  cols 103..118  (16 cols x 30 rows)   RIGHT pillar
Pic.data  (mono)     rows  6..37  cols   1..12   (12 cols x 32 rows)   LEFT pillar
Pic.data  (mono)     — nothing —                                       RIGHT pillar ABSENT
```

**So the right pillar is not mis-tiled; it is never placed.** The left one is placed but at a different size and origin (12 cols x 32 rows from row 6, against the colour art's 16 x 30 from row 8). Everything else in the frame — banner, compass, drop cap, room icon, prose — renders correctly in both, so this is specifically the side-flank path.

## Why, most likely — verify before building

The mono archive is drawn for a **480x300** picture space where the colour archive is **320x200** (SQ-0838, sourced from `mac/gfx.p`: `GF_MONO = $0008; { this pic is mono, and scaled for a 480x300 screen (std Mac) }`). The flank geometry derives the right-hand column's origin from the art's picture space mapped onto the unit screen; at 320 that lands at cols 103..118 of a 120-column frame, and at 480 it evidently lands nowhere the placer will accept.

**This is entangled with SQ-0838's OPEN half and should probably not be fixed before it.** That quest's own note records the root condition: `native_std_window` / `PictureOverride::std_window` still hand back (320, 200) → a 640x400 unit screen, so 480x300 art is being laid into a screen the game was never told about. Tiling computed against the wrong screen model would be a fix on top of a wrong premise, and would have to be redone when the Macintosh profile lands. **Sequence this after the Mac screen model, or establish the screen model as part of it.**

## Corroborating detail

The mono capture's left pillar spans rows 6..37 where the colour one spans 8..37 — it starts two rows higher, i.e. it is not merely a narrower version of the same strip but a differently-anchored one. Any fix has to account for the vertical anchor as well as the horizontal placement.

Renders are reproducible with the commands above; `--png` draws the screen the oracle resolved, which is what made this visible without a terminal at all.

--- note 2026-08-13T21:58:33Z ---

USER OBSERVATION, 2026-08-13, from the rendered capture: "in addition to fixing the right pilar we will also need to tile it differently as the pilars are very different than the other formats (and we are not even showing the feet right now)."

So this is NOT "place the missing right pillar and reuse the existing strip logic". Three separate defects:

1. **The right pillar is never placed** (the emitted-placement evidence in the note above).
2. **The tiling itself is wrong for this art.** The Macintosh pillars are structurally different from the other formats' side borders — they are not a uniform strip that repeats. Whatever the other media do, this needs its own composition.
3. **The feet are missing.** The pillar's base is not being drawn at all. Together with the left pillar starting two rows HIGHER than the colour one (row 6 against row 8), that says the piece is being anchored and extended as if it were a plain repeating rule, when it is a composed column — capital, shaft, base — whose end pieces have to land at both ends rather than be tiled over.

SEQUENCING, agreed with the user: **the Mac screen model (SQ-0838's open half) goes FIRST, then this is revisited.** The user's words: "let's do the mac screen model and revisit." The reason stands from the previous note — the mono art is drawn for 480x300 and is currently laid into a 640x400 unit screen the game was never told about, so any tiling computed now is computed against a screen that is about to change. Re-measure the placements after the profile lands before touching this.

Relevant history to read before designing the fix, because this project has been wrong here before: SQ-0750 (in hybrid, never rasterise what the game printed as a character — classify a strip by what is IN it, not where it sits), SQ-0819 (the side-border TILER is the wrong path for a picture seated in a panel), and SQ-0793 (raster's flank extension ported without hybrid's exclusion). The Mac column may well be a case none of those established paths fits.
