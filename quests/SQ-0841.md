THE TILING ALGORITHM ALREADY EXISTS — do not design a new one. Checked 2026-08-13 in response to the user asking whether we had an approach in mind.

`crates/app/src/render/v6_border.rs`:

* **`tile_down(dst, strip, start_y, end_y, overlap, initial_parity, flip) -> u32`** — a port of bocfel's `tile_section_down`. Stride is `strip.height() - overlap`, so tiles **overlap rather than butt together**, and `flip` alternates each tile's vertical flip from `initial_parity`. Its own doc: "Both devices exist to hide the seam in a repeated pattern. Arthur needs neither (his repeat unit is two lines of a plain texture); Zork Zero's patterned masonry is the case they were written for." Returns the row the next tile would have started at.
* **`erase_below(dst, y)`** — bocfel's `erase_lines_in_bitmap`, and its doc says exactly what it is for: "used to drop the overshoot of the last whole tile **before the foot goes on**."

So the intended composition is already **capital → tile the shaft down → erase the overshoot → place the foot**, which is precisely what the ground-truth Macintosh screenshot shows, and it is why the COLOUR pillars come out correct today.

**Therefore the defect is not a missing algorithm. It is that the foot's anchor is computed in the wrong picture space.** The monochrome art is 480x300 where the colour art is 320x200, and the foot lands 61% down the column instead of at the bottom. `erase_below` then presumably clears from that point, which is consistent with the bare shaft seen beneath it and nothing at the end.

## Practical consequence — check before building

**This may largely fix itself when SQ-0838's screen model lands.** If the foot's anchor derives from the declared screen geometry, correcting the geometry corrects the anchor. So the first action on this quest is to RE-MEASURE, not to write code:

```sh
cargo run -p app --example pty_capture -- --story "stories/Zork Zero Disk.image" \
    --size 120x40 --keys wait:2500,cr,wait:1200 --arg --pictures --arg Pic.data --png after.png
```

and compare the foot's position against the 61% recorded here. Only if it is still wrong does anything need designing — and then the question is which geometry feeds `end_y` and the foot's y, not how to tile.

## The right pillar is probably a DIFFERENT bug

It is absent entirely, not mis-tiled, so tiling is unlikely to be the cause. The closest precedent is SQ-0830, where Journey lost its whole panel treatment because a plan gate answered before the question that mattered — one classification going the wrong way silenced `menu_flank_panel`, the panel fill, the vertical centring and the tiler exclusion all at once. Look for a flank not being recognised on that side rather than for a tiling error. Instrument the placer and read off what it asks for on each side.

--- note 2026-08-13T22:51:30Z ---

THE RULE, stated in full by the user 2026-08-13. This supersedes the acceptance criteria in the previous note.

> "the key is that repeats need uniform spacing"
> "as the pilars grow in length the repeats will need to be recalculated"

So the column's composition is a FUNCTION OF THE AVAILABLE SPAN:

1. **The foot is anchored at the bottom** and is the bottom-most ink on the column. No shaft beneath it.
2. **The repeats are uniformly spaced** — one stride across the whole run, capital → band → band → … → foot, with the last repeat meeting the foot exactly. No odd gap anywhere, and specifically no different final gap where the run meets the foot.
3. **The count is DERIVED from the span, not fixed.** A taller pane gets MORE band segments, not longer gaps; a shorter pane gets fewer. Recalculated whenever the pillar's length changes.

## Why this is a real algorithm change, not an ordering fix

`tile_down` takes a FIXED stride (`strip.height() - overlap`) and walks until it passes `end_y`. That necessarily leaves an arbitrary remainder — and that remainder IS the bare shaft below the foot measured in the previous note (y 623..695, four cell rows). Anchoring the foot at the bottom without touching the stride would merely move the irregular gap to just above the foot instead of removing it. Fixed-stride-then-truncate cannot satisfy rule 2 by construction.

The shape the fix wants: determine how many repeats fit the span between capital and foot, then **solve for the stride (or effective overlap) that distributes exactly that many evenly**, so the last one lands on the foot.

## Testing note, because a fixed-count implementation passes a single-height test perfectly

Test across SEVERAL pane heights, not just the 120x40 the defect was measured at, and choose heights that are not multiples of one another. At each, assert: uniform stride, foot at the bottom, and a count that grows monotonically with the span. Today's 120x40 render is a reference point — the user has seen and approved that articulation, so the count must not regress there — but it is a lower bound at that size, **not a constant to freeze**.

## Still standing

* The repeat itself is WANTED. Do not reduce the articulation; the doubled-foot look mid-column is liked.
* `tile_down`'s flip behaviour stays.
* The colour rendition tiles correctly today and must be verified unmoved.
* Ground truth for the foot's appearance is the user's real Macintosh screenshot (512x342), base flush at the bottom of the text frame — though note babelmap's pane is TALLER than a real Mac window, which is exactly why the count has to scale rather than match the screenshot's single band.
