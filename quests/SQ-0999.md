## The evidence

`cargo run -q -p app --example gallery` on 2026-08-21 at ~21:05: **5 frame(s), 8 failure(s)**.

Regenerated (new mtimes): journey-amiga, journey-narrow, journey-wide, journey-halfblocks, zork1-map.
Stale, i.e. failed (mtimes still 08:40-08:44): journey-blorb, zork0-blorb, zork0-amiga, zork0-dos, zork0-macintosh, arthur-blorb, scopa, fmvpoker.

**Note the failed set is exactly the eight shots SQ-0963 resized** from 117x40 @ 8x18 to 162x53 @ 8x16 (the nine kitty shots less journey-amiga, which passed). The four that passed are the ones whose geometry SQ-0963 left alone or changed differently — journey-narrow 96x28, journey-wide 242x78, journey-halfblocks 130x43 at 10x20, and zork1-map, a v3 with no pixel screen.

The failure message is the SQ-0942 `expect` guard firing correctly:

    `fmvpoker`: the frame puts art on 0 cell(s), wanted at least 3000 — this is not
    the screen the manifest asked for (a browser, a boot prompt, or a different
    story off the same medium).

Note it also leaves the STALE png in place, so `index.html` silently mixes fresh and months-old frames. A proof sheet that can do that is a problem in its own right — a failed shot should remove or visibly mark its old file.

## THE CONFOUND — do not diagnose from this run alone

That run overlapped merging SQ-0995 and SQ-0996, both of which change kitty image ids and placement lifetime (stable ids, `p=1`, re-transmit under the same id). "0 art cells" is ALSO exactly what you would see if the oracle stopped resolving placements. The binary the gallery drove may have been mid-rebuild.

So there are two live hypotheses and they need separating before anyone changes code:

1. **SQ-0963's resize** — a bigger terminal means the game draws a different screen, or the keypress count no longer reaches the one the manifest names. Plausible: at 162x53 a story may show a browser or a boot prompt where 117x40 showed art.
2. **The id changes** — the gallery resolves frames through the placement oracle, and if an id or placement no longer resolves, art cells go to zero regardless of what the game drew.

**Re-run cleanly on a settled tree first.** If the eight still fail, bisect by checking out the commit before SQ-0995 and re-running; if they pass there, it is the id work, not the resize.

## Worth knowing

The SQ-0963 lane reported regenerating all 13 shots with 0 failures at the time it landed, so whatever this is, it arrived after that lane's own run.

## CORRECTION — "the gallery writes nothing" was my own cwd error, not a defect

While diagnosing, I reported that the gallery ran, claimed frames, and produced no files, and that `target/gallery` had vanished. All of that was wrong. A `cd` from an earlier compound command had left the shell inside `target/gallery`, so every relative path resolved there: `ls target/gallery/*.png` was looking for `target/gallery/target/gallery/*.png`, and `crates/app/` genuinely does not exist inside `target/gallery`. `git status` still looked sane because git walks up to the repo root.

The gallery writes its output correctly. All 13 PNGs, `index.html` and `gallery.json` are present. A single-shot run (`--only journey-wide`) produced its frame normally.

**Use absolute paths when verifying tool output.** A relative-path check that "finds nothing" is as likely to be looking in the wrong place as to be a finding, and I raised a high-priority alarm on one.

## What remains real, and still needs the bisect

The 8 failures stand: `5 frame(s), 8 failure(s)` on two separate runs, failing the SQ-0942 art guard with "the frame puts art on 0 cell(s), wanted at least 3000". The failed set is still exactly the shots SQ-0963 resized from 117x40 @ 8x18 to 162x53 @ 8x16 — journey-blorb, zork0-blorb/amiga/dos/macintosh, arthur-blorb, scopa, fmvpoker — and their PNGs on disk are still the stale 08:4x files.

The confound also stands: the second run was on a settled tree at 7ddba838, which INCLUDES SQ-0995/0996's id changes, so it does not separate the hypotheses either. The bisect described above is still the way: check out the commit before SQ-0995 and re-run; if the eight pass there it is the id work, if they fail it is the resize.

And the stale-file problem is real and worth fixing regardless: a failed shot leaves its previous PNG in place, so `index.html` mixes fresh frames with old ones and says nothing about which is which.

--- note 2026-08-22T05:03:20Z ---

## ROOT CAUSE FOUND — SQ-0991, not SQ-0963 and not the id changes. Both hypotheses were wrong.

The user reported that journey-amiga, journey-narrow and journey-wide showed no graphics — and those are shots that PASSED. That collapsed two symptoms into one: the eight guard failures and the blank passes are the same defect, and the failed set merely correlating with SQ-0963's resize was a coincidence I read as a cause.

**`crates/app/examples/gallery.rs:189` passed `&c.bytes` — the raw WIRE stream — to `oracle::resolve`.** Since SQ-0991 a kitty transmit may be zlib-deflated (`o=z`), so the resolver finds the placement correctly and then has no pixels to paint. Verified on a live capture: the oracle still resolves `image 0x77be7dfd rows 18..37 cols 4..42 (39 cols x 20 rows, 780 cells, virtual)` and the wire carries `q=2,i=3641255370,p=1,a=T,U=1,f=32,o=z,t=d,s=920,v=575` with 4,462 placeholders. Placement fine, pixels missing.

That explains every observation at once:
- Blank illustration panels on shots that pass (no art guard, or a low threshold).
- "the frame puts art on 0 cell(s), wanted at least 3000" on shots that have one.
- The stale 08:4x PNGs having art: they predate compression.

**How the gap happened, and it is worth remembering.** The SQ-0991 lane added `Capture::terminal_bytes()` and `pty_stream/inflate.rs` for exactly this problem, and updated `pty_oracle.rs`, `pty_flank_alpha_seam.rs` and `examples/pty_capture.rs` — then said explicitly: *"oracle.rs and gallery.rs were not touched (concurrent lanes)."* A correct decision about file ownership left one consumer of a changed contract un-migrated, and nothing failed: the gallery is not run by the gate, so a silent pixel loss sat there until a human looked at a picture.

Fixed by resolving `&c.terminal_bytes()` instead, with a comment saying why.

## Still worth doing, and NOT fixed here

1. **A failed shot leaves its previous PNG in place**, so `index.html` mixes fresh frames with old ones and says nothing about which is which. That is what made this look like a partial regression rather than a total one — five "new" frames beside eight from that morning, all presented identically.
2. **Nothing in the gate runs the gallery.** A silent loss of all artwork in the project's own proof sheet was invisible to 5,945 passing tests. Even a cheap smoke — one shot, assert non-zero art cells — would have caught this the moment compression landed.
3. `--only` rewrites `index.html` with just that shot, which is defensible but surprising; a partial run silently discards the sheet.
