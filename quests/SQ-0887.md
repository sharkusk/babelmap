--- note 2026-08-15T08:22:41Z ---

THE REPORT: on a real Amiga, Shogun's ornate side panels are recoloured by the scene — blue-and-white in the storm on deck, red-on-cream below decks — same artwork, different palette. babelmap draws them gold-on-dark in every scene.

NOT A REGRESSION FROM SQ-0881, and this was checked rather than assumed. Reverting today's `image_under_current_palette` change and re-capturing the identical frame (`James Clavell's Shogun.adf`, menu → START → down → down, 100x40) gives **0 differing pixels of 576,000**. The user said it had never worked; the measurement agrees.

ROOT CAUSE — the machinery is switched off entirely for this archive. `PictSource::image` opens with

    if self.adaptive.is_empty() {
        return self.get(resnum).cloned();
    }

and Shogun's Amiga `Pic.data` declares **zero** adaptive pictures (48 entries, no hardware palette, every picture carrying a palette of its own). So `image` takes that fast path, never calls `set_current_palette_from`, `current_plte` stays `None`, `palette_gen` never moves, and `session::replay_under_current_palette`'s `if self.palette_gen() != palette_before` never fires. The whole SQ-0567 path is inert here — nothing to do with which branch `image_under_current_palette` takes, which is why the revert changed nothing.

THE DEEPER POINT, and it is the interesting one. SQ-0881's commit message argued the machine distinction outright:

    Amiga Pic.data     1 palette   — a machine with sixteen colours to share
    DOS .MG1           3 palettes  — a DAC with 256 entries, and Infocom used them

The Amiga has ONE hardware palette, so loading a scene's palette recolours everything already on the screen — which is exactly what the screenshots show, and exactly the "whole screen shares one palette" model SQ-0881 removed for Arthur's MCGA. It was right to remove it there and it is right to want it here. So the principled rule is **per MACHINE**, not per adaptive-flag:

  - single-palette machine (Amiga, and presumably the ST) — a palette load recolours the screen, border included;
  - MCGA — pictures keep their own palettes, because there are 256 DAC entries and Infocom used them;
  - EGA/CGA — a hardware table outranks everything and the question never arises.

SQ-0881's fix keyed on adaptive-versus-base. That is correct for Arthur's MCGA and INERT for Shogun's Amiga, so nothing broke — but it is the right answer for the wrong reason, and this quest is where the reason gets fixed. Note `MachineProfile` already carries `global_colour_pens` for the Amiga's §8.3 text rule; a palette-scope flag would sit naturally beside it and `zvm-cli --machines` would print it.

WHAT TO MEASURE FIRST: whether an Amiga archive's per-picture palettes actually differ between the storm and below-decks scenes (they must, for the screenshots to look like that) and which picture numbers the border is. Then whether making a base draw establish the Current Palette on a single-palette machine is enough on its own, since the replay already exists and only needs `palette_gen` to move.

DO NOT fix this by simply reverting SQ-0881 — that reintroduces Arthur's grey map ground and rainbow scrolls, which is a confirmed, user-reported, falsification-tested defect. `v6_adaptive_palette_arthur::a_replay_recolours_the_adaptive_frame_and_leaves_base_art_alone` is the pin that must keep passing.

RELATED: SQ-0886 (the same disk's credits/menu screen loses its panels and its ground) — the user notes those ARE correct in raster mode, so that one is hybrid-specific and probably unrelated to this.
