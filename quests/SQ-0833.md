--- note 2026-08-13T18:06:59Z ---

SURVEY of the user's actual images, measured 2026-08-13 by parsing the FAT12 BPB and root directory directly. Do not re-derive; verify if the corpus changes.

All of them are plain FAT12: 512-byte sectors, 2 sectors/cluster, 1 reserved, 2 FATs, 112 root entries, 3 sectors/FAT. 720K images are 1440 sectors, 360K are 720. **So the filesystem work here is trivial** — far simpler than the AmigaDOS parsing `blorb/src/adf.rs` already does by hand at zero dependency cost. That is NOT where the difficulty of this quest lives.

## Where the difficulty actually lives: one game's files span several images

**Zork Zero, 720K PC release (r393, serial 890714):**
* Disk 1 (vol `ZORK0 1`) — `ZORK0.ZIP` 300032 (the STORY; `.ZIP` here is Infocom's Z-machine Interpreter Program data, NOT PKZIP), `ZORK0.MG1` 226436 (MCGA art), `ZORKZERO.EXE`, `EZR.EXE`, `INSTALL.EXE`, `IZORK03.RUN`
* Disk 2 (vol `ZORK0 2`) — `ZORK0.CG1` 244507, and nothing else

**The Lost Treasures of Infocom, 5×720K (vol labels `Tresure.1` … `Tresure.5`):**
* floppy1 — `ZORK1.DAT`, `ZORK3.DAT`, `BEYONDZO.DAT` (262190, so v5), `INFIDEL.DAT`, plus `ZIP1.COM`/`ZIP2.COM`/`ZIP3.EXE`/`ZIP4.EXE`, `INFOCOM.EXE`, `SETUP.EXE`, `INSTALL.BAT`, `ANSI3/4/5.SYS`
* floppy2 — `HITCHHIK`, `ZORK2`, `ENCHANTE`, `BALLYHOO`, `SORCERER`, `SUSPECT`
* floppy3 — `LURKING`, `MOONMIST`, `STARCROS`, `SPELLBRE`, `DEADLINE`, `PLANETFA`
* floppy4 — `STATIONF`, `SUSPEND`, `WITNESS`, **`ZORK0.CG1`**, `ZORKZERO.EXE`
* floppy5 — **`ZORK0.EG1`** 333654, **`ZORK0.ZIP`** 300032

TWO STRUCTURAL FACTS THAT SHAPE THE DESIGN:

1. **A single game's story and its art live on DIFFERENT images.** Zork Zero's story is on collection disk 5 while its CGA art is on disk 4 and its EGA art is on disk 5; on the standalone 720K release the story and MCGA art are on disk 1 and the CGA art on disk 2. So mounting ONE image cannot in general produce a runnable game. This needs a **set** model — several images mounted together — not a per-file mount. The same question applies to the Amiga side, where Zork Zero also shipped on two disks (`adf.rs` says it was verified against both).
2. **A collection image holds MANY stories**, so the Amiga model of "find *the* story by content" does not transfer. `looks_like_story` would return 4 candidates on floppy1 and 6 on floppy2. This needs a LISTING and a choice — which is the picker's job, not the mounter's.

Art extension → video card is already understood in the codebase: `interpreter.rs` documents `.MG1` (MCGA), `.EG1`/`.EG2` (EGA) and `.CG1` (CGA) as `Flavour::Pc` — three cards, one machine. So a set that carries several art archives is a CHOICE of card, not of platform, and the existing `PictureOverride::flavour` path is where that choice already lives.

Volume labels look usable as set identity (`Tresure.1`…`Tresure.5`, `ZORK0 1`/`ZORK0 2`) but that is an observation from five samples, not a verified convention — do not build on it without checking more media.

Fixture note: these live in the user's gitignored `stories/`, so any test over them must skip vacuously when absent, and each release must be pinned in `crates/app/tests/suites/real_media_releases.rs`. The 360K and 720K Zork Zero images are both r393/890714, but per the project's standing rule a disk image is a different release from the bare story file — name the exact image in any finding.

`.ZIP` IS NOT A CONTAINER — PROVEN, not inferred. Extracted `ZORK0.ZIP` from `floppy5.ima` by walking the FAT chain and hashed it:

```
ZORK0.ZIP   size=300032  sha256=a89c38f0072c8b2aaf9d2ce61c613d81ac79fcdec66419dfa92bda8db25affc1
stories/zork0-r393-s890714.z6  a89c38f0072c8b2aaf9d2ce61c613d81ac79fcdec66419dfa92bda8db25affc1
```

**Byte-identical.** Header opens `06 00 01 89` — version 6, flags 0, release `0x0189` = 393, matching the fixture's own name. So `.ZIP` is simply Infocom's DOS filename extension for a bare Z-machine story file (Z-machine Interpreter Program), and `zvm` already reads it today with no work at all. Likewise `zork0.cg1` (244507) and `zork0.eg1` (333654) in `stories/` are exactly the sizes on floppy4 and floppy5 — the user's loose fixtures came off these very disks.

**So this quest is purely a container/mount problem. There is no new story format and no new art format to support.**

ONE REAL GAP, and one trap in fixing it. `picker.rs:108` `STORY_EXTS` is:

```rust
&["z3","z4","z5","z6","z7","z8","zblorb","blorb","zlb","dat","ulx","gblorb","blb","adf"]
```

* `dat` IS present — so the Lost Treasures `.DAT` stories are already listed once extracted. Nothing to do.
* `zip` is ABSENT — an extracted `ZORK0.ZIP` would run fine if opened directly but would not be LISTED by the picker.

**Do not simply add `"zip"` to that list.** `has_story_ext` is extension-only, and a story directory very plausibly contains real PKZIP archives; listing every one of them as a story is a worse bug than the omission. If `.zip` is to be supported, gate it on CONTENT — `blorb`'s `looks_like_story` already exists for exactly this, and the ADF reader's whole design is "identify candidates by content, use conventional names only as a tiebreak". That is the pattern to follow here.

SURVEY 2 — *The Lost Treasures of Infocom Vol II*, added by the user as `disk1.img` … `disk4.img` (4×720K). Measured 2026-08-13. **This CORRECTS the volume-label hypothesis in the first survey.**

```
disk1  DISK 1   AMFV.DAT 262018 + AMFV.COM, YES.COM, SETUP.INF/EXE, INSTALL.EXE/DAT, DISK.ID
disk2  DISK 2   PLUNDERE.DAT 128963 + .COM, TRINITY.DAT 262065 + .COM, DISK.ID
disk3  DISK 3   BORDERZO.DAT 178373 + .EXE, BUREAUCR.DAT 243341 + .COM, CUTTHROA.DAT 112640 + .COM,
                SEASTALK.DAT 117763 + .COM, DISK.ID
disk4  DISK 4   NORDANDB.DAT 170285 + .COM, SHERLOCK.DAT 188445 + .EXE, HOLLYWOO.DAT 109651 + .COM,
                WISHBRIN.DAT 128905 + .COM, DISK.ID
```

FOUR THINGS THAT CHANGE THE DESIGN:

1. **`DISK.ID` is the real set identity, and it is machine-readable.** 53 bytes of plain text, present on every disk:
   `'The Lost Treasures of Infocom Vol II\r\n1.00\r\nDisk 1\r\n\x1a'`
   Set name, version, disk number, DOS EOF. That is exactly what a set model needs, and it is far better evidence than anything inferred.

2. **VOLUME LABELS ARE NOT SET IDENTITY — the first survey's hypothesis is FALSIFIED.** Vol II labels its disks the generic `DISK 1` … `DISK 4`, which says nothing about which collection they belong to; only Vol I happened to use `Tresure.1` … `Tresure.5`. Do not build set detection on the volume label. (Recorded as a caution in survey 1; now settled as wrong.)

3. **Vol II needs no cross-disk set model at all.** Every game is self-contained: each `.DAT` sits on the same disk as its own interpreter (`AMFV.COM`, `TRINITY.COM`, `SHERLOCK.EXE` …), and there is NO art anywhere — all twelve titles are text-only. The cross-disk asset problem is specific to the v6 graphical titles: Vol I's Zork Zero (story + EGA on floppy5, CGA on floppy4) and the standalone Zork Zero release (story + MCGA on disk 1, CGA on disk 2). So a set model earns its keep only where art exists.

4. **The file extension is unreliable.** These are `.img`; Vol I and the standalone releases are `.ima`. The OEM string differs too (`MSDOS5.0` here, `IBM PNCI` on Vol I, `IBM  3.3` on the standalone Zork Zero). **Detect by content — parse the BPB and sanity-check it — exactly as `blorb::adf::Adf::looks_like_adf` does, rather than by matching a name.** The whole ADF design already establishes this pattern; follow it.

Interpreter naming differs between volumes too: Vol I ships four shared interpreters (`ZIP1.COM`, `ZIP2.COM`, `ZIP3.EXE`, `ZIP4.EXE`) plus `INFOCOM.EXE`, while Vol II pairs a per-game binary with each story. Neither is something we need to run — noted only so a content scan is not surprised to find executables that look nothing alike.

## The same title on two media is not the same GAME — it is not even the same Z-MACHINE VERSION

Extracted both copies of `HITCHHIK.DAT` and read their headers:

```
standalone .ima            v3  r58  s851002  113333 bytes  sha256 c678e01937f8c1ea…
Lost Treasures I, floppy2  v5  r31  s871119  158413 bytes  sha256 26dcdab275054e58…
```

**v3 against v5.** The collection ships the later "Solid Gold" edition — a different engine version, a different release, a different serial, and 45 KB more story. The project's standing rule says a disk image is a different release rather than the same story on other media; this is that rule at its most extreme, and it is now demonstrated rather than asserted. Any finding about "Hitchhiker's" MUST name which medium and which release, and a result off one proves nothing about the other.

Practical consequence: the Solid Gold v5 releases carry **built-in hints**, which `crates/app/src/hints.rs` already knows how to surface (it reads them out of `.adf` today). So a mounted collection disk may expose in-game hints where the standalone disk of the same title cannot.

## One new structural fact: subdirectories exist

This disk has a `DEMO` directory — the first subdirectory anywhere in the corpus surveyed. So a FAT12 reader cannot assume everything lives in the root. Either recurse, or do what `blorb::adf::Adf` already does and **scan for candidates by content rather than walking the directory tree** — which finds files in subdirectories for free and is less code. That is a second, independent argument for the content-first design the ADF reader established.

## Corpus summary so far (all FAT12, 512-byte sectors, 2 sectors/cluster, 112 root entries)

| media | OEM | sectors | shape |
|---|---|---|---|
| Lost Treasures I, `floppy1-5.ima` | `IBM PNCI` | 1440 | 20 stories + shared ZIP1-4 interpreters; **Zork Zero's art spans disks 4 and 5** |
| Lost Treasures II, `disk1-4.img` | `MSDOS5.0` | 1440 | 12 stories, each self-contained with its own interpreter, no art; `DISK.ID` names the set |
| Zork Zero standalone 720K | `IBM  3.3` | 1440 | story + MCGA on disk 1, CGA on disk 2 |
| Zork Zero standalone 360K | — | 720 | three disks, not yet dumped |
| Hitchhiker's standalone 360K | `IBM  2.0` | 720 | one disk, has a `DEMO` subdirectory, v3 r58 |

Four different OEM strings across four sources, two disk geometries, two file extensions (`.ima`, `.img`), root-only and subdirectoried layouts. **Nothing about the filename or the OEM string is a reliable signal. Parse and sanity-check the BPB.**

--- note 2026-08-14T01:21:12Z ---

BUILT. `crates/blorb/src/fat12.rs` (hand-rolled, zero deps) + two `FORMATS` rows (`Fat12Dos`, `Fat12AtariSt`) over one reader, since GEMDOS puts its BPB at the DOS offsets.

DISCRIMINATOR: **the x86 jump over the BPB** (`EB xx 90` or `E9 xx xx`). DOS's own load protocol requires it — the BIOS executes the sector from offset 0 — and GEMDOS has no such requirement (TOS runs a boot sector only when its 256 big-endian words sum to 0x1234). Unanimous across the corpus, which is 24 images, not 17: 15 DOS + 9 ST. Deliberately NOT the `55 AA` at 510, which agrees on all 24 but is a boot signature on one machine and a CHECKSUM word on the other — one coincidence from being wrong, and two rules that can disagree need a tie-break nothing establishes. The agreement is pinned as a test so a counterexample in `stories/` is caught.

CORRECTIONS TO THE SURVEYS:
- The Zork Zero **360K release is now dumped**: three disks. Disk 1 = `INSTALL.EXE`/`EZR.EXE`/`IZORK0.RUN` + `ZORK0.CG1`; Disk 2 = `ZORK0.ZIP` + `ZORKZERO.EXE`; Disk 3 = `ZORK0.EG1` alone. (Survey 3 listed it as "not yet dumped".)
- Vol I volume labels are `Tresure 1` (space, then NULs in the 11-byte 8.3 label), not `Tresure.1`.
- ST comps 1-7 are 11 sectors/track, 1804 sectors; comp **8 has 96 root entries**, comp 9 has 112 — root-entry count is not constant.
- `SEASTALK.DAT` on Lost Treasures II disk3 is r16 **s850603**, while the ST's `SEASTAL.T` is r16 **s850515**: same release number, different serial. Release alone is not an identifier either.

**GEMDOS DOES NOT REPEAT THE MEDIA DESCRIPTOR IN FAT[0].** All nine ST disks declare media `F9` at 0x15 and open their FAT with `00 00 00`. The classic `FAT[0] == media` sanity check is a DOS convention, not a FAT12 one; requiring it rejected every ST disk in the corpus. Recorded in `Bpb::parse` as a NOT-checked with the reason.

DECISION FOR THE USER (deliberately not taken here): the DOS row answers `interpreter_number: None`, not ZMSD §11.1.3's 6. Reason: `InterpreterProfile::IbmPc` — where a DOS disk resolves — already returns `None` on purpose, because the IBM PC's honest number is version-dependent (Frotz's 6-for-v6/1-otherwise) and no single constant expresses it. Hard-coding 6 is NOT inert: `BEYONDZO.DAT` is on `floppy1.ima`, and *Beyond Zork* swaps Font 3 arrows for CP437 character graphics when it believes it is on an IBM PC. That may well be the authentic Lost Treasures experience — it is a visible rendering change on real media that a container lane cannot settle, and it needs the user's eye. Flip the row's `interpreter_number` to `Some(6)` if wanted.

STILL OUT OF SCOPE, reported not built — the multi-image SET model. What it needs: (1) a way to name several images as one release, since `DISK.ID` (53 bytes of plain text, on every Lost Treasures II disk) is the only machine-readable set identity in the corpus and Vol I has none — volume labels are FALSIFIED as set identity, Vol II uses the generic `DISK 1`…`DISK 4`; (2) a join across mounts, because `MountedDisk` is one image and one volume; (3) a resolution rule for story-here/art-there, which is the only case that earns it — Vol II's twelve titles are each self-contained and text-only. Affected: Zork Zero only (Vol I story+EGA on floppy5, CGA on floppy4; 720K standalone story+MCGA on disk1, CGA on disk2; 360K standalone installer+CGA/story/EGA across three disks).
