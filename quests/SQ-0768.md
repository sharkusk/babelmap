NOT A WORKFLOW BUG — my error, corrected. The quest title overstates it; the real finding is smaller and is recorded here.

`release.yml` extracts the section with `awk '$0 ~ "^## " tag "( |$)"'` where tag is `$GITHUB_REF_NAME`, i.e. **`v0.1.0-beta.5`, with the leading `v`**. Every previous heading is `## v0.1.0-beta.4`, `## v0.1.0-beta.3`, and so on. The beta.5 heading was written as `## 0.1.0-beta.5` without the `v`, so the match found nothing and the release was published with no summary. Fixed in `eb19ac69`; the draft's body was then patched with the extracted section (899 lines) ahead of the download instructions, assets untouched.

Also clarified while investigating: the workflow creates every release as a **draft** (`draft: true`, `prerelease: true` for hyphenated tags), so publishing is a deliberate manual step. The draft state was not caused by the edit.

WHAT IS ACTUALLY WORTH FIXING, and it is what let this through: a missing section emits `::warning::no CHANGELOG.md section found for $GITHUB_REF_NAME` and then **publishes the draft anyway**. Nobody reads a workflow warning after a successful run, so the first sign of trouble was a human noticing the release body was thin. Options, none chosen yet:
- fail the job when the section is empty — a release with no summary is almost always a mistake, and a failed run is re-runnable after fixing the heading;
- or put a visible marker in the draft body itself (`> **No CHANGELOG section found for this tag.**`), so the omission is impossible to miss while reviewing the draft before publishing.

The second is gentler and fits a workflow whose whole point is that a human reviews the draft. Either way the aim is that the signal appears where the release is *reviewed*, not only in the run log.
