--- note 2026-07-16T00:48:50Z ---

FULLY FIXED (67f0dc4). The "SEPARATE WART, not filed" recorded in the previous note WAS the user's reported bug — they diagnosed it directly: "the problem is the map is not being centered because it doesn't know the pane dimensions."

ROOT CAUSE: `apply_recenter` hard-coded an 80x24 pane. `recenter_on` divides the pane by the zoom step (Boxes: 13x7) to place the view, so on a real pane of, say, 140x48 it computed cells_w=6/cells_h=3 instead of 10/6 — putting the target ~3 cells right and ~1 down from the pane's top-LEFT rather than in the middle. That explains the original report ("the center seemed to always happen around the current room, not the selected room") without the selection logic ever being wrong: the selected room was being aimed at correctly, then parked in a corner, while the current room could sit nearer the visual centre by luck. This is why driving both selection routes through the real code showed them working — the target was right, the placement was not.

FIX: `render_map_layered` records the rect it drew into on `state.map_pane_size` (Cell<Option<(u16,u16)>>), and `apply_recenter` reads it. This reuses the render->input channel already established for `input_text_origin` (the input line's screen origin, for click hit-testing); threading a pane param through apply_action's ~40 call sites was the alternative and is far more invasive.

Two deliberate choices:
- Recorded in the LIB (render_map_layered), not in main.rs's draw_frame. draw_frame would have needed the field `pub` and — the deciding point — could not be unit-tested, so deleting the write would have gone unnoticed. In the lib both halves are testable, and recording it at the point of draw means it cannot drift from what the player sees.
- Records `area`, not `body_area`: the run loop's own recentres measure the whole content rect via map_pane_dims(last_panes.map), so a key recentre must agree with them rather than differ by the layer strip's row.

80x24 survives only as a fallback for before the first frame / while the map pane is hidden.

Tests (both halves of the wiring, each mutation-verified): `center_map_measures_the_real_map_pane_not_a_guess` (input) dies when apply_recenter ignores the recorded size; `rendering_the_map_records_the_pane_size_for_recentring` (render) dies when the renderer stops recording. `center_map_falls_back_to_eighty_by_twentyfour_before_the_first_frame` pins the fallback. app 1417 green, workspace green, no new clippy warnings (25 before and after).

Marked done rather than confirm: the centring math and both halves of the wiring are test-covered. The visual outcome is inferred from that, so reopen if pressing `c` still lands off-centre.
