Committed 13d2b90. app 1412 green, tree clean. Left at `confirm`: the stated fallback is fixed and test-covered, but the user's OBSERVED problem was never reproduced.

WHAT THE QUEST ASKED FOR (done): center-map already aimed at the selected room; only the fallback was wrong — no selection meant recentring on the ORIGIN (0,0), an arbitrary corner that need not hold a room. Now falls back to the current room, and an unplaced selection falls through to it too. Origin survives as a last resort. The command's description never mentioned the fallback it actually had; corrected.

USER'S REPORT — NOT REPRODUCED: "when i tried it the center seemed to always happen around the current room, not the selected room". Driven through the real code, both selection routes WORK:
  - key 'n' (select-room next) then 'c'  -> centres on the selected room (verified: scroll matched room 2's centre, not the current room's).
  - LEFT-CLICK a room then 'c'           -> ShowRoomInfo sets selected_room=Some(id), focus=Map, opens the info panel; 'c' then centred on the CLICKED room (scroll=(4,6) = room 2, vs (-1,1) for the current room).
So apply_recenter honours the selection on both paths.

WHY IT MIGHT STILL LOOK WRONG (six auto-recentres on the CURRENT room exist):
  turn.rs:174,354,533   — after every turn; ALSO does select_room(current), so the selection is replaced each turn.
  loop_tick.rs:132,191  — whenever a background TIDY job completes (tidy runs as rooms are discovered), with no user input at all.
  startup.rs:453
The loop_tick pair is the only one that fires unprompted, so it is the best candidate for "it kept snapping back". USER RULED THIS OUT AS A CONCERN: "i'm okay with things like a re-tidy resetting the selected room to current room. the only thing that needs to work is that when i select a room (and nothing else is going on) the center key should center on the box that is clearly selected."

I had changed loop_tick's tidy recentre to follow recenter_target (selection-aware) and REVERTED it on that instruction — the user explicitly does not want it, and auto-follow is intended behaviour.

STILL TO VERIFY (user will check later): select a room with nothing else going on, press 'c', confirm it centres on the highlighted box. If it does not, the next suspects are (a) focus — 'c' is only bound to center-map in Context::Map, and in Game focus 'c' is just a typed character; (b) an open room-panel/overlay changing routing.

SEPARATE WART, not filed: apply_recenter hardcodes an 80x24 pane ("TODO(run-loop): pass the real pane size when available"). The real size lives in the run loop's last_panes, which apply_action cannot reach — so centring is off-centre on any other pane size. turn.rs/loop_tick.rs both pass the real dims via map_pane_dims(last_panes.map).
