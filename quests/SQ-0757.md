--- note 2026-08-10T05:41:16Z ---

USER 2026-08-09: "one other note on amiga shogun, the score: and moves: in the score area are only aligned if the width is 82 or 83 (without map pane). they always align and right justify with the ibmpc version."

WHY THIS IS A GOOD BUG REPORT: it comes with a within-title control and a precise window.
- Same game, same layout, same pane. The only variable is the interpreter profile.
- IbmPc aligns and right-justifies at EVERY width.
- Amiga aligns at exactly 82 or 83 columns and nowhere else, map pane closed.

A two-column-wide window of correctness is the signature of a value computed in one unit and applied in another — the alignment is right only where the two coincide. Shogun's status fields are placed by the game in native pixels; the pane is measured in cells. At 8px cells, 82-83 columns is 656-664 native px, i.e. right where a 640px game screen plus a border lands. Treat that as a hint about where to look, NOT as a diagnosis — measure the actual placement arithmetic before concluding anything.

FIRST MEASUREMENT: dump the native x of the `score:`/`moves:` runs and the column each is placed at, swept across pane widths either side of 82-83, under BOTH profiles, both honour modes. The IbmPc column is the oracle: whatever it computes is correct at every width, so the question is what the Amiga path does differently with the same input.

Note the profile audit finding (2026-08-09): there is exactly ONE branch on the profile variant in the whole app (`interpreter.rs:79`), and the render path never asks which profile is loaded. So the difference cannot be a profile conditional — it must come from the profile's DATA (cell metrics, standard window size, art scale) flowing into shared arithmetic. Find which value differs and why the arithmetic is only correct for one of them.

Related: SQ-0742/SQ-0750 are the other Amiga-vs-IbmPc divergences on this same game, and all three may share the "computed in pixels, applied in cells" family.

WHICH PROFILE VALUE DIFFERS, AND WHY THE ARITHMETIC TOLERATED ONE. Not std_window, not the cell metric, not the palette — `interpreter_number()`. Byte $1E = 4 makes the GAME paint its status band one run per character CELL, padding included (109 runs in the band window), where the same release under interpreter 6 emits 8 runs, one per FIELD, with no padding at all. So the profile data reaches the render path through the game, exactly as the audit predicted; there is still no branch on the profile variant.

THE DEFECT IS OURS, IN THE SHARED ARITHMETIC. `draw_chrome_text_strip` → `collapse_row_rules` merged each row's abutting fragments (SQ-0509, tol 4). Blank runs abut, so a whole row glued into ONE run. A merged run is POSITIONED once through the letterbox scale and then advances ONE TERMINAL COLUMN per character — the two rates coincide only at one column per native 8px cell. Row 0 glued from native x 351 (a 7px gap after SHOGUN broke it there); row 1 glued from x 47. Hence the two rows placed native x 503 differently, by an amount proportional to how much padding each was glued to. Same family as SQ-0727 / SQ-0742 / SQ-0747.

FIX: `merge_strip_fragments` (crates/app/src/render/screen.rs) — the merge no longer glues ink to PADDING. One blank cell (8px) is a word space and still merges, so Arthur's "St Anne's Day, Compline" stays one phrase; a wider blank stretch is layout and what follows it is a field placed at its own scaled column. Three call sites in `collapse_row_rules` swapped. `merge_row_fragments` itself is unchanged (the anchored-band path filters blanks out already).
