## The data already exists

`tests/pty_stream/driver.rs` returns `Capture { bytes: Vec<u8>, flushes: Vec<Flush> }`
with `Flush { at: Duration, offset, len }` — timestamped byte ranges from the REAL
binary under a real pty, driven by a scripted `--keys` spec.

An asciinema v2 cast is a JSON header line followed by `[seconds, "o", data]`
events. So the recorder is mostly a serialiser over what the harness already
collects: one event per flush, `at.as_secs_f64()` and the bytes at
`offset..offset+len`, with the header carrying the width and height the harness
already controls.

That makes this SMALLER than SQ-0942's stills, and independent of it: no font
rasteriser, no new dependency, nothing to decide about typography. It could land
first.

## The design decision that matters: answer as a NON-graphics terminal

The asciinema player does not render kitty graphics (confirmed 2026-08-20; it is a
request on their forum, not a feature). The harness currently answers the
capability queries convincingly AS kitty — deliberately, because a capture that
does not is silently measuring the half-block backend and every geometry number in
it is worthless.

For a CAST that is exactly backwards. Recording a kitty session produces a file
whose graphics escapes the player drops, so the artwork silently vanishes and
lanthorn looks like it draws nothing — the worst outcome.

Answer as a terminal with NO image protocol instead, and lanthorn renders the v6
screen through its CELL path, which `record_cell_path_click_map` describes as
re-laying the screen out "as ordinary terminal text filling the whole pane". That
replays perfectly, and it is honest: it is a real thing lanthorn does on a real
terminal that has no graphics.

So the harness needs the capability answering to be a MODE, not a constant, and the
cast recorder must select the non-graphics one. Whichever it picks should be stated
in the cast's own metadata or filename, because "why is there no art in this
recording" is otherwise a question nobody can answer later.

## What to record

The casts the site plan (`docs/superpowers/plans/2026-08-20-website.md`) calls for,
all of them text-only and so captured completely:

  - the TUI automapper building a map as you walk — the project's differentiator
  - `zvm-cli --machines` — the machine table in the ACTUAL colours, with its
    provenance line; the whole fidelity argument in about four seconds
  - `zvm-cli --period-look "Zork I …adf"` — a v3 game on the Amiga's own blue page
    and block cursor, no TUI chrome in the way
  - `--pin bottom` — a frozen status line with real scrollback, which only exists
    in a recording of an actual terminal
  - one cast per engine: `zvm-cli`, `gvm-cli`, `scott-cli`

## Notes for whoever builds it

- **Pacing will be mechanical.** `--keys` uses `wait:MS`, so a cast has no human
  hesitation. That may read as robotic; it may also read as clean. Worth looking at
  one before deciding whether jitter is wanted.
- **Pin `random_seed`** for any game with randomness, or the cast differs every
  release for no reason (a first fmvpoker comparison on 2026-08-20 showed 37,097
  differing pixels that were entirely a different card deal).
- **The gitignored media** (`stories/`, `treasures/`, `masterpieces/`) is required
  for most of these, so this cannot run in CI as it stands — same constraint as
  SQ-0942, and worth solving once for both.
- Casts embed anywhere, stay small and keep text selectable, which is why they
  carry five of the eight sections in the site plan while video is reserved for the
  one thing they cannot show.

## CORRECTION: half-blocks replay, so a cast CAN carry the artwork

The note above says a cast should answer as a terminal with no image protocol so
lanthorn falls back to its CELL path — the v6 screen re-laid as ordinary text. That
was wrong on two counts and the real answer is both simpler and better.

**Half-blocks are text.** `▀` and `▄` with a foreground and a background colour are
glyphs and SGR, nothing more. Verified 2026-08-20: the asciinema player supports 16
colours, a 256 palette AND 24-bit true colour, via `CSI 38;2;R;G;B m` and
`CSI 48;2;R;G;B m`. So a half-block frame replays exactly. (The one known gap is
iTerm2's COLON-separated RGB form, which the player does not parse; crossterm emits
the semicolon form, so lanthorn is unaffected.)

**And lanthorn already falls back to half-blocks on its own.** `pty_capture`'s own
verdict line says so when the harness declines the kitty query: "NOT KITTY — …so it
detected half-blocks". `ratatui_image`'s picker treats half-blocks as the universal
fallback, so the v6 PIXEL path still runs; it simply renders to cells. The cell
path — genuinely no image protocol at all — is a third thing and not what we want
here.

So the recorder needs no new mode beyond NOT answering the kitty capability query,
and the result carries the artwork at half-block resolution rather than dropping it.
That is a much better cast than plain text: Zork Zero's frame, Journey's picture
column and Arthur's border all survive, chunky but recognisable.

### What this costs

Half-block frames are far heavier in bytes than text frames — every cell can carry
two 24-bit SGR colours, and an animated sequence (Arthur's intro) redraws a lot of
them. Still far smaller than video, and still selectable text, but a long cast of a
graphical title is worth checking for size before it goes on a page. Prefer short
casts of one or two moments over a full play session for the graphical titles; the
text titles and the CLI clients have no such constraint.

### What it does NOT change

The stills and video in the site plan still have a job. Half-blocks are two
vertical samples per cell, so they are honest but coarse — good enough to show that
lanthorn draws the art, not good enough to judge the art by. The `/graphics` page
still wants a real kitty screenshot or a WebM for the "this is what it actually
looks like" claim, with a cast alongside for "and here it is running".
