SURVEY — the user's ST image, measured 2026-08-13. **The headline is that this quest is much cheaper than filed.**

`Infocom Compilation 9 (19xx)(-).st`, 839680 bytes:

```
BPB: bps=512 spc=2 res=1 fats=2 rootent=112 tot=1640 spf=5 spt=10 sides=2
HITCHHIK/      DIR 72   DIR2 0   HITCHHIK.PRG 15739   STORY.DAT 113444
BUREAUCR.ACY/  STORY.DAT 243200  BUREAUCR.PRG 21706   BILL1.SAV 19456  BILL2.SAV 19456
CUTHROAT/      CUTTHROA.PRG 15721   STORY.DAT 112558
LEATHER.GOD/   STORY.DAT 129024  LEATHER.PRG 21093    STEVE1.SAV 12288
DESKTOP.INF 478
```

**GEMDOS puts its BPB at the SAME offsets as DOS FAT12** — `0x0B` bytes/sector, `0x0D` sectors/cluster, `0x0E` reserved, `0x10` FATs, `0x11` root entries, `0x13` total sectors, `0x16` sectors/FAT. The identical parser read this disk with no ST-specific code at all. **So `.st` support is not a second filesystem — it is the same reader plus a geometry the BPB already describes** (820K here: 1640 sectors, 10 per track, 2 sides, against DOS's 720K/1440 or 360K/720). That collapses most of this quest into SQ-0833.

Differences that are real but small: the ST boot sector has a 68000 `BRA.S` at `0x00` instead of DOS's `EB xx 90`, and the OEM field is 6 bytes at `0x02` rather than 8 at `0x03` — **and on this disk it is all zeros**, which is one more reason not to key detection on the OEM string.

## Two findings that bear on SQ-0833's design as much as this one

1. **Every story on this disk is called `STORY.DAT`.** The filename identifies nothing; the DIRECTORY names the game (`HITCHHIK/`, `BUREAUCR.ACY/`, `CUTHROAT/`, `LEATHER.GOD/`). And everything lives in subdirectories — the root holds only `DESKTOP.INF` and four folders. This is the third independent argument for the content-first scan `blorb::adf::Adf` already uses: identify by content, and take the LABEL from the directory rather than the filename.
2. **The disk carries someone's 1996 saved games** — `BILL1.SAV`, `BILL2.SAV`, `STEVE1.SAV`. A content scan must not mistake a save for a story. Worth an explicit negative test.

**A THIRD Hitchhiker's release**, distinct again from both DOS copies: ST is v3 r56 s841221, the DOS standalone is v3 r58 s851002, and Lost Treasures I is v5 r31 s871119. Three media, three releases, two Z-machine versions. Name the exact image and release in every finding.

**CAVEAT ON THE PROFILE HALF OF THIS QUEST:** this compilation is text-only — no v6 titles, no art. So it proves the *format* but exercises nothing of an ST interpreter profile. Before building `InterpreterProfile::AtariSt`, get an ST image of a graphical v6 title (Zork Zero, Arthur, Journey, Shogun); without one there is no way to verify a palette or art path, and a profile written from memory is exactly what this project's rules forbid.

FOUR THINGS WORTH KEEPING:

1. **Two disk shapes and two layouts in one series.** Comps 1-7 are 902K (1804 sectors) with flat 8.3 names in the root; comps 8-9 are 820K (1640 sectors) with one directory per game and every story called `STORY.DAT`. The BPB describes both correctly, so a single reader handles them — but nothing about the naming is stable, which is the fourth corpus to say so.

2. **The same release can have DIFFERENT FILE SIZES on different media.** `LURKING` is 153600 bytes on Comp 5 and 129024 on Comp 8, and both are v3 r203 s870506 — identical release and serial. So **file size is not a release identifier and must never be used as one**; read the header. (Trailing padding differs; the story proper does not.)

3. **`ZORKTUU.T` is v5 r16 s970828** — *Zork: The Undiscovered Underground*, 1997. A post-Infocom Activision release that has drifted into an "Infocom compilation", and a reminder that these compilations are fan-assembled rather than authoritative releases. Provenance here is weaker than for the DOS and IIgs sets, which carry publisher installers and `DISK.ID` files.

4. **Hitchhiker's is r56 s841221 on BOTH ST disks**, so the corpus still holds exactly three Hitchhiker's releases: ST v3 r56 s841221, DOS standalone v3 r58 s851002, Lost Treasures v5 r31 s871119.

**Consequence for this quest:** the container half is ready to build and well-evidenced (and mostly shared with SQ-0833, since GEMDOS puts its BPB at the DOS offsets). `InterpreterProfile::AtariSt` remains unbuildable — there is no ST v6 fixture, so an ST palette or art path could not be verified, and deriving one from memory is exactly what this project's rules forbid. Same position as the IIgs (SQ-0836). Only the Macintosh has a v6 fixture (SQ-0837).

CONTAINER HALF BUILT; **PROFILE HALF STAYS OPEN BY DESIGN.**

The ST reads through `crates/blorb/src/fat12.rs` with no ST-specific code beyond the machine sniff, exactly as the survey predicted. `DiskImage::Fat12AtariSt` is a `FORMATS` row with label `"ST"`, and its `interpreter_number` is **`None`** — where `Hfs` stood before SQ-0838. ZMSD §11.1.3 numbers the ST 5 and that is not in doubt; the number does not travel alone in this codebase, and the corpus scan is why: all 38 stories across the nine compilations are v3/v4/v5, so there is no ST v6 fixture to verify a palette, screen or default colours against. Pinned audibly: *Trinity* off `Infocom Compilation 8` answers VERSION with "Release 11 / Serial Number 860509 / **Interpreter 1**" in `real_media_releases.rs`, so the day an ST press of a graphical title arrives, that line is where the change shows.

PROFILE HALF BUILT (baf460af). The previous note's "stays open by design" is superseded, and the reason it was wrong is worth keeping.

**The blocking argument was: the number travels with a palette/screen/colours, none verifiable without an ST v6 fixture. Both halves of that turned out to be false.**

1. The failure mode the bundle rule guards against — a number that CONTRADICTS the artwork — cannot occur on a corpus with no artwork. All ST stories are v3/v4/v5.
2. The ST's own interpreters answer the other questions outright. `github.com/erkyrath/infocom-zcode-terps` has an `st/` directory, and it is as decisive as `mac/xzip.lst` was for SQ-0838.

## Sourced, verbatim

```
st/stx1.s:384   PINTWD  EQU   30      * INTERPRETER ID/VERSION      (30 = $1E)
st/stx1.s:422   INTWRD  DC.B  5       * MACHINE ID FOR ATARI ST     (XZIP, v5)
st/stx1.s:731           MOVE.W INTWRD,PINTWD(A2) * SET INTERPRETER ID/VERSION WORD
st/stzip.s:340  INTWRD  DC.B  5       * MACHINE ID FOR ATARI ST     (IFEQ EZIP, v4)
st/stzip.s:345  INTWRD  DC.B  0       * (UNUSED)                    (IFEQ CZIP, v3)
st/xzip.c:156   #define DEF_FORE 2    /* default ST foreground id = black */
st/xzip.c:157   #define DEF_BACK 9    /* default ST background id = white */
st/xzip.c:262   return ((DEF_BACK << 8) | DEF_FORE);   /* (used by 68K init) */
```

**The number is a FLAT CONSTANT, not a version-dependent rule** — the question that matters, since that dependence is exactly why the DOS row stays `None`. The only conditional is the v3 build, which DECLINES the byte ($1E means nothing before v4) rather than claiming another machine.

`st/xzip.c`'s `color_table` is §8.3.1's eight colours in order at full saturation (0x03A9 = 937/1000, 0x003E = 62/1000 in VDI units), so palette = Standard, read rather than defaulted. `st/color.note` (5/26/87) adds the ST could show only 4 of the 8 at once in 80-column mode, background always index 0 — a display ceiling a terminal lacks, so nothing to express.

**DECLINED: `std_window`.** Not a gap awaiting a fixture — Infocom never wrote a YZIP for the ST (the repo README lists ZIP + XZIP for `st/`; YZIP appears only for Apple and Macintosh). So there is no ST v6 art for a standard window to size. The ST's own screen word is the LIVE text size (`_rows`/`_columns`, "40 OR 80"), not a pixel geometry.

## What actually moves — all 39 stories booted under 1 and 5, traces diffed

- **32 byte-identical.**
- **6 print the number only**: Sherlock, Border Zone, Nord and Bert, Trinity (comps 5 and 8), ZTUU.
- **1 behaves differently — Beyond Zork** r49 s870917, comp 6 (which opens to it: BEYZORK.T is 262144 bytes vs ~85K per Zork).

Told 1, Beyond Zork opens with **"Is this a VT220?"**; answer NO and you get a stripped screen — no box, compass as `\` and `@-`, "Use the UP and DOWN arrow keys". Told 5 it never asks, draws the boxed UI with block-graphic compass and real ↑/↓, and VERSION changes **"DEC-20 Color Version A" → "Atari ST Color Version A"**. The ST frame is byte-identical to interpreter-1-after-answering-YES, so nothing new is rendered; the ST is simply not asked a DEC-20 question. CP437 is NOT involved (gate is `$1E == 6`), asserted not assumed.

Bonus: with `honor_game_colours = false` the same game says "Atari ST **Version A**" — it drops "Color" when colour is not offered. Pinned in both modes.

CORRECTION TO THE SURVEY: the corpus is **39** stories, not 38 — the earlier note's prose said 38 while its own table listed 39 (6+4+5+4+3+5+4+4+4).

`real_media_releases.rs`'s Trinity pin moved 1 → 5 as intended, and Beyond Zork (Atari ST) was added to MEDIA. New suite `crates/app/tests/suites/atari_st_profile.rs` (4 tests, in the `engines` group). zvm-cli needed no change and now answers "Interpreter 5 Version A" off an ST floppy via the SQ-0839 rule.
