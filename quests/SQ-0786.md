MEASURED 2026-08-11, read-only (a real timing run was not possible — a lane was live in the main tree and building underneath it has already cost work twice this session).

    crates/app/tests/*.rs          103 files  = 103 separately-linked binaries
    zvm 9, gvm 3, scott 2, mapper 3, blorb 0, audio 0
    target/debug/deps executables  626 files, 6.4 GB, mean 10 MB, largest 72 MB (app lib test)
    target/                        38 GB main checkout, ~5 GB per worktree
    workspace Rust                 242,379 lines
    cores / RAM                    12 / 32 GB
    dev profile                    debug = "line-tables-only"  (already set)
    .cargo/config.toml             ABSENT — no linker or build tuning at all
    cargo-nextest / sccache / mold / sold / lld   ALL ABSENT

626 executables against ~120 current test targets means the deps dir is carrying roughly 5x stale artifacts.

HYPOTHESIS, explicitly not yet confirmed — this quest's first job is to falsify or confirm it, not to act on it:
1. **`cargo test` runs test binaries one at a time**, threading only *within* a binary. With 103 app binaries, many of them small, a 12-core machine sits mostly idle. This is the suspected dominant cost.
2. **`cargo clippy --workspace --all-targets` shares almost nothing with the test build** — different rustc wrapper, different fingerprints — so the gate is close to two full passes over 242k lines.

FIRST ACTION: one instrumented run on a QUIET tree. `cargo build --tests` timed separately from the test execution, and clippy timed separately again, so the compile / link / execute split is known before anything is changed. `CARGO_LOG` or `--timings` gives the per-crate breakdown. Everything below is a candidate, not a plan.

CANDIDATES, with their real costs stated:
- **`cargo-nextest`** — global scheduling across all binaries; typically a large win on exactly this shape (many binaries, 12 cores). **COST: it does not run doctests**, and CLAUDE.md's gate cross-checks `Running` + `Doc-tests` line counts against `test result:` lines to catch a binary that died mid-run. Adopting it means restructuring that gate (a separate `cargo test --doc`) — a change to a rule the project states precisely, so it is the user's call, not an implementer's.
- **Fewer, larger test binaries** — the structural fix and the biggest one, since it attacks the 103 links directly. **COST: a large refactor that would collide with every running lane**, and the gate currently relies on per-file names appearing in the `Running` lines (the documented way to catch a newly-added test file that cargo never enumerated). Do not attempt while lanes are in flight.
- **`sccache`** — fits the many-worktrees pattern specifically: every new worktree currently rebuilds ~5 GB from scratch. Does not cache linking, and interacts badly with incremental compilation.
- **A shared `CARGO_TARGET_DIR` across worktrees** — would save disk (38 + 5 + 5 GB) and let lane N+1 reuse lane N's dependency build. **COST: cargo locks the target dir, so parallel lanes would serialise** — which directly opposes the standing preference for running lanes concurrently. Probably wrong for this workflow; recorded so it is not rediscovered as an obvious win.
- **`debug = 0`** instead of `line-tables-only` — cuts link time, loses backtrace line numbers. Modest, real cost.
- **Faster linker** (`lld`/`mold`) — low confidence on macOS, where Apple's ld-prime is already reasonably fast. Measure before installing anything.
- **Prune stale artifacts** — 626 executables where ~120 are current. Minor for build time; meaningful for the 38 GB.

CONSTRAINT ON ANY FIX: the gate's two properties must survive — it must still print 0, and it must still detect a test binary that died mid-run AND a test file cargo never enumerated. A faster gate that quietly stops catching either of those is a regression, not an optimisation.
