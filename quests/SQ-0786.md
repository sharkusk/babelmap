MEASURED 2026-08-11, read-only (a real timing run was not possible — a lane was live in the main tree and building underneath it has already cost work twice this session).

    crates/app/tests/*.rs          103 files  = 103 separately-linked binaries
    zvm 9, gvm 3, scott 2, mapper 3, blorb 0, audio 0
    target/debug/deps executables  626 files, 6.4 GB, mean 10 MB, largest 72 MB (app lib test)
    target/                        38 GB main checkout, ~5 GB per worktree
    workspace Rust                 242,379 lines
    cores / RAM                    12 / 32 GB
    dev profile                    debug = "line-tables-only"  (already set)
    .cargo/config.toml             ABSENT — no linker or build tuning at all
    cargo-nextest / sccache / mold / sold / lld   ALL ABSENT

626 executables against ~120 current test targets means the deps dir is carrying roughly 5x stale artifacts.

HYPOTHESIS, explicitly not yet confirmed — this quest's first job is to falsify or confirm it, not to act on it:
1. **`cargo test` runs test binaries one at a time**, threading only *within* a binary. With 103 app binaries, many of them small, a 12-core machine sits mostly idle. This is the suspected dominant cost.
2. **`cargo clippy --workspace --all-targets` shares almost nothing with the test build** — different rustc wrapper, different fingerprints — so the gate is close to two full passes over 242k lines.

FIRST ACTION: one instrumented run on a QUIET tree. `cargo build --tests` timed separately from the test execution, and clippy timed separately again, so the compile / link / execute split is known before anything is changed. `CARGO_LOG` or `--timings` gives the per-crate breakdown. Everything below is a candidate, not a plan.

CANDIDATES, with their real costs stated:
- **`cargo-nextest`** — global scheduling across all binaries; typically a large win on exactly this shape (many binaries, 12 cores). **COST: it does not run doctests**, and CLAUDE.md's gate cross-checks `Running` + `Doc-tests` line counts against `test result:` lines to catch a binary that died mid-run. Adopting it means restructuring that gate (a separate `cargo test --doc`) — a change to a rule the project states precisely, so it is the user's call, not an implementer's.
- **Fewer, larger test binaries** — the structural fix and the biggest one, since it attacks the 103 links directly. **COST: a large refactor that would collide with every running lane**, and the gate currently relies on per-file names appearing in the `Running` lines (the documented way to catch a newly-added test file that cargo never enumerated). Do not attempt while lanes are in flight.
- **`sccache`** — fits the many-worktrees pattern specifically: every new worktree currently rebuilds ~5 GB from scratch. Does not cache linking, and interacts badly with incremental compilation.
- **A shared `CARGO_TARGET_DIR` across worktrees** — would save disk (38 + 5 + 5 GB) and let lane N+1 reuse lane N's dependency build. **COST: cargo locks the target dir, so parallel lanes would serialise** — which directly opposes the standing preference for running lanes concurrently. Probably wrong for this workflow; recorded so it is not rediscovered as an obvious win.
- **`debug = 0`** instead of `line-tables-only` — cuts link time, loses backtrace line numbers. Modest, real cost.
- **Faster linker** (`lld`/`mold`) — low confidence on macOS, where Apple's ld-prime is already reasonably fast. Measure before installing anything.
- **Prune stale artifacts** — 626 executables where ~120 are current. Minor for build time; meaningful for the 38 GB.

CONSTRAINT ON ANY FIX: the gate's two properties must survive — it must still print 0, and it must still detect a test binary that died mid-run AND a test file cargo never enumerated. A faster gate that quietly stops catching either of those is a regression, not an optimisation.

--- note 2026-08-12T04:18:14Z ---

THE STATED BLOCKER DOES NOT EXIST — measured 2026-08-11, and it removes the one reason this quest was framed as "the user's call".

The previous note said adopting `cargo-nextest` would mean restructuring the gate because nextest does not run doctests, and CLAUDE.md's completeness cross-check counts `Doc-tests` lines. **This project has zero doctests, by deliberate policy.** Six of seven crates carry `doctest = false` in their `[lib]` section, each with the same comment:

    # No doctests in this crate; skip the rustdoc doctest pass (it costs seconds of
    # harness compilation for zero tests). Drop this if real doctests are added.
    doctest = false

Present in `app`, `blorb`, `zvm`, `gvm`, `mapper`, `audio`. Confirmed against a live gate run: `grep -c '^   Doc-tests'` over the output = **0**.

Two consequences:
1. **The `Doc-tests` term in the gate's grep counts a category that can never appear.** It is vestigial. It costs nothing to keep and should stay as a tripwire (if someone drops `doctest = false`, the count changes and the cross-check still works), but it is not an argument against any tool.
2. **`scott` is the only crate without the setting** and has zero doc-comment code fences, so it pays the rustdoc harness compile for nothing. Free win, one line.

SECOND MEASUREMENT — the shape that makes global scheduling worth it. From a partial gate run (51 of 124 binaries complete):

    binaries: 51    total tests: 2715    median tests/binary: 3    max: 2343
    binaries with <= 3 tests: 25 of 51

**Half the binaries carry three tests or fewer, while one carries 2343.** `cargo test` runs binaries strictly one at a time, parallelising only *within* a binary — so on 12 cores a 3-test binary uses at most 3 threads and then the process exits. And these are not fast unit tests: many app integration binaries drive a whole story through a VM, so a 3-test binary can be slow *and* nearly serial. That is precisely the workload global scheduling fixes, because binary A's three slow tests would overlap binary B's.

`cargo-nextest` 0.9.143 installed from the prebuilt binary (no compile, no project dependency, reversible by deleting `~/.cargo/bin/cargo-nextest`). Next step is the A/B on a quiet tree: same merged HEAD, warm cache, `cargo test` vs `cargo nextest run`, plus a separately timed `cargo clippy --workspace --all-targets` so the clippy share is known rather than assumed.

CONSTRAINT UNCHANGED: whatever replaces the gate must still print 0 AND still catch (a) a test binary that died mid-run and (b) a test file cargo never enumerated. nextest reports per-binary results and a summary, so both remain checkable — but the exact grep will need rewriting against nextest's actual output format, not against an assumed one.

**Same test set, verified rather than assumed**: `cargo test` summed 4176 passed / 12 ignored across 125 `test result:` lines; nextest reported `Starting 4176 tests across 124 binaries (12 tests skipped)` → `4176 tests run: 4176 passed (2 slow), 12 skipped`. The 125-vs-124 binary count is explained: six binaries report `ok. 0 passed` under cargo test (all their tests filtered out) and nextest counts only binaries with tests to run. Not a completeness gap.

`user 784s / real 98.66s` = **7.9x parallelism**. cargo test was achieving roughly 1.4x on the same work. The serialisation hypothesis is confirmed with numbers, and the earlier distribution measurement explains why it bites so hard: median 3 tests per binary, 25 of 51 sampled binaries at <= 3 tests, one binary at 2343 — and many app binaries drive a whole story through a VM, so a 3-test binary is both slow and nearly serial.

**CORRECTION TO THIS QUEST'S OWN HYPOTHESIS #2.** It said clippy is "close to a second full pass". Half right: 149s cold, **0.29s warm**. Clippy is a one-time cost after a test build, not a recurring tax, and it is cheap enough to re-run rather than reason about. The dominant cost was always `cargo test`'s binary-at-a-time execution.

WHOLE GATE: ~691s (11m31) before, ~248s (4m08) after, and ~99s on a repeat with no source change since clippy stays warm.

CHANGES MADE:
- `CLAUDE.md` — the gate is now `cargo nextest run -p blorb -p zvm -p gvm -p scott -p app 2>&1 | grep -acE "..."`, still "must print 0", with the grep-exits-1-is-the-pass note kept. Completeness is now checked against **nextest's own summary** (`Starting N ... across M binaries` must be followed by `N tests run: N passed`, same N) rather than by counting `Running` vs `test result:` lines — a binary that dies now fails the run outright instead of vanishing. The never-*enumerated* caveat is unchanged and still stated, with `cargo nextest list | grep <name>` as the check when adding a test file. Install line and the measured numbers are recorded in the file so the next reader does not have to rediscover them.
- `crates/scott/Cargo.toml` — added the `doctest = false` block the other six crates already had; scott was paying a rustdoc harness compile for zero doctests.

TWO CAVEATS WRITTEN INTO CLAUDE.md, because they are real semantic differences and not just speed:
1. **nextest runs each test in its own process.** A test depending on state another test left behind in the same binary will fail under it. That is a defect being exposed, not an incompatibility — but someone will hit it eventually and should know what they are looking at.
2. **It does not run doctests**, which costs nothing here because every crate now sets `doctest = false`. If a real doctest is ever added, remove that setting and run `cargo test --doc` alongside.

NOT DONE, and no longer obviously worth doing: the "fewer, larger test binaries" refactor. It was the biggest structural lever when execution was serial; with global scheduling the 103-binary layout is no longer the bottleneck, and the refactor's cost (colliding with every lane, plus the gate's reliance on per-file names) now clearly exceeds its benefit. Left recorded rather than pursued. `sccache` and the shared-target-dir idea are likewise untouched — the cold-worktree build remains unmeasured, and is the one case this quest did not address.

Method: `touch crates/blorb/src/lib.rs` (forces blorb, app and every dependent test target to rebuild), then `cargo build --tests -p blorb -p zvm -p gvm -p scott -p app --timings`.

    real 140.95s

        15.84  app babelmap "bin"
        15.66  app pty_oracle "test"

        14.62  app v6_fmvpoker_hybrid "test"
        14.57  app v6_journey_menu "test"
        ... ~100 more app test targets at ~14s each

**IT IS NOT LINK-DOMINATED. Each test target is a separate CRATE costing ~14s to compile**, and there are ~103 of them. The earlier "~272s of linking" figure was inferred by subtraction from a run that also changed `crates/scott/Cargo.toml` (a manifest change widens the rebuild), so it overstated both the total and the attribution. A clean rebuild of everything after touching a low-level crate is **141s**, not 272s.

Also note the parallelism is already GOOD — 10.9x on 12 cores. There is no idle-core problem here, unlike the execution half. The cost is total work, not scheduling.

**THIS INVALIDATES THE OBVIOUS FORM OF THE CONSOLIDATION FIX.** Collapsing 103 test binaries into ONE would compile a single ~32k-line crate whose front end is largely single-threaded, forfeiting the 10.9x parallelism that currently hides most of the cost. It could plausibly be SLOWER in wall-clock. The plausible shape is instead ~10-12 binaries — grouped by topic, matched to core count — which cuts the per-crate overhead paid 103 times while keeping enough units to fill the machine. That is a different and more delicate refactor than "merge them all", and it must be measured, not assumed.

MECHANISM IS AVAILABLE AND ALREADY PROVEN IN-REPO: `crates/app/tests/pty_stream/` is a subdirectory cargo does NOT auto-build, and three test files already pull it in via `mod pty_stream;` and `#[path = "pty_stream/driver.rs"]`. So moving `tests/*.rs` into `tests/suites/` and declaring them as `#[path]` modules from a small number of group binaries needs no content rewrite — and the 46 duplicate copies of `fn stories_dir() -> PathBuf` do not collide, because each file becomes its own module.

COSTS, unchanged and real: it changes a documented workflow (`cargo test -p app --test v6_arthur_status` becomes a filter against a group binary, and CLAUDE.md's command list would need updating), and it must not be attempted while lanes are in flight. The gate's per-file check survives, since nextest reports test names module-qualified and the module name is the old filename.

A/B RUNNING: ten `v6_*` files built as ten separate binaries versus the same ten as one consolidated binary, both after touching blorb so they share identical rebuild overhead. The delta is the per-crate overhead consolidation would actually recover, measured rather than argued.

CONSOLIDATION MEASURED 2026-08-11 — decisive, and it retires the objection I raised against it two notes ago.

FIRST ATTEMPT WAS INVALID, recorded so nobody quotes its numbers: I ran `cargo build --tests -p app --test X ...`. The `--tests` flag selects ALL test targets and unions with `--test X` rather than narrowing to it, so arm A built the whole suite (225.78s) while arm B inherited that work and built one target (140.21s). Those two figures compare nothing. (A separate zsh trap on the way: unquoted `$A` does NOT word-split in zsh, so a built-up argument string arrives as one argument — use an array.)

CORRECT RUN, `--tests` dropped so each arm builds only what it names, each arm preceded by `touch crates/blorb/src/lib.rs`, ordered C then B then A so the consolidated arm cannot inherit the separate arm's work:

    C  overhead only (blorb + app lib)        9.04s
    B  ten v6_* files as ONE binary          15.05s   ->  B - C =  6.01s
    A  the same ten as TEN binaries          23.33s   ->  A - C = 14.29s

**2.4x**, and it cross-checks against an independent measurement: 14.29s per 10 files extrapolates to ~147s for 103 files, against the 141s full rebuild measured by `--timings`. The arms are consistent with each other and with the earlier run.

**TEST SET IS PRESERVED EXACTLY**: `cargo nextest list` reports **40 tests in the consolidated binary and 40 across the ten separate binaries**. The ten files carry duplicate `fn stories_dir() -> PathBuf` definitions and consolidated without collision, because each file becomes its own module. Sample is representative — 2921 lines against 19043 for all `v6_*` and 32243 for the whole corpus.

PROJECTED WHOLE-GATE PICTURE (build figures corrected to the 141s measurement, not the earlier bad 272s inference):

    phase              originally   now (nextest)   + consolidation
    build + link          141s          141s            ~25s
    test execution        542s           97s             97s
    clippy (cold)         236s          236s            ~60s   (--all-targets analyses every test target too)

**THE WORKFLOW OBJECTION LARGELY EVAPORATES UNDER NEXTEST.** I had recorded that consolidation changes a documented command (`cargo test -p app --test v6_arthur_status`). nextest filters by test NAME, not by binary, and the module path carries the old filename — so `cargo nextest run v6_arthur_status` keeps working. That was the main user-visible cost and it is mostly not a cost.

MY EARLIER OBJECTION IS ALSO RETIRED. I argued consolidation would forfeit the existing 10.9x parallelism by serialising one big crate's front end. That is true of collapsing to ONE binary and false of grouping: ~10-12 group binaries keep enough units to fill 12 cores while paying the per-crate overhead 10x fewer times. The measurement above is exactly that shape — ten files per group.

MECHANISM, already proven in-repo: `crates/app/tests/pty_stream/` is a subdirectory cargo does not auto-build, and three test files pull it in via `mod pty_stream;` / `#[path = "pty_stream/driver.rs"]`. Moving `tests/*.rs` into `tests/suites/` and declaring them as `#[path]` modules from group binaries needs no content rewrite.

KNOWN WRINKLE FOR THE IMPLEMENTER: `pty_query_replies.rs`, `pty_emitted_stream.rs` and `pty_oracle.rs` each declare `mod pty_stream;` or `#[path = "pty_stream/driver.rs"] mod driver;`. Two of them inside one group binary compile (each nests under its own module) but duplicate the shared code. Either keep the three pty files in their own group, or hoist `pty_stream` to a single `mod` in the group root. Decide deliberately.
