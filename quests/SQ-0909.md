## What landed, and the finding under it

The absence of scrollback was self-inflicted. A terminal pushes a line into history only when the FULL screen scrolls; a line scrolled out of a DECSTBM region is **discarded**. Pinning the status bar therefore threw away every line of narrative the player had read.

Nothing is stored on our side. The rule is the one `quiet_status_line`'s doc already argued: **one row is chrome, taller is content.** One-row status bars flow into the transcript and reach history; menus, forms, InvisiClues panels and BeyondZork's compass still pin.

`/pin` toggles it, because height cannot settle every case: an InvisiClues menu is transient and releases itself, while BeyondZork's stats-and-compass is permanent chrome, so pinning it would cost scrollback for a whole game. That is not a property of the window — it is what the player is doing right now.

**The premise is measured, not asserted.** `screen::scrollback_tests` feeds `enter_region`/`leave_region`'s own output to `qwertty-term-vt` (Ghostty's core, the second opinion `app` already uses for image placement) and counts history: **0** rows survive a pinned run, a full screen's worth survives an unpinned one, and history resumes the moment the region is dropped — which is what makes `/pin` usable mid-session rather than a launch flag. Testing our renderer against our own decoder would only have proved it agrees with itself. Dev-dependency only; `cargo tree -p zvm-cli -e normal | grep -c qwertty` prints 0.

## What gvm-cli needs, and why it is not the same job

`glk_term.rs` confines a buffer window below grid windows with the same DECSTBM, but Glk layouts are arbitrary — grid above buffer, side-by-side, gutters, sub-column bands — and a grid window is usually genuine content rather than chrome. There is no honest one-row heuristic, so it wants the `/pin` toggle without the automatic rule, defaulting to pinned as it does today. The measurement above already covers the mechanism; what is left is the plumbing and deciding what `/pin` means when several windows are pinned at once.

## Done, and by a different route than the first attempt

Commits c978201e (zvm-cli + the shared module) and ac52b076 (gvm-cli). Gate 0, clippy clean, 5620/5620.

### The design, after the first one was rejected

The first attempt (1bcea805) bought scrollback by UNPINNING one-row status bars — pin only content, let chrome flow. The user's verdict was direct: *"this is not what i want."* Correct, and the reason is that it gave up the thing the player looks at to get the thing they occasionally want.

The real answer came from a second measurement. A terminal archives a line that scrolls off the **top of the screen**, and it judges that by the scroll region's TOP MARGIN — not by whether a region exists. Fed 30 lines to a 10-row screen, against Ghostty's core:

| region | rows reaching history |
|---|---|
| none | 21 |
| rows 2..10, pinned at the **top** | **0** |
| rows 1..9, pinned at the **bottom** | **22** |

So pinning is not what costs the history; pinning *at the top* is. Move the same rows to the bottom, the region starts at row 1 again, and everything scrolling past is archived exactly as with no region at all. **You can have both.**

`--pin <top|bottom>`, default `top` — where Infocom put it, and unchanged for anyone who does nothing. `--scrollback` is an alias for `--pin bottom`, on the `--screen-reader`/`--plain` precedent: the placement is the mechanism, the history is what a player actually wants, and nobody looking for scrollback searches for "pin". `/pin [top|bottom]` swaps it mid-session, because the reason to move it changes within one game.

**Nothing is buffered by babelmap.** That was the question the user asked — *"do we need to manage our own scroll?"* — and the answer is no, which is worth recording because the alternative was real: a ring buffer, a pager, re-wrapping on resize, SGR replay, and mouse reporting that would have DISABLED the terminal's own text selection. Worse than the native history at everything people use history for.

### The three clients

| client | state |
|---|---|
| **scott-cli** | already correct — emits no escape sequences at all, has no status window to pin, always had native scrollback. Verified rather than assumed (`\x1b` appears nowhere in it). |
| **zvm-cli** | full support, both placements |
| **gvm-cli** | the ordinary layout — full-width grids stacked above one full-width buffer — swaps; anything else is left where Glk put it |

gvm-cli's swap rewrites the RECTS once in `window_layout` rather than remapping rows at each of the eleven sites that turn a rect into a screen row. Everything downstream reads the rects and needed no change, and under the default placement `swap_bands` is never called, so the shipped path cannot regress.

### Common code moved to cli-host

`cli_host::pin` now owns the placement, the region helpers, the `/pin` parser and the exit teardown — gvm-cli had its own copy of `leave_region`. `enter_region` stays local to gvm-cli because it confines a band between two explicit rows, where the shared helper puts N rows of chrome at one end; that difference is documented at both sites.

### Also: every exit now un-pins AND parks below the game (SQ-0913)

Dropping the region without moving the cursor left the shell prompt in the middle of the story — the user's reported symptom. The paths that got it wrong were the ones that never reach `main`: zvm-cli's Ctrl-C/Ctrl-D passed `leave_region()` alone, gvm-cli's passed an empty prefix, and gvm-cli's normal teardown did too. Both placements need the same treatment, since the bottom row is occupied either way — by the last line of story under a top pin, by the chrome itself under a bottom pin.
