## The remaining half of SQ-0905's class

SQ-0958 made every READER state the palette it assumes, enforced by `palette_lock_discipline`'s new reader case and paired structurally by `app::v6_palette(p)` (which takes `V6_PALETTE_LOCK` and installs a palette in one call, so you cannot hold one without naming the other).

What it did NOT do: every guarded WRITER still installs a machine palette and never puts `Palette::Standard` back. The table stays dirty for the remainder of that group binary's process, so correctness now rests entirely on each reader declaring itself. That works, and it is checked — but it is the weaker of the two guarantees, because a reader that forgets is a defect while a writer that cleans up would make forgetting harmless.

`v6_shogun_title_header` is the worked example: it boots `shogun-r322-s890706.z6` under `InterpreterProfile::IbmPc`, installs the IBM YZIP table, and leaves it. Five more `v6_shogun_*` siblings install machine tables too. That is what made `shogun_hybrid_status_band_floods_game_background` and `shogun_raster_status_band_floods_game_white` read `Rgb(173,173,173)` where they expected `#FFFFFF`.

## The fix, and why it was deferred

Make the guard restore the previous palette on drop. The cost is not the restore — it is that the 29 suites still using their own `static PALETTE: &Mutex<()>` would have to move to `app::v6_palette` first, since a bare mutex guard has nothing to restore. The SQ-0958 lane judged that outside its quest, correctly: it had already swept 41 suites and 231 cases, and mixing a 29-suite migration into that would have made the diff unreviewable.

## Do this WITH the migration, not before it

Restoring on drop while some suites still hold a bare mutex gives a half-state that is harder to reason about than either end — some writers clean up and some do not, and which is which depends on a detail no reader can see. Convert all 29 to `app::v6_palette`, THEN add the restore, as one lane.

## Verification, which the local gate structurally cannot do

`cargo nextest run` gives every test its own process, so no test can observe another's palette and the gate prints 0 either way. This needs `cargo test --workspace`, run several times — CLAUDE.md's Commands section states this exception and SQ-0958 updated it to describe the reader check as well as the writer one.

Worth noting for whoever takes it: SQ-0958 measured that the reader population is not obvious. Sweeping only the 16 suites that assert an RGB literal turned `v6_state` red, because `v6_restore_paint_ground` names no colour at all — it compares one boot's painted ground against another's — and `v6_hardware_palette` flips the table between them, 4080 pixels differing on a PREMISE assertion. The marker set had to cover painted surfaces (`RgbaImage`, `paint_surface`, `pictures_canvas`, `to_rgba8`), which took the population from 16 to 41. Expect the same surprise here.
