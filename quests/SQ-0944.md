## The claim that started this, and the claim it overturns

CLAUDE.md's hybrid rule is "never rasterise what the game printed as a character",
and the stated exception has been text sitting ON artwork — the InvisiClues banner
title, a v6 status strip over a border. The reason given for that exception, by me,
repeatedly, on 2026-08-20, was that a terminal glyph cannot be drawn over a kitty
placement.

**That is not true, and the repository already documented why.**
`tests/pty_stream/raster.rs`, on the kitty protocol's Z index:

    placements below -1073741824 draw under the cell backgrounds, placements from
    there to -1 draw over the backgrounds but UNDER THE TEXT, and z >= 0 draws over
    everything. The z used for that bucketing is the one the RENDERER sorts on,
    which for every virtual placement is the -1 upstream hardcodes.

So every placement lanthorn emits already sits at z = -1: over the cell background
and under the text. A glyph drawn in a cell an image covers appears ON TOP of the
image, with no work at all. The rasterise-text-over-art exception may be
unnecessary on kitty, and if so a good deal of today's reasoning about the
InvisiClues header rests on a limit that does not exist.

Not yet TESTED — this is read from the protocol note, not measured. The oracle can
settle it: place art, print a glyph in a covered cell, and see which wins.
`pty_stream/oracle.rs` resolves draw order the way a real terminal does, so it is
the right instrument.

## The two backends need different mechanisms

**kitty** — nothing to build beyond stopping. Draw the text as glyphs instead of
rasterising it into the chrome canvas; the placement is already underneath. The
existing `glyph_rows` / `TextLayer::SkipGlyphRows` machinery (SQ-0903) is exactly
the control for this: it already tells `build_chrome_canvas` which rows NOT to
paint because the ring will draw them with glyphs. Today `ChromeStrip::Art`
contributes no glyph rows. If the z-order holds, it could.

**half-blocks** — no z-order exists; text and art share one cell, so a glyph must
carry a background, and the right one is the art behind it. Sample the art under
the cell and pick the nearest background so the glyph sits in the picture rather
than in a box. Two vertical samples per cell means the art is coarse anyway, so an
approximate ground will not be conspicuous — while the text becomes exactly right.

## Why half-blocks matter more than they look

Rasterised text on half-blocks is catastrophic: a cell is TWO vertical samples, so
an 8x16 glyph is reduced to 8x2 and is not merely ugly but unreadable. Real glyphs
are perfect. So this is the difference between a usable and an unusable backend
for:

  - terminals with no kitty or sixel at all, and tmux
  - **asciinema casts** (SQ-0943), which record exactly this backend — lanthorn
    falls back to half-blocks when the kitty query goes unanswered, and half-blocks
    replay in the player because they are glyphs plus 24-bit SGR

So this lands directly on the site plan: it is the difference between a cast that
shows a legible game and one that shows coloured mush with a picture in it.

## Order of work

Do the KITTY half first if the z-order holds, because it is subtractive — stop
rasterising, let `glyph_rows` cover art strips — and it is testable against the
oracle without touching the half-block path.

The half-block half needs a new sampling step and a colour-distance choice, and its
result is judged by eye, so it wants frames rather than assertions.

## Related

- SQ-0934 — where the "must be rasterised" reasoning was applied to the InvisiClues
  banner. If this holds, revisit that conclusion.
- `docs/superpowers/plans/2026-08-20-website.md` — half-blocks carry five of the
  eight sections.

## Policy, decided by the user 2026-08-20

Keyed on what the BACKEND can do, not on preference:

    half-blocks    glyphs over art — DEFAULT, and no knob
    kitty          glyphs over art — OPTIONAL, off by default
    sixel, iTerm2  rasterised text only — not offered

### Why each

**half-blocks: default, unconfigurable.** Rasterised text there is two vertical
samples per cell and is unreadable — not a taste, a defect. There is no reason a
user would want it back, so there is no setting. Fewer knobs.

**kitty: optional, off by default.** Here rasterised text is not broken, it is
FAITHFUL: the art and the characters composite exactly as the game drew them, at
the game's own resolution, which is what the machine did. Crisp terminal-font text
over pixel art is a different look — sharper and more readable, less authentic. That
is a genuine preference, so it gets a switch, and the authentic rendering stays the
default.

**sixel and iTerm2: not offered.** Neither has kitty's Z index; their images become
cell content, so text at the same position cannot be layered over them reliably.
The capability is absent, so the option is absent too — rather than offered and
silently doing nothing, which is the trap SQ-0936 fell into when the raster arm
never saw its setting.

### What this implies for the code

The question to ask is "can this backend put text over graphics", with three
answers, and `ratatui_image`'s picker already knows which protocol negotiated — the
same source `pty_capture`'s VERDICT line reads. So it is a capability lookup, not a
guess.

Then the policy on top: half-blocks always on, kitty follows the setting, everything
else forced off. Only ONE config key is needed and it only affects kitty; make sure
its settings row and docs say so, or it repeats SQ-0936's caveat where a setting
appeared to apply generally and quietly did nothing on some paths.

## STEP 1 MEASURED — the kitty premise is FALSE

Measured with the oracle (`pty_oracle.rs`, qwertty-term-vt), two probes on a
virtual placement with a glyph printed into a covered cell:

**Glyph on the LEAD cell** (the one carrying the diacritic triple):

      row1 col2: ch='W'        image_id=None
      row1 col3: ch=U+10EEEE   image_id=None
      row1 col4: ch=U+10EEEE   image_id=None
      row1 col5: ch=U+10EEEE   image_id=None
      PIXELS col2..col5: art=false, default_bg=true  (ALL FOUR)

The whole row's placement dies. The art is not under the glyph; it is gone.

**Glyph on a NON-LEAD covered cell** (diacritics intact):

      row1 col2: U+10EEEE  image_id=Some(..)  source_y=Some(0)   art=true
      row1 col3: U+10EEEE  image_id=Some(..)  source_y=Some(0)   art=true
      row1 col4: ch='W'    image_id=None                         art=false, default_bg=true
      row1 col5: U+10EEEE  image_id=None                         art=false, default_bg=true

The glyph's own cell loses the image AND the run is TRUNCATED — every cell after
the glyph loses it too.

In neither case does a glyph draw over the image. It draws INSTEAD of it, and
takes the rest of the run with it.

## Why, structurally — it was never about z

A kitty **unicode-placeholder (U=1) virtual placement is positioned BY the
placeholder characters in the cells**. The image IS the cell content. There is no
separate glyph layer in those cells to be "over" anything.

The z=-1 "over backgrounds, under text" bucket governs **classic pin-anchored**
placements, where the image is placed by cursor position and the cells keep
independent text. That is exactly what the repo's existing
`a_negative_z_placement_draws_under_the_text` covers — and its own doc comment
already said it pin-anchors "so the text can be printed over it WITHOUT
destroying the placeholder run". The distinction was already written down.

Three independent blockers, any one fatal:

1. **The placeholder IS the image.** Overwriting it removes the image (measured).
2. **`ratatui-image` 11.0.6 emits no `z=` at all.** `transmit_virtual()` writes
   `i={id},a=T,U=1,f=32,t=d,s={w},v={h},` — there is no z parameter. The `-1` in
   `raster.rs`'s note is the number the RENDERER internally sorts virtual
   placements at, which that module's docs actually say ("the z used for that
   bucketing is the one the RENDERER sorts on"). It was read as the z lanthorn
   emits; lanthorn emits none.
3. **The app cannot address those cells anyway.** `ratatui-image` writes the whole
   row's escape into the row's FIRST cell and sets `CellDiffOption::Skip` on every
   other cell in the row, so ratatui's diff would never emit a glyph written there.

## Consequence for the policy

The decided policy had three rows; it collapses to two. Kitty joins sixel and
iTerm2 in "capability absent, so the option is absent" — for a different reason
(placeholder positioning, not missing z), but with the same outcome.

That leaves **half-blocks as the only backend with the capability, and it was
already specified as default-on with no knob. So NO config key is needed at
all.** The one key the plan called for has nothing left to configure.

## FALSIFIED: the kitty half is dead, and the premise above was mine and wrong

The note above says a glyph drawn in a cell a kitty placement covers appears on top
of it, because every placement lanthorn emits sits at z = -1, "over the backgrounds
but under the text". Measured with the oracle, it does not. A glyph printed into a
covered cell DESTROYS the placement:

  - in the LEAD cell (the one carrying the diacritic triple) the entire row's
    placement dies and all its cells fall back to bare background;
  - in a CONTINUATION cell, that cell and every cell to its right lose the image —
    only the cells before the glyph keep art.

**The reason has nothing to do with z.** lanthorn's placements are VIRTUAL (`U=1`),
positioned by `U+10EEEE` placeholder characters — the image IS the cell's content,
so there is no glyph layer in that cell for anything to be "over". Three
independent confirmations:

  1. the measurement above;
  2. `ratatui-image` 11.0.6's `transmit_virtual` emits NO `z` parameter at all. The
     `-1` in `raster.rs` is what the RENDERER sorts virtual placements at
     internally — that module's own sentence says so, "the z used for that
     bucketing is the one the RENDERER sorts on" — and I read it as the z lanthorn
     emits. It emits none;
  3. `ratatui-image` writes the whole row's escape into the row's FIRST cell and
     marks the others `Skip`, so the app could not address them regardless.

**And the repository already knew.** `pty_oracle`'s
`a_negative_z_placement_draws_under_the_text` uses `a=T` — a pin-anchored, classic
placement — and its own doc says it does so "so the text can be printed over it
without destroying the placeholder run". The z-index quote is true for CLASSIC
placements. lanthorn does not emit those. It was true and irrelevant, which is the
harder kind of wrong to catch.

### What that does to the policy

Kitty joins sixel and iTerm2 in "capability absent, option absent". Half-blocks is
then the ONLY capable backend, and it was already specified as default-on with no
knob — so **no config key was needed at all**, none was added, and the
settings-row index hazard never arose. The policy got simpler by being wrong about
one third of it.

### And SQ-0934's conclusion stands after all

The InvisiClues banner really does have to be rasterised on kitty. The reason I
gave for it was wrong, but the conclusion was right for a different reason:
virtual placements own their cells outright.

--- note 2026-08-21T01:40:10Z ---

Follow-up on the user's two notes, both reproduced and fixed (1a3cfd8d, merged + pushed to main).

1. THE RASTERISED TEXT WAS STILL THERE. The row skip fired correctly (measured: glyph_rows=[10,26], runs at y=11/27), but `build_chrome_canvas` gated its "this grid is drawn from its RUNS" `continue` on the runs that SURVIVED the skip. A grid that loses every run — exactly what the ring asks for under half-blocks — fell through to the cell-grid painter, which places rows at `oy + row * FONT_H`. Zork Zero's runs are at native 10/26, the cell grid's at 0/16, so the skip set could never match and the banner was painted straight back in one text row above the glyphs. Gate is now on `g.px_texts`, a property of the grid. Invisible until now because every existing test of the skip has an empty `cells` vec, so the fall-through drew nothing and passed.

2. THE BACKGROUND BEHIND THE HALF-BLOCKS. The bands still shipped alpha and half-blocks has none: ratatui-image's primitive encoder calls `to_rgb8()` (transparent -> RGB 0,0,0) and `pick_side` collapses the equal halves to a SPACE, so the symptom is space cells on black, not anything image-shaped. That was the black gutter down both sides of Zork Zero's pillars where kitty shows the white page. Bands now resolve their transparency onto the same page raster has flattened onto since SQ-0510, via one shared rule (`v6_composite_page`) asked by both modes. Declared per frame on GraphicsRender and hashed with each band. Applied to each band's finished IMAGE, never to the shared canvas — the carves that punch holes in it have not all run, and `v6_border::recognize` reads that canvas's transparency to tell a pillar from its ground.

Kitty/iTerm2 ship an alpha channel and composite it themselves, so they are untouched; flattening for them would paint the letterbox margin the game's page instead of the terminal's ground. Sixel hands to_rgba8() to its encoder and was not measured — it keeps today's behaviour.

Note for a reviewer: `a_banner_glyph_sits_in_the_picture_not_in_a_box` needed a new REFERENCE, not a new tolerance. It sampled "the nearest cell still showing a ▀", and a ▀ is what the encoder emits when a cell's two halves DIFFER — with the ghost gone the ribbon is uniform and comes out as SPACE, so the nearest two-tone cell became the pillar thirty columns away. It now measures against the ribbon itself, and in that form it also falsifies against the ghost.

All three new cases falsified against the unfixed code with the reported symptoms ([0,0,0] in the gutter; the banner back above its glyphs). Gate 5735/5735, clippy clean. Before/after captures at target/sq0944/sq0944-{before,after}.png (117x40, cell 10x20 to match the half-block picker's own font size — the earlier 8x18 captures measured a geometry lanthorn was not using).

Still awaiting the user's eye on a real terminal.
