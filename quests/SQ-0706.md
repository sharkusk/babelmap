--- note 2026-08-09T13:58:24Z ---

FIRST MEASUREMENTS 2026-08-09 (headless probes, both fixtures present in stories/). The two games fail for DIFFERENT reasons — this is two quests wearing one coat.

SUNBURST.Z6 (65KB, NO resource blorb, 0 pictures declared)
Boots clean: quit=false, no fault, menu renders. The menu is NOT inert — it is keyed by each item's LOWERCASE INITIAL, and nothing else:
  i -> Instructions (prints the full intro: "You are George Raft, an employee at a small space trading company...")
  s -> Start game   (title + "Copyright Att Scoddams 1982 / (Type 'about' for help)")
  r -> Reset computer ("As good as reset...") and pending_input flips Char -> LINE, i.e. the game proper begins
  l -> Load game (no output without a save)
  I (uppercase) -> ignored. Enter, space, Esc, arrows (129-132), mouse codes (253/254), digits, y/n -> all ignored, no output.
So the engine drives this game correctly and "nothing is selectable" was discoverability, not a defect.

The REAL sunburst defect, reported by the user once past the menu: after the ">" prompt each typed character gets a linefeed, and the first character starts one line BELOW the ">". zvm performs no input echo at all (no echo path in exec.rs), so this is app-side. Prime suspect, already measured: the model publishes TWO windows BOTH flagged primary=true at the identical (0,0) 640x400 rect, and classify_windows takes the first as `story` and files the SECOND ONE UNDER CHROME. A second primary buffer is not chrome, and if the prompt and the echo are mirrored from different windows that is exactly a one-line offset. Verify that before anything else.

SCOPA.Z6 (101KB, blorb resolves, 82 pictures declared)
Boots clean, but the model contains NO Buffer window at all and NO Graphics window — only three Grids: (0,0) 640x400 bg set, (280,214) 80x1, and (301,190) 38x16 carrying 4 runs (almost certainly the 4-item menu the user cannot click). No @draw_picture has executed, which is why no cards appear: the game has not reached its table yet, it is sitting at its opening menu.
The ONLY screen ops in the whole boot are three of @buffer_screen(mode=-1) -> prev=0 (ZMSD sect.15 v6 double-buffering; -1 = report current mode without changing it). pending_input=Char, and space/enter do nothing.
Next step when resumed: determine what that read_char is waiting for. A v6 menu click arrives at read_char as char 254 (single) / 253 (double) WITH the click coordinates set, so the probe must deliver a positioned mouse click, not the bare code — sending 253/254 alone was tested and does nothing. babelmap already has working v6 mouse (see v6_mouse_zork0.rs, and SQ-0576 compass clicks), so the plumbing exists; the question is whether scopa reads the click through a path we do not feed.

Note the user's framing: both titles fail the same way under Spatterlight, so supporting them is an opportunity to beat the reference interpreter rather than a regression to repair.

--- note 2026-08-09T14:02:07Z ---

SCOPA, SECOND ROUND 2026-08-09 — user reports that in RASTER mode the menu IS clickable (help, credits and quit all work), but the card images still never appear. That splits scopa cleanly into two independent defects.

DEFECT A — clicks work in raster, not in hybrid. Since the VM plainly receives clicks (below), this is a hybrid click-MAPPING bug, not an input-delivery one: the pane->native-pixel transform for the hybrid ring/letterbox must be landing clicks somewhere the game does not recognise. V6ClickMap::map_click and the hybrid scale/offset are where to look; the raster path evidently maps correctly. Cross-check against the existing v6_mouse_zork0.rs harness, which only exercises one mapping.

DEFECT B — no picture is ever drawn, in EITHER mode. Confirmed by tracing: across four positioned clicks that drove the game hard (one produced 45812 screen ops, opening win5 and win3, resizing, setting true colour), the count of @draw_picture ops was ZERO every time. So the cards are not being drawn-and-lost by the renderer; the STORY never issues a draw at all. Any renderer-side hypothesis is therefore already falsified — do not start there.

Mouse plumbing is fine and is NOT the cause: Engine::set_mouse takes (y_px, x_px) in that order, and @read_mouse(array=0x225a) correctly reports back what was set with buttons=0x0001. (A probe that passes them as (x, y) will look like a coordinate swap; it is not one.)

The blorb is healthy: 82 pictures declared and resolvable, and the first eight are all 52x84 — card-sized, exactly the deck you would expect.

NEXT STEP WHEN RESUMED: find what gates the game's decision to draw. Prime suspect is a capability probe the game runs before committing to graphics — @picture_data(0, array) (ZMSD sect.15: number 0 asks for the picture-file release/count rather than one picture's dimensions), and/or the Flags 1 "pictures available" bit for v6. If the game concludes graphics are unavailable it will run its whole table in text and never call draw_picture, which is precisely the observed shape. Trace those calls and their return values before touching anything else.
