--- note 2026-08-11T22:23:39Z ---

DEFERRED BY DECISION, not by neglect. Recorded 2026-08-11 so the reference reading survives and can be picked up later.

WHAT WE FOUND. Bocfel — the interpreter Spatterlight ships — has a dedicated `terps/bocfel/z6/draw_border.cpp`, header: *"Used by Arthur, Shogun, and Zork Zero."* (Journey is absent, which independently corroborates that Journey's frame is TEXT rather than artwork — see SQ-0750.) **It tiles and never stretches**, for all three games including Zork Zero.

THE MECHANISM, worth copying wholesale if this is ever taken up:
```c
static int tile_section_down(uint8_t *section_to_repeat, size_t linessize,
                             int pillar_height, int overlap,
                             int start_y, int desired_height,
                             bool initial_parity, bool flip)

void extend_pillars(int top_cut, int foot_height, int total_height,
                    int pillar_height, int overlap, bool flip,
                    bool bw_hint_foot, int desired_height)
```
  - Structure is **capital → tiled shaft → foot**, which is exactly the shape of Zork Zero's columns as we render them today.
  - Stride between stamps is `pillar_height - overlap`, so tiles OVERLAP rather than butt together; `flip` alternates each tile's vertical flip from `initial_parity`. Both devices exist to hide seams in a repeated pattern — copying the repetition without them would look worse than what we have now.
  - Extends only when the pane exceeds the art: `if (desired_height <= total_height) return;`
  - Ordering hazard they documented: *"Snapshot the pillar strip before erasing anything: for Arthur, top_cut equals total_height - foot_height, so the strip's source rows sit inside the foot region erased just below."*
  - Zork Zero specifically has THREE scene-specific routines — `extend_mac_bw_castle_pillars`, `extend_underground_pillars` (alternating left/right so the masonry stays consistent), `extend_jungle_pillars`.
  - Rationale, verbatim: *"The original games did not do this, but it looks better with modern screen sizes."* Tiling is a modern-interpreter courtesy, NOT fidelity to the originals — so neither approach can claim authenticity, and this is a judgement call about appearance rather than correctness.

WHY WE ARE NOT DOING IT NOW (user decision, having seen the above): Zork Zero renders correctly today — its side canvas is fully painted, columns reach the bottom with a proper base — and its frames are pinned byte-for-byte in the render corpus. Switching it to tiling would move every pinned frame and require re-blessing them all, for no visible gain. Arthur and Shogun are the two with measurably unfilled canvases (empty below roughly 75%), and they are handled by SQ-0698.

PICK THIS UP IF: Zork Zero shows visible distortion at some pane size nobody has captured yet (tall panes are the risk — a stretch factor grows with height while a tile's does not), or if SQ-0698's tiling path lands and it becomes cheaper to run all three titles through one mechanism than to maintain two. Measure before deciding: capture Zork Zero at a deliberately tall pane and look at the shaft's texture for smearing.

MEASUREMENTS ON RECORD (SQ-0698 has the full set): Zork Zero side bands upload 128x972px and place at rows 8..61, cols 1..16 and 100..115 at a 115x61 pane — placement exactly matches upload, canvas fully painted.

--- note 2026-08-11T23:05:56Z ---

UN-DEFERRED 2026-08-11, same day it was deferred. The user ruled that since Arthur and Shogun need per-title side-bar handlers anyway, Zork Zero should get one too — and, asked to clarify, chose **per-title routine AND switch it to tiling**. So this quest's subject is now in scope and is being done as part of SQ-0698 rather than separately.

That reverses the reasoning recorded here this morning ("Zork Zero renders correctly today, its corpus frames are pinned, switching would move every pinned frame for no visible gain"). The counter-argument that won: three titles going through two different mechanisms is worse than re-blessing one title's frames, and the per-title architecture the reference uses makes the marginal cost of Zork Zero's routine small once Arthur's and Shogun's exist.

WHAT THIS QUEST STILL CONTRIBUTES, and why it was worth writing down rather than just deciding: the Bocfel mechanics it captured are the implementation spec — `extend_pillars()`'s signature, the `pillar_height - overlap` stride, the alternating `flip`, the cap → shaft → foot structure, the snapshot-before-erase ordering hazard, and the three scene-specific Zork Zero routines (castle, underground, jungle, the last alternating left/right so the masonry stays consistent). Zork Zero's patterned masonry is precisely the case that NEEDS the overlap and flip, unlike Arthur's plain 2-line texture.

CLOSE THIS TOGETHER WITH SQ-0698. Its acceptance is the same: Zork Zero's re-blessed corpus frames must be a deliberate, explained diff, and the user sees rendered PNGs at several pane heights — including a deliberately tall one, where the old stretch factor was largest and the difference will be most visible — before it lands.
