--- note 2026-08-09T18:20:59Z ---

User's screen, transcribed verbatim from advent.z6's help screen (hybrid/Ghostty, 2026-08-09), after SQ-0712 landed:

                                    About Adventure
     N   n xt subj ct                                           P = previous
     RETURN = r ad subjec                                       Q   r sume game

Almost certainly should read:

                                    About Adventure
     N = next subject                                           P = previous
     RETURN = read subject                                      Q = resume game

WHAT IS DROPPED. Lowercase `e` and `=`, and not uniformly:
- "N = next subject" loses the `=` and both lowercase `e`s (indices 2, 5, 13) but keeps everything else.
- "RETURN = read subject" KEEPS its `=`, loses the `e` in "read", and appears truncated after "subjec".
- "Q = resume game" loses the `=` and the `e` in "resume".
- "About Adventure" on the line above is INTACT, including two lowercase `e`s — so whatever this is, it does not affect that row.
- Uppercase `E` in "RETURN" survives.

DO NOT assume it is glyph-specific. `e` and `=` being the victims may be coincidence of position rather than of character: v6 places text at PIXEL coordinates and the cell paths map that to a fixed grid, so accumulated rounding can drop whichever glyph happens to land in a cell another glyph already claimed. Measure the runs' x coordinates before theorising about characters. That "About Adventure" is centred on its own row while the damaged rows carry left/right pairs is consistent with a column-mapping problem and inconsistent with a font/encoding one.

SECOND, RELATED DEFECT — same rows, different path. The SQ-0712 agent reported, and explicitly did not fix: "advent's help screen renders its reverse-video header rows (About Adventure, N = next subject) fine as cells but they are missing from the RASTER composite. Present both before and after my change, unrelated to either quest." So in raster these rows do not appear at all. Both belong to this quest; a fix should account for the rows existing in one path and being mangled in the other.

STILL UNKNOWN, ask the user: which render mode produced the transcription above (presumed hybrid, unconfirmed), and whether the truncation after "subjec" is real or an artefact of copying out of the terminal.

--- note 2026-08-09T18:22:25Z ---

User answered both open questions 2026-08-09: render mode was **hybrid**, and the truncation after "subjec" is **real**, not a copy artefact.

The truncation matters more than it looks. Interior drops alone (a glyph losing a cell race) would leave gaps but still place the final `t` — the string would keep its span. Losing the tail as well points at a single mechanism instead of two: the run is being fitted into a cell span computed from its PIXEL width, and every glyph past that budget is discarded. Interior collisions and a clipped tail are then the same bug seen twice, and the row's total cell count is the thing to measure first — compare the run's character count against `pixel_width / cell_width` for these rows and see whether the shortfall equals the number of missing characters.

Raster still shows these rows not at all, per the SQ-0712 agent's finding above.

--- note 2026-08-09T19:10:42Z ---

RASTER HALF FIXED 2026-08-09 (commit 9c48ce29, worktree branch worktree-agent-a5638a57fe9a3fae0). The hybrid half of this quest is UNTOUCHED and still open.

ROOT CAUSE, measured. `build_chrome_canvas`'s over-art probe (SQ-0487) asked `region_has_opaque` of the LIVE canvas, which by that point carried the highlight blocks of every reverse run drawn before it. advent paints the help bar as one run per label PLUS reversed spacer spaces; the spacer at 1-based x=289 lands inside "About Adventure" (px 248..368). So the label's probe saw the spacer's own white block, concluded it was over frame art (where a block would erase the picture), drew no block and put its ink in `default_bg` — which `flatten_onto_page` then resolved onto a `default_bg` page. Black on black. Measured before the fix: 93% of the run's span was bare page across 2 colours.

FIX: `build_chrome_canvas` clones the canvas after pass 1 (graphics) and both the per-run probe and `fill_reverse_row_gaps` read that frozen art layer. Exactly what `build_graphics_canvas` already does for the hybrid band decomposition (SQ-0500) — the comment there says the full chrome canvas cannot answer "is this over art?" because rasterized text is itself opaque, and that is the same sentence.

Zork Zero's ribbon labels (the case the over-art rule exists for) still draw dark ink with no block: they really are over the banner artwork, which the art layer still carries. PNG of the help screen after the fix reads: "About Adventure" centred, "N = next subject   P = previous", "RETURN = read subject   Q = resume game", all as dark ink on a light bar.

Tests: crates/app/tests/v6_raster_text_loss.rs, both honor_game_colours modes, asserting the run's span is <50% bare page and carries >=2 colours. Falsified.

STILL OPEN HERE: the hybrid/cell defect — lowercase `e` and `=` dropped from the same rows, and "RETURN = read subject" clipped after "subjec". That is the column-mapping family (shared with SQ-0729's concatenated fmvpoker menu labels) and belongs to whoever owns the cell paths; nothing in this commit touches it.
