USER 2026-08-12: *"so, when we specify eg1 in our config will we automatically also read the eg2 file?"* — **No, and the loss is large.** Measured while answering.

`crates/app/src/graphics.rs` never looks for a sibling part. `InfocomPics::part()` exists in blorb (`infocom_pics.rs:656`) and reads header byte 0, but resolution never consults it — a named archive is opened and that is all.

    arthur.eg1    97 of 137 pictures with data load    40 MISSING (29%)
                  including id 84 (584x196) and id 85 (508x164)
    journey.eg1   80 of 135 load                        55 MISSING (41%)
                  including ids 78, 110, 159, 164 — 222x127-ish scene plates

Zork Zero is unaffected: its 360K release gave EGA a whole disk, so `zork0.eg1` is a single complete part.

**THE FORMAT IS EXPLICIT ABOUT THIS.** Header byte 0 is the part number (`.EG2` files read `02`), and Frotz's DOS port builds the filename as `extension[3] = '0' + number` with the comment *"EGA pictures may be stored in two separate graphics files"* (`src/dos/bcpic.c:61-77`). Its `open_graphics_file(int number)` takes the part as a parameter precisely so the interpreter can open either.

**MEASURED STRUCTURE, so the fix does not have to rediscover it:**

    arthur.eg1  125 entries, ids 1..171, part 1
    arthur.eg2  101 entries, ids 34..171, part 2
                55 ids in BOTH, identical dimensions, different offsets
                union = 171 entries == arthur.mg1 exactly
                union with data = 137 == arthur.mg1's 137 exactly

So the two parts together carry **precisely the MCGA set**, no more and no less. The overlap is deliberate multi-disk practice: EGA art is 640-wide and would not fit one 360K disk, so pictures needed on both sides of the game are duplicated rather than making the player swap. Each disk is self-sufficient for its stretch.

**MERGE RULE THIS IMPLIES:** when an id appears in both parts, either copy will do — they are the same picture at the same dimensions. (Dimensions and ids are measured; **pixel identity is inferred, not verified** — worth confirming with the decoder before relying on "either will do".) Prefer whichever avoids a second file read, or part 1 for determinism; state the choice.

**ANOMALY, unexplained and worth a look but not a blocker:** Journey's EGA union is **135** ids against `journey.mg1`'s **134** — the EGA release carries one picture MCGA does not. Identify it; it may be a genuine per-adapter extra.

**IMPLEMENTATION NOTES:**
- Discovering part 2 by filename (`.EG1` -> `.EG2`) is **not** the stem-based auto-discovery SQ-0734 rejected. That rejection is about pairing an archive to a *story* on a guess. This is following the format's own part number to the continuation of an archive the user already named explicitly — the pairing is asserted, and the part number is in-band. Say so in a comment so nobody mistakes one for the other.
- Still verify what you open: a `.EG2` whose header part byte is not 2, or whose picture ids do not extend the set, should be refused loudly rather than merged blindly. SQ-0734's rule that an unusable named archive is loud applies to its continuation too.
- **Interaction with SQ-0789's dialog, currently in flight:** the launch dialog lists detected sidecars, and today would offer `arthur.eg1` and `arthur.eg2` as two separate choices. Once part 2 is auto-loaded, offering `.EG2` alone is meaningless — it is half an archive. The list should show the *set* as one entry. Coordinate at merge.
