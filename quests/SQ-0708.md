ANALYZED, NOT IMPLEMENTED. There is no in-game pacing mechanism to honour -- verified by tracing arthur-r74-s890714.z6.

Measured: the graveyard->Merlin turn is 31 instructions end to end, with only 14 between @draw_picture(2) (graveyard, y=5 x=29) and @draw_picture(3) (Merlin, y=51 x=81). No busy-wait, no @sound_effect, no intervening read. Both draws are in one uninterrupted opcode run, then @set_cursor(row=-1) hides the cursor and a timed @read_char waits.

The read_char timers are NOT the animation: 150 tenths (15s) on picture screens, 600 tenths (60s) on text screens, routine 8317 -- an auto-advance for a player who does not press a key. ZMSD sect.15 verified: read_char time/routine are 'dealt with as in read', where the routine is called every time/10 seconds, so the units are tenths. babelmap already honours these (loop_tick.rs arms input_deadline from pending_timeout()).

So Spatterlight's visible pause is an artifact of an interpreter that blits each draw_picture to the display as it executes: you see the 584x392 graveyard painted, then the 480x300 Merlin painted onto it. The author relied on that incremental compositing; there is no Z-machine construct expressing it.

Honouring it therefore means babelmap presenting INTERMEDIATE picture states within a single turn, which it deliberately does not do: GameSession::drain_pictures (session.rs:1235) takes the whole of machine.pending_pictures at the end of a turn and folds every event into pictures_canvas before anything renders. That is the single place the collapse happens, and the place any design would hook -- PictureEvents already carry their order.

Design forks for the user to decide (not picked, per brief):
1. Where the pacing lives. Post-hoc replay of a turn's PictureEvent queue over successive frames (no VM involvement, main thread stays free) vs yielding to the renderer between events (blocks the interpreter -- wrong shape per CLAUDE.md: only the story interpreter belongs on the main thread).
2. Skippable or not -- does a keypress collapse the remaining frames instantly?
3. Interaction with the [more] pager, which already owns the 'game output is paced by the player' path.
4. Scope: every v6 game, or opt-in? Zork Zero/Shogun/Journey all queue multi-picture turns, so this changes their feel too.
5. The delay itself: fixed per-event, proportional to painted area (which is what the original hardware effectively did), or configurable.

No code written for this quest.
