## Parser landed and verified; the ARTHUR font is measured as the wrong tool, with a picture to prove it

Commit 30d68e79 — `blorb::amiga_font` plus `native_disk_font.rs` pinning it against the real floppies. Gate 0, clippy clean, 5607/5607. No render path consumes it yet, and this note is why that stopped.

### The blocker is not effort, it is that the result looks worse

Rendered the same three lines twice at 4× — top with today's `font8x8`, bottom with Arthur's `char.data` centred in the same fixed 8×16 cells. Arthur's letterforms are unmistakably Infocom's, and the text still reads WORSE: the font is **proportional** (widths 2–8), so a narrow `l`/`i`/`t` gets centred in an 8px cell and words stop holding together. "Hall", "jewelled", "little" visibly fall apart into letter-spaced strings. The rhythm is the thing a reader actually sees, and a fixed cell destroys it.

Left-aligning instead of centring does not fix it; it moves the gap to one side. The only real fix is advancing by glyph width, which our v6 model cannot do: text is placed by CELL and the game computes its own columns from the font size in header `$26`/`$27`. Proportional advance would desync our layout from the game's arithmetic — a much larger and riskier change than swapping glyphs, and not what this quest is.

**So: Arthur's font is not usable here, and the reason is structural rather than fixable by tuning.** Recorded rather than attempted, because the wiring would have cost ~100 call-site edits across five public functions in the most-burned file in this repo (`build_chrome_canvas` alone has 48 call sites) before anyone could see it was wrong.

### The Macintosh fonts are the ones that would work

MEASURED off the `FONT` resources in `/MAC/ARTHUR FOLDER/ARTHUR`:

| resource | cell | advance widths |
|---|---|---|
| `FONT` 524 | 7×15 | 6, 7 |
| `FONT` 1033 | 7×12 | **6 only** |

Effectively fixed-pitch — 1033 has a single advance for every defined character. That drops into a fixed-cell model cleanly, which is exactly what Arthur's Amiga font cannot do. Every Mac v6 title carries both (Arthur, Journey, Shogun, Zork Zero), and Beyond Zork carries 1033.

**Blocked on reading Macintosh resource forks**, which `hfs.rs:203` records as deliberately unread and which SQ-0911 is deferred on. That deferral was correct on its own evidence (no Mac sound lives in a resource fork) but this is a second, better reason to revisit it — the fonts genuinely do.

### Journey's font is a third case, and a weak one

`Char.data` is fixed 8×8 so the cell fits, but it is the font-3 SET, not a typeface. Using it would mean inverting `font3_translate` (Unicode back to font-3 code), which is lossy — 38 and 39 both map to `─` — and it would only replace box-drawing glyphs `font8x8` already draws well. Low payoff, real ambiguity; not worth it.

### Standing recommendation

Keep the parser (it is what identified all of the above, and it now backs `font3_shipped_font.rs` too). Do not wire the Amiga fonts. Revisit when Macintosh resource forks are readable, and drive it from `FONT` 1033.

## Retired deliberately — the parsers stay, the renderer change does not happen here

User's decision, 2026-08-18: *"let's leave the parsers and file the metrics quest. we may not do it for this tui, but if we build a gui later it will make more sense."* Succeeded by **SQ-0917**.

### What this quest actually produced

Not what it set out to. The goal was "draw v6 raster text with the shipped font", and the answer is that you cannot do that well without also adopting the shipped font's cell size — which is a change to what `$26`/`$27` tell the game, not a rendering detail. Two rendered comparisons made that concrete rather than arguable, and both were worth more than the code would have been:

1. Arthur's Amiga font (proportional, widths 2–8) centred in a fixed 8×16 cell reads visibly **worse** than the public-domain font it would replace — words come apart.
2. Zork Zero's Macintosh `FONT` 524, once its left side bearings are honoured, is uniform and legible but a pixel loose per character, because its advance is 7 against our 8.

Both were produced BEFORE spending the ~100 call-site diff across five public functions in `v6_layout`/`screen.rs` that wiring would have cost. That ordering is the thing worth repeating: the change was cheap to evaluate and expensive to make.

### What stays

`blorb::amiga_font` (commit 30d68e79) and, via SQ-0911, `blorb::{bitmap_font, mac_font, resource_fork}` plus `Hfs::read_resource` (013d81c5). All pinned against real floppies. `font3_shipped_font.rs` also stopped carrying its own copy of the Amiga parser and took the production one.

Two corrections this quest made along the way, both to claims that were already in shipped comments:

- `bitfont.rs`'s font-3 entries are **not** dead code — Journey is v6 and ships the identical font-3 file, so the box-drawing half is live in the raster path (544185aa).
- The Macintosh font is **not** proportional over the range a game prints; it advances every printable character by 7. My first reading said otherwise, and my first preview of it dropped the side bearings, which made a uniform face look ragged. Both errors are recorded on SQ-0911.

### Not lost

Everything a future attempt needs is in SQ-0917, including the recommendation to start from the Macintosh rather than Arthur, and to capture an Amiga Arthur screenshot before pinning any geometry against it.
