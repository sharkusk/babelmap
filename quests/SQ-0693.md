DESIGN SETTLED WITH THE USER 2026-08-09 — all five decisions, to be implemented as specified. (1) WALKABLE EDGES: directed, known-direction only. Traverse each connection origin->dest ONLY, and skip Direction::Unknown — the same filter matrix::entrances already applies. A one-way passage is usable only in its real direction, so the highlighted route is always one the player can actually walk. Rejected: treating edges as bidirectional (would confidently highlight a route back through a one-way passage that does not exist) and requiring mutual passages (would fail in exactly the half-mapped mazes this view exists for). (2) LAYERS: search the WHOLE graph, render only the in-layer steps. A room is a room; layers are a presentation grouping, not a walkability constraint. The existing out-of-layer cell marks where the route departs. Rejected: confining the search to the layer (returns 'no path' in the maze/peel cases that matter most) and auto-switching layers to follow the path (the view moving under the player is disorienting). (3) HIGHLIGHT: ONE CELL PER STEP — mark the cell at row = the room you are in, column = the direction you LEAVE BY. Reads top-to-bottom as walking instructions. Needs its OWN style.toml selector, visually distinct from the existing entrances bolding (matrix::entrances, which answers the different question 'how do I get back here'). Rejected: whole-row highlighting (says nothing about which exit to take — the information the matrix exists to carry) and writing step NUMBERS into the cells (overwrites the glyph that says what kind of passage it is). (4) NO PATH: select the room as normal and show a brief status message ('no known route from here'). Silence is indistinguishable from the feature being broken, and no-path will be common mid-exploration. Rejected: highlighting the closest reachable room (invents an answer to a question the player did not ask). (5) ESC: two-stage — first Esc clears the PATH but keeps the room selected (and its entrance bolding); second Esc clears the SELECTION. Matches the room dock's existing two-stage Esc (unpin, then close). SCAFFOLDING THAT ALREADY EXISTS (do not rebuild): render_matrix already returns (room, rect) click targets feeding the same room_rects list the drawn view uses, so clicking already sets state.selected_room; step_selection handles keyboard row nav; Esc already clears selection via Action::UnpinRoomDock (input.rs ~2499). THE GENUINELY MISSING PIECE is graph search — the mapper has NO pathfinding at all; router.rs's route_all/route_side are edge ROUTING (drawing connector lines), not shortest-path. Current room is mapper.graph.current().
