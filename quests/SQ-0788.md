--- note 2026-08-12T05:08:54Z ---

USER REPORT 2026-08-11, verbatim:

> "in scopa, if i select one card, then change my mind and select a different card the selection outline does not move. however, when clicking okay, the new card is played"

**THE GAME'S MODEL IS CORRECT AND ONLY THE DISPLAY IS STALE.** That is the most valuable fact in the report and it narrows this sharply: the card actually played is the newly-selected one, so scopa knows about the change and is presumably drawing the outline in its new position. What fails is that the OLD outline is still on screen. This is a failure to ERASE, not a failure to draw, and it is not an input-routing or click-mapping bug — clicks are landing on the right card (contrast SQ-0742's click half, which was the opposite shape: correct drawing, wrong hit).

**LEADING HYPOTHESIS, and it connects to work already open — SQ-0753 / SQ-0763.** Those recorded that `a=d` kitty deletes are **zero in every capture we have taken**: babelmap appears never to delete an image placement. A selection outline drawn as a kitty placement would then persist exactly like this — the game erases it in its own model, we never emit the delete, and the old outline stays lit while the new one is added beside it. If that is the mechanism, the user has just supplied the first *reproducible, user-visible* symptom of a defect that until now was only an absence in a byte stream. That would make this quest the way to fix SQ-0753/0763 rather than a separate problem.

DO NOT ASSUME IT, THOUGH. The competing explanation is a cell-path erase: scopa may draw the outline with reverse-video or box glyphs rather than a picture, in which case this is a background/rune clearing bug in the raster or ring path and has nothing to do with placements. **Establish which before theorising further** — the emitted-stream harness answers it in one run, and the two look identical on screen while being completely different bugs (that distinction is exactly what `crates/app/tests/pty_stream/` exists for, per CLAUDE.md).

FIRST MEASUREMENT: drive scopa to a hand, select card A, then select card B, and capture. Then ask of the capture: (1) is the outline an image placement or painted cells? (2) if a placement, is there an `a=d` for the first outline anywhere in the stream? (3) if cells, what does the game emit for the old outline's area — does it send an erase we drop, or does it send nothing and expect us to have tracked it?

REPRODUCTION IS CHEAP AND ALREADY SOLVED. The SQ-0784 lane worked out a headless restore recipe requiring no `--restore` flag, since `auto_load` defaults to true:

    mkdir -p $S/home/saves/scopa.z6.save
    cp ~/.babelmap/saves/scopa.z6.save/default.babelmap $S/home/saves/scopa.z6.save/
    cargo build -p app --bins --examples
    cargo run -q -p app --example pty_capture -- \
        --story stories/scopa.z6 --user-dir $S/home \
        --size 117x64 --keys wait:4000 --png $S/scopa.png

Two gotchas it paid for: `pty_capture --user-dir` **overwrites** the per-game `config.toml` with `show_map = false`, so per-game overrides must come via `--arg --config <path>`; and `cargo build -p app --example pty_capture` does **not** rebuild `target/debug/babelmap`, which the example actually runs — a stale binary reports "no change".

Note the user's own save may not be usable as the starting point here — the SQ-0784 lane found that restoring it does not bring back scopa's blue card panels or dealt cards (that observation was filed as SQ-0787 and then discarded as uninteresting on its own merits, 2026-08-11). Playing a hand forward from a fresh boot is likely the more reliable route to a selectable card.

BLAST RADIUS IF THE PLACEMENT HYPOTHESIS HOLDS: every v6 title that draws and removes transient artwork. Zork Zero's and Journey's frames are pinned frame-by-frame in the corpus tests and must not move.

--- note 2026-08-12T05:11:21Z ---

CORRECTION 2026-08-11, from the user — **"we also don't draw the new outline."**

This retracts the framing in the note above, which called it "a failure to ERASE, not a failure to draw" and made SQ-0753/0763's missing `a=d` deletes the leading hypothesis. Both halves of the update are missing: the old outline is not removed AND the new one never appears. A delete-specific defect cannot explain a missing *draw*, so that hypothesis is now the weaker one and must not be pursued first.

**THE SHARP FACT IS THAT THE FIRST SELECTION WORKS.** Select a card and its outline appears. Select a different card and nothing on screen changes at all — while the game, as originally reported, plays the newly-selected card on OK. So the model is still correct throughout; it is the second and subsequent repaints that never reach the screen. Whatever the mechanism, it distinguishes the FIRST draw from every later one, and that is the thing to characterise.

REVISED HYPOTHESES, none preferred, all cheap to separate:
1. **The frame is not repainted at all after the second selection.** If the render pass is triggered by a classification of story output that the selection change does not satisfy, the whole frame stays stale. Test: does ANYTHING else on screen update after the second selection?
2. **Dirty-region tracking excludes the area.** The first draw marks the region dirty and paints; the second is computed as clean and skipped. Consistent with first-works-then-nothing.
3. **The game moves the outline by a mechanism we do not implement, where the first draw happens to work by another route.** Inversion/XOR of a card rectangle is the classic way a v6 game shows selection — draw once looks right, and the "undo the old, apply the new" pair silently does nothing if the mode is unimplemented. This would explain the asymmetry directly.
4. Placement lifetime (the original hypothesis) — retained only because the harness will answer it in passing, not because it fits.

FIRST MEASUREMENT, unchanged in method but now asking a better question: drive scopa to a hand, select card A, capture; select card B, capture. Then diff the two captures. **If the two frames are byte-identical, hypothesis 1 or 2 is right and the game's output never reached the renderer.** If they differ but the screen does not, the update is being computed and lost downstream. That single diff splits the space in half before any code is read.

Then, on the second capture: is the outline an image placement or painted cells? What does the game emit at the moment of the second selection — anything at all? A game that emits nothing is a very different bug from one that emits an update we discard, and per CLAUDE.md the emitted-stream harness (`crates/app/tests/pty_stream/`) is the layer that tells those apart; they are indistinguishable on screen.

The reproduction recipe and its two gotchas are in the note above and are unaffected by this correction.

--- note 2026-08-12T05:15:26Z ---

DISCRIMINATOR 2026-08-11, from the user — the behaviour splits on whether the newly-selected card can capture:

> "if the new card has a match on the board, the selection will change. only selecting different cards with no match doesn't update."

    match present on the board  -> the outline DOES move. Correct.
    no match                    -> nothing changes on screen. The reported defect.

**HYPOTHESIS 1 (no repaint occurs at all) IS BADLY WEAKENED.** The repaint machinery demonstrably works — in the same game, on the same screen, one keypress apart. Whatever is wrong is not "we never render after a selection", and the earlier note's framing of "the second and later repaints never reach the screen" is too broad.

**LIKELIEST READING, to be tested rather than adopted:** when the new card has a match, scopa also highlights the matching board cards, which is a LARGER redraw. The hand-card outline update is probably dropped in BOTH cases and merely becomes visible in the match case, because a bigger co-located repaint drags it along. That reframes this from "two behaviours" to **one always-dropped update that is sometimes masked by a neighbouring correct one** — which is a much more tractable defect.

It also makes a falsifiable prediction: find a match case where the board highlight does NOT overlap or adjoin the hand cards. If the hand outline still fails to move there, the reading is confirmed and the defect is entirely about the hand-outline update.

**HYPOTHESIS 3 (XOR/inversion) now fits best.** If the game inverts a card rect to show selection and the mode is unimplemented, the invert is lost — while a full redraw of the card area from scratch (which a match-triggered repaint performs) carries the correct selection state and looks right. The asymmetry falls straight out of that. **HYPOTHESIS 2 (dirty-region)** fits too, with the small invert failing to mark the region dirty where the larger board draw does. The two separate cleanly at the emitted-stream layer: inversion-not-implemented means the game EMITS something we discard or mis-execute; dirty-region means we compute the region as clean and emit nothing. Indistinguishable on screen, different bugs — exactly the distinction `crates/app/tests/pty_stream/` exists for.

**THE MEASUREMENT IS NOW A FOUR-WAY, AND WE HAVE A POSITIVE CONTROL FOR THE FIRST TIME:**

    A  select a no-match card          -> capture
    B  select a different no-match card -> capture    (broken pair)
    C  select a card WITH a match       -> capture
    D  select a different matching card -> capture    (WORKING pair)

Diff A-vs-B and C-vs-D **in the emitted stream, not only the rendered frame**. C-vs-D shows what a *correct* selection update looks like on the wire, so the broken pair can be compared against known-good rather than against expectations. That is worth more than reading the render path.

The running lane has been sent all of this.

    right <-> left      outline updates   (works)
    right <-> middle    outline updates   (works)
    left  <-> middle    NOTHING happens   (the defect)

**THE VARIABLE IS NOT "does the selected card have a match".** It is **whether the board-highlight state CHANGES**. Selecting into or out of the matching card makes the board highlight appear or disappear — a larger redraw that drags the hand outline along with it. Left-to-middle changes no board highlight at all, since neither card matches and there is nothing to add or remove, so with no neighbouring repaint to mask it the dropped hand-outline update is exposed.

**Therefore the hand-card outline update is being lost in ALL FOUR transitions and is merely invisible in three of them.** Any fix built around "matching cards behave differently" would be built on a confound. The outline update is uniformly broken; the board highlight is the masking agent.

This also collapses the earlier four-way capture matrix into a much sharper pair — a positive and a negative control **for the same update**, rather than for two different behaviours:

    LEFT -> MIDDLE    the update is dropped, nothing masks it     (broken, isolated)
    LEFT -> RIGHT     the same update, masked by the board redraw (positive control)

Diff those two in the EMITTED STREAM. Whatever the game emits for the hand outline should appear in BOTH, with only the board highlight differing. If the hand-outline bytes are present in both while the screen changes in only one, the update is emitted and lost on our side. If they are absent from both, the game never emits it and the defect is upstream of the renderer entirely. That single comparison decides which half of the system to open.

The running lane has been sent this, along with the reproduction recipe and the caveat that a restored scopa Save State was previously observed not to repaint the blue card panels or dealt cards (filed and discarded as SQ-0787) — it was told to check the model before concluding the save is unusable, and to report a block rather than work around it silently.

UNEXPLAINED LOOSE END, recorded 2026-08-11 so the fix is not mistaken for a complete account of what the user saw.

The lane established and fixed the **in-game hand-card** case by direct measurement: `v6_raster_gen` did not read the painted ground, so a ground-only repaint left `v6_wants_build` false. That is settled, falsified and gated.

**It could NOT reproduce the user's start-menu deck claim as a deck effect.** All three decks behaved identically at the gate — `gen_changed=false` on every card-to-card transition before the fix, `true` on all of them after — and it concluded the real confound is the board highlight, which is hand-dependent rather than deck-dependent.

**BUT IT FOUND AN ANOMALY IN EXACTLY THAT AREA AND SET IT ASIDE**, in its words:

> "the menu's three samples are Neapolitan `#101` and Sicilian `#301` as real Blorb pictures, while `@picture_data(201)` returns **MISSING**"

So of the three deck samples on the start menu, **the middle one has no picture resource**. The user's report was that the RIGHT deck always works and that the failure is between the LEFT and MIDDLE. A middle sample whose picture is missing is a suspicious coincidence with that description, and it is a completely different mechanism from the raster-gate defect just fixed — a missing resource cannot be fixed by rebuilding more often.

WHAT THIS MEANS PRACTICALLY: **the user may still see something wrong on the start menu after this fix ships.** If they do, it is not a regression and not an incomplete fix of this defect — it is this second thing, and the first question to ask is why `@picture_data(201)` reports MISSING when 101 and 301 resolve. Candidates worth separating: the Blorb genuinely lacks 201 (in which case what does the game expect to draw, and does a real interpreter show anything there?); or our resource resolution fails for that id specifically.

The lane's dismissal was correct on its own evidence — it measured the gate and the gate is deck-independent. This note exists because "could not reproduce" and "does not happen" are different claims, and the user watched it happen.

ASK THE USER TO RE-CHECK THE START MENU once this is in a build they run. If the deck selection still fails to update there, that observation now has a concrete first suspect.
