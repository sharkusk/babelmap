--- note 2026-08-14T20:59:32Z ---

THE DEFECT, measured. `crates/zvm-cli/src/main.rs`'s `build_machine` takes `interpreter_number` and `honor_game_colours`, calls `machine.set_interpreter_number(...)` and `init_caps()`, and that is all — **`default_colours()` appears nowhere in the crate**. The app does the other half at `crates/app/src/startup.rs:478`, where `cfg.interpreter_profile.default_colours()` becomes `host_default_colours` and is passed into the session, which is what seeds header `$2C`/`$2D`.

So off a ProDOS disk the CLI tells Beyond Zork it is interpreter 10 while its default pair is still zvm's own §8.3.2 seed. The story is told which machine it is but not what that machine looks like — the same half-wired state SQ-0836 refused to ship when it declined `Some(10)` until a profile existed. SQ-0740, SQ-0846 and SQ-0857 all argued a profile is a BUNDLE (number + colours + palette + screen); the CLI currently gets one field of it.

THE CAUSE IS PLACEMENT, not an oversight in the CLI. `InterpreterProfile` is in `crates/app/src/interpreter.rs` (1,159 lines), and `zvm-cli` cannot depend on `app`.

PROPOSED SHAPE, measured against the dependency graph:

```
blorb      zero deps                 already holds the interpreter NUMBERS
cli-host   blorb + crossterm         NO zvm dep; also serves gvm-cli and scott-cli
zvm-cli    cli-host + zvm + blorb
app        cli-host + zvm + blorb + …
```

`InterpreterProfile` needs `blorb::infocom_pics::Flavour` **and** `zvm::screen::Palette`, so its home must see both. Putting it in `cli-host` would force a `zvm` dependency onto a shared layer that `gvm-cli` and `scott-cli` use without running a Z-machine — reject that unless you can argue otherwise.

A small dedicated crate depending on `blorb` + `zvm`, consumed by `app` and `zvm-cli`, avoids the cycle (profile → blorb, never the reverse). Split the facts by KIND rather than arbitrarily: **`blorb::medium` keeps saying which machine a medium implies** (a disk-format fact, already there, zero-dep); **the new crate says what that machine looks like**. That keeps one source per question instead of splitting one question across two homes.

THE OVERRIDE CONTRACT, which must survive: `--interpreter N` selects the WHOLE bundle, not just the byte — asking for 4 gets the Amiga's colours too — and `--no-game-colours` (plus `NO_COLOR`) declines the lot. `crates/zvm-cli/src/main.rs:1295` documents the precedence as a contract (SQ-0839): a number on the command line beats the medium, which beats zvm's default rule. Preserve that ordering exactly.

ONE OPEN QUESTION THE USER SHOULD SETTLE IF IT COMES UP: whether the CLI should paint a machine's page at all. `InterpreterProfile::IbmPc` deliberately returns `None` for colours so "default" means what the player's terminal actually shows, and that argument is stronger in a terminal client than in babelmap, which paints a canvas it owns. The user's instruction was to centralise so both front-ends "obtain the correct colors (unless user overrides)", so implement that — but if honouring a machine's page turns out to fight a themed terminal in an obvious way, report it rather than shipping something unpleasant.

GUARDS: every existing profile resolution is unchanged in the app (`real_media_releases.rs` pins medium→profile); both `honor_game_colours` modes; SQ-0860's artwork force-off and SQ-0855's `--no-game-colours` still behave; `gvm-cli` and `scott-cli` gain no new dependency.

SCHEDULING: touches `crates/zvm-cli/src/`, which SQ-0869 holds. Start after it lands.

--- note 2026-08-14T21:00:34Z ---

PLACEMENT CORRECTED — the user proposed `zvm` and it is better than the new-crate idea in my previous note. Disregard that proposal; this is the design.

**zvm already owns this domain**, which I failed to check before proposing a new crate:

```
zvm::screen::Palette              { Standard, Amiga }, plus a process-wide ACTIVE_PALETTE
zvm::screen::amiga_screen_pair    reads $2D/$2C, gated on AMIGA_INTERPRETER_NUMBER
zvm::screen::default_interpreter_number(version)        Frotz's rule, 6 for v6 else 1
zvm::screen::init_header_caps(…, interpreter_number)    writes $1E
crates/zvm/Cargo.toml             [dependencies] is EMPTY
```

`zvm-cli` already depends on `zvm`, so the machine table lands there with **no new crate and no new dependency anywhere**, and the CLI gets the colours for free.

THE LINE TO HOLD is zvm's charter from CLAUDE.md: zero external dependencies, no I/O policy. So this is not "move `InterpreterProfile` into zvm" — it is a split:

- **Into zvm**: the machine table — interpreter number, default `$2C`/`$2D` colour pair, palette. Pure data plus rules zvm already applies. `amiga_screen_pair` is the existing precedent for exactly this kind of per-machine rule and should end up expressed through the table rather than beside it.
- **Staying in app**: `InterpreterProfile::resolve(path, …)`, which reads the medium — that is I/O policy and explicitly against the charter; the art-flavour preference, which needs `blorb::infocom_pics::Flavour` and would break zero-dep; and `std_window`, which is picture-space geometry stated by an ARCHIVE, not by the machine (SQ-0857 left `AppleIIgs::std_window` as `None` for reasons that have nothing to do with the machine's identity — do not disturb that).

THE NUMBERS ARE ALREADY SPLIT and this quest must not make it worse. `AMIGA_INTERPRETER_NUMBER` is in `zvm::screen`; `MACINTOSH_INTERPRETER_NUMBER`, `ATARI_ST_INTERPRETER_NUMBER` and ProDOS's are in `blorb::medium`, where the `FORMATS` rows need them. `blorb` cannot depend on `zvm` without coupling two crates that are deliberately independent, and `zvm` must not depend on `blorb`. So either:

- blorb keeps its own constants for the **medium→machine** question, with a test asserting the two tables agree on every shared machine — cheap, and it makes a future divergence fail loudly; or
- the numbers move wholesale and blorb gains a dependency — which I would resist, and you should argue for explicitly if you choose it.

Everything else in the previous note stands: the override contract (`--interpreter N` selects the whole bundle; `--no-game-colours` and `NO_COLOR` decline it; the SQ-0839 precedence of command line > medium > zvm default), the guards, and the open question about whether a terminal client should paint a machine's page at all.
