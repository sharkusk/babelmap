--- note 2026-08-14T20:59:32Z ---

THE DEFECT, measured. `crates/zvm-cli/src/main.rs`'s `build_machine` takes `interpreter_number` and `honor_game_colours`, calls `machine.set_interpreter_number(...)` and `init_caps()`, and that is all — **`default_colours()` appears nowhere in the crate**. The app does the other half at `crates/app/src/startup.rs:478`, where `cfg.interpreter_profile.default_colours()` becomes `host_default_colours` and is passed into the session, which is what seeds header `$2C`/`$2D`.

So off a ProDOS disk the CLI tells Beyond Zork it is interpreter 10 while its default pair is still zvm's own §8.3.2 seed. The story is told which machine it is but not what that machine looks like — the same half-wired state SQ-0836 refused to ship when it declined `Some(10)` until a profile existed. SQ-0740, SQ-0846 and SQ-0857 all argued a profile is a BUNDLE (number + colours + palette + screen); the CLI currently gets one field of it.

THE CAUSE IS PLACEMENT, not an oversight in the CLI. `InterpreterProfile` is in `crates/app/src/interpreter.rs` (1,159 lines), and `zvm-cli` cannot depend on `app`.

PROPOSED SHAPE, measured against the dependency graph:

```
blorb      zero deps                 already holds the interpreter NUMBERS
cli-host   blorb + crossterm         NO zvm dep; also serves gvm-cli and scott-cli
zvm-cli    cli-host + zvm + blorb
app        cli-host + zvm + blorb + …
```

`InterpreterProfile` needs `blorb::infocom_pics::Flavour` **and** `zvm::screen::Palette`, so its home must see both. Putting it in `cli-host` would force a `zvm` dependency onto a shared layer that `gvm-cli` and `scott-cli` use without running a Z-machine — reject that unless you can argue otherwise.

A small dedicated crate depending on `blorb` + `zvm`, consumed by `app` and `zvm-cli`, avoids the cycle (profile → blorb, never the reverse). Split the facts by KIND rather than arbitrarily: **`blorb::medium` keeps saying which machine a medium implies** (a disk-format fact, already there, zero-dep); **the new crate says what that machine looks like**. That keeps one source per question instead of splitting one question across two homes.

THE OVERRIDE CONTRACT, which must survive: `--interpreter N` selects the WHOLE bundle, not just the byte — asking for 4 gets the Amiga's colours too — and `--no-game-colours` (plus `NO_COLOR`) declines the lot. `crates/zvm-cli/src/main.rs:1295` documents the precedence as a contract (SQ-0839): a number on the command line beats the medium, which beats zvm's default rule. Preserve that ordering exactly.

ONE OPEN QUESTION THE USER SHOULD SETTLE IF IT COMES UP: whether the CLI should paint a machine's page at all. `InterpreterProfile::IbmPc` deliberately returns `None` for colours so "default" means what the player's terminal actually shows, and that argument is stronger in a terminal client than in babelmap, which paints a canvas it owns. The user's instruction was to centralise so both front-ends "obtain the correct colors (unless user overrides)", so implement that — but if honouring a machine's page turns out to fight a themed terminal in an obvious way, report it rather than shipping something unpleasant.

GUARDS: every existing profile resolution is unchanged in the app (`real_media_releases.rs` pins medium→profile); both `honor_game_colours` modes; SQ-0860's artwork force-off and SQ-0855's `--no-game-colours` still behave; `gvm-cli` and `scott-cli` gain no new dependency.

SCHEDULING: touches `crates/zvm-cli/src/`, which SQ-0869 holds. Start after it lands.

--- note 2026-08-14T21:00:34Z ---

PLACEMENT CORRECTED — the user proposed `zvm` and it is better than the new-crate idea in my previous note. Disregard that proposal; this is the design.

**zvm already owns this domain**, which I failed to check before proposing a new crate:

```
zvm::screen::Palette              { Standard, Amiga }, plus a process-wide ACTIVE_PALETTE
zvm::screen::amiga_screen_pair    reads $2D/$2C, gated on AMIGA_INTERPRETER_NUMBER
zvm::screen::default_interpreter_number(version)        Frotz's rule, 6 for v6 else 1
zvm::screen::init_header_caps(…, interpreter_number)    writes $1E
crates/zvm/Cargo.toml             [dependencies] is EMPTY
```

`zvm-cli` already depends on `zvm`, so the machine table lands there with **no new crate and no new dependency anywhere**, and the CLI gets the colours for free.

THE LINE TO HOLD is zvm's charter from CLAUDE.md: zero external dependencies, no I/O policy. So this is not "move `InterpreterProfile` into zvm" — it is a split:

- **Into zvm**: the machine table — interpreter number, default `$2C`/`$2D` colour pair, palette. Pure data plus rules zvm already applies. `amiga_screen_pair` is the existing precedent for exactly this kind of per-machine rule and should end up expressed through the table rather than beside it.
- **Staying in app**: `InterpreterProfile::resolve(path, …)`, which reads the medium — that is I/O policy and explicitly against the charter; the art-flavour preference, which needs `blorb::infocom_pics::Flavour` and would break zero-dep; and `std_window`, which is picture-space geometry stated by an ARCHIVE, not by the machine (SQ-0857 left `AppleIIgs::std_window` as `None` for reasons that have nothing to do with the machine's identity — do not disturb that).

THE NUMBERS ARE ALREADY SPLIT and this quest must not make it worse. `AMIGA_INTERPRETER_NUMBER` is in `zvm::screen`; `MACINTOSH_INTERPRETER_NUMBER`, `ATARI_ST_INTERPRETER_NUMBER` and ProDOS's are in `blorb::medium`, where the `FORMATS` rows need them. `blorb` cannot depend on `zvm` without coupling two crates that are deliberately independent, and `zvm` must not depend on `blorb`. So either:

- blorb keeps its own constants for the **medium→machine** question, with a test asserting the two tables agree on every shared machine — cheap, and it makes a future divergence fail loudly; or
- the numbers move wholesale and blorb gains a dependency — which I would resist, and you should argue for explicitly if you choose it.

Everything else in the previous note stands: the override contract (`--interpreter N` selects the whole bundle; `--no-game-colours` and `NO_COLOR` decline it; the SQ-0839 precedence of command line > medium > zvm default), the guards, and the open question about whether a terminal client should paint a machine's page at all.

--- note 2026-08-14T21:04:37Z ---

THE FULL SCATTER, measured across the workspace. This is the inventory to centralise; do not assume it is complete, but it is what a sweep found.

**Duplicated values**
- `AMIGA_INTERPRETER_NUMBER = 4` exists in BOTH `crates/zvm/src/screen.rs` and `crates/blorb/src/medium.rs`.
- Frotz's default rule is `zvm::screen::default_interpreter_number(version)`, and `crates/app/src/launch_options.rs` open-codes it TWICE — `if version == 6 { 6 } else { 1 }` at :677 and :697.

**One concept, two homes** — the clearest evidence for this quest:
- The Amiga's screen-pair rule is `zvm::screen::amiga_screen_pair` (screen.rs:1018), gated on the Amiga number, inside **zvm**.
- The Macintosh's is `machine_screen_pair` at `crates/app/src/session.rs:3237`, gated on `blorb::medium::MACINTOSH_INTERPRETER_NUMBER`, inside **app**.
That asymmetry arrived with SQ-0846 and is why `zvm-cli` can see one machine's rule and not the other's.

**Constants by crate today**
```
blorb/medium.rs    AMIGA 4, MACINTOSH 3, ATARI_ST 5, APPLE_IIGS 10
zvm/screen.rs      AMIGA 4                                  (duplicate)
app/interpreter.rs AMIGA_DEFAULT_{BACKGROUND 12, FOREGROUND 9}, MAC_{9,2},
                   ST_{9,2}, APPLE_{2,9}, AMIGA_STD_WINDOW, MACINTOSH_STD_WINDOW
app/graphics.rs    INFOCOM_V6_STD_WINDOW (320,200)
```

**Also gated on the number, and worth knowing rather than moving**: `crates/zvm/src/cpu/exec.rs` branches on `read_byte(0x1E) == 6` for its CP437 remap (cited at `app/launch_options.rs:18`). That is VM behaviour and already in the right crate; SQ-0857 and SQ-0864 both leaned on it when arguing that declining a number is not neutral, because the fallback lands on 6.

DOES BLORB NEED THE MEANING OF THE NUMBERS? The user asked, and the answer is **no — but keep the number anyway**, for a specific reason.

Blorb's job is to say WHICH MEDIUM this is, and it already answers that with the `DiskImage` variant (`Adf`, `Hfs`, `Fat12Dos`, `Fat12AtariSt`, `ProDos`). Answering an interpreter number is blorb reaching into ZMSD §11.1.3, and it carries substantial §11.1.3 rationale in doc comments to justify values zvm should own. Removing it entirely, though, needs a shared machine vocabulary across a boundary kept deliberately thin — zvm must not depend on blorb, blorb must not depend on zvm — so something has to map `DiskImage → machine`, and that something is `InterpreterProfile::resolve`, in app.

So: **blorb keeps answering a number** (a compact, stable, published encoding that requires no shared type, which is exactly why it works as a lingua franca between two independent crates), but it stops carrying the REASONING. The §11.1.3 knowledge, the colour pairs, the palette and the per-machine screen-pair rules belong in zvm's table; blorb's rows cite it instead of re-deriving it. What is duplicated today is the knowledge, not the value, and knowledge is what rots.

If you conclude otherwise while implementing — for instance that a `Machine` enum in blorb consumed by app is cleaner — argue it explicitly rather than doing it silently. The Atari ST row's comment is the standard to match: it sources its 5 from ZMSD AND from Infocom's own `st/stx1.s`, and that kind of sourcing must survive wherever the value ends up.

COVERAGE MATRIX, measured from `InterpreterProfile`'s match arms. We model four machines plus a catch-all, against ZMSD §11.1.3's eleven numbers.

```
 #  machine          profile   number   colours   palette    std_window
 1  DECSystem-20     — →IbmPc
 2  Apple IIe        — →IbmPc
 3  Macintosh        yes       3        9 / 2     Standard   320x200
 4  Amiga            yes       4        12 / 9    Amiga      320x200
 5  Atari ST         yes       5        9 / 2     Standard   None (no ST YZIP ever existed)
 6  IBM PC           yes       None*    None**    Standard   None
 7  Commodore 128    — →IbmPc
 8  Commodore 64     — →IbmPc
 9  Apple IIc        — →IbmPc
10  Apple IIgs       yes       10       2 / 9     Standard   None (cell metrics, SQ-0857)
11  Tandy Color      — →IbmPc
```
\* deliberately version-dependent (Frotz's rule). \*\* deliberately the player's terminal.

THE CONCRETE GAP is `for_interpreter_number`'s `_ => Self::IbmPc` (interpreter.rs:289). Since SQ-0855 shipped `--interpreter`, a user can now ask for 8 and get a story advertised as a Commodore 64 while dressed as an IBM PC. That is the same half-wiring this quest exists to fix, pointing the other way. **A missing machine is not itself a bug** — falling back to IBM PC behaviour is right for an unknown terminal — but the fallback is SILENT, and asking for a machine we do not model should say so rather than quietly substituting another.

FILL ORDER, with the reason each is ranked there:

1. **7 and 8, Commodore 128 / 64** — live, not hypothetical. SQ-0869 is mounting `TRINITY1.D64`, **v4 r12 s860926, which reads `$1E`**; Hitchhiker's on the same shelf is v3 and cannot notice. Infocom's own Commodore interpreter is in `github.com/erkyrath/infocom-zcode-terps`, the tree that sourced the Atari ST (`st/stx1.s`) and the Apple (`apple/yzip/rel.15`). Note a `.d64` is a 1541 image usable by BOTH machines, so the medium cannot choose between 7 and 8 — the same ambiguity ProDOS has across the Apple family, which SQ-0857 resolved by picking the top of the family and arguing declining is worse.
2. **2 and 9, Apple IIe / IIc** — nearly free. SQ-0857 established they share the entire Apple YZIP bundle except the number, and `bsubs.asm`'s `MACHINE:` routine picks between `IIeID 2`, `IIcID 9` and `IIgsID 10` at boot. The sourcing is already done and quoted in `interpreter.rs`.
3. **1, DECSystem-20** — needs a DECISION more than data. It is what declining falls through to, and it is what makes Beyond Zork ask "Is this a VT220?" (measured in SQ-0835 and again in SQ-0857). Whether it deserves a profile or is honestly "a terminal, same as IbmPc" should be written down rather than left implicit.
4. **11, Tandy Color** — lowest. Infocom pressed for the CoCo but we have no fixture and no sourced constants, so anything we wrote would be guesswork. Better absent than invented.

STANDARD FOR FILLING ANY OF THEM: source every value, do not recall it. The Atari ST row is the bar — ZMSD §11.1.3 **and** `st/stx1.s`'s `INTWRD DC.B 5 * MACHINE ID FOR ATARI ST`. Where a value cannot be sourced, decline it explicitly as `AppleIIgs::std_window` and `IbmPc::interpreter_number` both do; a profile that honestly carries only what is known beats one that guesses.

--- note 2026-08-14T23:14:01Z ---

SHIPPED in 1e79b42b (worktree `agent-a2c3404b542b2a880`, not merged). Two findings the user should know before confirming.

**1. The ProDOS press is exactly where the defect was invisible.** The Apple II YZIP's page is standard colour 2 (black) over ink 9 (white), and zvm's own §8.3.2 seed is `DEFAULT_BG_COLOUR = 2` / `DEFAULT_FG_COLOUR = 9`. They are the same pair. So off `Beyond Zork (1988)(Infocom).2mg` the byte and the page agreed all along, and a pty capture before and after the fix is byte-identical in its SGR profile. The presses where the old code really did hand out a machine that said one thing and looked like another are the Macintosh (9/2) and the Atari ST (9/2) — `-I 3` now reports `[3/9/2]` where it reported `[3/2/9]`. Both are pinned; the ProDOS test carries a comment saying why it cannot be the falsification.

Related: the Amiga's dark grey (12) is a Version 6 grey, and `clamp_default_colour` folds it to black below v6. `zvm-cli` refuses v6 outright, so the Amiga's own page can never reach that front-end. Stated in the test rather than left to look like a bug.

**2. The open question answers itself — nothing unpleasant ships.** `zvm-cli::screen::push_colour_sgr` maps `ZColour::Standard(2..=9)` to the bare ANSI 30–37/40–47 codes and `ZColour::Default` to no SGR at all, so a machine's page is what the story is TOLD, never something painted over the player's theme. That is also exactly what babelmap does below Version 6 (`machine_screen_pair` is a v6-only path), so the two front-ends now match on both halves. No change was needed to keep it that way, and none was made.

**Declined, and named rather than fixed:** blorb's §11.1.3 doc prose still restates the reasoning the zvm table now owns. Migrating it means editing `crates/blorb/src/medium.rs`, which SQ-0870 holds. The VALUES are pinned against each other by `interpreter_profile::blorb_and_zvm_agree_on_every_machine_they_both_name`, which also asserts every number any medium hands out names a machine zvm models — so a divergence fails loudly. The prose de-duplication is a follow-up for after SQ-0870 lands.
