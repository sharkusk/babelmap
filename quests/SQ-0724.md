--- note 2026-08-09T18:03:33Z ---

Screenshot evidence 2026-08-09 (mysterious01, hybrid/Ghostty). Screen from the top: the room illustration (a red-and-black spooky forest with a green ground strip), then three lines of room text — "I'm in a dense SPOOKY Forest" / "Obvious exits: NORTH SOUTH" / "Visible items: Old Cloak, Rotting leaves" — then the game's dotted divider row, and only BELOW that the scrolling transcript.

So the room description is not in the transcript at all. It is redrawn in the game's upper region every turn, Scott-Adams style, which is the layout these Brian Howarth ports use.

STARTING POINT, so nobody re-derives it: room detection in `crates/app/src/session.rs` runs off a room SNAPSHOT (`snap.number`, `snap.name`) fed to `mapper.observe` / `observe_moved` / `observe_relocation` around lines 2865-2894, and the snapshot comes from the Z-machine OBJECT TREE (`zvm::objects::object_snapshot`, `crates/zvm/src/objects.rs:427`) — not from parsed text. mysterious01 is a Z-machine port of a Scott Adams game, so it very likely keeps the current location in a global rather than as the player object's parent, which would defeat object-tree detection entirely. VERIFY that before building anything: dump the object tree and the globals across a couple of moves and see which one actually tracks the room.

If it is the globals, note that babelmap already has a native `scott` engine whose sessions solve this exact problem for the original Scott Adams format — look at how `scott_session.rs` reports rooms before inventing a v6-specific mechanism. A text-parsing fallback that reads the upper window is the other candidate, and it would generalise to other ports, but it is the weaker signal and should not be the first choice.

Related, same title, same session: SQ-0722 (title splash stuck in the transcript) and SQ-0723 (opaque text background over artwork).

User `/dump-windows` during play 2026-08-09 narrows this considerably — full dump in SQ-0723's notes. The two lines that matter:

    win0  640x140 at (1,261)  [wrap scroll transcript buffered]  <- current+input
            game: attrs=1111, 0 paint run(s), 0 prose line(s)
    win1  640x260 at (1,1)    [buffered]
            game: attrs=1000, 95 paint run(s), 0 prose line(s)   model: Graphics

`paint run(s)` is `w.texts.len()`. So the room description exists as **95 painted text runs inside win1**, the graphics window, while the story Buffer win0 is completely empty. Two consequences:

1. Anything that watches the transcript for room text will never see a thing on this game — win0 has no prose at all.
2. But the text IS available to us, already parsed into runs, in the window model. A text fallback would not need to scrape a rendered frame; it would read `w.texts` on the upper window.

That does not settle the approach. Object-tree detection is still the first thing to check (see the earlier note: `zvm::objects::object_snapshot` at `crates/zvm/src/objects.rs:427` feeding `mapper.observe` around `session.rs:2865-2894`) — if mysterious01 tracks location in a global rather than the player's parent, that is the real defect and a text fallback would be papering over it. Dump the object tree and the globals across two moves before choosing.
