There is nothing here to honour: the game declares no colour at all, and what we paint is a deliberate design choice meeting artwork with a baked-in ground. HARNESS. mysterious01.z6, booted past "Resume play on a game ?" with `n` and stepped one `look` (the recipe in `mysterious_room_detection.rs::boot_into_play`), so the frame is the opening room the report was filed against. THE SCREEN MODEL, exactly:

    [0] px 640x260 @(0,0)   Graphics win=1  canvas 640x260
    [1] px 640x140 @(0,260) Buffer primary=true bg=None fg=None px_runs=4
    [2] px 640x260 @(0,0)   Grid  bg=None fg=None px_texts=95 fill=None reverse=false

Window 1's canvas, by opaque-row profile:

    y   0..191  512 opaque px per row   <- the illustration
    y 192..242  0 opaque                <- the room description prints here
    y 243..258  512 opaque px per row   <- the dotted row of circles
    y 259       0

and the 95 runs sit at native y = 196, 212, 228 — rows 195..243, filling that gap almost exactly.

BOTH HYPOTHESES ARE DEAD.
1. "win1's own page": `Grid.bg` and `Buffer.bg` are BOTH `None` — `ZColour::Default`. The game never set a window colour. `fill` is `None` too, so no `erase_window` fill is live either.
2. "an explicit background on the 95 text runs": every one of the 95 runs carries `fg=0x00000000 bg=0x00000000` — Default on both channels, `packed_explicit` false. The game never coloured its text.

So the earlier framing — "we are failing to paint a background the game asked for" — is wrong because the game asked for NOTHING. And the framing before it ("text punches a cell-shaped hole through opaque artwork") is wrong too: rows 192..242 carry no opaque pixel at all, so there is no artwork behind the text to erase. The dump line the quest quoted, `art opaque down to native y=258`, is the EXTENT of opacity, not a claim that it is continuous.

WHAT WE ACTUALLY PAINT, and it is by design. The art is 512 px wide in a 640 px window, so the bare region is an L: the 51-row gap AND the right-hand 128 px column on every row. Both take the HOST page:

    raster row 100 (inside the illustration): [0,0,0]x318  [168,0,0]x176  [#280050]x128
    raster row 193 (the gap):                 [#280050]x640
    raster row 230 (gap, with glyph ink):     [#280050]x602 [200,200,200]x38
    raster row 258 (the divider):             [0,0,0]x512  [#280050]x128

The picture's own ground is pure black; everything it does not cover is the host page. In hybrid the same gap comes out as cells with the `upper_window` theme background (`Color::Black` under `terminal_default`) — see the second finding below.

AND THAT IS WHAT A REAL INTERPRETER DOES. On a real v6 interpreter every window is a clipping region over ONE screen bitmap initialised to the INTERPRETER'S DEFAULT BACKGROUND, and Spatterlight's is black — which is why its gap is black and continuous with the circles. babelmap's is the host theme, and it says so to the game: `loop_tick` advertises `host_default_colour_pair(theme transcript / OSC probe)` into header $2C via `set_default_colours`, so the story is TOLD its default page is the terminal's colour. The model is self-consistent; there is no spec violation and no missing paint. Spatterlight and babelmap differ in ONE value — the interpreter's default background — and the seam is that value meeting art that has black baked into its own pixels.

This also disposes of "extend the artwork's ground into the bare region" as a candidate: a real interpreter does NOT do that. It shows the screen default there, exactly as we do.

SECOND FINDING, real but also a design call, filed here rather than as its own quest because it is the same seam: THE TWO V6 PATHS DISAGREE ABOUT WHICH HOST COLOUR. Raster fills the gap with the host PAGE (`v6_host_pair` — theme `transcript` over the OSC probe); hybrid fills it with `upper_window`'s background, because `draw_chrome_text_strip` (crates/app/src/render/screen.rs) floods a text strip with `base` whenever no run names an explicit colour. Under `terminal_default` both land on black and the divergence is invisible; under any theme whose `upper_window` background differs from its `transcript` background the same frame renders two different colours in the same place depending on `v6_render`.

THE DECISION, which is the user's and not a lane's — what should the v6 screen ground be inside the game's own 640x400 rect?
  (a) Leave it. The host page is the host page; the seam is the price of a themed interpreter, and mysterious01 is the title that shows it because its art is 512 of 640 px wide on a black ground.
  (b) Give the v6 screen the Z-machine's own default page (black, `zvm::screen::DEFAULT_BG_COLOUR = 2`) instead of the terminal's, inside the frame only. This is what Spatterlight does and it makes the seam vanish — but it repaints the bare ground of EVERY v6 title, and it contradicts the deliberate choice `loop_tick` implements.
  (c) Do (b) per-title, through the knob that already exists: `InterpreterProfile::default_colours()` — `Amiga` already reports Infocom's own Amiga default page (medium grey 11) and `IbmPc` returns `None` meaning "use the host's". A third profile, or a per-game `config.toml` key, would let mysterious01 (and any other title with baked-in art ground) ask for a black page without moving anything else.
  (d) Fix only the second finding: make hybrid's text-strip fallback fill use the same host page raster uses, so the two modes agree. Narrow, objective, and does nothing for the reported seam on its own.

Retitle when a direction is chosen — the current title ("text drawn over a picture paints an opaque cell background, erasing the artwork behind it — needs a transparent-background path") describes none of the above, and the "is it kitty-only?" question it carries is moot: no transparency mechanism is involved anywhere in this.
