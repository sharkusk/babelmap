--- note 2026-07-10T00:07:41Z ---

Root cause found — NOT OOB-read tolerance. loadw/loadb/storew/storeb computed the array address in 32-bit space (a + 2*index as u32) instead of wrapping at 16 bits like the reference interpreter (frotz uses zword). praxix passes a word-index of 0xFFFF (meaning -1); we produced a + 0x1FFFE (~0x20A56, far OOB) → memory-fault halt, whereas frotz wraps to a-2 (in-bounds). Fix: compute the address with u16 wrapping arithmetic. praxix's "Array loads and stores" group now passes and the interpreter no longer halts. The OOB-read-tolerance approach was implemented then reverted as unnecessary (the strict fault safety-net is preserved). Also fixed the praxix regression test, which was vacuous (fed empty input so praxix never ran) — it now drives the core groups and asserts they pass without faulting.
