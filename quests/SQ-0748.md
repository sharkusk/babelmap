--- note 2026-08-10T02:46:24Z ---

SYMPTOM (user, 2026-08-09): reproduces on ANY version of Beyond Zork. From the opening screen, type `BEGIN`; the story text plays; the game then returns to its centred title screen — but the first screen's text (including the line where `BEGIN` was typed) is still on the pane, showing beneath/behind the centred title. Per the walkthrough only the centred title text should be present at that point.

Fixtures on hand: `stories/beyondzork-r57-s871221.z5` (a plain v5, drivable headlessly — start here), `stories/bzorkizm.z5`, `stories/beyondzork.blb`, `stories/Beyond Zork - The Coconut of Quendor.adf`. The user says every version behaves the same, so the .z5 is a faithful oracle and no disk image is needed.

WHERE TO LOOK — hypothesis, not a finding, so measure it first. Beyond Zork is a v5 whose story window is the host transcript, not a v6 painted window. The likely mechanism is that the game's screen clear (`erase_window`) is not clearing what the pane actually shows: either the opcode does not reach the transcript at all, or it clears the model while retained scrollback replays the old lines back into the viewport. Trace what the game emits around the title repaint before deciding — `@erase_window -1` vs `@erase_window 0`, and whether a `@split_window`/`@set_cursor` sequence is involved, are different bugs with different fixes.

This is a v5 cell-path defect, NOT the v6 composite. Whatever the fix, it must not disturb v6 titles, and any transcript-clearing change needs checking against games that legitimately expect scrollback to survive.

--- note 2026-08-10T03:08:55Z ---

MEASURED (headless probe, beyondzork-r57-s871221.z5, 80x25, trace_screen on).

Route to the defect: boot asks 'Is this a VT220?' -> answer NO -> 'Do you want to begin a new game, restore a saved game, or quit? [Type BEGIN, RESTORE or QUIT.] >' -> BEGIN -> the 'Our doom is sealed' prologue (erase_lower=true, prologue printed BELOW the erase, so it top-anchors correctly) -> pending=Char -> ONE keypress produces the title repaint.

WHAT THE GAME EMITS ON THE REPAINT TURN, in order:
  @erase_window(all(unsplit))     = erase_window(-1)
  @split_window(20)
  @set_cursor(row=8,  col=24)     'B  E  Y  O  N  D      Z  O  R  K'
  @set_cursor(row=9,  col=29)     'The Coconut of Quendor'
  @set_cursor(row=11, col=29)     'An Interactive Fantasy'
  @set_cursor(row=12, col=14)     copyright line
  @set_cursor(row=13, col=16)     trademark line
The turn's lower-window transcript is EMPTY. Every character of the title is PLACED in the upper window. No erase_window(0), no erase_window(-2).

THE NOTE'S HYPOTHESIS DID NOT HOLD. erase_window reaches the pane perfectly: erase_lower is set, turn::apply_game_driven_result truncates back to the prior anchor and calls mark_screen_clear, and state.clear_anchor is correct. Nor is retained scrollback replaying into the viewport by any general rule.

REAL CAUSE — an off-by-one in the anchor lookup, in the RENDERER, not the clear. render::transcript::anchor_row_at did 'starts.get(a)', where starts has exactly one entry per transcript line. Because the title turn prints nothing, mark_screen_clear leaves clear_anchor == transcript.len() — one index PAST the last starts entry. get() returned None, i.e. 'no anchor at all', so window_wrapped_rows fell through to bottom-sticking, and the five rows under the 20-row title showed the tail of the very screen the game had just erased. render::screen.rs's raster path (build_main_text) had the same lookup open-coded.

FIX: an anchor exactly AT the end is not out of range — it is a cleared screen with nothing printed into it yet, so every row precedes it and the post-clear screen is empty. anchor_row_at returns Some(total) for a == starts.len(); window_wrapped_rows renders that as a blank viewport with the erased screen still reachable by scrolling up. screen.rs now calls the shared helper instead of its own get().
