EVIDENCE (from the user's save `stuck-in-maze-no-debug.babelmap`, 431 turns, advent.blb):

Cause: Glulx room identity is `heading_to_room(name)` -> `synthetic_room_id(name)`, a hash of the room NAME alone. Every Adventure maze room is named "Maze", so all of them collapse into one node. The saved map holds 21 rooms / 57 connections with exactly ONE node named "Maze" (id 63778), a single edge in and zero self-loops. The Z-machine is unaffected: its id is the real object number.

Text-based identity is NOT sufficient: 62 maze arrivals in the transcript, only 18 carried a description (Inform prints the description on first visit, bare heading on revisits). Those 18 span 11 distinct descriptions, so ~11 real rooms collapsed. And this is only the "all different" maze -- Adventure's "all alike" maze has identical descriptions too.

THE VM HAS THE ANSWER. advent.blb never calls @accelparam, so gvm's accel-param table (which would give Inform's object-model layout) is empty for this game. But a plain correlation scan of RAM finds the identity anyway:

  * Snapshot all RAM words each turn (advent: ramstart 0x1df00, 13375 words, ~53 KB -- trivial to diff).
  * Score each word on whether it changes exactly when the room heading changes.
  * Winner at ramstart+0x28 (0x1df28), 9 agreements / 0 disagreements, plus several aliases
    (0x1df90, 0x1df94, 0x1dfa0, 0x1fe40, 0x1ff20 mirror it; 0x1fe44 tracks with different values).
    Values are room object addresses: Inside Building = 0x1ffec, At End Of Road = 0x1feec,
    At Hill In Road = 0x1ff8c. This is Inform's `location` global.
  * PROOF IT SOLVES THE MAZE: restoring the user's save and walking gave three distinct values
    -- 0x21b0c, 0x21b2c, 0x21b4c -- all under the identical heading "Maze".

AGREED DESIGN (user chose "build it", fallback = today's name hash):
  learn -> lock -> use -> unlock, mirroring the existing zvm `player_obj` lock.
  Fall back to `synthetic_room_id(name)` while unlocked, so nothing regresses for
  non-Inform Glulx games or ones where no such global exists.

SCORING MUST SKIP AMBIGUOUS TURNS -- this is the subtle part, and it is exactly the maze case:
  * confident CHANGED     = a heading was printed AND differs from the last one.
  * confident NOT-CHANGED = no heading was printed at all (take/wait/failed move).
  * AMBIGUOUS (skip)      = a heading was printed and EQUALS the last one. That is either a
    `look`, or a move into a DIFFERENT room with the SAME NAME. Scoring those turns would
    penalise the correct candidate every time the player walks the maze.

ID-MIGRATION WRINKLE (found during design, not yet solved in code): switching the id scheme
mid-session would duplicate every room mapped before the lock engages (name-hash id vs object
id). Mitigations: (a) persist the learned address per-game in the game-dir sidecar, as
`write_per_game_show_map` does, so every run after the first locks from turn 0 -- object
addresses are stable for a given story file; (b) on the first run, emit a remap table for the
handful of rooms observed during learning (their headings and the locked word's value are both
recoverable from the retained learning snapshots) and have the app apply it via a new
`Mapper::rekey_rooms`.
