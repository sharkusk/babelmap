MEASURED by SQ-0769's agent, reported as found-not-fixed.

`crates/app/src/term_colors.rs` sends the OSC 10/11 colour queries on **every** platform, but `drain_stdin_nonblocking` is a **no-op on Windows** — there is no portable non-blocking console read. So the answers are never consumed and arrive at the app as ordinary key events.

This is NOT the unix race SQ-0769 fixed. Unix leaked only when the terminal answered late; **Windows leaks on every launch**, deterministically, because nothing ever reads the replies. SQ-0769's `QuerySweep` gives up immediately on non-unix rather than holding the tty deaf, which is the right conservative default but leaves the platform unprotected.

VISIBLE SYMPTOM would be the same as SQ-0769's: the payload of the colour answers typed into the game — `0;rgb:…` / `11;rgb:…` — skipping keypress waits and answering prompts, since crossterm 0.29 has no OSC handling (`parse_event` falls through `ESC ]` to `Alt+']'` and hands the following bytes over as plain `Char`s).

RELEASE RELEVANCE: babelmap ships Windows binaries, and [[cross-platform-requirement]] is a standing rule. Whoever picks this up should decide between two shapes:
- **Read them.** A Windows-side console reader (crossterm's own event source, or the Console API) that consumes the replies, feeding the same `QuerySweep` machinery SQ-0769 built so the matching logic is shared rather than duplicated.
- **Do not ask.** If the queried values are not actually needed on Windows — or can be obtained another way — not sending the queries removes the problem entirely and is far less code. Establish what `term_colors` is used for before assuming the first shape is required.

The second deserves genuine consideration: a query whose answer we cannot read is pure liability.

RELATED, from the same investigation, both minor and unfiled elsewhere:
- The picker's own probe has the same shape — `ratatui-image` returns as soon as its reader thread signals Done, and only *then* restores the termios it saved.
- `pixel_mouse::query_pixel_mouse_support` shares `query_with` and is currently never called. If it is ever switched on it inherits the identical hazard and should hand its unanswered case to `QuerySweep`.
