--- note 2026-08-12T03:04:33Z ---

REOPENED 2026-08-11 — the feature works as specified but is wrong in two cases the user hit. Their report: "ADF games don't show the filename (they should show the ADF). Scott games just show 'arrow1' or 'mysterious03' instead of their actual story title (that is listed in the story list)."

Both diagnosed read-only; neither is speculation.

**PART A — a container's filename must always be shown.** `format_pane_title` (session.rs:3484) compares `normalize_ident(name)` against `normalize_ident(stem)`, and `normalize_ident` (hints.rs:212) strips every non-alphanumeric character. So `"Journey: The Quest Begins"` and the stem of `Journey - The Quest Begins.adf` both normalise to `journeythequestbegins`, the two are "the same", and the parenthetical is suppressed. Same for `Arthur - The Quest for Excalibur.adf`.
That is the specified behaviour and it is the wrong call for a mounted container. **CLAUDE.md's own rule (SQ-0760): a disk image is a DIFFERENT RELEASE, not the same story on other media** — `stories/journey.z6` is release 83, the ADF is release 30, and they behave differently. Which medium is loaded is exactly what the title should disclose. So: when the story is mounted from a container (`.adf` certainly; decide deliberately about `.zblorb`/`.blb`/zip, which are also containers but usually the same release), show the filename regardless of how well it matches the name.
Note this interacts with SQ-0771, just merged, which added `StoryMeta.story_bytes` beside `size_bytes` and names both in the info panel only when they differ — the same "the container is not the game" distinction, so the two should read consistently.

**PART B — Scott titles already exist in the tree and the pane never asks for them.** `crates/app/src/scott_titles.tsv` feeds `scott_titles()` in `picker.rs:529`, a table **keyed by filename stem** carrying canonical title, author, IFDB tuid and description ("the ScottFree corpus (Brian Howarth's Mysterious Adventures reuse 1-11 …)"). The story browser shows those titles, which is why the list is right and the pane is wrong.
`resolve_title` (session.rs:3447) never consults it. Its cascade is: `override_name` → `known_title(ifid)` → banner → filename stem. A Scott game has no IFID for the Z-machine table and no banner the heuristic can parse, so it lands on the stem — hence `arrow1`, `mysterious03`.
**Fix: give `resolve_title` the Scott table, keyed by stem, ahead of the banner/stem fallbacks.** The data needs no new source. Watch the layering: `scott_titles()` currently lives in `picker.rs` (the browser) while `resolve_title` lives in `session.rs`; move or share it rather than duplicating the table — two copies of a title list will drift.

WORTH CHECKING WHILE THERE, not yet verified: whether Glulx games get a good name. `known_title(ifid)` is Infocom-heavy, so a modern Glulx game depends entirely on `title_from_banner`. If it also has a metadata source the browser uses and the pane does not, that is the same defect a third time.

ACCEPTANCE: an ADF-mounted story names its `.adf` in the pane; a Scott story shows the same title the story browser shows; existing bare-name cases (`bureaucracy.z4` → "Bureaucracy") are unchanged; the existing unit tests in session.rs (`format_pane_title_*`, `resolve_title_*`) still pass or are updated deliberately with the reason stated.

--- note 2026-08-12T03:05:03Z ---

PART C, user 2026-08-11: "anchorhead only shows 'anchor'" — `stories/anchor.z8` shows its filename stem instead of "Anchorhead".

This is the third instance of the same family and it implicates the remaining step of the cascade. Anchorhead is a modern Z-machine game, so `known_title(ifid)` (Infocom-heavy) misses; the title must therefore come from `title_from_banner`, and it does not.

**LIKELY MECHANISM, with independent corroboration.** The SQ-0782 lane, hunting for a story with full-width prose, reported: *"Anchorhead was tried first per the 'wordy prose' brief but its paged title screen never advanced under the harness."* So Anchorhead boots into a PAGED TITLE SCREEN. At the moment `startup.rs:741` takes the banner (`session.take_transcript_elems()` / `take_transcript()`), the transcript may hold nothing parseable — a title plate and a keypress prompt rather than the conventional "TITLE\nAn Interactive …\nCopyright (c) …" banner the heuristic is built for. Verify before fixing: dump what `banner` actually contains for `anchor.z8` at that point. It may be empty, may be a `[MORE]`/keypress prompt, or may be text the heuristic rejects — three different fixes.

**THE PATTERN ACROSS ALL THREE PARTS.** A, B and C are one shape: the pane title falls back to the filename stem whenever its better sources miss, and the better sources are narrow. The story browser knows better in at least the Scott case (Part B) and possibly here — **check what the browser shows for `anchor.z8`**; if it shows "Anchorhead" then the browser has a metadata source the pane never asks for, and that source (not a better banner heuristic) is the real fix for the whole family.

Candidate sources worth checking, in the order a fix should prefer them: an IFID hit in an extended table; Blorb/iFiction metadata where a container carries it; whatever the browser/IFDB cache already resolved for this story (`ifdb_search.rs`, `fetch_worker.rs`, `picker.rs`); then the banner; then the stem. Deferring the banner heuristic below real metadata would fix C, B and any Glulx case at once, and would leave the stem as the genuine last resort it was meant to be.

DO NOT simply special-case Anchorhead or add it to a table by hand — that treats the instance and leaves the family.

--- note 2026-08-12T03:07:22Z ---

PART D, user 2026-08-11: "Photopia shows 'photo201'".

Two files exist in `stories/`: `photopia.z5` and `photo201.blb`. The reported title is `photo201`, so the user is launching the **blorb** and getting its stem. Expected "Photopia".

MEASUREMENT that rules out one candidate source for this specimen (coordinator, read-only): **`photo201.blb` carries NO Treaty-of-Babel metadata.** Chunk types present: `RIdx` only — no `IFmd` chunk, no `<title>` XML; the only "photopia" string in the file is an incidental `` `photopia ``.

So "read the container's iFiction metadata" cannot be the whole fix. Our blorb crate DOES support it — `crates/blorb/src/lib.rs:129` recognises `IFmd`, `Blorb::metadata()` (:202) returns the raw ifindex XML, tests at :667 — so it belongs in the source ordering for blorbs that carry it, but a fix leaning on it alone still shows `photo201`.

WHAT THAT LEAVES for Photopia: an IFID hit, or whatever the story browser already resolved. Which makes the question this quest already turns on — *what does the browser show, and where does it get it?* — apply to `photo201.blb` as much as to `anchor.z8`. A browser that names "Photopia" for a blorb with no IFmd is naming it from a source the pane never asks, and that source is very likely the family fix for A, B, C and D together.

FOUR SPECIMENS NOW, one shape: `Journey - The Quest Begins.adf` (container suppressed), `arrow1`/`mysterious03` (Scott table not consulted), `anchor.z8` (banner heuristic defeated by a paged title screen), `photo201.blb` (blorb stem, no metadata in the file). Any proposed fix should be checked against all four before it is called done — and against a Glulx title, which nobody has yet confirmed either way.
