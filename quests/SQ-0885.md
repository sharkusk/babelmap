--- note 2026-08-15T08:05:44Z ---

MEASURED, on the same build both sides — `James Clavell's Shogun.adf`, release 295 / serial 890321, at the credits-and-menu screen.

  original (Amiga)   "Amiga Interpreter version 6.8"
  babelmap           "Amiga Interpreter version 6.65"

(My first reading of the low-resolution screenshot said 6.0; the user corrected it to 6.8. The mechanism is the same either way and 8 is the plausible value — an interpreter release number.)

WHO PRINTS IT: the STORY does, not us. Shogun reads header byte `$1E` (interpreter number, 4 → the word "Amiga") and `$1F` (interpreter version) and formats them, and this build formats `$1F` as a DECIMAL rather than as a character. `zvm::screen::init_header_caps` writes

    // Interpreter version (0x1F): b'A' = 0x41.
    mem.write_byte(0x1F, b'A');

unconditionally, for every machine and every story version. 0x41 is 65, so the banner reads 6.65. The original Amiga interpreter evidently wrote 8.

SAFE TO CHANGE: nothing in the VM reads `$1F`. Grepped — the only reader is a test asserting the byte is `b'A'`. The byte exists solely for a story to print, so this changes what the player sees and nothing else.

THE OPEN QUESTION, and it needs a second data point before anything is written. `$1F` is plainly a per-machine constant, but it may also be per-INTERPRETER-RELEASE, and two Amiga games disagree about how they render it:

  Shogun r295 (v6, 1989)        "Amiga Interpreter version 6.8"     — formats $1F as a decimal
  Nord and Bert r19 (v3, 1987)  "Infocom Interpreter 4 Version C"   — renders a LETTER, 'C'

If both read the same byte, the Amiga wrote 'C' (67) for Nord and Bert's era and 8 for Shogun's — two different interpreter releases on one machine, which is entirely plausible and means a single per-machine constant cannot be right for both. If instead Nord and Bert prints its own build letter from elsewhere and only Shogun reads `$1F`, one constant per machine is fine. RESOLVE THIS BEFORE PICKING A VALUE: find a second Amiga v6 title's banner, and check what an Apple/Macintosh/DOS press prints in the same slot — the corpus has bootable media for all of them and every one of those banners is a free measurement.

Note this sits in the same family as SQ-0872's machine table and SQ-0873's period look: another small per-machine constant that is visible to the player and currently hard-coded to one value for every machine. If it does turn out to be per-machine, it belongs as a column in `zvm::interpreter::MachineProfile` beside `number`, and `zvm-cli --machines` should print it.

--- note 2026-08-15T08:07:26Z ---

PROVENANCE OF OUR VALUE, asked by the user: there is none.

`git log -S "0x1F, b'A'"` gives exactly one commit — **d3e1d5e9, 2026-06-18, "feat(zvm): screen model, status line, windows, output stream 3"** — the first screen-model commit, where `$1F` arrived in a batch with Flags1, Flags2, the interpreter number and the standard revision. The whole justification is the comment it shipped with:

    ///   - 0x1E: interpreter number — 6 (IBM PC), a common neutral value.
    ///   - 0x1F: interpreter version — 'A' (ASCII 0x41), standard v1.1 era.

No section citation, no fixture, no measurement. Nothing in `docs/` discusses it.

**THE LINE ABOVE IT IS THE POINT.** `$1E` came out of the same batch as "6, a common neutral value" — precisely the unsourced guess that SQ-0872 replaced with a machine table sourced from `st/stx1.s`, `zboot.asm` and `mac/xzip.lst`. `$1F` is its sibling, sitting two lines away, and was never revisited. It is the last unsourced member of the batch that produced the interpreter-number defect.

That also means the "standard v1.1 era" rationale is itself unverified in-repo: it asserts that a Standard 1.0+ interpreter writes an ASCII letter, without naming the section. Check ZMSD §11.1.3.1 against the document before either keeping 'A' or replacing it — per the project's rule that spec constants are verified against the source and never from memory. It is entirely possible the standard's advice and Infocom's actual bytes simply differ, in which case this is a policy choice (present as a modern Standard interpreter, or present as the machine) and should be written down as one rather than settled by accident.

--- note 2026-08-15T17:43:34Z ---

RESOLVED BY THE USER'S RESEARCH 2026-08-15 — no code change, and the quest closes here.

Their finding: the interpreter-version value **does not matter as long as it is greater than 6.6**, and likely not even then, because **no story should key off it**. Real-world ceilings they established:

| machine | peak interpreter version |
|---|---|
| Apple IIgs | 6.9 |
| Amiga | 6.8 |
| IBM | 6.7 |

DECISION: **keep the `--interpreter-version` command-line argument, do NOT change our current defaults.** The argument (shipped in `82d202c0`, `zvm::screen::set_interpreter_version` + `app::config::parse_interpreter_version`) stays as an experimentation lever; the shipped `$1F` values stay as they are.

WHY THIS CLOSES RATHER THAN DEFERS. The quest was opened because our `$1F` value was unsourced and I could not tell whether it should vary per machine or per interpreter release — the plan was to obtain a second Amiga v6 banner and decide from it. That investigation is now unnecessary: the question was "which value is right", and the answer is "the distinction does not affect behaviour". A second capture would refine a number nothing reads.

STILL OBSERVABLE, recorded so it is findable rather than rediscovered as a bug: our banner prints "Interpreter version 6.65" where the original Amiga press printed 6.8 (measured earlier this session from the user's screenshot of `james_clavells_shogun_02.png`), and the Apple press's own banner in our render reads "Apple IIgs Interpreter version 6.65". So the printed banner text still differs from period hardware. Per the decision above this is ACCEPTED, not a defect — but if period-accurate banner text is ever wanted for authenticity (it would sit naturally beside SQ-0873's period-look work), the ceilings above are the sourced numbers to use, and this note is the reference.

NOT ESTABLISHED, and deliberately not chased: whether the "6.65" our banner shows is derived from `$1F` at all or from a separate constant. Nobody needs to know unless the authenticity question above is ever taken up.
