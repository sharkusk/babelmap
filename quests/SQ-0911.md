--- note 2026-08-18T04:19:04Z ---

## What is missing

`crates/blorb/src/hfs.rs` reads **data forks only**. Its own doc says so — *"a Macintosh application is `all` resource fork"* — and it records `resource_size` (from `filRLgLen`) without ever reading the extents. `FIL_R_LG_LEN` is already parsed at `hfs.rs:165`.

MEASURED on `stories/Sherlock.img` while implementing SQ-0907: the mount reports exactly **two files**, `Desktop` and `SHERLOCK`, and `native_sound::from_medium` finds nothing. The Amiga floppy of the same game yields fifteen effects. Everything the Mac release ships — sounds, and very likely its artwork — lives in the resource fork of that application.

## Two layers, and the second is the bigger one

1. **Fork extents.** An HFS catalogue record carries both forks' first extents and lengths; the reader takes the data fork's. Reading the resource fork is the same walk against different fields, plus the extents overflow file when a fork is fragmented.
2. **The Macintosh resource MAP.** A resource fork is not a filesystem — it is a header, a data area, and a map of typed, numbered resources. Infocom's Mac sounds are `snd ` resources, which is a **different container again** from the Amiga's (SQ-0907's ten-byte header) and from AIFF: a format/type word, then either a sampled-sound or a note-list command sequence. Do not assume it is the Amiga container renamed.

## Worth knowing before starting

- The payoff is broader than sound. If the Mac releases keep their artwork in the resource fork too, this is the door to Macintosh renditions generally — `InterpreterProfile::Macintosh` already exists, and `v6_border.rs` already documents the Mac B/W plate's geometry, so something must currently be reaching it another way. Check what, and whether that path is a workaround this would retire.
- `SQ-0907`'s verification pattern applies here as well and should be reused: decode, then compare against a rendition somebody else made rather than trusting the bytes. If no Blorb of Sherlock's Mac sounds exists, say so in the finding rather than shipping an unchecked decoder.
- The corpus has at least `stories/Sherlock.img` and the five `.dc42` *Lost Treasures* Macintosh discs added during SQ-0910, so there is material to test against.

## CORRECTION — the Mac releases do not carry the sound, so this is not a sound quest

The user pointed out that Macintosh ARTWORK is already detected on the Masterpieces disc, which is true and is the clue: there the Mac games are folders of ordinary files — `MAC/ZORK ZERO/CPIC.DATA`, `MAC/ZORK ZERO/PIC.DATA` — living in **data forks**, which `hfs.rs` reads today. Packaging differs per release, and the first note guessed that a floppy must therefore be hiding its assets in the resource fork. MEASURED, it is not:

| medium | file | data fork | resource fork |
|---|---|---|---|
| `stories/Sherlock.img` | `SHERLOCK` | **190,464** | 23,110 |
| | `Desktop` | 0 | 1,059 |
| `…Disk 1 - Beyond Zork, Lurking Horror.dc42` | `Beyond Zork` | 262,144 | 22,692 |
| | `Lurking Horror` (×2, plus `The Lurking Horror`) | 129,024 | 16,810 |

Two things fall out:

1. **The story is already reachable.** `SHERLOCK`'s 190,464-byte data fork is exactly the size of the Amiga floppy's `Story.Data`. Nothing about the Z-code is behind a fork we cannot read.
2. **There is nowhere for the sound to be.** Sherlock's Amiga samples total roughly half a megabyte; the whole resource fork is **23 KB**, and Lurking Horror's is **17 KB**. Those hold icons, menus and code — not fifteen sampled effects. The Macintosh releases of both games simply ship without the sound, or ship it on media not in this corpus.

So SQ-0907 is not missing a Macintosh half, and nothing here blocks it. That is the useful outcome: a quest that would have gone looking for samples that do not exist.

## What is left, and it is smaller and different

`hfs.rs` still reads data forks only (`FIL_R_LG_LEN` is parsed at `hfs.rs:165` and the extents are never walked). That remains a real gap — a Macintosh application IS all resource fork, so babelmap can see that these files exist and never what is in them — but the case for closing it is no longer "to get the sound". Re-open it when something concrete is wanted from a resource fork; on this corpus nothing yet is.

Worth a passing note for whoever picks this up: the `.dc42` disc lists `Lurking Horror` **twice** alongside `The Lurking Horror`, all three at 129,024 bytes. Aliases or duplicate catalogue entries; harmless, but a browser row per copy would look like a bug to a player, and SQ-0908's lesson is that duplicate-looking rows on a compilation deserve a check rather than a shrug.

Settled for Sherlock: the Mac release ships no sound at all, so there is no Mac pitch question.

`stories/Sherlock.img` (HFS, 410,624 bytes) holds exactly two catalog entries:

    data      rsrc  type   creat  name
       0      1059  FNDR   ERIK   Desktop
  190464     23110  APPL   INH1   SHERLOCK

The 23,110-byte resource fork is the Mac interpreter's own code and resources — two orders of magnitude short of the ~500 KB of PCM the Amiga release carries. A raw scan of the whole image finds zero occurrences of `snd `, `.dat`, `.mid`, `FORM` or `AIFF`, and only 192,366 of 410,624 bytes are nonzero at all — essentially the story and nothing else. By contrast the Amiga ADF of the same game carries 24 `.mid` references.

So the unread resource fork (hfs.rs:203 "not read") is not hiding audio here, and the two-note pitch model (`.mid` note + per-effect note from the interpreter binary) is Amiga-only: it describes how Paula's `ioa_Period` is programmed, and the Mac release has no sampled-sound path to program. Confirms the earlier deferral rather than reopening it.

## Correction to the note above: the Macintosh release is NOT silent — that floppy is just incomplete

The previous note concluded "the Mac release ships no sound at all" from `stories/Sherlock.img`. The measurement stands for that image — two catalog entries, a 23,110-byte resource fork, zero occurrences of `snd `/`.dat`/`.mid`/`FORM`/`AIFF` — but the conclusion drawn from it does not.

`treasures/LostTreasures2.iso` carries `/MAC/SHERLOCK` (190,464 data + 23,110 resource — the SAME sizes as the floppy's) and, beside it at the top of `/MAC`, a **`SOUND` folder**: thirteen `S<n>` samples and four `M<n>` pitch/index files. So `Sherlock.img` is one disk of a multi-disk release and the sound lived on another; a single floppy proving nothing about the release is the same trap CLAUDE.md records for disk images generally.

The resource-fork question is untouched by this and remains correctly deferred: the sound is in ordinary data forks, exactly as `hfs.rs:203` says an Infocom release keeps its story and artwork, so nothing here argues for reading resource forks.

SQ-0912 shipped support for that layout (commit 85147a5c), and it is where the pitch model was finally settled — the Macintosh `M<n>` files are the only place in the corpus where a pitch file's two notes differ.

## A second, better reason to revisit this: the Macintosh FONT resources

The original deferral stands on its own evidence — no Mac release keeps *sound* in a resource fork, and SQ-0912 found the Mac sound sitting in ordinary data forks under `/MAC/SOUND`. But SQ-0916 turned up something that genuinely does live in a resource fork and that we genuinely want.

Every Macintosh v6 title (Arthur, Journey, Shogun, Zork Zero) carries two bitmap `FONT` resources, and *Beyond Zork* carries one. MEASURED off `/MAC/ARTHUR FOLDER/ARTHUR` on *Lost Treasures* disc 2:

| resource | cell | advance widths |
|---|---|---|
| `FONT` 524 | 7×15 | 6, 7 |
| `FONT` 1033 | 7×12 | **6 only** |

The advance-width table is what matters: 1033 gives every defined character the same advance, so it is fixed-pitch and drops straight into babelmap's fixed-cell v6 raster model. That is precisely what the **Amiga** fonts cannot do — Arthur's `char.data` is proportional (widths 2–8), and SQ-0916 has a rendered comparison showing that centring it in a fixed 8×16 cell reads visibly worse than the public-domain font we ship today, because the word rhythm is destroyed.

So the Macintosh fonts are the only ones in the corpus that would actually improve the raster path, and they are behind the fork reader that `hfs.rs:203` documents as deliberately unread ("an Infocom release keeps its story and its artwork in data forks" — true, and now known to be incomplete: it keeps its FONTS in the resource fork).

Scope if this is picked up: the resource-fork extents come from the same catalog record the data fork's do, so `hfs.rs` already has the file's `resource_size` and needs the extent walk pointed at `filRExtRec` rather than `filExtRec`. The ISO9660 side is separate and already visible — associated files (`/MAC/... ASSOC`) carry the same forks and `iso9660.rs` skips them by design, for the good reason recorded there (taking both would list every Macintosh game twice); that skip would need a way to ask for a fork by name rather than being lifted.

Nothing here changes the sound conclusion. Reopening would be about fonts.
