## The idea

> "rather than publishing in static documentation, let's let the application report actual values (including graphics modes) in `--machines` (and add that arg to app)."

Two parts: put `--machines` on `lanthorn` as well as `zvm-cli`, and widen what it prints so the values that VARY are visible rather than flattened.

## Start from what already exists — it is good, and its shape should be kept

`zvm-cli --machines` already prints the whole §11.1.3 table in two sections, with provenance stated per section: part 1 "WHAT THE STORY IS TOLD", read out of Infocom's own interpreter source, colours resolved through each machine's own §8.3.1.1 palette; part 2 "WHAT THE SCREEN LOOKED LIKE", explicitly OBSERVED from `machine-screenshots/` and explicitly not read from source, with a dash meaning "no capture" rather than "no look". It also explains `global pens`, `v6 screen page` and `one screen palette` in prose underneath. That is the register to preserve.

## What is currently FLATTENED, and is the actual content of this quest

The table prints one pair per machine, and the IBM PC's pair is not one value:

  - **It varies by story VERSION.** `zvm::screen::ega_true_colour` has `9 if yzip => 0x7FFF` (white `#FFFFFF`) against the xzip `0x56B5` (light grey `#ADADAD`), and colour 9 is the ONE entry the two IBM interpreters disagree on. v6 selects yzip (SQ-0939's `palette_for(number, zversion)`). So the row printed today — `bg 6 #0000AD  fg 9 #ADADAD` — is the v1–v5 answer, and a v6 story is told something different. Nothing on the screen says so.
  - **It varies by GRAPHICS MODE.** SQ-0956 gives a CGA rendition `bg 2 #000000` under a light-grey ink, against EGA/MCGA's blue. Same machine, same interpreter number, different card.

So the IBM PC has at least three distinct answers and the table shows one. That is precisely the kind of thing static documentation gets wrong slowly and a printed table cannot.

## Depends on SQ-0956

Do this AFTER it lands. The CGA values are what this is meant to surface, and building the display against a design rather than against shipped code is how the two end up disagreeing.

## Worth considering while designing the output

  - The period-look section should NOT gain a card axis. SQ-0955's note records why: `machine-screenshots/dos-hitchhiker.png` is a CGA machine running a v3 story and its page is the same blue the EGA v6 captures show, so a card changes the v6 graphics screen and not the text-mode look. Printing a card column there would invent a distinction the captures deny.
  - lanthorn's build knows things `zvm-cli` does not — which archive a story would load, what `hardware_palette()` says about it. A `--machines` that can take an optional story path and print what THIS launch resolves would be more useful than a static dump, and is closer to "report actual values" than "print the table twice".
  - It feeds the website plan (`docs/superpowers/plans/2026-08-20-website.md`), whose `/machines` page is built around this command as a cast. Keep it worth watching: it is pure text, so asciinema captures it whole.

## And it changes SQ-0955

That quest is "the period-look table in `docs/features/interpreter.md` is stale". Once this exists, the right fix there is to DELETE the table and point at the command, not to correct it — see the note on SQ-0955.
