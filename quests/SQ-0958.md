--- note 2026-08-21T05:07:40Z ---

## The failure

`crates/app/tests/suites/v6_shogun_gameplay.rs::shogun_hybrid_status_band_floods_game_background` reads `Rgb(173, 173, 173)` — EGA white — where it expects `#FFFFFF`. Roughly two runs in three.

Found by the SQ-0956 lane, which added a suite that boots a DOS press. **It is PRE-EXISTING**, not caused by that work: the lane stashed its entire diff and reproduced the failure 3/3 on the clean base before reporting it.

## Why the gate cannot see it, and why CI can

This is the SQ-0905 class, described in CLAUDE.md's "Commands" section. `zvm::screen::set_palette` is process-global. Under `cargo nextest run` every test gets its OWN PROCESS, so no test can observe another's palette and the race is *structurally invisible* — the gate will print 0 forever. Under `cargo test` a binary's tests share one process across many threads, and the race fires.

**CI runs `cargo test`. The local gate runs nextest. So main is red in CI and green locally**, which is exactly the split SQ-0905 recorded and exactly why that quest added `palette_lock_discipline`.

## Why `palette_lock_discipline` did not catch it

That source-level case fails a suite under `tests/suites/` that SETS the palette without `app::V6_PALETTE_LOCK`. It can only see WRITERS.

This is a **reader**: a suite that resolves colour numbers through whatever palette happens to be installed, without setting one or taking the lock. That is harmless only while every other suite in its group binary leaves `Palette::Standard` there — and it stops being harmless the moment a sibling suite boots a press that installs the IBM YZIP table. `#FFFFFF` against `Rgb(173,173,173)` is precisely Standard-white against EGA-white.

The SQ-0956 lane hit the same shape in `v6_hybrid_zork0` and fixed it there — that suite now states the palette it always assumed, under `V6_PALETTE_LOCK`. `v6_shogun_gameplay` was left alone deliberately, to keep a CGA diff from growing into a suite it does not concern.

## The fix, and the bigger question behind it

Narrow fix: have the suite state the palette it assumes and take `app::V6_PALETTE_LOCK`, as `v6_hybrid_zork0` now does.

The bigger question is whether `palette_lock_discipline` should be extended to catch READERS as well as writers, because the next such suite will be written by someone with no reason to know any of this — which is the reasoning SQ-0905 used to justify the writer check in the first place. A reader is harder to detect at source level than a writer (it is an absence, not a call), so this may want a different mechanism: for instance, having the suite harness install a known palette by default so a suite that never states one still gets a deterministic answer.

## Verify with the right command

`cargo nextest run` CANNOT confirm this fixed. Use `cargo test -p app --test v6_shogun_gameplay` (or `cargo test --workspace`), and run it several times — at ~2/3 a single green run proves nothing.

## THE USER'S RULE, which is the real scope of this quest

> "No test should be written that makes an assumption about a palette it did not write."

That is stronger and cleaner than "fix the flaky suite", and it reframes the whole thing. The narrow fix — have `v6_shogun_gameplay` state its palette under `V6_PALETTE_LOCK` — is now just the first instance of the rule, not the deliverable.

Under this rule the defect is not "this suite races". It is **"this suite resolved colour numbers through a palette nobody in it installed"**, which is a defect whether or not a sibling ever happens to install a different one. The race is only how it became visible. `v6_hybrid_zork0` had the same defect and was fixed in the SQ-0956 lane; `v6_shogun_gameplay` is the one that stayed.

## What has to be true when this is done

1. Every suite under `crates/app/tests/suites/` that resolves colour numbers **states the palette it assumes and takes `app::V6_PALETTE_LOCK`** — including the ones that assume `Palette::Standard`, because assuming the default is still an assumption it did not write. `v6_hybrid_zork0` is the worked example.
2. The rule is **enforced at source level**, so the next such suite cannot be written by someone with no reason to know any of this. That is the same reasoning SQ-0905 used to justify `palette_lock_discipline`, and it is why that check exists at all.

## The hard half, stated honestly

`palette_lock_discipline` catches WRITERS — a suite that calls `set_palette` without the lock — and a writer is a call, so it is easy to see in source. A reader is an ABSENCE, which is not.

Two shapes worth weighing, and neither should be picked without measuring against the corpus first:

  - **Require the pair.** Enumerate suites that reach a colour-resolving entry point (the render harnesses, `packed_to_rgba`, the v6 boot helpers) and fail any that does not also mention `V6_PALETTE_LOCK`. Catches everything, but it is a grep-shaped rule and will want an explicit allow-list for suites that legitimately touch none of it.
  - **Remove the assumption instead of policing it.** Give the shared boot/render harness a palette parameter with no default, so a suite cannot reach a rendered frame WITHOUT stating one. This makes the rule structural rather than checked — the compiler enforces it, and there is nothing to keep in sync. More churn up front, no ongoing cost, and it is closer to what the user's sentence actually asks for.

The second is probably right, and is the one to cost first.

## Verification, which the local gate structurally cannot do

`cargo nextest run` gives every test its own process, so the race cannot fire and the gate will print 0 whether or not this is fixed. Use `cargo test -p app --test v6_shogun_gameplay` and `cargo test --workspace`, several times each — at ~2 failures in 3 a single green run proves nothing.
