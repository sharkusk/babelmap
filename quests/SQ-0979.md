## SEQUENCING — held deliberately, not orphaned

Blocked on the SQ-0950 lane, which is concurrently editing `crates/app/src/render/graphics.rs` and `render/screen.rs`. The fix here lives in `GraphicsRender::render` in that same file. Dispatch as soon as SQ-0950 merges.

## What the fix has to account for that the v6 one did not

SQ-0973's approach was to compute the cell rect by arithmetic (`v6_halfblocks_grid`) and resample the canvas once onto `cols x 2*rows` with `resize_directional`, then construct `Protocol::Halfblocks(Halfblocks::new(...))` directly so the crate's `resize_exact` is a 1:1 identity pass. The same shape should work here, but the generic path differs in ways that matter:

- It honours `gw.upscale` (blow a small canvas up to fill the window vs leave it native and centre it) — Scott room pictures want the former. The v6 path has no equivalent.
- It caches per `gw.win` keyed on `(version, area.width, area.height)`, not on a generation counter.
- SQ-0829 is pinned on this path: a canvas LARGER than its window (advent.blb's 1104-px toolbar in a narrow pane) was being minified by dropping columns, which is why `fit_for_protocol` resamples directionally. Whatever replaces it must keep that property — check the SQ-0829 case still passes and understand it before touching this.
- Content here is arbitrary Glulx PNG/JPEG, not 16-colour pixel art, so "Nearest keeps it crisp" is not automatically the right filter choice; a photograph wants a smooth minifier. `resize_directional` already distinguishes direction — read it rather than assuming.

Kitty is unaffected (returns early into `render_kitty_virtual`); sixel and iTerm2 genuinely encode and should keep `Fit` + pre-scale.

## SCOPE WIDENED — four consumers, not one. The title understates it.

Filed as "Glulx graphics windows". The code says otherwise, at `render/graphics.rs:78`, documenting what `resize_directional` serves:

> "...and, through `fit_for_protocol`, **cover art, gallery tiles, the resource preview** and the non-kitty graphics-window blit"

So everything reaching `fit_for_protocol` + `new_protocol(Resize::Fit(None))` still pays the pre-scale-then-shrink pair under half-blocks:

1. Glulx graphics windows (the non-kitty blit).
2. **Cover art in the story list's info panel.**
3. **Gallery tiles — the cover-view grid**, which shows every story's cover art instead of a list. This is the heaviest case in the app: N images resampled twice per frame rather than one. Each tile's intermediate is small in isolation, but the cost is multiplied by the number of visible tiles and paid on every scroll.
4. The resource preview.

`crates/app/src/cover_gallery.rs` holds the grid geometry (`columns`, `visible_rows`, `tile_rect`, `wheel_scroll`); `picker_ui.rs`, `picker.rs`, `assets.rs`, `ifdb.rs` and `fetch_worker.rs` are the surrounding machinery.

## Which makes the filter question sharper, not softer

Cover art and IFDB artwork are PHOTOGRAPHIC. Infocom v6 art is 16-colour pixel art. The v6 fix (SQ-0973) could lean on Nearest staying crisp; this path cannot, and must not regress cover art into a posterised or aliased mess. `resize_directional` already filters per axis by direction — replication growing, area average shrinking — which is the right behaviour for both, so the fix should preserve that rather than substituting a single filter. Read its doc comment before changing anything: it states the two guarantees it exists to provide, and SQ-0829 is pinned on the second.

## Measurement note

Before optimising, MEASURE the gallery case specifically. The v6 numbers (50 MB, 155 ms at a 458x144 pane) came from one large canvas; a grid of small tiles has a different profile, and the win may come from tile count rather than tile size. Do not assume the v6 numbers transfer.

## Measured outcome — the v6 numbers did NOT transfer, as the brief suspected

Gallery grid (36 tiles, 200x50): 76.2 ms / 211.4 MB -> 43.6 ms / 132.4 MB, **1.75x** and 0.63x bytes. Cover panel: 1.94x. These are real but modest, and nothing like SQ-0973's 70x.

Why: a tile's pre-scale is 190x220, not 4580x2862, and the first pass costs O(source) whichever grid it lands on — so the gallery win is the SECOND pass plus the intermediate, not the elimination of a huge magnification. The dramatic case here is the magnifying one, a Glulx window at 320x200 -> 100x40 with upscale: 6.78 ms / 9.2 MB -> 0.29 ms / 0.9 MB, **23.4x**. That is v6-shaped, and it is where the win actually lives.

## Known, accepted regression — recorded here rather than filed as its own quest

A canvas already at NATIVE size in its window is ~0.04 ms slower (0.14 -> 0.18 ms, 0.83x): the direct path performs alpha association that the pre-scale's 1:1 Nearest copy skipped. Sub-noise in absolute terms, and it buys the alpha correctness SQ-0827 exists for, plus a cut-out edge that no longer averages toward black. This is a deliberate trade with a stated benefit, not an oversight — noted so nobody rediscovers it as a mystery.

## Methodology note worth keeping

The lane's FIRST measurement was wrong and it caught it: reusing six image paths across 36 tiles meant it was benchmarking the LRU cache rather than the resampler. Each tile has its own cache key, so N tiles are N builds. Any future benchmark of this path must use distinct keys or it measures nothing.

In every case measured the cell rect is byte-identical before and after, so nothing on screen moved.
