--- note 2026-08-14T19:41:40Z ---

FIXTURES now in `stories/`, all 174,848 bytes (35-track 1541), all currently read as raw story files (`Error: Z-machine version 0 is not supported`):

- `Hitchhikers_Guide_to_the_Galaxy_The_1984_Infocom.d64` — disk name `HITCHHIKER GUIDE`, **DOS version bytes read `TG`, not the standard `2A`** — a custom or copy-protected directory. Z-header found at raw 0x05400: **v3 r47 s840914**, declared length 112,622.
- `TRINITY1.D64` — disk name `TRINITY`, standard `2A`. Z-header at raw 0x02a00 (= track 3, sector 0): **v4 r12 s860926, declared length 131,032, checksum `16AB`**. That IFID, `ZCODE-12-860926-16AB`, is one of the four IFDB registers for Trinity, so this is a known build.
- `TRINITY2.D64` — disk name `SIDE 2`, standard `2A`, **no Z-header**: continuation data, so a Commodore release can span two disks.

WHAT I MEASURED AND WHAT I COULD NOT. The story is **not contiguous** from its header: summing `0x40..131032` straight off the image gives `E3C9` against the declared `16AB`. A naive CBM sector-chain read from track 3 sector 0 (2-byte link + 254 data per sector) also failed — the resulting bytes are not a coherent header. So the layout is neither flat nor a plain chain from that point, and it needs real work rather than a shell probe. **The checksum is the oracle**: a wrong layout yields a plausible story with a wrong checksum, exactly as it did for the Apple disk in SQ-0868, so verify rather than eyeball.

THE INTERPRETER-NUMBER QUESTION BECOMES REAL HERE, and it did not before. Byte `$1E` carries no meaning before Version 4 — SQ-0835 proved that empirically by tracing all thirty-two v3 stories in the ST corpus under interpreter 1 and 5 and getting byte-identical output — so the v3 Hitchhiker's cannot notice what we advertise. **Trinity is v4 and reads it.** ZMSD §11.1.3 gives the family two numbers, 8 for the C64 and 7 for the C128, and a `.d64` is a 1541 image usable by both, so the medium cannot name the machine — the same ambiguity ProDOS has across the IIe, IIc and IIgs.

Follow SQ-0857's precedent rather than reasoning afresh: it established that DECLINING is not neutral, because `None` falls through to interpreter 1 (or 6, the IBM PC, for v6 — not reachable here, as no Commodore v6 exists). Whether that matters for Trinity is measurable the way the ST was settled: trace it under the current default and under 8, and say whether anything moves. If a profile is warranted it is the full bundle again — number, default colours, and the C64's distinctive 16-colour palette — sourced from Infocom's own Commodore interpreter in `github.com/erkyrath/infocom-zcode-terps`, the tree that settled the Atari ST and the Apple.

SCHEDULING: needs a `FORMATS` row in `crates/blorb/src/medium.rs`. That file is free again as of SQ-0863 landing, but SQ-0868 (the raw Apple II DOS 3.3 disk) also wants it, so the two serialise.

--- note 2026-08-14T20:50:37Z ---

CORRECTION to my earlier note, found by SQ-0868 and worth having before you start.

I wrote that "the checksum is the oracle — a wrong layout yields a plausible story with a wrong checksum". **That is weaker than I claimed.** The Z-machine header checksum is a byte SUM over `0x40..len`, so it is **blind to ordering**. On the Apple disk it discriminated the four candidate sector orders only because the story ended mid-track and each order put different sectors in that tail. SQ-0868's lane found a sector swap that did NOT cross that track and which passed every test written at the time — right length, right checksum, right header.

So for a layout question — sector order, chain following, interleave — a checksum match is necessary but **not sufficient**. That lane settled it three ways, and you should expect to do the same:

1. **An order-sensitive fingerprint** (it used FNV-1a over all 426 sectors in order), which is what actually pins a permutation.
2. **Decoding a structure the layout would corrupt** — it read the dictionary at the header's own pointer and required a sane shape: 3 separators `,."`, 7-byte entries, 665 words. Wrong orders gave 100 or 204 separators and 148 or 210-byte entries. A structure with internal consistency is a far better oracle than a sum.
3. **Booting the game.**

This matters here because the Commodore layout is a *chain* rather than a flat run — following it wrongly can easily produce the right bytes in the wrong order, which is precisely the failure a sum will not see. `TRINITY1.D64`'s story is v4 r12 s860926 checksum `16AB`, declared length 131,032; a contiguous read from its header at 0x02a00 sums to `E3C9`, and my naive 2-byte-link chain read from track 3 sector 0 did not produce a coherent header at all. Both are dead ends, not near misses.

Also note SQ-0868 corrected my sector-order table by INVERTING it — I gave a mapping in the wrong direction, and "physical sector holding logical sector i" versus "logical sector at physical i" are different tables that both look plausible. State which direction yours is.
