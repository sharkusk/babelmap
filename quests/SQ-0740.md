--- note 2026-08-09T23:05:35Z ---

MEASURED 2026-08-09 on the real Zork Zero Amiga floppy, booted headless through the app's own loading path under the completed Amiga profile (SQ-0719).

WHAT THE USER SAW: "the story bg is light grey and the text white (poor contrast) while input text is black." SQ-0719's note listed this as knob 5 and flagged it as possibly an independent input-surface defect. IT IS NOT. The input line is the surface that is RIGHT.

THE MEASUREMENT. Boot Zork Zero from the .adf with interpreter number 4 and dump the v6 screen model's story window:

  IbmPc: Buffer at (44,40) 552x352  fg=None bg=None
  Amiga: Buffer at (88,80) 464x320  fg=Some(0x1000002) bg=Some(0x100000A)

i.e. under interpreter 4 Zork Zero picks its Amiga colour scheme and sets the story window to fg = Standard(2) BLACK on bg = Standard(10) LIGHT GREY. `game_input_style` (render/screen.rs:102) reads exactly that pair via `story_pair_packed`, so the input line renders black on light grey — precisely what the game asked for. The window layout also changes (the banner grows 40->80px, the story window inset doubles), confirming the game really is running its Amiga branch.

So the mismatch is that text ALREADY ON SCREEN is not black. Zork Zero paints its prose through the grid/window path, not the story Buffer (b.lines stayed 0 across two turns); those glyphs keep whatever colour they were painted with, and a Default foreground resolves to the interpreter default in $2D — the user's terminal white in their hand-set experiment, and white again under the finished profile since the Amiga's own DEF_FORE is 9.

THE RULE THIS VIOLATES, and it is in the standard. ZMSD 8.3, verbatim:

  "Note that a Version 6 interpreter going under the Amiga interpreter number
   must use the same pair of colours for all windows when running Infocom's
   games. If either is changed, then the interpreter must change the colour of
   all text on the screen to match. This simulates the Amiga hardware, which
   used two logical colours for text and switched palette to change their
   physical colour. This behaviour should not occur when running non-Infocom
   games, and modern games should never expect it. An interpreter that does not
   wish to handle this behaviour at all should avoid using the Amiga interpreter
   number when running Infocom's Version 6 games."

CONFIRMED IN INFOCOM'S OWN SOURCE (github.com/erkyrath/infocom-zcode-terps, amiga/yzip3.c:919-943). The comment above `set_color`:

  "Under YZIP, the various fore/back text colors are now supported using only
   the first two 'pens' (all other pens are used for graphics). Therefore, the 2
   text colors are now 'global', meaning they /can't/ be changed for a single
   word on the screen, or for a certain window. ... We allow text colors to be
   changed only in window 0, and ignore requests in other windows (except for
   the special case of bg = -1)."

and `set_fore`/`set_back` call `SetRGB4(&ZScreen->ViewPort, 1, ...)` / `(..., 0, ...)` — they move colour REGISTERS, so every pixel already drawn in pens 0/1 recolours retroactively. That is the hardware behaviour the standard is describing, and it is why the game feels free to set its scheme once and expect the whole screen to follow.

SCOPE / WHY IT WAS NOT FOLDED INTO SQ-0719. This is a seventh knob with real repaint semantics, not a colour constant:
- `set_colour` in v6 under interpreter 4 must apply to ALL windows, and be ignored outside window 0 (except bg = -1).
- Every glyph already on screen must adopt the new pair — a retroactive recolour with no Z-machine event behind it, which the screen model has no concept of today.
- The standard scopes it to "Infocom's games" only, so it needs an is-this-an-original-Infocom-story test (8.3.1.1 already contemplates exactly such a test for palette substitution).
- It touches crates/app/src/render/** and the zvm screen model, and needs the whole v6 corpus re-checked, since IbmPc must stay byte-identical.

The standard's own escape hatch is worth weighing first: "An interpreter that does not wish to handle this behaviour at all should avoid using the Amiga interpreter number." Doing this HALF way — Amiga number without the global pair — is what produces the contrast the user is looking at, so the honest choices are to implement the rule or to reconsider selecting the Amiga number for Infocom v6 titles.

--- note 2026-08-09T23:29:27Z ---

SCOPE IS BIGGER THAN "RECOLOUR THE TEXT". Field evidence 2026-08-09, user running Zork Zero and Arthur under the Amiga profile:

> "the un-available compass direction colors look a bit off (light grey inside with green outline, diagonal sw is purple in scullery, down box is white arrow with bright blue background) … map works, and room icon is shown there, but room icon is drawn with light green. Amiga Arther top banner background is not getting the correct colors applied, and pallet doesn't update when entering church."

Every one of those is a **picture** rendering with the wrong colours — compass direction indicators, the room icon, Arthur's banner — not text. So this quest is not "recolour on-screen text when the colour pair changes"; it is **colour-register semantics**, and on an Amiga the registers are the hardware palette that the ARTWORK is drawn through as well.

WHY THAT MATTERS ARCHITECTURALLY. Amiga graphics are palette-indexed: a picture is stored as colour indices and rendered through the current registers. Infocom's own `set_color` moves registers 0/1, so a colour change retroactively recolours everything painted in those pens — glyphs and art alike. babelmap renders pictures with **baked RGB** (PLTE bytes resolved at decode time), so a register change cannot reach them. That is the gap.

Note this interacts with, and is distinct from, the Blorb adaptive-palette mechanism we already implement (§11.3: an adaptive picture takes the palette of the last non-adaptive picture drawn — see `graphics.rs`, and SQ-0720's 38930-row oracle which confirms our implementation is faithful). The pictures the user names are exactly the APal set: Zork Zero declares 172 adaptive pictures (ids 9..485), Arthur declares its own. "Palette doesn't update when entering church" is `arthur_frame_follows_the_scene_palette`'s subject matter from the other side. **Establish first whether these are two mechanisms or one seen twice** — whether the Amiga profile should drive the Current Palette through the interpreter's registers rather than through the last non-adaptive picture, or whether both apply. Do not assume; the oracle says our §11.3 behaviour matches Infocom's own converter, so any change must keep that 38930-row test passing.

MEASUREMENT TO TAKE FIRST: for one named case — the "down" compass box, reported as a white arrow on bright blue — dump the picture's own palette, the Current Palette at draw time, and the interpreter's colour registers, then compare against what an Amiga would have shown. One fully-explained case beats four half-explained ones.

Not in scope here: drop caps and room icons failing to appear at all from a native archive — that is a separate quest, and the room icon renders correctly inside the in-game map, so the pictures decode fine.

--- note 2026-08-10T03:18:06Z ---

HANDED OVER from SQ-0743, which fixed the adaptive-palette resolution and explicitly did NOT take this on.

Measured: native colour registers 0 and 1 are reserved (0 = transparent). Our `DEFAULT_PALETTE` fills them with EGA's `[0,0,0]` and `[0,0,170]`, while Infocom's own converter put black in BOTH — so every native palette differs from the Blorb's at entry 1 by 170.

Invisible today, and the reason is measured rather than assumed: an index histogram over all 172 adaptive pictures' pixels is

    [58725, 0, 3941, 2750, 210, 1022, 24720, 3559, 0,0,0,0,0,0, 70, 0]

Index 1 is used by ZERO pixels. So nothing on screen currently reads that register.

Why it lands here and not on SQ-0743: registers 0 and 1 are exactly what Infocom's `set_color` moves. Their real runtime values are this quest's subject — the colour-register semantics — not the adaptive-palette question. SQ-0743's new test asserts entries 2..=15 agree with the Blorb and documents why the first two are excluded; whoever fixes the registers should expect to revisit that exclusion.

--- note 2026-08-12T20:04:41Z ---

RESOLVED on branch worktree-agent-a11cccf855070070e, commit c73c4be6 (`Confirm: SQ-0740`). Two findings, both measured on `Journey - The Quest Begins.adf` release 30 / serial 890322 through the shipped hybrid path.

**THE PEN WAS NEVER LOST.** Frame glyphs, rendered at 115x61, before this commit:

    IbmPc:  fg White              bg Black   (152 cells)
    Amiga:  fg Rgb(255, 255, 255) bg Black   (489 cells)

It arrived at the cells and was INVISIBLE. Journey asks for standard 9, which is white, and the host theme's story ink is white too — so the one channel that moved was the one nobody can see. The page could not move at all: a window that never declared a page has no pixel for a page pen to reach, and Journey declares none (correctly — that carve-out stops a black set_colour painting out Journey's illustration). The previous lane's "all four Amiga frames render to an identical distinct-cell-style count before and after" was the tell, read the other way. `packed_explicit` was NOT the problem; the transcript carve-out was NOT the problem; nothing gates the pen out.

**WHAT WAS ACTUALLY MISSING** was the machine's DEFAULT pair. §8.3.3 has an interpreter write its own page/ink into header $2C/$2D, babelmap wrote the Amiga's (11, 9) faithfully, and then painted the host terminal, because a v6 window at `ZColour::Default` resolves to the theme. On real hardware those bytes ARE the registers — every pixel no picture and no set_colour claimed is the background pen. So an Amiga reported as an Amiga and rendered as an IBM PC.

**BEHAVIOUR CORRECTION (part one).** Infocom's window-0 gate is now implemented: `amiga/yzip3.c` changes text colours "only in window 0, and ignore[s] requests in other windows (except for the special case of bg = -1)". Journey r30's single `set_colour(9, 2)` is on window 3, so it is dropped whole — which is why the user's walkthrough evidence ("light grey with white text") shows the Amiga DEFAULT pair rather than the black page that call asks for. Reasoning recorded in `set_amiga_colour_pair`'s doc comment and docs/features/interpreter.md, explicitly addressed to whoever is later tempted to restore the letter of §8.3.

ASSERTION FLIPPED: `one_pair_serves_every_window_of_an_amiga_release` (window 0 takes Standard(9) from the window-3 call) is now `a_colour_set_outside_window_0_never_lands_on_an_amiga` — every window stays Default. Zork Zero picks up the sharing rule instead (`a_colour_set_from_window_0_moves_the_pen_for_every_window`), since its call IS on window 0. The zvm `-1` unit test moved with it: a window-1 request now moves no ink pen either.

CHANGES: `zvm::screen::amiga_screen_pair` (the pair, read back out of the header); `session::v6_screen_model` publishes it as the v6 pane page; `AppState::v6_page_pair` carries it per frame; `render::screen::v6_host_pair` takes it as a layer above theme/OSC/fallback for the pixel paths and the new `v6_machine_page` does the same for the cell paths (chrome ring run style, transcript normal style).

AFTER: all 489 frame glyphs `Rgb(255,255,255)` on `Rgb(115,115,115)`, and 4683 of 7015 pane cells carry the page. IbmPc byte-for-byte unchanged.

Gate 4376/4376, 0 fixture skips, clippy clean. Falsified both halves (page reverted -> `got {("White", "Black"): 489}`, the user's symptom exactly; gate reverted -> `left: Standard(9), right: Default`).
