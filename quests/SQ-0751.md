--- note 2026-08-10T03:09:48Z ---

MEASURED by SQ-0748's agent, reported as found-not-fixed.

`finish_command_turn` marks the screen-clear boundary at the START of a turn, regardless of where within that turn the erase actually falls. A turn that prints and THEN erases would therefore keep its pre-erase text on screen — the clear is recorded as having happened before output that in fact preceded it.

Latent today: no game in the agent's sweep does that. Beyond Zork's prologue turn erases then prints, which top-anchors correctly; only the v6 `ScreenClear` element can split a turn at all. The sweep covered Zork I and Enchanter (v3), Bureaucracy and Trinity (v4), Border Zone (v5), Beyond Zork, LostPig (v8), Zork Zero / Arthur / Journey / Shogun (v6), Counterfeit Monkey and Kerkerkruip (Glulx).

Left alone deliberately rather than widened mid-lane. Whoever takes it needs a game that actually prints-then-erases in one turn, or a synthetic story that does — without one, any fix is unfalsifiable, and this codebase's rule is that a fix must be shown to fail with the original symptom when reverted.

Related: SQ-0748, which fixed the adjacent off-by-one (an anchor AT the end of the transcript read as "no anchor" instead of "cleared screen with nothing printed into it").

--- note 2026-08-12T18:18:06Z ---

FIXED 2026-08-12, commit 2e96d745, with the synthetic story this quest said any fix would need.

THE MECHANISM. The erase's position in the character stream is knowable only while the opcode executes, and only the sink knows how much it has taken — so the VM tells it rather than counting for it. `Output::screen_cleared` (new trait method, default no-op, beside `set_buffer_mode` which is the exact precedent) is called from `erase_window`'s non-v6 arm; the app's `CaptureSink` records its char count at that moment; `drain_turn` turns a NON-ZERO offset into a `ScreenClear` element on the same interleave channel the v6 boundaries already ride (SQ-0697/0755). One line in `crates/zvm/src/cpu/exec.rs`, which another lane owns — flagged rather than hidden.

ONE ADJACENT CHANGE, and it is the part worth reading. `interleave_story_elems` snapped every mark BACK to the start of its line. That is right for a picture, which anchors to the paragraph it was drawn beside, and wrong for a clear: it put the pre-erase text below the boundary, i.e. the very defect, one line's distance away. A `ScreenClear` now splits exactly where it was stamped. Justified from the standard rather than convenience — `erase_window` homes the cursor (ZMSD §8.7.3.2.1), so what the game prints next begins a new line by definition; the clear IS the break, not a position within a line. Every clear in the corpus falls on a line start anyway, where the two rules agree.

NOTHING IN THE CORPUS MOVES. An erase at offset 0 — every game in this quest's own sweep, all of which erase before they print — takes no interleave at all and stays on the flat path byte for byte, which is pinned by its own test. The full gate ran 4325/4325 with Beyond Zork, Journey, Shogun, Arthur and Zork Zero all in it.

TEST: `crates/app/tests/suites/print_then_erase_boundary.rs` (3 tests, `zmachine_screen` group). Two dozen bytes of hand-assembled v5 — `read` / `print_char 'A'` / `erase_window -1` / `print_char 'B'` / `read` — so it needs no fixture and never skips. It asserts the three-element shape out of the engine, the resulting `clear_anchor` position through `apply_transcript_elems` ("A" above the boundary in scrollback, only "B" on the cleared screen), and that the erase-first shape is untouched.

FALSIFIED by deleting the `self.out.screen_cleared()` call: "left: [] / right: [\"A\", \"<clear>\", \"B\"]", and the transcript test panics on `the turn recorded a screen-clear boundary`. Before the snapping change was made the same test failed with "left: [\"<clear>\", \"AB\"]", which is the snap-back putting the pre-erase text on the cleared screen — worth recording, because it is the defect reproduced from the other direction.
