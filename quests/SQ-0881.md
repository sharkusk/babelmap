--- note 2026-08-15T03:34:02Z ---

Item 4 (EG1/EG2 listed twice) is DONE and pushed in 22400160, together with SQ-0878 and SQ-0880. Items 1-3 remain.

Lead on item 2 (F-key emits a line feed at the cursor), not yet confirmed: a listed terminator goes through `main.rs`'s `plain` branch → `submit_line_with_terminator(&cmd, term)` → `turn::finish_command_turn(&cmd, …)`, and `cmd` is EMPTY when the player pressed a function key without typing anything. `finish_command_turn` then still runs its echo block: with `command_bar` on, or when the last transcript line is not story, it does `push_transcript_kind("> ")` — a bare prompt line with nothing after it, which is exactly a stray line feed at the cursor. The echo exists to show what the player typed; with nothing typed there is nothing to echo. Suspect the fix is to skip the echo when the line was terminated by a special key and the command is empty, but do NOT conflate that with a plain Enter on an empty line, which legitimately echoes (that submit goes through a different path).

Verify before fixing: ZMSD §7.1.1.1 on whether the interpreter echoes the terminating newline when the read ended on a terminating character other than 13 — read the standard, do not take the above on trust. Frotz's `read_line` is the cross-check.

Items 1 and 3 are v6 render work and untouched: (1) DOS Arthur's F2 map screen clearing to grey with rainbow side scrolls smells like a palette/erase-fill question on the MCGA path; (3) Mac Arthur with the monochrome `PIC.DATA` drawing upper-frame pixels into the side art suggests a picture-space or geometry mismatch — that archive declares a 480x300 picture space against the colour archive's 320x200, which `std_window` and `art_scale` both read.

--- note 2026-08-15T04:06:47Z ---

Item 2 (F-key line feed) is DONE and pushed in 4fd5614d. Confirmed by measurement, not reasoning: at an ordinary line prompt on arthur-r74-s890714.z6, `submit_line_with_terminator("", 134)` returns an empty transcript and one empty text element — Arthur draws its map into a v6 window and prints nothing — so every character of the stray line came from the host. Arthur's terminating-characters table is [129..=138, 253, 254]: the four arrows, F1-F6 and both mouse clicks. Fix is `turn::silent_terminator_turn`.

Items 1 and 3 remain. Groundwork done for item 3, and it narrows the search:

The Macintosh Arthur ships TWO archives with GENUINELY DIFFERENT geometry, which is the thing to hold on to. `MAC/ARTHUR FOLDER/CPIC.DATA` is a 320-wide picture space with plates at 292x196 (169 entries); `MAC/ARTHUR FOLDER/PIC.DATA` is a 480-wide space with plates at 436x294 (168 entries) — a higher-resolution redraw for the Mac's 512x342 B/W screen, not a two-colour copy of the same pixels. Note the entry counts differ by one, so picture IDs may not correspond between them.

What is already correct: `PictSource::native_std_window` reads the archive's own `picture_space_width`/`height`, and startup.rs's resolution order is named-archive → native → profile, so selecting `PIC.DATA` should yield a 480x300 standard window. `interpreter::MACINTOSH_STD_WINDOW` is (320, 200) but is only the fallback — worth re-reading anyway, because one constant cannot be right for a machine that shipped two picture spaces.

So suspect DOWNSTREAM geometry rather than the standard window. Best candidate for "side art looks like a piece of the upper frame": babelmap's own border/flank analysis (`v6_archive_border_sweep.rs`, `v6_frame_border_medium.rs`, `graphics::art_scale`) picks the side rule out of the archive itself. If any of that assumes a 320-wide space or a fixed plate size, a 480-wide archive yields a wrong source rect — which is exactly "a piece of the upper frame". The status/score bar symptom is consistent with the same scale error, since Arthur's bar is pixel-positioned runs the app maps to a native row.

Item 1 (DOS Arthur F2 map screen: background cleared to grey, side scrolls rainbow) is untouched. Rainbow scrolls on the MCGA path smell like a palette question — check whether the map screen's `erase_window` fill and the adaptive palette agree; `v6_adaptive_palette_arthur.rs` and `v6_hardware_palette.rs` are the existing pins.

--- note 2026-08-15T04:15:42Z ---

ITEM 3 ROOT CAUSE FOUND (not yet fixed). `PictSource::art_scale` in crates/app/src/graphics.rs:627 divides with INTEGER division:

    let unit_w = INFOCOM_V6_STD_WINDOW.0 * V6_ART_SCALE;   // 320 * 2 = 640
    let unit_h = INFOCOM_V6_STD_WINDOW.1 * V6_ART_SCALE;   // 200 * 2 = 400
    Some(((unit_w / space_w).max(1), (unit_h / space_h).max(1)))

Every archive in the corpus until now had a picture space that DIVIDES 640x400: 320-wide gives scale 2, 640-wide gives scale 1. The Macintosh monochrome archive is 480x300 — the first that does not — and 640/480 truncates to 1, 400/300 truncates to 1. So the art is not scaled at all and the unit screen becomes 480x304 rather than the fixed 640x400 presentation space `session.rs`'s own docs promise ("the unit screen is the same 640x400 for every rendition — it is babelmap's presentation space, not the card's"). The 304 is 300 rounded up to a whole 16-pixel row grid (19 x 16).

Verified with `cargo run -p app --example border_preview`, which prints the geometry outright:
  CPIC.DATA: picture space 320x200 at scale 2x2 -> art screen 640x400, native screen 640x400
  PIC.DATA:  picture space 480x300 at scale 1x1 -> art screen 480x300, native screen 480x304

The same preview shows both flanks COMPOSING correctly (colour 12 units wide over 368 art rows, mono 8 units wide over 275), so the flank extraction and the border recognition are sound — the reported corruption is downstream placement, which is consistent with the game being told a 480x304 screen while the surrounding layout expects 640x400. The status/score bar symptom fits the same cause: Arthur's bar is pixel-positioned runs mapped to a native row, and the row grid moved.

STATED AS A LEAD, NOT A PROOF: the truncation is certain and it is exactly the archive reported broken, but I have not rendered the full screen to confirm it produces the specific artefacts described. Do that first.

Fix is a real design decision, not a one-liner — `art_scale` returns (u32, u32) and cannot express 4/3. Either it gains a rational/float scale (and every consumer is checked), or the unit screen is allowed to be per-archive and the layout is made to follow it consistently. Check `INFOCOM_V6_STD_WINDOW` too: session.rs already carries a third copy of (320, 200), noted as a follow-up in an earlier sweep.
