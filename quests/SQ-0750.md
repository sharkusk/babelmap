--- note 2026-08-10T04:33:36Z ---

THE PRINCIPLE, from the user 2026-08-09: "difference seems to be how the frame is drawn (line border vs reverse space)".

That is the correct framing and it supplies the rule this quest was missing.

BOTH profiles draw the frame as TEXT. IbmPc prints reverse-video spaces; Amiga prints box-drawing glyphs. Neither is artwork. The current code rasterises every side band wholesale into a single `Art` strip — and that is lossy for characters, but the loss is INVISIBLE for reverse-video spaces, because a solid filled block survives being scaled by a non-integer factor and still looks like a solid filled block. A thin box-drawing stroke does not: it lands between pixels, changes weight, and antialiases against a font glyph drawn from the same character on the adjoining rows. That is precisely why nobody noticed until the Amiga profile arrived; IbmPc's particular input masked the defect for years.

SO THE RULE IS NOT "handle Amiga differently". It is: **a border the game printed as characters should be drawn as characters, whichever characters they are.** A band is art only when it is actually artwork. That is the measured "is this run text?" test this quest already called for — the user has now supplied the principle behind it.

Note the architectural direction this confirms. An audit of `crates/app/src` found exactly ONE branch on the profile variant in the whole app (`interpreter.rs:79`, mapping an interpreter number to a profile); every other Amiga/IbmPc mention in `render/`, `session.rs`, `graphics.rs`, `colors.rs`, `loop_tick.rs`, `reset.rs` and `startup.rs` is a comment. The profile is a data bundle, not a code path. Any fix here must keep it that way — no `if amiga` in the decomposition. The discriminator is what the band CONTAINS, not which profile is loaded.

Corpus reach is unchanged and still the reason for care: Zork Zero's and Shogun's flanks genuinely ARE artwork, and must keep being rasterised.

--- note 2026-08-10T06:10:36Z ---

FIFTH PASS — the reverse-space emitter is FOUND, FIXED and falsified. Commit d309aad4.

## WHAT EMITS IT

`flank_divider_extension` + `draw_chrome_band_stretched`, and it is unconditional — no profile branch anywhere, exactly as the audit predicted. The extension carries a flank's border down the reclaimed gap as a ONE-PIXEL-TALL slice of the chrome canvas, and `draw_chrome_band_stretched` RESIZES that crop to fill the band. So the crop's width against the band's width IS the extension's horizontal magnification. The crop was `(dnx0, mid, dnx1 - dnx0, 1)` — the border's INK alone.

- A border printed as a reverse-video SPACE inks its whole 8-pixel text cell, so ink width == cell width and the stretch comes out at the letterbox scale. IBM PC was right by accident.
- A `│` glyph's stroke is **ONE pixel** inside its 8-pixel cell. Magnification 16.00x against a 2.03x scale at the user's pane. Both vertical borders became SOLID FILLED BLOCKS two and one terminal columns wide, for their whole height.

That is the reverse-space idiom, generated by us, standing in the same line as the box glyphs the top, bottom and menu rows draw as crisp text. The user's exact words.

## THE MEASUREMENT THAT SETTLES 'IT IS OURS'

Journey/Amiga at the party menu, every run in the menu band: **style=00 on all of them** (the one exception is `Cast`, style=10 — bold, not reverse). Frame drawn with ┌ ─ ┐ │ └ ┘ ▌. The same frame under IBM PC: style=01 blank runs at x=121/249/377/505 on every row — reverse-video spaces. And the rendered Amiga CELL buffer contains zero REVERSED cells in either honour mode. So every reverse-video-looking thing in the Amiga frame came out of the band path, not the game and not the cell path.

Cell evidence at pane 163x61 (the user's), cell 8x18, halfblocks harness, BEFORE:
    cols 66,67 rows 3..48: fg == bg == Rgb(220,220,220)   (left border, 2 cells solid)
    col  162    rows 3..48: fg == bg == Rgb(220,220,220)   (right border, 1 cell solid)
AFTER: 24,24,24 / 39,39,39 / 46,46,46 — a stroke averaged into the panel ground, no filled cell anywhere.

## THE FIX

The crop is now the native columns the band's CELLS cover — `inv_x(dcell0)..inv_x(dcell1)`, the same inversion `flank_crop` already uses, widened (never narrowed) so the ink survives either rounding. Magnification becomes the letterbox scale, like every other pixel in the ring. No profile test added; the discriminator stays what the band CONTAINS.

## MECHANISM

Two producers, both classified by POSITION:
- `decompose_chrome_strips` (screen.rs): "Side bands (narrower than the pane) are never text — one Art strip."
- `flank_border_extension` + `draw_chrome_band_stretched`: each flank's inner/outer border column is a 1-native-row crop stretched into a 1-cell-wide, full-height band. THOSE are the four bitmaps — not the flank strip, which under a Menu plan is `menu_flank_panel`'s picture box.
- and `strip_has_art` asked `region_has_opaque(gfx, 0, y0, gfx.width(), h)` — the strip's ROWS across the whole canvas. So Journey's right flank (8 native px of border, no artwork) was drawn as a band because the LEFT flank's picture shares its rows.

## THE CONTENT TEST

In `flank_border_extension`, after the ink run is located: (1) the graphics-only canvas must be clear across the border's native columns over the story's whole row span; (2) one of the game's paint runs must cover those columns at the sampled row, and its character must actually ink (a non-reverse space cannot be what was found). Then it returns `BorderInk::Glyph(ch, style, fg, bg)` at the column `run_cell` maps the run to — one column wide, the same mapping the top rule uses for its `┌`. Otherwise `BorderInk::Band(crop)`, unchanged. `strip_has_art` now tests both axes.
