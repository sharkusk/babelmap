MEASURED (SQ-0747's second pass, Journey/Amiga, hybrid). User's report: "we are still using unmatched lines on the outside edges of the journey frame."

Tally of every character in the frame's outer column over its full row span, at 100x71 (same shape at 98x69, 110x51, 138x51):

    left col 0        count
    U+250C / U+2514   1 each   (corners)
    U+2502  '|'       6        (the menu-strip rows)
    U+2584  block     1        (band boundary leak)
    space             61       (the story rows)

One continuous vertical line, THREE producers. Box-drawing glyphs on the six menu-strip rows plus the corners; an uploaded IMAGE over the ~61 story rows, blank in the cell buffer because `decompose_chrome_strips` makes every side band a single `Art` strip wholesale — so the `|` the game printed on every story row is rasterised rather than drawn as text; and block elements leaking at the boundary between the two.

In a real terminal that is the user's font `|` sitting directly above a bitmap of the same character scaled by a non-integer factor. They cannot match in weight or antialiasing however precisely they are aligned, which is exactly what "unmatched lines" describes.

DISTINCT from SQ-0747's corner defect (the top border rounds its columns while `flank_divider_extension` floors and ceils the same native pixel). That is a POSITION error; this is a GLYPH/renderer-family error. Fixing either leaves the other.

WHY IT WAS LEFT: `flank_divider_extension` also serves Zork Zero's and Shogun's flanks, where the band genuinely IS artwork and rasterising it is right. A fix needs a measured "is this run text?" test applied per band, plus corpus proof across those titles, not a blanket change. Check IbmPc too — it draws these dividers as reverse-video spaces, so it may not exercise the same path.

--- note 2026-08-10T04:33:36Z ---

THE PRINCIPLE, from the user 2026-08-09: "difference seems to be how the frame is drawn (line border vs reverse space)".

That is the correct framing and it supplies the rule this quest was missing.

BOTH profiles draw the frame as TEXT. IbmPc prints reverse-video spaces; Amiga prints box-drawing glyphs. Neither is artwork. The current code rasterises every side band wholesale into a single `Art` strip — and that is lossy for characters, but the loss is INVISIBLE for reverse-video spaces, because a solid filled block survives being scaled by a non-integer factor and still looks like a solid filled block. A thin box-drawing stroke does not: it lands between pixels, changes weight, and antialiases against a font glyph drawn from the same character on the adjoining rows. That is precisely why nobody noticed until the Amiga profile arrived; IbmPc's particular input masked the defect for years.

SO THE RULE IS NOT "handle Amiga differently". It is: **a border the game printed as characters should be drawn as characters, whichever characters they are.** A band is art only when it is actually artwork. That is the measured "is this run text?" test this quest already called for — the user has now supplied the principle behind it.

Note the architectural direction this confirms. An audit of `crates/app/src` found exactly ONE branch on the profile variant in the whole app (`interpreter.rs:79`, mapping an interpreter number to a profile); every other Amiga/IbmPc mention in `render/`, `session.rs`, `graphics.rs`, `colors.rs`, `loop_tick.rs`, `reset.rs` and `startup.rs` is a comment. The profile is a data bundle, not a code path. Any fix here must keep it that way — no `if amiga` in the decomposition. The discriminator is what the band CONTAINS, not which profile is loaded.

Corpus reach is unchanged and still the reason for care: Zork Zero's and Shogun's flanks genuinely ARE artwork, and must keep being rasterised.

--- note 2026-08-10T05:46:09Z ---

USER 2026-08-10: "also, we are mixing the reverse space into the amiga line drawing."

So the Amiga frame contains BOTH kinds of border at once — reverse-video spaces (the IbmPc idiom) interleaved with the box-drawing glyphs the Amiga game actually prints. That is a third distinct failure on this edge, alongside the glyph-vs-raster split already measured here and SQ-0747's corner position error.

WHY IT MATTERS: under the Amiga profile the game prints box glyphs and nothing else. A reverse-video space appearing anywhere in that frame is therefore NOT the game's output — it is ours. Something in the chrome path is generating an IbmPc-style border rather than passing through what the game drew. Find what emits it. Candidates worth checking, in no particular order and none of them confirmed: `menu_flank_panel`'s fill, the divider extension replicating a native row, or a generic app-chrome border style applied regardless of profile.

This sharpens the rule already recorded on this quest. It is not only that a text border must be drawn as text rather than rasterised — it is that the characters drawn must be **the game's own**. We should never be choosing border characters at all.

Note the profile audit (2026-08-09): exactly ONE branch on the profile variant exists in the whole app (`interpreter.rs:79`), and the render path never asks which profile is loaded. So this cannot be an `if ibmpc` emitting reverse spaces — it is either unconditional, or driven by profile DATA reaching shared code. Establish which.
