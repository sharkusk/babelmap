## Not a bug — checked against the spec, and the premise was wrong

I filed this believing ENDMEM was runtime-mutable and that comparing all 128 IFhd bytes
against live memory could reject a legitimate save. The Glulx spec says otherwise, quoted
verbatim:

- "The contents of the game-file identifier ('IFhd' chunk) are simply the first 128 bytes
  of memory." — so live memory IS the correct comparison target, not the game file.
- `setmemsize`: "It must be greater than or equal to ENDMEM (the initial memory-size value
  which is stored in the header.)" — ENDMEM is the INITIAL size, and `@setmemsize` resizes
  the active map without touching the header field.
- "the section marked ROM never changes during execution; it is illegal to write there."

RAMSTART is at least 256, so all 128 bytes are ROM and constant for the life of the
process. There is no mutable field in that range, and
`restore_quetzal`'s byte-exact check is correct exactly as written. No code change.

Worth keeping as a note rather than deleting: it also strengthens SQ-0595's conclusion.
If every one of those 128 bytes is immutable ROM, then ANY difference is proof of a
different build — which is what made Counterfeit Monkey's embedded save provably foreign
rather than merely suspicious.

Lesson: this was filed from recollection about `@setmemsize` instead of from the spec,
which is the exact failure mode CLAUDE.md's "verify spec constants against authoritative
sources, never from memory" exists to prevent.
