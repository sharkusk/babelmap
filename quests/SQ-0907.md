## Verification fixture (user, 2026-08-17)

`treasures/Lost Treasures of Infocom, The_Disk4.adf` — the **Amiga Lurking Horror**, release 219 / serial 870912. It is one of only two Infocom titles that use sound effects at all (the other is Sherlock), so it is the right and possibly only fixture for this. `treasures/` is gitignored, so any test must skip vacuously.

## What the disk carries — MEASURED

50 files, 2 directories. Beside `Story.Data` (130,048 bytes) there is a **`Sound/` directory holding 14 effects**, each as a THREE-file set:

| effect | `.dat` bytes | | effect | `.dat` bytes |
|---|---|---|---|---|
| s3 | 49,766 | | s11 | 40,010 |
| s4 | 20,530 | | s12 | 44,330 |
| s6 | 46,010 | | s13 | 56,586 |
| s7 | 60,000 | | s15 | 51,610 |
| s8 | 7,738 | | s16 | 25,050 |
| s9 | 58,024 | | s17 | 39,258 |
| s10 | 33,290 | | s18 | 50,010 |

**The numbering is the Z-machine's own.** ZMSD §9 reserves effects 1 and 2 for the interpreter's bleeps, so a game's own sounds start at 3 — and these are `s3`…`s18` with **5 and 14 absent**, which is a gap in the game's use rather than a gap in the disk.

The three parts:

- **`sN.nam`** (20–25 bytes) is a manifest tying the set together: `01 00` then `"sN.dat"` NUL `NUL` `"sN.mid"` NUL, zero-padded. It names its own pair, so it is the index rather than a caption.
- **`sN.mid`** (11 bytes, every one) is a MIDI-shaped event pair — e.g. `00 09 90 54 40 FF 00 07 90 54 00`: `90 <note> 40` is Note-On channel 0 at velocity 64 and `90 <note> 00` is the matching Note-Off. The note varies per effect (0x43–0x5A). Read it as the PITCH the sample is played at, which is how Amiga sample playback is specified, rather than as music to synthesise.
- **`sN.dat`** is the sample. Its first big-endian u16 is the **file size minus 2** (0x8208 = 33,288 in a 33,290-byte file; 0x9C48 = 40,008 in 40,010; 0xDD08 = 56,584 in 56,586 — holds for every one), and the u16 at offset 8 is that value minus 8. So there is a short header before the audio, not a bare raw sample and not IFF (no `FORM`).

**Do not finish decoding this from the bytes alone.** The size relation is solid, the rest is inference. Check the format against an authoritative description before building on it — the Blorb spec documents how Infocom sound resources are wrapped, and ZMSD §9 governs `sound_effect` semantics (§9.2's volume, repeats and the routine-on-finish callback). This project's standing rule is that a spec constant read out of a file is a guess until a source confirms it.

## What already exists

- `crates/audio` has `play_sample(bytes, SoundFormat, z_volume, repeats)` and `play_tone`, so the playback end is built.
- `crates/blorb` already models `Snd ` resources and distinguishes AIFF (`FORM`) from Ogg, with an "undecoded" arm — which is where this format would land today.
- The ADF reader now reports **full paths** (SQ-0908), so `Sound/s10.dat` is addressable by name; before that fix every file on a disk was a bare basename and these fourteen `.dat` files could not have been told apart from anything else by path.

So the missing pieces are: identify the `.dat` container, map effect number → `Sound/sN.*` off the mounted medium, and route `sound_effect` to it. Note the search must be for a **directory** on the medium, not a Blorb chunk — this is the disk-native path, which is the whole point of the quest.

## Cross-check worth doing

Sherlock's Amiga release, if the corpus has it, should carry the same `Sound/` shape. If it does, the format is Infocom's rather than one game's, and that is worth knowing before writing a decoder.
