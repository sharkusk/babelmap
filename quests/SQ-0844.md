--- note 2026-08-14T00:48:26Z ---

THE DECIDING EVIDENCE — measured 2026-08-13. This is not a convenience feature.

`stories/Zork Zero — The Revenge of Megaboz (1989) (r393, Serial 890714) (360K) (Disk N).ima`, the original three-disk retail release:

```
Disk 1   vol "ZORK0 1"   ZORK0.CG1 244507  INSTALL.EXE  EZR.EXE  IZORK0.RUN     — NO story
Disk 2   vol "ZORK0 2"   ZORK0.ZIP 300032  ZORKZERO.EXE                          — NO art
Disk 3   vol "ZORK0 3"   ZORK0.EG1 333654                                        — NO story
```

**No single disk carries both a story and its artwork.** Open disk 2 alone and Zork Zero runs with no pictures at all — for a v6 graphical game that is broken, not merely reduced. Disks 1 and 3 have nothing to open.

Contrast, so the scope is honest: the **720K** release (disk 1 = `ZORK0.ZIP` + `ZORK0.MG1`) and **Lost Treasures I** (floppy5 = `ZORK0.ZIP` + `ZORK0.EG1`) ARE self-sufficient — there a set buys you a choice of rendition. The 360K retail release is where a set buys you the game.

## Derive the set from the DISKS, not from the filename

Ranked by strength, all verified against the user's corpus:

1. **Volume labels** — `ZORK0 1/2/3`, `Tresure.1`…`Tresure.5` (Lost Treasures I), `INFOCOM1`…`INFOCOM7` (Apple IIgs Lost Treasures). A shared stem plus a disk number. Covers three of the four sets.
2. **`DISK.ID`** — Lost Treasures II labels its volumes generically (`DISK 1`…`DISK 4`) but ships a 53-byte text file: `'The Lost Treasures of Infocom Vol II\r\n1.00\r\nDisk 2\r\n\x1a'` — set name, version, disk number. Covers the fourth.
3. **Filename adjacency** — ONLY as a hint about which images to peek at, so building one menu does not mount the user's whole library. `disk1.img` is far too generic to be identity, and an earlier note in SQ-0833 already records the volume-label-as-identity hypothesis being falsified once; do not repeat that with filenames.

Neither 1 nor 2 alone covers the corpus. Both together do.

## Two cases, and they want different behaviour

* **A COMPILATION set** (Lost Treasures I/II, the IIgs seven-disk set, the ST compilations) → present ONE combined menu of every game across the set. Vol I has 20 stories over five disks; the IIgs set has 28 over six, with disk 1 carrying no games at all.
* **A SINGLE-GAME set** (the 360K Zork Zero) → NO menu. There is one game; the set exists so the story on disk 2 can reach the art on disks 1 and 3. Offering a picker here would be noise.

Distinguishing them is part of the work: a set whose disks yield one story is the second case.

## Constraints inherited

* Cost: mounting five to nine images to build a menu is not free. The browser's info panel asks per story; do not make it sluggish. This is why filename adjacency earns its place as a search hint.
* Every fixture is in the gitignored `stories/`, so tests skip vacuously when absent.
* Content-first identification throughout — the ST compilations name every story `STORY.DAT`, and five of nine Amiga floppies call theirs `Story.data`.

## Sequencing

**Queued after the FAT12 lane (SQ-0833/0835), at the user's direction.** That lane deliberately does one image at a time and was told to report what a set model would need; read its report before designing. ProDOS (SQ-0836) is also queued behind FAT12 because both add a `DiskImage` variant and a `FORMATS` row to the same table.

--- note 2026-08-14T01:49:55Z ---

TRIGGER SPECIFIED by the user 2026-08-13: "for 844 i want the set to scan the entire collections (eg diskx.img, etc) when disk1.img is passed in (and equivalent files)."

So opening **any one member** of a set pulls in the rest. Pass `disk1.img` and the whole Lost Treasures II collection is available — not just disk 1's four games. Same for `floppy3.ima`, `Infocom Compilation 5 (19xx)(-).st`, `…(Disk 2 of 7).2mg`, and the 360K Zork Zero disks.

**This refines, and does not contradict, the identity ranking in the note above.** Filename adjacency is how we decide WHICH IMAGES TO PEEK AT — that is its job, and it is why it earns a place at all: mounting the user's whole `stories/` directory to answer "what else is in this set?" would be unacceptable when the browser's info panel asks per story. What the filenames must NOT do is decide membership on their own. The sequence is:

1. **Adjacency proposes.** From the opened image's name, derive sibling candidates in the same directory — `disk1.img` → `disk2.img`…; `floppy3.ima` → `floppy1..5`; `…(Disk 2 of 7).2mg` → the other six; `Infocom Compilation 5` → 1..9. Note the corpus uses at least four naming shapes, including a parenthesised `(Disk N of 7)` inside a long title, so this is prefix-and-index matching rather than a single regex.
2. **Content confirms.** Mount each candidate and check it actually belongs — `DISK.ID` where present (Lost Treasures II), volume label stem where present (`ZORK0 1/2/3`, `Tresure 1`, `INFOCOM1`), and format agreement. A neighbour that merely shares a prefix but is a different set, or not a disk at all, is dropped.
3. **Neither signal alone covers the corpus** — Vol I has volume labels and no `DISK.ID`; Vol II has `DISK.ID` and generic labels; **the FAT12 lane found NO ST compilation carries a volume label at all**, while every DOS disk does. Plan for a candidate that confirms by format and index alone.

**Corrections from the FAT12 lane, which supersede the survey above:** Vol I's labels are `Tresure 1` with a SPACE, not `Tresure.1`. And the Zork Zero 360K release is now dumped — disk 1 is installer + `ZORK0.CG1`, disk 2 is `ZORK0.ZIP` + `ZORKZERO.EXE`, disk 3 is `ZORK0.EG1` alone.

**Scope reminder:** that lane also confirmed the story-here/art-there case affects **exactly one title — Zork Zero**, and only its 360K three-disk release. Every other set is a convenience (a combined menu, a choice of rendition). Do not let the join machinery grow beyond what those two jobs need.

--- note 2026-08-14T04:00:09Z ---

Real case from the ST corpus, found while the user was checking Trinity: the same BUILD appears on more than one disk of one collection. `Infocom Compilation 5 (19xx)(-).st` stores its stories as flat files (`TRINITY.T`) and `Infocom Compilation 8 (19xx)(-).st` stores them in per-game directories (`TRINITY/STORY.DAT`), and both carry Trinity v4 r11 s860509 checksum FAAE — one identical IFID, ZCODE-11-860509-FAAE. Lurking Horror (r203/870506) and Moonmist (r4/860918) are duplicated the same way. So the set model needs to DEDUPE by IFID across the volumes of a collection, not merely concatenate their menus, or the merged list shows the same game two or three times. Note this also interacts with SQ-0850: both copies key to the same save directory, which is correct and desirable — the dedupe is a presentation question, not a storage one.

Separately measured while here: IFDB has no record of the ST Trinity build at all (it holds ZCODE-12-860926, ZCODE-12-860926-16AB, ZCODE-15-870628 and ZCODE-1-220319-07F1), so a not-found from the metadata fetch is correct for these presses rather than a defect. The bundled `known_titles.tsv` does carry ZCODE-11-860509, so the title still resolves.

--- note 2026-08-14T04:25:17Z ---

Found by SQ-0850's lane and left for this quest: **the TUI can only open ONE story per image.** `hints::read_story_file` takes `MountedDisk::story()` — the format's own tiebreak — and there is no equivalent of `zvm-cli`'s `--story` selector. So babelmap cannot reach the other five games on a compilation at all, even though as of SQ-0850 it keys each of them to the correct save directory when it does reach them.

That makes this quest bigger than "merge several disks into one menu": before a set can be presented, a SINGLE image with several stories has to be selectable. Sequence it that way — per-image story selection first, then the multi-disk set on top — rather than building the set model against a loader that can only ever yield one story.

`zvm-cli --story N` already exists and works (SQ-0850 smoke-tested it picking Hitchhiker's and Planetfall off one image, each landing in its own save directory), so the CLI is the reference for what the TUI needs to grow.
