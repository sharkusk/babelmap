--- note 2026-08-11T15:24:11Z ---

EVIDENCE (SQ-0764 oracle, Journey ADF r30, hybrid, 117x64, 8x18px cells, kitty negotiated):

WHAT BABELMAP EMITS, correctly, at paint time — 33 runs, each `CUP row;1`, `│`, `ESC[38;2;166;107;21m`, then 115 placeholder cells. Only the LEAD cell of each row carries the diacritic triple, e.g. `['0x30d','0x305','0x1dc0']` = row 1, col 0, high-byte index 164 (0x1DC0). The other 114 cells are BARE U+10EEEE, relying on the protocol's continuation rule.
   off=2831193 len=115 lead=['0x30d','0x305','0x1dc0'] cup=('17','1')
   off=2831393 len=115 lead=['0x30e','0x305','0x1dc0'] cup=('18','1')

WHAT LATER FRAMES DO: they overpaint cols 1..46 (the #222222 text box and the 320x378 art) and cols 114..115 (the 16x900 sidebar strip), which DESTROYS the diacritic-bearing lead cell of every row and leaves an orphaned 67-column middle slice (cols 47..113, rows 15..46, 2109 cells).

CONSEQUENCE: with the lead cell gone, the remaining bare cells carry only the fg colour's low 24 bits, so the id truncates from 2762369813 to 10906389 and `image_by_id` misses. The oracle reports, for all 33 surviving runs:
  run: image_id=10906389 placement_id=0 frag(row=0,col=0) w=67 h=1 at screen Some((15,47)) -> NO IMAGE with id 10906389 in storage
`resolve_placements` therefore returns ZERO placements for that image: a real terminal draws nothing in those 2109 cells.

THE RULE THIS BREAKS: repainting a region that shares rows with an existing virtual placement must either re-emit the lead cell (row/col/high-byte diacritics) or clear the whole placement. Clipping its left edge silently invalidates the entire remainder of the row.

SECOND FINDING, in our own harness: `decode.rs` attributes cells to an image by low-24-bit fg colour alone and never models the diacritic continuation rule, so it reports a live 67x32 placement where a real terminal has a dangling id. Any existing assertion of the form "the art covers rows 15..46 cols 47..113" is currently pinning something Ghostty does not do.

NOT YET CONFIRMED, and it must be before this is written up as user-visible: (1) whether the art is actually invisible on screen in Ghostty — the oracle is a faithful port, not Ghostty itself, and a five-second eyeball settles it; (2) whether the art was correctly visible in an EARLIER frame and then vanished, or was never right — the capture's flush boundaries make this easy to replay and it is the obvious next question. Related but distinct from SQ-0763 (a placement OUTLIVING its frame); this is a live placement being KILLED by a later partial overpaint.

--- note 2026-08-11T15:34:49Z ---

USER DECISION 2026-08-11: fix regardless of whether the damage is visible in today's Ghostty — "a new version of ghostty (or future terminal) may be sensitive to the issue." Correct framing: we rely on continuation state that we then destroy, and any conforming terminal is entitled to drop that art. So the eyeball check is no longer a gate on fixing; it is only evidence about current impact.

EMITTER LOCATED (read-only recon by the coordinator, not yet acted on).

`crates/app/src/render/graphics.rs:1368` `kitty_place_rows`:
```rust
let [_, id_r, id_g, id_b] = id.to_be_bytes();   // TOP BYTE DISCARDED
write!(symbol, "\x1b[s\x1b[38;2;{id_r};{id_g};{id_b}m\u{10EEEE}{}{}{}",
       KITTY_DIACRITICS[y as usize], KITTY_DIACRITICS[0], KITTY_DIACRITICS[0]);
//     row = y                       col = 0              id_extra = 0
for _ in 1..area.width { symbol.push('\u{10EEEE}'); }   // every other cell BARE
```
Two defects visible in those six lines:
  (a) the lead cell is the only self-describing cell in the row — the rest rely on continuation, which is what a later partial overpaint destroys (the SQ-0772 mechanism);
  (b) the placeholder always declares id high byte = 0 (`KITTY_DIACRITICS[0]` as id_extra) while the transmit sends the FULL 32-bit `i={id}` (`kitty_transmit_virtual`, same file line 1331). Those agree only while every id this path allocates is genuinely 24-bit. `graphics.rs:636` comments "top byte stays 0 so the id_extra diacritic is 0", so the invariant is known but is nowhere enforced — nothing stops a future id allocation from breaking it silently. Note also KITTY_DIACRITICS holds only the first 140 of kitty's 297 entries, so this path cannot express a high byte above 139 even if it wanted to.

THERE IS A SECOND EMITTER. The orphaned image in the Journey capture is id 2762369813 (high byte 164) and its lead cell carried diacritic U+1DC0 = index 164 — which `kitty_place_rows` CANNOT emit (its table stops at index 139 and it always passes index 0). So the main art is placed by a different encoder, almost certainly `ratatui-image`'s kitty backend (dep `ratatui-image` 11.0.6). CONFIRM THIS BEFORE FIXING — the remedy differs by owner:
  - our own emitter: make every placeholder cell self-describing (explicit row AND column diacritics per cell, plus the real id high byte), so no cell depends on a neighbour surviving. Local change, costs ~6 bytes/cell of stream; weigh against SQ-0514 (Zork0 hybrid re-encode/retransmit cost).
  - ratatui-image's placements: we do not control that encoding, so the fix is app-level — never partially overpaint a live placement; delete it (`a=d`) and re-place instead. That lands in the same territory as SQ-0753 (band uploads never deleted) and SQ-0763 (a placement outliving its frame), and the three may share one fix.

Do not guess between those two; measure which encoder owns each placement first.

--- note 2026-08-11T15:36:37Z ---

SECOND EMITTER CONFIRMED (measured, not inferred). `ratatui-image` 11.0.6, `src/protocol/kitty.rs`:
```rust
let row_diacritics: String = std::iter::repeat_n('\u{10EEEE}', width_usize - 1).collect();   // :157
...
write!(symbol, "\x1b[s{id_color}\u{10EEEE}{}{}{}", diacritic(row_y), diacritic(0), diacritic(*id_extra));  // :192-195
// Use inherited diacritic values
symbol.push_str(&row_diacritics);                                                            // :200-201
```
Same shape as our `kitty_place_rows`: full triple on the LEAD cell only, bare U+10EEEE for the rest, with an explicit "use inherited diacritic values" comment. Differences from ours: it carries kitty's full 297-entry DIACRITICS table (`:272`) and encodes the id's high byte as `id_extra` — which is exactly why the orphaned Journey image carried U+1DC0 (index 164), a diacritic our own 140-entry emitter cannot express.

CONSEQUENCE FOR THE FIX: both encoders share the weakness, so making OUR emitter self-describing fixes nothing for the main art (ratatui-image places it). The unifying remedy is app-level: never partially overpaint a live virtual placement — delete it (`a=d`) and re-place, or repaint the full placement rect. That is the same rule SQ-0753 (band uploads never deleted) and SQ-0763 (a placement outliving the frame that made it) are circling from different directions; treat the three as one fix and check whether closing this closes those.

Our emitter's high-byte truncation (note above, defect (b)) is still worth fixing on its own — it is a live-but-currently-harmless invariant violation, not covered by the app-level rule.
