--- note 2026-08-11T15:24:11Z ---

EVIDENCE (SQ-0764 oracle, Journey ADF r30, hybrid, 117x64, 8x18px cells, kitty negotiated):

WHAT BABELMAP EMITS, correctly, at paint time — 33 runs, each `CUP row;1`, `│`, `ESC[38;2;166;107;21m`, then 115 placeholder cells. Only the LEAD cell of each row carries the diacritic triple, e.g. `['0x30d','0x305','0x1dc0']` = row 1, col 0, high-byte index 164 (0x1DC0). The other 114 cells are BARE U+10EEEE, relying on the protocol's continuation rule.
   off=2831193 len=115 lead=['0x30d','0x305','0x1dc0'] cup=('17','1')
   off=2831393 len=115 lead=['0x30e','0x305','0x1dc0'] cup=('18','1')

WHAT LATER FRAMES DO: they overpaint cols 1..46 (the #222222 text box and the 320x378 art) and cols 114..115 (the 16x900 sidebar strip), which DESTROYS the diacritic-bearing lead cell of every row and leaves an orphaned 67-column middle slice (cols 47..113, rows 15..46, 2109 cells).

CONSEQUENCE: with the lead cell gone, the remaining bare cells carry only the fg colour's low 24 bits, so the id truncates from 2762369813 to 10906389 and `image_by_id` misses. The oracle reports, for all 33 surviving runs:
  run: image_id=10906389 placement_id=0 frag(row=0,col=0) w=67 h=1 at screen Some((15,47)) -> NO IMAGE with id 10906389 in storage
`resolve_placements` therefore returns ZERO placements for that image: a real terminal draws nothing in those 2109 cells.

THE RULE THIS BREAKS: repainting a region that shares rows with an existing virtual placement must either re-emit the lead cell (row/col/high-byte diacritics) or clear the whole placement. Clipping its left edge silently invalidates the entire remainder of the row.

SECOND FINDING, in our own harness: `decode.rs` attributes cells to an image by low-24-bit fg colour alone and never models the diacritic continuation rule, so it reports a live 67x32 placement where a real terminal has a dangling id. Any existing assertion of the form "the art covers rows 15..46 cols 47..113" is currently pinning something Ghostty does not do.

NOT YET CONFIRMED, and it must be before this is written up as user-visible: (1) whether the art is actually invisible on screen in Ghostty — the oracle is a faithful port, not Ghostty itself, and a five-second eyeball settles it; (2) whether the art was correctly visible in an EARLIER frame and then vanished, or was never right — the capture's flush boundaries make this easy to replay and it is the obvious next question. Related but distinct from SQ-0763 (a placement OUTLIVING its frame); this is a live placement being KILLED by a later partial overpaint.
