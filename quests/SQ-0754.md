--- note 2026-08-10T04:25:19Z ---

MEASURED by SQ-0742's flank work, reported as found-not-fixed because it needs a design decision rather than a measurement.

Journey/Amiga, pane 138x68. `draw_chrome_text_strip` packs 7 game rows one per terminal row into a 10-row band, so the frame's bottom border lands 3 rows above its true position. Rows 65..67 of the menu band are painted by nothing.

WHY THE OBVIOUS FIX DOES NOT WORK: handing the leftover rows to the ring fails, because `clear_text_rows` blanks each text run's native rows across the FULL canvas width, so art there is transparent by construction. That is also why the `menu:art` band at row 68 is an entirely empty 138x1 upload.

THE DECISION NEEDED: where should a packed block anchor inside a bottom-anchored band — top, bottom, or distributed? Each choice moves the frame's bottom border somewhere different, and the right answer depends on what the frame is supposed to look like rather than on what any measurement says. This wants the user's eye.

Related and deliberately separate: SQ-0747 item C (row 2's blank sliver strip — the "gap at the top"), SQ-0750 (the glyph/raster split on rows 58..64).

--- note 2026-08-10T17:27:24Z ---

DECIDED by the user 2026-08-10: **"Top anchor but grow the box with blank lines at the end."**

So the content keeps its current placement — 7 game rows, one per terminal row, contiguous, starting at the band's first row, no stretching and no gaps between them. What changes is the BOX: its bottom border moves down to the band's last row, and the rows between the last content row and that border become blank *interior* rows with the side borders continuing through them.

    ┌─ The Party ─────┐
    │ Proceed  ▌...   │
    │ ...             │
    │                 │   <- new: blank interior, side borders continue
    │                 │
    └─────────────────┘   <- bottom border on the band's LAST row

This keeps the top rule flush with the story area (the thing top-anchoring already gets right) and puts the bottom border where the frame actually ends, without the stretched interior that proportional placement would produce.

IMPLEMENTATION NOTE — and it resolves an apparent conflict with [[SQ-0750]]. That quest's rule is that the characters drawn must be the game's OWN, and that we should never be choosing border characters. Growing the box means painting border glyphs on rows the game did not draw. The resolution: **replicate the game's own glyphs, do not synthesise new ones** — take the side-border character from the rows the game did draw and repeat it down the blank interior, and take the bottom-border and corner characters from the game's own bottom row before moving it. That is extension by replication, exactly what `flank_divider_extension` already does for the side borders, so the precedent is established and consistent. If a frame is encountered where the glyph to replicate cannot be identified, leave the rows blank rather than inventing a character.

CONTEXT FROM THE ORIGINAL MEASUREMENT (still current): `draw_chrome_text_strip` packs 7 game rows into a 10-row band, so at 138x68 rows 65..67 are painted by nothing. Handing the leftover to the ring does NOT work — `clear_text_rows` blanks each text run's native rows across the full canvas width, so art there is transparent by construction, which is also why the `menu:art` band at the bottom row is an entirely empty upload.

Still open and NOT part of this: SQ-0747 item C (row 2's blank sliver, the gap at the top) and SQ-0750's glyph-vs-raster split.

--- note 2026-08-12T16:39:23Z ---

RESOLVED BY SQ-0765, not by the box-growing decided on 2026-08-10. Confirmed as a symptom, exactly as SQ-0765's note anticipated.

With the menu band sized from its OWN game rows and bottom-anchored (SQ-0765's fix, commit 4e05b3e0), the leftover the decision was about is zero at every pane shape. There are no blank interior rows to grow the box through, and the game's own bottom-border row — release 30's `└────┘`, release 83's "Game" row — lands on the pane's LAST row by construction. So nothing here replicates or synthesises a border glyph, and SQ-0750's rule is untouched: every character drawn is one the game printed.

The empty `menu:art` upload noted in the original measurement is gone too — it was the run-less leftover row at the band's foot, and there is no leftover row now.

MEASURED, release 30 (`Journey - The Quest Begins.adf`) at 138x68, before: `menu:text(518 runs)(0, 57, 138, 10)` + `menu:art(0, 67, 138, 1)`, and terminal row 67 written by nothing at all. After: a single `menu:text(518 runs)(0, 61, 138, 7)`, with `└` and `┘` on row 67.

Left at `confirm` rather than `done` because the anchor was the user's design call and only their eye on a real terminal settles whether the frame now reads right.
