## The gap this exposes, which is worth more than the bug

`zvm::screen::set_palette` is **process-global**. The local gate is `cargo nextest run`, which gives every test its **own process**, so no test can observe another's global state and a race on it is *structurally invisible*. CI runs `cargo test`, which runs a binary's tests in **one process on many threads**. Both harnesses are right about their own model; a process-global needs a lock to be correct under either. CLAUDE.md documents the hazard in one direction only ("a test that depends on state left behind by another test in the same binary will fail under nextest") — this is the other direction, and it is the one CI catches and the gate cannot.

MEASURED: four consecutive red runs on main (31996890039, 32044356277, 32046201580, 32050880485) across ubuntu, macos and windows, all on `machines::tests::printing_the_table_leaves_the_active_palette_where_it_found_it`, with `screen::colour_tests::style_wrap_emits_colour_sgr` and `screen::page_bg_tests::zcolour_rgb_standard_and_true` joining it depending on scheduling. Reproduces locally with `cargo test -p zvm-cli` and never under nextest. **Nothing in `crates/zvm` or `crates/zvm-cli` had changed since the last green run** — it is a pre-existing race that thread scheduling had been hiding.

The tell is the colour: `#737373` where §8.3.1's medium grey is `#8C8C8C`. `#737373` is the Amiga's value for the same number, read while `machines::swatch` had the global palette borrowed.

## Fixed here

`crates/zvm-cli` — a `PALETTE` mutex held by every test that WRITES the palette (which is every test calling `table()` or `swatch()`, not only the one calling `set_palette` outright — `swatch` borrows and restores it per row) and by the two `screen.rs` cases that READ a palette-resolved RGB.

Note `swatch`'s own doc argued it was safe because "nothing else is running: `--machines` prints and exits before a story is read". True of the binary, false of the test harness — a good example of a safety argument that is sound about production and silent about tests.

## Still unguarded — the actual quest

These call `set_palette` with no lock reference in the file. App suites are modules inside group binaries, so they share a process with every other suite in their group and can race the same way:

- `crates/zvm/tests/amiga_palette.rs` (4 calls, 0 guards)
- `crates/app/tests/suites/v6_hardware_palette.rs`
- `crates/app/tests/suites/v6_macintosh_profile.rs`
- `crates/app/tests/suites/v6_mac_input_echo.rs`

They are not failing today, which means only that their binary-mates do not currently read a palette-dependent value at the wrong moment — not that they are safe. Add the same guard, and check whether any *reader* in those binaries needs it too; a lock only on writers still races a reader.

## Worth considering instead

The durable fix is to stop resolving colours through a global. `swatch(n, palette)` already takes the palette it wants and then has to launder it through `set_palette` because `standard_true_colour(n)` reads the global. A `standard_true_colour_in(n, palette)` would make the borrow-and-restore dance unnecessary and the race impossible rather than merely locked. That is a `zvm` API change and larger than this quest, but it is the real answer.
