Measured surface, 2026-08-14, from each binary's own --help / arg table:

babelmap   --config --data-dir --debug --image-protocol --interpreter-number --no-accel --no-images --no-sound --pictures --trace --user-dir
zvm-cli    --data-dir --interpreter --lower-only --no-aux --no-game-colours --no-more --no-page --no-sound --no-status --no-timed-input --plain --screen-reader --show-status --story --story-only --volume

scott-cli  --max-turns --no-more --no-page --plain --screen-reader --seed

THE DECIDED CHANGE: babelmap's --interpreter-number becomes --interpreter, matching zvm-cli. Pre-release, so rename outright — no deprecated alias, per the project's no-back-compat rule. The old spelling appears throughout doc comments in config.rs and in docs/, so it needs a sweep, not just an arg-table edit.

ALREADY CONSISTENT, leave alone: --data-dir, --no-sound, --no-accel, --no-more, --no-page, --plain, --screen-reader, --show-status, --story-only.

THE REAL GAP FOUND WHILE MEASURING: --no-game-colours exists on zvm-cli and gvm-cli but NOT on babelmap, even though babelmap owns the honor_game_colours config and a /set-game-colours command. Every render suite in this project pins both colour modes precisely because that switch matters; not being able to launch the TUI into the declining mode is an asymmetry worth closing. Treat as a question for the user rather than an automatic addition.

NOT divergences, do not "fix": --lower-only, --no-aux, --no-status, --no-timed-input, --volume, --story, --max-turns, --seed are engine- or CLI-specific; --config, --user-dir, --image-protocol, --no-images, --pictures, --debug, --trace are TUI-specific. The test is whether two binaries express the SAME concept under different names, not whether one has a flag the other lacks.

DECIDED by the user: add --no-game-colours to babelmap too, matching zvm-cli and gvm-cli.

Shape it on the precedent already in this codebase rather than inventing one. `--interpreter-number` is a ONE-RUN override that must not be persisted — config.rs carries both the rule and its regression tests ("a one-run --interpreter-number must not be persisted; file now: {back}", and SQ-0646's "sticky for the run, not for the user"). `--no-game-colours` is the same kind of switch and needs the same treatment: it overrides the config's honor_game_colours for that launch only, never writes it back, and must not defeat a later /set-game-colours in the same session any differently than the config value would.

Three things to get right, each with existing precedent to follow:
- Precedence against the per-game sidecar (<game_dir>/config.toml) and the launch-options dialog — config.rs:1587 already documents how --interpreter-number, a launch-options choice and a game's sidecar resolve against each other; --no-game-colours must slot into that same order rather than a new one.
- The live/config distinction the render path depends on: several sites gate on `state.config.honor_game_colours` as the LIVE value precisely so a mid-game /set-game-colours off is honoured (see the flood gate in render/screen.rs and the SQ-0846 startup rule). A launch flag must set that value, not a separate parallel one.
- Startup already forces the flag off in one case — a monochrome archive sets honor_game_colours = false and pins it for the run (startup.rs, SQ-0846). An explicit --no-game-colours must compose with that rather than fight it.

Test both modes, as the project's colour-render convention requires.
