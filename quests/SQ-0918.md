## Done — the listing, the number-pick, and the overwrite guard the first pass missed

Commits 13527813 (listing + number), 97dd3cf0 (overwrite), fcf7b64f (docs). Gate 0, clippy clean, 5632/5632.

### What shipped

`cli_host::existing_saves` is the exact inverse of `resolve_save_input` — one turns `cellar` into `<game_dir>/cellar.qzl`, the other turns the directory back into the names you would type — so the two cannot drift, and a test round-trips every name it lists. Sorted case-insensitively, because a list that reorders itself between turns is worse than no list. Nothing prints before the first save, so a fresh game looks exactly as it always did.

At the **restore** prompt a number picks from the list; anything else is a filename, which keeps a save genuinely called `2` reachable. At the **save** prompt a number is NOT accepted — there it would mean "overwrite that one" — and that asymmetry is the thing most likely to be quietly tidied away later, so it is what the integration test falsifies against (route `pick_save` through the save arm and the case fails with `a save called 1 was written: ["cellar.qzl"]`).

### The overwrite guard, which the user had to ask for

`fs::write` is unconditional, so a repeated save name silently destroyed the earlier save in **both** CLIs. That is precisely the defect SQ-0648 fixed in the TUI — and the previous commit cited SQ-0648 as the reason a number is refused at the save prompt while the plain-name path beside it clobbered without a word. Invoking a principle to justify one thing and leaving the actual instance unfixed is the mistake worth remembering here.

Now it warns, naming the EXISTING save rather than echoing what was typed (the two can differ, and what the player needs to know is what they are about to lose — the TUI's dialog does the same). Anything but an explicit `y` is a no, including a bare Enter and EOF, so the destructive branch is never the one reached by not answering; that matches the TUI's Cancel-focused dialog. A refusal is a cancel, which is the path an empty filename already takes.

The predicate and the message are in `cli-host`; the reading is not, because the hosts read input three different ways — cooked stdin, a raw-mode editor, a Glk line request — and `storage.rs` has no business picking one.

### Dropped on the user's challenge

A `/saves` host command was proposed and rejected, correctly. `/status` and `/menu` exist because that information scrolls away with no other route back; a save list has an obvious one — type `restore`, read, press Enter. The only thing a command would have bought is not telling the game a save failed in order to peek, which is cosmetic. It was proposed by pattern-matching to the existing host commands rather than by checking it earned its place.

### Not covered

`scott-cli`, which has no save of any kind — SQ-0919. And host snapshots, which are a separate inventory from the game's own `@save`/`@restore`.
