--- note 2026-08-09T21:27:52Z ---

POLICY DECIDED by the user 2026-08-09: "the 3-tier approach seems good". This is the spec for this quest — implement it, do not re-open it.

**Three tiers, in decreasing confidence. Never guess a pairing.**

1. **Blorb** — zero config, as today. The container validates its own contents; a `.blb`/`.blorb` beside the story, or the story itself being a Blorb. Unchanged.
2. **ADF disk image** — zero config. The story and its picture archive live in the same image and are therefore guaranteed to belong together. This is SQ-0719's job; this quest consumes what it mounts.
3. **Explicit config key** — the user names a native archive and thereby ASSERTS the pairing. Use the existing per-game sidecar `<game_dir>/config.toml` (bare lines, absent key = inherit, never templated — see CLAUDE.md), e.g. `pictures = "FMVPOKER.EG1"`. This is the tier that serves fmvpoker, whose art is Zork Zero's picture file renamed and which will never appear on any disk image.

**EXPLICITLY REJECTED: stem-based auto-discovery** (looking for `<story-stem>.pic` or similar beside the story). Reason, measured rather than assumed: every Infocom Amiga release names its picture archive `Pic.data` — Zork Zero and Arthur both do — so any name-based rule requires the user to rename, and a wrong rename is undetectable. The format offers almost nothing to validate a pairing with: the header carries a part number and a picture count, no release number and no serial. The failure mode is therefore "plausible but wrong art", e.g. Arthur's plates drawn into Zork Zero. Do not reintroduce this to close the DOS-art gap below.

**KNOWN GAP, recorded so nobody rediscovers it and quietly re-adds tier-0.** The Blorbs in circulation are already Amiga conversions — SQ-0713's decoder confirms this at 383/388 byte-exact against `Zork0.blb`. So tier 2 mostly yields art we already have. The genuinely DIFFERENT art is DOS EGA/MCGA, which circulates as loose `.EG1`/`.MG1`/`.CG1` files or FAT12 floppy images. Under this policy that art is reachable only through tier 3 today; reaching it with zero config would need FAT12 support, which is not scheduled and is not part of this quest. Related: SQ-0735 (decoding the PC LZW flavour) is the prerequisite for tier 3 being useful on DOS art at all — the current reader handles only the Amiga Huffman codec.

**Open sub-question for the implementer, not yet decided:** when both a Blorb and a tier-2/3 native archive are present, which wins? The tiers above are ordered by confidence in the PAIRING, not necessarily by preference of CONTENT — a user who explicitly names a native archive probably wants it used. Propose a rule with reasoning rather than picking silently.

--- note 2026-08-09T21:30:26Z ---

PRECEDENCE DECIDED by the user 2026-08-09, closing the open sub-question above: **"the config file override always wins (if the file exists)"**.

So tier 3 outranks tiers 1 and 2 whenever the named file is present. Naming an archive in `<game_dir>/config.toml` is an instruction, not a hint — if a Blorb sits beside the story, or the story came out of an ADF carrying its own `Pic.data`, the explicitly named archive is still the one used.

IMPLEMENTATION DETAIL the user did not specify, and which the implementer should NOT resolve by silently falling back: what happens when the key names a file that exists but cannot be used — wrong container flavour (the current reader rejects the PC LZW form as `UnsupportedContainer`; see SQ-0735), corrupt, or truncated. Silently dropping to the Blorb would recreate the exact failure this whole policy exists to prevent, only inverted: the player believes they are seeing native art and is not, with nothing on screen to say so. Surface it — an error or a visible warning naming the file and the reason — and only then decide whether to continue with the Blorb. "If the file exists" was the user's condition for the override winning; a file that exists but does not decode is a different case and deserves to be loud.

--- note 2026-08-09T21:32:47Z ---

FURTHER DIRECTIVE from the user 2026-08-09: "if we specify a specific file-type for override, we should automatically pick the matching interpreter number (unless that is also overriden)".

So **the art you name determines the machine you are emulating.** Naming a DOS `.EG1` means you are asking for the IBM PC experience; naming an Amiga `Pic.data` means the Amiga one. The resource selects the interpreter profile, and an explicit interpreter setting overrides the inference.

PRECEDENCE, most specific first:
1. An explicit interpreter-number setting (config or CLI) — always wins.
2. Inferred from the flavour of the native archive named in the config override (tier 3).
3. Inferred from the medium — a story loaded out of an ADF is an Amiga (SQ-0719's second half).
4. The existing default: Frotz's rule, 6 for v6 and 1 otherwise.

INFER FROM CONTENT, NOT FROM EXTENSION. SQ-0713's reader already distinguishes the containers structurally: the Amiga/Mac flavour is big-endian Huffman + RLE + per-line XOR (flags `EF_PHUFF`), and the PC flavour is little-endian GIF-style LZW — `parse()` currently returns `UnsupportedContainer` for the latter (SQ-0735 will add it). A file's extension can be wrong; its codec cannot. Extension is a reasonable tiebreak only.

Flavour → machine, as far as the source Infocom shipped tells us: `.EG1`/`.MG1`/`.CG1` are the PC family (EGA / MCGA / CGA); `Pic.data` in the Huffman form is Amiga; the same interpreter source also carries a Macintosh graphics path, so a Mac flavour exists and should be recognised rather than assumed away.

**VERIFY THE NUMBERS AGAINST THE ZMSD, DO NOT RECALL THEM.** The interpreter-number table is ZMSD §11.1.3. CLAUDE.md is explicit that spec constants come from an authoritative source; a wrong number here is silently wrong, since the game simply behaves like a different machine.

BLAST RADIUS, already measured: header byte 0x1E is not inert. `crates/zvm/src/cpu/exec.rs:4052` branches on `read_byte(0x1E) == 6`, and the current default gives every v6 story that value. So any inference that moves a v6 game off IBM PC changes what the game does, and the whole v6 corpus (Zork Zero, Arthur, Shogun, Journey, advent, scopa, mysterious01, fmvpoker) must be re-checked frame-by-frame, not just the path that triggered the change. This is why SQ-0719's first agent was scoped to exclude the interpreter profile entirely.
