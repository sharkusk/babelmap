Landed on worktree-agent-aa3a64f6cfad0a040 (3 commits, rebased on c7dc0ae4). All three pieces of the decode are done and gated:

1. CONTAINER — Flavour::Apple, 8-byte records. Sourced from apple/yzip/rel.15/zip.equ: PLDID/PLDWID(1)/PLDHGHT(1)/PLDFLG(1)/PLDPTR(3), PLDSIZE EQU PLDPTR+3 = 8. Header flags are the Apple's own set, NOT the Amiga's: $8 is PHFPAL "No pallette information", not the PC's picture-space-width bit.
2. CODEC — pic.asm's ZDECLP: RLE (byte >= 16 is a count, n-14; else the next colour, run of 1) + unconditional per-line XOR against a zero row before row 0. No Huffman (PHFHUFF clear). 3-byte big-endian length prefix skipped, which serves as an independent oracle: prefix+3 tiles all four archives contiguously, 131 of 134 gaps nose-to-tail, 3 seams = the part boundaries.
3. PIXELS — decode lands one palette index per pixel, exactly like every other flavour; the Apple's own 4-bit screen packing (PIC2SCR) is the interpreter writing to DHGR video memory and is downstream of the format, so no separate "hi-res unpacking" step is needed. Colours from apple/yzip/apl2iff/apple.pal, Infocom's own table, in canonical DHGR order.

Also corrected infocom_packed's index doc: entry+2 and entry+6 were read as unused page counts; zip.equ names them SGTPICOF ("picture data offset", a block number, 0 = no art) and SGTGPOF ("Global Directory Offset"). Arthur's five read 0/209/60/67/38 and archive headers sit exactly there.

Result: 168 pictures (51+26+53+38), 135 with pixels, 33 placeholders, no id in two parts. Reachable via ProDos::packed_pictures / infocom_packed::pictures.

BLOCKED, and deliberately not done here: ProDos::pictures does NOT fall through to packed_pictures. An archive states a picture space, and the Apple's is 140x192, which PictSource::native_std_window turns into a 560x384 story window where release 63 is pinned at 640x400 — two real_media_releases cases fail. That is the same question SQ-0857 declined when it left InterpreterProfile::AppleIIgs::std_window as None (the space cannot be expressed while the v6 cell is a compile-time 8x16). Wiring the art in without settling the run-time-cell question moves Arthur's whole screen as a side effect. Needs a deliberate decision + likely a run-time-cell refactor; NOT filed as a separate quest per the no-orphan-spinoffs rule — sequence it.

No edit to medium.rs (SQ-0864's). Acceptance census over every loose archive + every file on every mountable image is byte-identical before/after: 31 accepted, no row changed.
