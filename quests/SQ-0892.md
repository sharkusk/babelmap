MEASURED 2026-08-15 on `155b9b91`, via a temporary probe over `shogun-r322-s890706.z6`'s credits/menu screen (probe reverted, tree clean).

**THE GAME DOES NOT BAKE IN A FONT SIZE — IT ASKS US.** V6 games measure a string by printing it to output stream 3 and reading the width back from header `$30` (ZMSD §15; our implementation is `crates/zvm/src/screen.rs:1374`, cited at `crates/zvm/src/cpu/exec.rs:2499`). We answer `chars × V6_FONT_WIDTH` — a MONOSPACE assumption we supply, pinned by tests asserting `8 * V6_FONT_WIDTH` and `6 * V6_FONT_WIDTH` at `screen.rs:2816`/`:2834`. `V6_FONT_WIDTH = 8`, `V6_FONT_HEIGHT = 16` (`screen.rs:1894`), sourced from Frotz's DOS mode table `{0x12, 640, 400, 8, 16}` for the authentic 80x25 (SQ-0479).

This is what the user's observation exposed: **Spatterlight centres this same text with a PROPORTIONAL font.** That is only possible because the game asks rather than assumes — Spatterlight reports its own glyph widths and the game centres correctly for them. Nothing is hardcoded anywhere in the story.

THE PROBE DATA (coordinates are 1-BASED, so subtract one before taking the modulus):

| run | chars | `(x-1) % 8` |
|---|---|---|
| `SHOGUN` | 6 | **0** |
| `A Story of Japan` | 16 | **0** |
| `All rights reserved.` | 20 | **0** |
| `SHOGUN is a trademark of James Clavell` | 38 | **0** |
| `Copyright (c) 1988 by Infocom` | **29** | **4** |
| menu single-char runs (`S`,`T`,`A`,`R`,`T`,…) | — | **2** |

Every `y` satisfies `(y-1) % 16 == 0` — vertically perfect. Horizontal pitch is exactly 8. **Even-length centred strings land dead on a cell; the one ODD-length line lands on a half-cell**, because centring is `(80 − 29)/2 = 25.5` cells. That parity comes from the DIVISION, not from the metric, so it survives any font width we report — changing `V6_FONT_WIDTH` cannot fix it.

**WHY THE EARLIER RING ATTEMPT FAILED, correctly diagnosed at last.** SQ-0886's lane tried the ring and got `"SI(RT th e ga me"`, and both that lane and I read this as "pixel-positioned text cannot be a cell grid". WRONG. The menu is emitted as 15 single-character runs at 8px pitch sharing one origin offset of +2px — a QUARTER of a cell. Rounding each run INDEPENDENTLY makes neighbours collide into one cell or skip one, which is exactly the doubled-and-gapped signature. A uniform 2px shift is invisible.

**THE FIX: quantize runs that share a baseline as a GROUP with one shared origin, not per run.** `START the game` then stays intact, merely shifted by a quarter cell. That is what SQ-0750 actually asks for — text as text, art as art — and it makes hybrid viable on screens that currently fall to the composite.

WHAT MUST BE ESTABLISHED, not assumed:
  - How to group. Sharing a `y` baseline is the obvious key, but a screen may legitimately carry two separate blocks on one baseline (a left label and a right menu column at the same y — this very screen has `You may choose to:` beside the menu). Grouping those under one origin would drag one of them sideways. Find the rule that keeps them apart; a gap threshold in whole cells is the likely shape, but MEASURE the corpus before fixing a constant.
  - Whether the odd-length half-cell line can be absorbed the same way, or needs its own rounding decision.
  - Whether any v6 screen relies on sub-cell placement in a way group-rounding visibly breaks. The corpus sweep is the evidence.

DO NOT change `V6_FONT_WIDTH`/`V6_FONT_HEIGHT`. They are sourced, they give the authentic 80x25, and per the arithmetic above they cannot fix the parity anyway.

CLEANUP MANDATE FROM THE USER, and it is part of this quest, not a follow-up: once hybrid can render these screens, review the code and REMOVE what is no longer needed. Prime candidates, each to be judged by MEASUREMENT rather than by reasoning:
  - `menu_over_art` (SQ-0886, `d1ffc8a0`, in `crates/app/src/render/screen.rs`) — the predicate that excludes such a frame from the cell escape and the ring so it falls to the composite. If the ring can now draw the frame correctly, this may be dead.
  - The `frozen_head` suppression (SQ-0890, `155b9b91`, `interleave_story_elems` + `Machine::v6_prose_retired_whole` at `crates/zvm/src/cpu/exec.rs:318`) — it exists because the composite gave the screen a 548x64 story box. If the frame stops taking the composite, the duplication it suppresses may not arise.
  - Anything else the change strands.

THE PRECEDENT FOR HOW TO DO THAT REMOVAL WELL is SQ-0888's lane: it deleted `story_text_box` only after measuring that it answered `None` on every corpus frame at boot and on every turn. Measure first, delete second, and state the measurement. **Do NOT delete a mechanism merely because it looks superseded** — and do not delete its tests to make a removal pass; retarget them to the new behaviour or say plainly why they no longer describe anything.

THE LEGITIMATE RASTER CASE, from the user 2026-08-15 — this bounds the fix and every verdict in the audit.

**Text composited ON TOP OF GRAPHICS must be rastered.** Their example: Zork Zero's location/score text drawn onto the ribbon art. This is already the documented rationale for the whole `px_texts` channel, `crates/app/src/engine.rs:168`: *"pixel raster draws status text where the game placed it (Zork Zero puts its banner text at rows 6/14, ON the ribbon art) instead of snapping to the char grid."*

**SO THE CRITERION IS "IS THERE ART BENEATH THIS TEXT?", NOT "IS THIS TEXT PIXEL-POSITIONED?"** That is the sharp version of the test this quest falsified, and it cleanly separates the two cases:

| | beneath the text | correct treatment |
|---|---|---|
| Shogun credits/menu | the machine's plain ground | **glyphs** — the runs account for every pixel |
| Zork Zero banner | the ribbon artwork | **raster** — no glyph can reproduce what is under it |

A glyph in a terminal cell carries its own background, which would occlude artwork beneath it. That is the physical reason the exception exists, and it is not a limitation to engineer around.

This is also the precise sharpening of SQ-0750's standard — *"reserve raster for pixels the runs cannot account for"*. Text over art is exactly a case where the runs cannot account for the pixels. Text over a plain ground is exactly the opposite.

TWO CONSEQUENCES, both now required of the lane:
  - The quantization predicate must EXCLUDE runs with opaque art beneath them, and Zork Zero's banner must be verified by measurement to still rasterise as part of the corpus sweep. Turning it into glyphs on a flat background would be a regression even though the text would read as "crisper".
  - The inventory must state this distinction explicitly per entry: art beneath = **correctly rasterising**, plain ground = **candidate**. That distinction is the survey's whole value.

The pairing — Shogun's credits become glyphs, Zork Zero's banner stays raster — is the clearest available demonstration that the new predicate discriminates rather than converting everything, and should be in the test coverage.

## The defect, in one sentence

A chrome text STRIP has grouped its runs before placing them since SQ-0509, and packed its rows since SQ-0543. **The in-viewport overlay that draws runs INSIDE the story box (`screen.rs:2058`, route 3 of the pipeline document's §2) never got either.** Shogun's menu lives there. The fix reuses both existing rules at the site that lacked them; nothing new was invented for the menu.

## The grouping rule, and the corpus measurement behind it

Dumped every chrome run of the eight-title corpus through a new `ring_scout --runs` and counted the native-pixel gap between consecutive runs on a baseline — 279 adjacencies:

    0px (abutting)   187      <- the whole of Shogun's menu
    8px (one cell)    16
    16..407px         76      Journey's menu columns, Shogun's status fields, advent's bar

The distribution is bimodal and the answer is **abutting only**, which is exactly `merge_row_fragments(runs, 4)` — `tol_px` 4 is below one 8px cell, so only gap-0 merges. That is `merge_strip_fragments`'s existing rule (SQ-0757: abutting fragments and one-cell word gaps join, a FIELD gap keeps its own column), reused not restated.

**Why a wider group is wrong, measured:** Journey's Amiga menu band has gaps of 1, 4.75, 0.25, 7, 10, 13 and 15 cells on one row. Grouping across those compresses the whole band inward from the pane edges.

## Y was broken too, and nobody had noticed

Found by the retargeted `shogun_resumed_prompt_lands_beside_the_menu`, not by inspection. The game prints its three items on **consecutive native rows 21/22/23**; the device mapping put them on terminal rows **26, 28 and 29** — a skipped row through the middle of a three-line menu — and `START the game` rounded to 26 against a viewport that **ceils** to 27, so the first item was clipped off the screen entirely. A ceil-vs-round disagreement on a shared boundary, the shape CLAUDE.md names.

Rows now count from the story box's own first row. The justification is stronger than the X one: these runs are stamped **ON the transcript**, and the transcript advances exactly one terminal row per line, so a run placed by device pixel drifts away from the very text it overlays. (The CELL path already did precisely this — `hybrid_menu_screen_renders_coherent_all_text_with_transcript` pins rows 6/7/8 "placed relative to the STORY BOX", SQ-0697. Only the ring was left out.)

## The credits needed a third thing, and it is not grouping

Nine centred lines, **one run per row** — nothing to group. The wobble is that a glyph block is `chars` cells wide while its native footprint is `chars x 8 x s` device px, so each line shrank about its own left edge **by its own length**: centres landed in columns 43, 44, 44, 45, 45.5, 46, 47, 47, 48 against the composite's 49. Five columns of raggedness on text whose entire design is that it is centred.

`strip_native_origin` lays such a strip out in the game's OWN text grid from one shared origin, offset in native cells, plus half the block's slack. All nine return to column 49, where native x=320 maps. **This is SQ-0543's argument on the other axis and that comment already makes it** — *"Inside a TEXT strip there is no art to stay aligned with ... so the game's own row structure is the truth to preserve, not the device-pixel position."* Only the Y half was ever written.

**The guard is the whole of it, and I got it wrong twice before measuring.** Native-cell indexing has slope 1 where the device map has slope `s`, so the two diverge with distance. I first tried a per-run centre anchor: it fixed the credits and **broke `journey_amiga_menu_dividers_line_up_down_the_panel`** (divider 8 columns adrift of its text) and **`the_fields_stay_whole_beside_their_values`** (at 74 cols, s<1, `Erasmus` pushed into the flank art). I then checked a window-width threshold and rejected it: Shogun's credits window is 432/640 = 67.5% and his gameplay status band 548/640 = 85.6%, so any threshold between them is a magic number with no derivation — and grouping the status band moves `Erasmus` 8 columns right and the score 5 columns left, out of a flood still drawn edge to edge, **while `shogun_status_alignment` still passes** (it asserts the two rows agree with each other, which they do). That was the near miss.

**The rule that survives is "every row of this strip carries exactly one run"**, asked AFTER the collapse so Arthur's 72 single-glyph runs are counted as the two they merge into. It separates the corpus cleanly with nothing to tune: Shogun's credits 1/row; Journey's band, Arthur's and Zork Zero's status rows and advent's bar all 2+. Its meaning is real — a run alone on its row has nothing beside it whose relative position it can break, and its only alignments are with the other ROWS, which is what this preserves and what per-run mapping destroys.

Slack is floored at zero: below one column per native cell the glyphs are WIDER than their footprint and there is nothing to distribute. That case is live (Shogun at 74 columns is s = 0.925).

### 1. CANDIDATE — `picture_takeover`, `screen.rs:802` (defined `:4155`)

Rasterises the **entire frame, art and the whole story transcript**, when the story window is present but any of four OR'd hatches fires. Stated reason (`:4096`): *"Such a frame has no ring to draw, so there is nothing for hybrid to do: the caller falls through to the RASTER composite, which draws the picture and rasterizes the story text over it in one canvas."* And the acknowledgement (`:4152`): *"The tradeoff is real and deliberate: a frame that stops taking the ring renders as a pixel image instead of crisp terminal cells. It is still the right trade, because the alternative for such a frame is not crisper art — it is no art."*

**Art beneath the text? UNASKED.** All four hatches are geometry plus a coarse whole-screen alpha probe: `story_covers_screen` (`:4286`, pure geometry, `SCREEN_SLOP = 16`); `art_paints_anything` (`:4174`, an 8x8 probe **anywhere on screen**, not under the runs); `art_fills_screen` / `art_encloses_screen` (8x8 grid / four edge strips); `story_plate_escapes_story_window` (`:4214`, box containment + a `STEP: 4` sample). **Not one of them calls `region_has_opaque` or `over_art`.** So a full-screen window whose plate paints anything rasterises every glyph on it, including glyphs on bare page.

**Verdict: SAME ASSUMPTION, at the largest scale on this path.** A fix means the hatches stop being all-or-nothing: the frame keeps a ring for the columns/rows whose pixels the runs cannot account for, and text over plain ground stays glyphs — the SQ-0894 content rule applied to a story box instead of a flank. That is a project, not a patch, and SQ-0894 already recorded it as what raster-removability needs. Note the honest limit alongside it: SQ-0894 measured that text over art has **no portable expression but rasterising the text** (sixel has no z-order, half-blocks ARE glyphs), so this can at best become a kitty fast path beside a composite that stays.

### 2. CANDIDATE — the `painted_ground` guard, `screen.rs:2197`

A no-story-window screen made **only of text runs** is drawn as glyphs by `draw_painted_screen`, *unless* any painted ground exists anywhere, in which case the whole thing falls to the composite. Verbatim (`:2185`): *"this path draws the RUNS and nothing else — every pixel on the screen is discarded. That is right for a screen that is only text (Zork Zero's InvisiClues, Shogun's boot menu: both no-story, both with no painted ground). It is wrong when the game's picture IS the screen. scopa ... draws its card table entirely with `erase_window` fills, so hybrid landed here and rendered SEVEN cells out of a 100x34 pane while raster drew the table. A painted ground means there are pixels that only the raster composite can show, and it draws the runs over them anyway, so fall through to it."*

**Art beneath the text? DECIDED GLOBALLY, NOT PER RUN.** `state.v6_paint.borrow().is_some()` is one whole-screen boolean. Any erase-fill anywhere sends **every run on the screen** to the rasteriser.

**Verdict: SAME ASSUMPTION.** The reasoning ("pixels only the composite can show") is right about scopa's table and wrong about a label standing beside it on bare ground. A fix is the cheapest on this list: keep the composite for the pixels and stamp the runs `over_art` says are NOT over art as glyphs on top — the discriminator already exists and is the one this quest leaned on. Worth its own quest.

### 3. CORRECTLY RASTERISING — `ChromeRowOracle::over_art`, `screen.rs:5397`, classifying at `:5437`
