MEASURED, not inferred. `cargo run -p app --example ring_scout -- --story stories/fmvpoker.z6`:

  booted as IbmPc · release 60 serial 001227 · screen 320x200 · art scale Some((2,2))
  win0 Some((0,0,640,400)) -> clear Some((0,0,640,400))  prose Some((22,234,594,158))
  picture_takeover: art_paints_anything  -->  RASTER (the ring never runs on this frame)

So this is NOT SQ-0944 failing. fmvpoker's story window covers the screen and its plate paints, so the frame goes to the full-frame raster composite, which rasterises every character on the screen by construction — chrome runs AND the transcript prose. Under half-blocks a rasterised 8x16 glyph arrives as 8x2, so the whole game is mush. A pty capture at 117x40 (cell 10x20, --image-protocol halfblocks) shows ZERO glyphs anywhere on the pane.

SCOPE. `--all` says fmvpoker is the only title taking raster on its BOOT frame (zork0, arthur, shogun, journey, mysterious01, scopa, advent all reach the ring). But `picture_takeover` is a per-FRAME decision, so any title hits this on a full-screen picture frame — Zork Zero's map/rebus and Arthur's Merlin composite are the ones already named in the code. fmvpoker is simply the title that is there from the first frame.

THE OBVIOUS CHEAP FIX DOES NOT WORK — tested, not assumed. Stubbing `art_paints_anything` to false does not route fmvpoker to the ring: `art_encloses_screen` fires next and it is raster again. Both arms are genuinely true of this screen (the plate paints AND encloses), so narrowing the gate means retiring several arms against a screen that really is a full-screen picture, which is what the takeover exists for. SQ-0711's scopa lesson points the same way: a screen with pixels on it can only be shown by the composite.

(An apparent difference in the card art between the two captures was a different deal, not a rendering change — fmvpoker animates. Pin `random_seed = 12345` in the harness config dir before comparing frames, as SQ-0936's previews had to.)

SO THE LIKELY SHAPE IS SQ-0944'S MOVE ONE LAYER UP: keep the composite, withhold the text rows from it (`TextLayer::SkipGlyphRows`, which raster currently never uses — it passes `TextLayer::All` and that is deliberate, "raster has no cells to draw text with"), and stamp the runs as glyphs over the placed image with a ground sampled from underneath, gated on `backend_flattens_alpha_to_black`/`backend_layers_glyphs_over_art` exactly as the ring is. Two things make it more work than the ring's version: the composite is built OFF-THREAD and cached (`V6Ready`), so the skip set has to reach the job and the stamp has to happen after placement; and the raster path also images the transcript prose and any secondary prose window (SQ-0729), so it is not only chrome runs.

Worth deciding first whether raster-on-half-blocks should exist at all, or whether the honest answer is that raster is a kitty-and-better mode and half-blocks always gets a cell-based rendering of the same screen.

--- note 2026-08-21T19:56:17Z ---

UN-DEFERRED. Deferred when half-blocks was a fallback nobody used seriously; it is now the backend producing near-native scopa (SQ-0964 removed the magnification cap, SQ-0972 fixed the u16 ceilings), so this is the gap between "scopa looks great" and "half-blocks is a complete recreation".

User's proposed direction: switch automatically between terminal glyphs and rasterised text based on how small the font glyphs are RELATIVE TO the graphics — i.e. add a resolution term to a decision that currently has none.

`picture_takeover_reason` (crates/app/src/render/screen.rs:4833) asks only what the ART does: story_covers_screen, then art_paints_anything / art_fills_screen / art_encloses_screen. Resolution is not consulted.

The metric: under half-blocks the composite has `cols` horizontal samples and `2 * rows` vertical against a native screen of native_w x native_h, so r = 2*rows / native_h samples per native pixel. A native character cell is 8x16, so a glyph gets 8r x 16r samples — r=1 is full native fidelity (confirmed: the user's scopa capture rendered "Help/Credits/Quit" crisply as raster pixels), r=0.5 is 4x8 and marginal, r=0.25 is unreadable, which is fmvpoker's takeover frame.

The trade, which is real: takeover exists BECAUSE the art paints where the text is, so falling back to glyphs punches holes in that art — the very thing takeover avoids. Justified anyway when the alternative is an unplayable frame, but it is not free and should be stated wherever it lands.

Two implementation requirements:
- HYSTERESIS. A pane hovering at the threshold would flip modes on every resize and look terrible. Needs a deadband.
- Gate on `picker.protocol_type()`, the way `v6_upscale_cap` does (SQ-0964). Kitty and sixel render at device pixels and never hit this.

Symmetry worth preserving in the comments: the existing rule is "in hybrid, never rasterise what the game printed as a character" (SQ-0750). This is its converse — "in raster, do not rasterise text the pixels cannot carry."

Composes with SQ-0917: the threshold depends on the native glyph size, which per-release font metrics would make accurate instead of assumed at 8x16.

SEQUENCING: do NOT dispatch alongside SQ-0973 — that lane is currently rewriting the half-blocks resample path in render/graphics.rs, and this work needs whatever it lands.

--- note 2026-08-21T20:20:28Z ---

DISCARDED by the user, and the reasoning inverts the premise this quest was built on.

The proposed fix was to fall back to terminal GLYPHS when the raster resolution is too low to carry text. The user's ruling: **hybrid will never work at small terminal font sizes, and small fonts are where half-blocks is actually used. Only full raster works there.**

Why the proposal was backwards for the case that matters:

- The metric (r = 2*rows / native_h samples per native pixel) is correct, but its consequence runs the opposite way from what was assumed. At SMALL fonts r is HIGH, so rasterised text is drawn at near-native fidelity and is perfectly readable — that is exactly what the user's scopa capture showed, with "Help / Credits / Quit" crisp.
- Meanwhile at those same small fonts the terminal's own GLYPHS are physically too small for a human to read. That was the user's original observation when this whole direction started: "if we reduce the font size very small, we can actually represent the graphics very well (except the terminal glyphs are not readable at that size). However, that shouldn't matter if we are in raster mode."
- So a glyph fallback would trade readable raster text for unreadable glyphs — strictly worse, in precisely the configuration this backend exists to serve.

The unreadable-fmvpoker frame that prompted the quest occurs at ORDINARY font sizes, where r is low. That is a real observation but not a mode anyone uses half-blocks in, so it does not justify the mechanism, its hysteresis, or the art damage that declining a takeover would cause (takeover exists because the art paints where the text is).

The lane was stopped mid-investigation with no commits; its worktree and branch are removed. Its one recorded finding before being stopped: `r` is monotone in the pane, zero downward steps — which would have made the hysteresis band easy, had the feature been wanted.

CONSEQUENCE: SQ-0979 was held behind this lane's edits to render/graphics.rs and render/screen.rs. That block is now released.
