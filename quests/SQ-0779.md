Placements: `image rows 2..23 cols 1..50` (the picture, 50 cols x 22 rows) and `image rows 24..24 cols 1..119` (a 119x1 FULL-WIDTH one-row band).
Background map: rows 2, 3, 4 all read `default[1..50](image)` — i.e. the artwork owns column 1.

FOUR DISTINCT FAULTS, all in one frame:
 1. **The left rule is swallowed by the artwork.** The picture placement spans cols 1..50 INCLUSIVE, so column 1 — the frame's left rule — is inside the art rect. `flank_border_extension`'s content test requires the graphics-only canvas to be CLEAR across the border's native columns; when the picture fills its entire allocated column the canvas is not clear there, so the rule is neither stamped as a glyph nor drawn as a band. It simply ceases to exist.
 2. **Row 2 is unclaimed on the right.** Art occupies cols 1..50 of row 2; cols 51..119 are blank. The SQ-0747 absorption fixed the 117x64 case (where row 2 was unwritten across all columns) but this size takes a different path: the strip is not absorbed, it is filled with art on one side only.
 3. **The right rule is drawn DOUBLE-WEIGHT against a single-weight top.** Row 3 shows `║` (U+2551) where the top border is `┌`/`─`/`┐` (single). At 117x64 the same rules came out `│` (single). So the glyph the stamp chooses is WIDTH-DEPENDENT — that is the "l/r borders are broken" report, and it is the more alarming half: a border whose character changes with terminal size.
 4. **A stray gap column before the pane border.** Row 1 ends `…┐ │` — the game's top-right corner, one blank column, then babelmap's own pane border. Row 2 has nothing there at all.

FIRST QUESTIONS FOR WHOEVER TAKES IT, in order:
 - Where does `║` come from? Is the game printing a different character at this size (plausible — it lays out against its own screen and may pick a different rule glyph), or is our run→glyph mapping picking one? Dump the game's paint run at that native column under both sizes and compare. If the GAME prints `║`, then the top border should be double too and the defect is that the top is single; if WE choose it, the mapping is wrong.
 - Should the border columns be excluded from the picture's allocated span, or should the content test tolerate art in the border column and stamp the run's character over it? The first is a layout change and the second a compositing one; they are not equivalent, and (1) is the load-bearing decision for this quest.
 - Sweep widths to find the boundary: 117 is correct, 121 is broken. The exact transition width will say whether this is a rounding threshold (the picture's cell span crossing an integer boundary) or a plan change.
