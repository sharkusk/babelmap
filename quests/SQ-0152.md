context: '[TODO-7b8a9f] BeyondZork (and likely other v4+ games with a custom status display) get NO automapping — no room is captured, so the map never updates. ROOT CAUSE: `zvm::current_location` (crates/zvm/src/location.rs:230) infers the current room by reading GLOBAL VARIABLE 0 — the Z-machine status-line location global. That convention holds for v1-3 (and v4+ games that keep the room there), but BeyondZork renders its own status (stats/compass in the upper window) and does NOT maintain global 0 as the current room, so current_location returns None/garbage → app''s current_room_name stays empty (main.rs:4179) → mapper never observes a room. FIX DIRECTION: detect the room more robustly than trusting global 0 — e.g. find the PLAYER object and use its parent (containing room) from the object tree (version-independent, works when global 0 is unused), possibly version-gated or with a fallback chain (global 0 → player-parent → status-line NameOnly resolution). Verify against BeyondZork + the normal v3 games (must not regress). Relates to the existing v4+ status-line name resolution (Location::NameOnly, session.rs:234) and the deferred LostPig Glulx upper-window detection gap. Surfaced 2026-06-30. VERIFIED 2026-07-02 (commit 4adf7f9 partially fixed this — STILL OPEN for BeyondZork itself): `detect_location`''s player-parent validation now resolves rooms for v4+ games with a LEFT-JUSTIFIED status line or a "Location:" label (confirmed: zork1-invclues, wishbringer-invclues, sherlock, LostPig, hitchhiker-invclues, planetfall-invclues, leathergoddesses-invclues, amfv; v3 games unaffected/no regression). New coverage: crates/zvm/tests/story_location_verify.rs (v3 regression + v4+ resolution + a BeyondZork canary test that will start failing once centered-title parsing is added, as a prompt to close this out). [automapping; zvm location.rs current_location + player-object detection] — completed 2026-07-02.
