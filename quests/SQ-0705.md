RESOLVED 2026-08-09 — user verified raster mode in Zork Zero renders correctly on the current build. No fix was written FOR this quest; it was carried by the day's work on the same path (SQ-0510 theme half 418360fc, and the three SQ-0704 commits 0582664e / 74f1ef07 / 1214dbb1, the last of which publishes AppState::v6_story_page from story_bg_rgba and flattens inline pictures onto it).

Both recorded suspects were falsified by measurement before the user confirmed the symptom was gone, so neither should be re-proposed if anything similar recurs:

(1) MIXED PAIR (game's page + host's ink) — does not occur. The raster path already resolves game_ink/game_page independently (screen.rs, `let ink = game_ink.unwrap_or(default_fg)`), and Zork Zero supplies BOTH channels at every step of a fresh boot: game_fg=Rgba([0,0,0,255]), game_bg=Rgba([255,255,255,255]) -> black on white, readable. Measured against a simulated Ghostty OSC pair (white ink, page 40/44/52), i.e. the reporter's own terminal, which is the configuration that would have produced white-on-white had the channels ever been mixed.

(2) AUTO-RESUME carrying a bg without an fg — does not occur. save_state -> fresh boot -> restore_state -> one further turn (so the game repaints) preserves the pair intact: black on white before the save, after the restore, and after the repaint. The "restored session carries an explicit white bg" half of the theory is true but harmless, because the fg is restored with it.

What was never reproduced headlessly is the SYMPTOM itself, in any mode. If it ever returns, the live-only evidence is what to collect first (/print-colors and /dump-windows from the failing screen), not another canvas-side hypothesis.
