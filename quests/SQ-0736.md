--- note 2026-08-09T21:56:49Z ---

STRONG HYPOTHESIS, from reading the two commits that meet here — verify before building, but this is very likely the whole of it.

SQ-0715 (`98b29882`) replaced the unconditional 2x art doubling with a rule taken from Blorb §11: a resource file with no `Reso` chunk declares no scalable images, so its art is shown at actual size. `crates/app/src/session.rs:800`:

    let art_scale = if machine.mem.version() == 6 && v6_screen_px.is_some() { V6_ART_SCALE } else { 1 };

SQ-0719 (`0f77cf48`) then reported, in its own words: "`std_window()` returns `None` for a native archive, which lands on the existing 320x200 art → 640x400 screen fallback". So a story mounted from an ADF gets `v6_screen_px == None` → **`art_scale = 1`**, while the screen is still 640x400. Zork Zero's 320x200 pictures therefore paint at half the size the game lays out for. That is exactly "the graphics are not being scaled".

Note the two rules are individually right and wrong together: the Blorb rule reasons "no Reso means the author declared non-scalable art", but a native Amiga archive has no Reso chunk because **the format has no such concept**, not because anyone declared anything. Absence of evidence is being read as evidence of absence.

THE FIX IS PROBABLY THE USER'S OWN RULE, ALREADY DECIDED. SQ-0734 records: the flavour of the art in play selects the interpreter profile, and SQ-0719's second half says a story from an ADF is an Amiga. An Amiga v6 machine is 640x400 with 320x200 art doubled — which is precisely what every Infocom Blorb's `Reso` chunk declares, and what babelmap already does for them. So the native path should assert the Amiga profile (standard window 320x200, scale 2) rather than fall through to "no declaration". Do NOT special-case `art_scale` for ADFs; derive it from the profile, or the two mechanisms will drift.

Do not disturb the Blorb rule itself: scopa and mysterious01 genuinely declare no `Reso` and must keep `art_scale = 1` (SQ-0715, SQ-0718).

TWO MORE REPORTS from the same test session, both needing clarification before they can be worked — asked of the user:
- "drop caps and room icons now working" — unclear whether this reports success or a defect (the sentence reads as success but arrived in a list of problems).
- "the map doesn't show up" — unclear whether this means babelmap's automap pane or Zork Zero's own in-game map. If art is at half scale the game's layout arithmetic still uses the 640x400 screen it was told about, so an in-game map drawn from picture dimensions would land wrong; that would make it a symptom of the same defect rather than a separate one.

--- note 2026-08-09T22:01:28Z ---

USER CLARIFICATIONS 2026-08-09, resolving both open questions from the previous note:

- **"drop caps and room icons NOT working"** — a defect, not a success. (Their correction: "sorry, drop caps and room icons NOT working.")
- **"the map"** is Zork Zero's **in-game map**, reached with the `map` command then `y` — not babelmap's automap pane.

CASCADE HYPOTHESIS — all three reports may be one defect. Test this before treating them as three:

`art_scale` does not only scale what we PAINT, it scales what we TELL THE GAME. `session.rs:808` multiplies every entry of the `picture_data` dimension table by `art_scale`, so with the ADF path stuck at 1 the game is told its 320x200 art is 320x200 while the screen it was given is 640x400. Every layout the game computes from those dimensions is then half-size against a full-size screen. Zork Zero is exactly the title that does this most: the v6 feature docs record that it queries `picture_data` on pictures it never draws, purely to position its banner, columns and compass. An in-game map assembled from picture dimensions would land wrong or off-screen for the same reason.

Drop caps and room icons have a second, sharper exposure: the inline/backdrop classification is scale-dependent. `session.rs:1679` reads

    let spans_window = ev.x <= 1 && pic_w * self.art_scale >= win_w.max(1);

so halving `art_scale` halves the left-hand side and can flip a picture between "backdrop" and "inline float" (SQ-0714's rule). A drop cap that classified correctly under the Blorb at scale 2 may classify differently off the ADF at scale 1 — which would make it vanish rather than merely render small.

SO: fix the scale first, then re-test all three. If drop caps and the in-game map come back on their own, they were never separate defects. If they persist after the profile is asserted, they are real and deserve their own investigation with fresh measurements. Do not open three fronts before the first is settled.
