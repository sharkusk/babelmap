--- note 2026-08-15T08:06:17Z ---

MEASURED, both sides, same build — `James Clavell's Shogun.adf` r295/s890321 at the credits-and-menu screen (one keypress past the splash).

Reproduce ours:
  cargo run -q -p app --example pty_capture -- --story "stories/James Clavell's Shogun.adf" \
    --size 100x40 --keys "wait:3500,space,wait:3000" --png <out>

THE ORIGINAL (320x256, rows 0..27 and 229..255 are the Amiga's letterbox, so the screen proper is 28..228). Row-classed across the screen area, every twelfth row:

  grey #424542 dominates EVERY row, typically 274 of 320 px — the credits rows included
  black is 4..46 px per row, and it is the side-panel detail and the menu selection box
  white is the text

So on the original there is NO black block behind the credits at all: the text sits directly on the machine's grey ground, and the ornate gold-and-black panels run down both edges from this screen onward.

`#424542` is the Amiga palette's colour 12 (`#424242` — the +3 on green is JPEG fuzz), which is exactly `AMIGA_DEFAULT_BACKGROUND` in `zvm::interpreter`. So the ground colour we already ship is right; we are simply not painting it here.

OURS (800x720): `#424242` IS the dominant colour overall (385,392 px), so the grey is reaching most of the frame. But rows 18..179 are `#000000` across 761 of 800 columns — a full-width black band over the top half — and there are no side panels anywhere.

THREE DEFECTS ON ONE SCREEN, and they may or may not share a cause:
  1. the side border panels are not drawn at all;
  2. a full-width black block covers the top half where the grey ground belongs;
  3. the same black extends behind the menu box.

WHAT NARROWS IT: the panels ARE drawn once the game proper starts. An in-game capture of the same disk measures `flank_source x0=0 x1=47 art=(0,336) native_h=400 → ShogunSinglePiece`, so the border machinery finds and composes this art correctly in play. It is specifically the pre-game credits/menu screen that loses them. So look at what that screen does differently — it is drawn before the story window layout the in-game path assumes, and the black band's extent (rows 18..179, i.e. the credits text window) suggests a window being cleared to black rather than to the machine page rather than anything wrong with the border reader.

Note this is a v6 story, so the machine's default pair IS the screen (`v6_screen_page: true` on the Amiga row) — see `machine_screen_pair`. A window cleared to the VM's own §8.3.2 seed instead of the machine page would produce exactly the observed black.

DO NOT confuse this with SQ-0873's period look: this machine's ground is v6 and sourced, so it is the existing `default_colours` path, not the new field.

The banner on this same screen is separately wrong — see SQ-0885.

--- note 2026-08-15T08:25:13Z ---

NARROWED BY THE USER, and this is the strongest clue on the quest: **in RASTER mode the side panels ARE drawn on this screen and the whole background IS painted correctly.** Only hybrid is wrong.

That relocates the search entirely. It is not the border reader, not the archive, and not the machine page — raster reaches all three correctly from the same bytes on the same frame. It is the hybrid ring's composition of this particular screen.

Two things that already fit:

- `render/screen.rs` builds `tiled_flanks` only from `ChromeStrip::Art(r)` strips where `r.width < area.width`, and skips the whole thing under `BottomPlan::Menu`. This screen HAS a menu (START / RESTORE / QUIT), so if it is classified `BottomPlan::Menu` the flanks are excluded by that guard — which exists for Journey, whose left column is a picture in a panel rather than a border to extend (SQ-0819). Shogun's menu screen may be falling into the same exclusion and losing genuine border art with it.
- `extend_raster_flanks` is the raster path's own equivalent and carries the SAME menu exclusion (`menu_strip_below_story`), so if that were the whole story raster would be wrong too. It is not — so the difference is upstream of the exclusion, in how each mode decides what this screen's strips ARE.

So: compare the two modes on this exact frame and find where they diverge. Reproduce with

  cargo run -q -p app --example pty_capture -- --story "stories/James Clavell's Shogun.adf" \
    --size 100x40 --keys "wait:3500,space,wait:3000" --png <out>

and the same with raster forced. The measured contrast to close: ours paints `#000000` across 761 of 800 columns on rows 18..179 with no panels; the original has `#424542` (the Amiga's colour 12) dominating every row with the panels down both edges.

--- note 2026-08-15T08:30:06Z ---

TWO MORE FROM THE USER, and together they change the shape of this quest.

1. **IT IS NOT AMIGA-SPECIFIC.** The IBM/Blorb Shogun loses its side panels on this same screen in hybrid mode too. So the title should not have said "Amiga" — the medium is incidental. Whatever this is, it is in the hybrid ring's handling of this SCREEN, reached identically from an `.adf` and from a Blorb.

2. **THE HYPOTHESIS: we are painting OVER them**, probably because of the centred text and the menu — not failing to compose them.

That is a better reading than mine and it fits the measurement. I recorded "no panels are drawn"; what the numbers actually say is that `#000000` covers 761 of 800 columns on rows 18..179, which is equally consistent with panels being drawn and then buried under a full-width black fill. A composition that never ran and a composition that ran and was overwritten look identical in a final-frame census — and only one of them is what raster does differently. Raster builds the whole frame at native size and resizes once, so a chrome fill drawn per-strip in hybrid has no equivalent there, which is exactly why raster survives.

So the thing to find is the fill, not the flank. Look for what paints the story window's ground across the full pane width on a screen with centred text and a menu, and why it is not clipped to the story window's own native rect the way the panels are. `draw_chrome_band`'s full-width crop (`r.width == area.width`) is the obvious suspect: a strip classified full-width is drawn as a straight sub-rect of the scaled canvas, and on this screen the region between the panels is exactly where the credits are centred.

REVISED REPRO — do both renditions, both modes, four captures:

  cargo run -q -p app --example pty_capture -- --story "stories/James Clavell's Shogun.adf" \
    --size 100x40 --keys "wait:3500,space,wait:3000" --png <out>
  …and the same with `stories/shogun-r322-s890706.z6` (Blorb), and each with raster forced.

If the Blorb one reproduces, this can be pinned without any gitignored Amiga medium — `Shogun.blb` is in the same directory but the story file is the fixture that matters, and a Blorb-based case is the one most likely to be reachable in CI.

The Z ORDER is the question to answer first: are the panels drawn before the fill, after it, or not at all? The emitted-stream harness answers it directly — an image placement is visible in the stream even when a later cell fill covers it, so `pty_capture --raw` plus the placement list will say which of the two stories is true, and that decides where the fix goes.
