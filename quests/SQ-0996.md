## Measured while doing SQ-0995

SQ-0995 fixed the id churn in `render_kitty_virtual` (`crates/app/src/render/graphics.rs`) — a graphics window now keeps one image id and replaces the data behind it, so a changed picture emits ONE placeholder cell instead of `w*h`. Measured 6.7×–11.3× fewer bytes per changed frame on Scott/Glulx room pictures.

**But no v6 story reaches that function.** Captured under the pty harness with kitty negotiated, grepping for lanthorn's own id range `0x00B0_xxxx` (11534336+):

| story | ids from `render_kitty_virtual` |
|---|---|
| journey-r83-s890706.z6 at 117×64 | 0 |
| zork0-r393-s890714.z6 at 117×50 | 0 |
| shogun-r322-s890706.z6 at 117×50 | 0 |
| arthur-r74-s890714.z6 at 117×50 | 0 |
| golden_baton.blb (Scott) at 117×50 | yes — `id=11534337` |
| advent.blb (Glulx) at 117×40 | yes — `id=11534337` |

v6 art goes through `WinNode::Layered` in `render/screen.rs` → the chrome ring's bands or the full-pane raster composite, and BOTH are placed by `ratatui-image`, whose ids are random per `Protocol`. `place_protocol` / `reseat_kitty_placement` then re-lay those rows into lanthorn's own self-describing placeholder cells (SQ-0772), so the cells carry a `ratatui-image` id in exactly the same per-cell way — foreground low 24 bits, third diacritic high byte.

So every band re-encode and every composite re-encode is a NEW id, and therefore a full repaint of that band's placeholder rect, on top of the (now compressed, SQ-0991) image. From a Journey r83 capture at 117×64: flush 3 transmits `id=3386397356` 312×360 for a 39×20-cell rect, a fresh random id — 780 cells re-laid. Zork Zero r393 at 117×50 re-encodes two 64×126 pillar bands per move, each a new id.

The composite is the big one: a 920×575 frame is roughly 115×32 cells = 3,680 placeholders, repainted every time the composite is re-encoded, which is every frame the game changes anything.

## What would have to happen

Same shape as SQ-0995, one layer harder, because the id belongs to `ratatui-image`:

- `Protocol` keeps its id private; `reseat_kitty_placement` already reads it back off the placement the crate just wrote, so the id is knowable but not settable.
- The crate is already forked here (`Picker::set_font_size` was added to it for SQ-0992), so giving `Protocol` a "re-encode into this existing id" path is on the table.
- Everything SQ-0995 established about the protocol applies unchanged: re-transmitting to a live id replaces the data (spec: *"the existing image and all its placements must be deleted"*), the transmit must carry `p=` so Ghostty — which does NOT delete placements on re-transmit — replaces its placement rather than piling internal ones, and a chunked transmit commits only on its final chunk so nothing blanks mid-transfer.
- The band cache (`chrome_scaled`, band hashing) and SQ-0817's `deletes_after_place` both assume an id per encode; both would need re-reading against a stable id, and SQ-0753's "ratatui-image never deletes, so we free ids ourselves" becomes largely moot for anything with a stable id.

Where the number is: half-blocks at 458×144 was measured at 489 KB per full repaint (SQ-0977) and kitty's placeholder grid at that size is the same 65,952 cells. That figure was quoted at SQ-0995 as if it were the kitty graphics-window cost; it is not — it is this path's.
