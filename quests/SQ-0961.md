## The report

`treasures/Lost Treasures of Infocom, The_Disk*.adf`. Point **zvm-cli** at the first disk and it offers only the games on THAT disk. Point **lanthorn** at the same disk and it lists the whole collection correctly.

So the behaviour is already right in one front-end. This is not "teach us to read a compilation" — it is "the CLI takes a narrower door than the TUI", and the TUI's is the reference implementation.

## Third instance of the same seam, which is the reason to read the other two first

  - **SQ-0941** — a disk with no story of its own gave up instead of asking its release. `mount_set` DID consult siblings, but only to reassemble a paged container; a DOS press has none, so the siblings were read, offered to the reassembler, found not to be segments, and dropped.
  - **SQ-0952** — `story_key_at`'s path-only door mounted the platter while the launch path mounts the set, so one game got two save-directory identities and the story list read its metadata from a directory the running game never wrote to.
  - **This one** — the CLI enumerates from the platter where the TUI enumerates from the release.

Every one is *the platter versus the release*, at a different call site. Worth asking, while fixing this, whether there is a single seam that should answer "what stories can this path reach?" the way `assets::volumes` answers "what artwork can this story use?" — `launch_options.rs`'s doc says that function is "the one place that answers" its question and "the seam that knows disks exist so that no caller has to". A sibling for stories may be what all three of these have been missing.

## The guard that must survive

`disk_set::mount_at`'s widening is deliberately restricted to a release carrying **exactly one game** — the mirror of `assets::volumes`' `stories > 1` threshold — precisely so that a twenty-game compilation does not hand one game's resources to another. **A fix here must not loosen that.** Listing every game across a compilation's volumes and letting one game reach another's plates are different questions, and the existing rule is the answer to the second, not the first.

SQ-0941's note records a related refusal that is CORRECT and should stay: `Lost Treasures (Disk 1 of 7).2mg` yields no single story, because 30 games is a browser, not a game.

## Where to look

Compare how each front-end enumerates: lanthorn's picker path (`picker.rs` / `picker_ui.rs`, and whatever walks a set for the browser rows — `disk_story_rows` and `disk_set_rows` are the suites that pin it) against `zvm-cli`'s menu. The suites `crates/app/tests/suites/disk_set_rows.rs` and `disk_story_rows.rs` already pin the TUI's answer, so the shape of a correct expectation is written down.

Verify on the actual `.adf` set — CLAUDE.md's rule applies: a disk image is a different release, so name the exact fixture and reproduce on it rather than on a bare story file.

## SCOPE WIDENED — this quest also closes the seam so there is no fourth instance

The user asked whether the multi-disk handling wants a generic refactor rather than fixes spread across call sites. **Measured, and it does not** — the seam already exists and almost everything already routes through it. After SQ-0952 there are exactly THREE production calls to the platter-only `blorb::medium::MountedDisk::mount`:

    cli-host/src/disk_set.rs:414   CORRECT -- inside the seam itself, mounting siblings
                                   plainly on purpose (mounting THEM across the set
                                   would recurse)
    zvm-cli/src/media.rs:332       bypass
    zvm-cli/src/main.rs:1604       bypass

Both genuine bypasses are in `zvm-cli`, and they ARE this bug. So the sprawl is already down to two call sites in one binary.

## The architecture as it stands, for whoever picks this up

  - **Stories** -> `cli_host::disk_set::mount_at`. Used by `startup.rs`, by `app/hints.rs` (whose doc records that both of its old paths became `mount_at`'s), and by `cli-host/storage.rs` as of SQ-0952.
  - **Artwork** -> `app::assets::volumes`, which calls `mount_set` directly and deliberately: it wants EVERY volume's plates and carries its own `stories > 1` refusal. `launch_options.rs` calls it "the one place that answers 'what artwork can this story use?' … the seam that knows disks exist so that no caller has to."
  - **Enumeration** -> **no seam at all.** Nobody answers "what stories can this path reach?" That absence is this bug.

## So this quest is two things

1. **Give stories the enumeration answer artwork already has** — one function, in `cli_host::disk_set` beside `mount_at`, answering "every story this path can reach across its release". Point `zvm-cli/src/media.rs:332` and `zvm-cli/src/main.rs:1604` at it. The TUI's answer is the reference: `crates/app/tests/suites/disk_story_rows.rs` and `disk_set_rows.rs` already pin what a correct list looks like.

2. **Add a source-level discipline check** — the same shape as `palette_lock_discipline` (SQ-0905/SQ-0958) — failing any production call to `MountedDisk::mount` outside `disk_set.rs`. Three bugs from one seam (SQ-0941, SQ-0952, this) is enough evidence that reasoning will not hold the line, and the next call site will be written by someone with no reason to know any of this. That is the exact argument SQ-0905 used to justify its own check.

   Note the check must allow `disk_set.rs`'s own use and should say WHY in its failure message, pointing at `mount_at`. Tests are a separate question: several legitimately mount a platter to establish a premise (SQ-0952's new case does exactly that, to prove a volume carries no story of its own), so the check should cover `crates/*/src/` and not `tests/`.

## Still holds from the note above

Do not loosen `mount_at`'s one-game guard. Listing every game across a compilation and letting one game reach another's plates are different questions, and that guard answers the second. `Lost Treasures (Disk 1 of 7).2mg` correctly yields no single story — 30 games is a browser, not a game.

## A SECOND FIXTURE, and it exposes a prerequisite nobody had noticed

The user pointed at `treasures/*.dc42` — a DiskCopy 4.2 press of the same compilation, with a different naming convention. Probed both sets through `app::disk_set::members`:

    Lost Treasures of Infocom, The_Disk1.adf                                    -> 6 members
    The Lost Treasures of Infocom - Disk 1 - Beyond Zork, Lurking Horror.dc42   -> 0 members
    The Lost Treasures of Infocom - Disk 5 - Zork Zero.dc42                     -> 0 members

**The DiskCopy set is not grouped at all**, and the naming is why:

    ADF     Lost Treasures of Infocom, The_Disk1.adf
            Lost Treasures of Infocom, The_Disk6.adf
            identical stem, digit LAST, nothing after it

    DC42    The Lost Treasures of Infocom - Disk 1 - Beyond Zork, Lurking Horror.dc42
            The Lost Treasures of Infocom - Disk 2 - Hitchhiker's, Infidel, Planetfall, Stationfall, Starcross, Suspended.dc42
            The Lost Treasures of Infocom - Disk 3 - Ballyhoo, Deadline, Moonmist, Suspect, The Witness.dc42
            The Lost Treasures of Infocom - Disk 4 - Enchanter, Sorcerer, Spellbreaker, Zork I, Zork II, Zork III.dc42
            The Lost Treasures of Infocom - Disk 5 - Zork Zero.dc42
            index in the MIDDLE, and NO COMMON SUFFIX -- each volume names its own games

A "common prefix + digit run + common suffix" rule groups the first and cannot group the second. The tail is not noise to be tolerated; it is different information on every volume.

## THIS IS A PREREQUISITE FOR THIS QUEST, not an aside

The enumeration seam this quest asks for — "every story this path can reach across its release" — is built on `members`. With `members` returning 0 for the DiskCopy press, pointing `zvm-cli` at the new seam would still list only that disk's games there. **Fix the grouping first, or the quest's own second fixture will not exercise the fix.**

It also means SQ-0941's widening and SQ-0952's key have never fired for this press. Neither is a defect on it today (a compilation is not a one-game set, and its volumes carry their own stories), but both would start applying once grouping works, so re-check them on it.

## Specimen note

Six ADF volumes against five DiskCopy volumes: these are **different releases of the same compilation**, not one release on two media. CLAUDE.md's rule applies — name the exact fixture and the volume count in any finding, and do not carry a result from one to the other.

The `.2mg` `Lost Treasures (Disk 1 of 7).2mg` is a THIRD arrangement, seven volumes, already named in SQ-0941's note as correctly yielding no single story. Three presses of one compilation, three naming conventions, three volume counts — a good corpus for a grouping rule, and a warning against tuning one to a single shelf.
