Located by the SQ-0524 lane: the shared `DialogField` renderer at `crates/app/src/render/dialog.rs:397-436` has NO scroll logic at all. It draws the value's chars left-to-right from index 0 and simply stops once it reaches `content.right()` — and the caret is dropped along with the overflow, so once the value is wider than the field you can neither see what you are editing nor where the cursor is.

This is a WIDGET-level limitation, not specific to any one dialog. It affects every consumer of `TextEntryDialog` today: EditNotes, RenameLayer, RenameRoom, RelabelEdge, ConfigEditPath, CreateFile.

It is PRE-EXISTING — SQ-0524 did not introduce it. But SQ-0524 made it far easier to hit in practice: before, the field always opened empty, so you only overflowed by typing a long value yourself; now it opens prefilled with the room's existing notes, so any room whose notes are already wider than the dialog opens in the broken state immediately.

Fix shape: a horizontal scroll offset kept in the field, derived from the caret position, so the visible window follows the caret and the caret is always drawn. Worth checking whether `TextField` (`crates/app/src/text_field.rs`) or the renderer should own that offset — the renderer knows the width, the field knows the caret, so the width probably has to be passed in.

Note the caret is already correct on the data side: `TextField::new` (`text_field.rs:19`) sets `cursor = value.chars().count()`, i.e. end-of-text, by design. This quest is purely about rendering a window onto a value too wide to show.
