--- note 2026-08-16T04:28:14Z ---

## Blocked on SQ-0896. Do not start before it.

`picture_takeover` (`screen.rs:4029-4040`) is four OR'd hatches:

    story_covers_screen && (art_paints_anything || art_fills_screen || art_encloses_screen)
    || story_plate_escapes_story_window

§4 of `docs/superpowers/specs/2026-08-15-v6-render-pipeline.md` judges all four as the same statement — *"there are pixels here the ring has nowhere to put"* — expressed four times because the ring's only container for pixels is `pane − viewport`. SQ-0896 gives it another container. Until then these hatches are load-bearing and removing any of them breaks frames that render correctly today (Zork Zero's map, fmvpoker's bet panel, Arthur's and Shogun's full-screen plates).

## SQ-0894 measured what does and does not move them

- Content-derived flank COLUMNS did NOT move any of them: no corpus frame changed routing. A content-built flank is somewhere to put pixels, but these hatches are not reached by frames that HAVE a ring — they are reached by frames the router never sends there.
- `menu_over_art` is a SEPARATE router and is SQ-0892's to retire, not this quest's. Do not conflate them: the Shogun credits screens take the composite via `menu_over_art`, not via `picture_takeover` (`story_covers_screen` requires the story box at the screen top-left and the Amiga menu's window 0 sits at native y=336).

## Method — one at a time, each with its own fixture

Each hatch has a documented motivating frame; retire it only after driving that frame and showing the ring now renders it correctly.

| hatch | fixture it was written for |
|---|---|
| `story_covers_screen && art_paints_anything` (SQ-0725) | mysterious01's title cards |
| `… && art_fills_screen` | Arthur's intro plate, Journey's title |
| `… && art_encloses_screen` (SQ-0729) | fmvpoker — measured as the ONLY title it fires for |
| `story_plate_escapes_story_window` (SQ-0739) | fmvpoker's "Current Bet" panel, where window 0 stops being the story window while still holding the 640x400 poker table |

The precedent for doing this well is SQ-0888's lane: it deleted `story_text_box` only after measuring that it answered `None` on every corpus frame at boot and on every turn, and said so. Measure first, delete second, state the measurement. A hatch that still earns its place should be KEPT with a stated reason — that is a good outcome, not a failure.

## Watch for the trap SQ-0894 hit

Disabling the `Frame`-plan stretch arm passed the FULL gate (5553 tests) and was still not evidence it was dead — the corpus simply had no fixture that reached it. Expect the same shape here: a hatch may be unreachable by the corpus and still correct. Check reachability explicitly before reading a green gate as permission.

## After this

Raster becomes removable as a MODE. That is its own quest and its own product decision — `v6_render = "raster"` is user-facing, ~51 test files reference raster, and the hybrid/raster PARITY assertions used as an oracle across the corpus need real assertions instead (the pipeline document already flags parity as weak: it cannot catch a defect both modes share, and it did not catch SQ-0890's credit collision). Follow the shape of the SQ-0895 frameless removal: silent config fallback, docs updated, README caveat until a release is cut.

## Result: 1 retired, 3 kept. Each verdict is a measurement.

### The instrument this needed first

A boolean cannot audit four OR'd predicates: they are tried in order, first match wins, and a hatch can be perfectly correct and never decide anything. `picture_takeover` now delegates to **`picture_takeover_reason(...) -> Option<&'static str>`** (pub). `ring_scout` prints the arm per frame; `picture_takeover_arms_across_the_corpus` (in `v6_fmvpoker_hybrid.rs`, both `honor_game_colours` modes) pins the census and fails when the set changes.

### THE CENSUS — `ring_scout --all --no-tap --turns 8 --size 98x37`

| title | arms over 8 frames |
|---|---|
| zork0, shogun, scopa, advent | ring only |
| arthur | `art_paints_anything` at turn 0 (the intro plate), ring after |
| journey | `art_paints_anything` at turn 1 (the title), ring after |
| mysterious01 | `art_paints_anything` on every frame |
| fmvpoker | ring at turn 0, `art_paints_anything` turns 1–8 |

`art_fills_screen` and `art_encloses_screen` decide **nothing** on this corpus. That is SHADOWING, not death — both also read CHROME art, which `art_paints_anything` (story plate only) never looks at.

### hatch 4 — `story_plate_escapes_story_window` (SQ-0739) — **RETIRED**

Two independent reasons: SQ-0746 removed its premise (a display panel the game declares is not its transcript never becomes the story window, so window 0 never stops being it), and SQ-0896 removed its need (the ring's canvas and art oracle carry the plate at its own native origin wherever that is). MEASURED false on every frame of all eight titles; its own corpus test had asserted exactly that since SQ-0746. Function and its 45-line doc deleted; the history moved onto `picture_takeover`.

### hatch 1 — `art_paints_anything` (SQ-0725) — **KEPT**, with a specific blocker

Disabled it and drove the corpus. Exactly ONE title changes route: Arthur's plate and Journey's title fall to `art_fills_screen`, all fmvpoker frames to `art_encloses_screen`, and mysterious01 — this arm's own fixture — goes to the ring. **What the ring draws there is wrong.** Its two 512x192 cards stack down the left of a 640x400 screen, so the content-carved ring makes them ONE 79x37 side flank over the whole pane, and a flank goes through the border-extension recipe. Band log, verbatim: `band 79x37@(0,0) [Art, tiled]: … source 516x544 native px … resample 516x544->632x666` — 160 native rows of picture invented below the second card, painted across the letterbox margins the Letterbox plan meant to leave bare. That is SQ-0819's mistake one title over (`tiled_flanks` excludes the Menu plan precisely because Journey's picture column is not a border).

**To retire it: the ring must tell a picture column from a border column.** That is a change in `v6_border::recognize`/`flank_source` and `tiled_flanks`, not in this router, and it must land first. Its own fixture is right there — `ring_scout --story stories/mysterious01.z6 --keys n --no-tap --bands` with the arm disabled reproduces the 516x544 source in one command. Note also that `v6_mysterious01_boot.rs` currently asserts `path == "raster"` at two places (both `honor` modes) and reads the cards off `build_v6_raster_canvas`; those become ring assertions when the arm goes.

### hatch 2 — `art_fills_screen` — **KEPT**, and not merely shadowed

It is the only arm reading CHROME art on a frame that SQ-0896 deliberately declines. SQ-0896's inset floor hands a window its DECLARED box back when the inset leaves less than one text cell, which is exactly a full-screen chrome backdrop under a full-screen story window: viewport = whole pane, ring empty, and without this arm the backdrop is not drawn at all — SQ-0570's original symptom returning. Separately, for a full-bleed PLATE the ring adds nothing: `story_prose_box` is `None` on such a frame so hybrid renders no transcript, and the ring would ship in N band uploads the same picture raster ships in one image. No text to keep crisp = no reason to prefer the ring.

### hatch 3 — `art_encloses_screen` (SQ-0729) — **KEPT**, because it is not only a routing test

`story_window_is_a_canvas` reuses this exact predicate, deliberately, so the two cannot drift — and the CANVAS reading of window 0 (live runs at the coordinates the game's own `set_cursor` named, no transcript at all) exists on the raster path alone, in `draw_story_canvas_runs`. Route fmvpoker to the ring and it gets a scrolling re-render of everything window 0 ever printed, wrapped into the `(22,234,594,158)` hole in its poker table — the reading SQ-0729 measured as wrong, and how its dealt hand overwrote the line the player needs. **To retire it: the canvas reading must exist on the ring path first.**
