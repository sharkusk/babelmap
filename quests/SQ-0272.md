--- note 2026-07-11T16:21:22Z ---

ROOT CAUSE (headless investigation): The Wizard Sniffer spins in a non-converging status-window auto-size loop during its intro (the 2nd "press any key"). Per-turn it repeatedly calls glk_window_set_arrangement(pair win 3, method 0x12 = BELOW|FIXED, size alternating 1<->2, keywin 0), then window_clear(2)/set_window(2)/move_cursor(2,0,0)&(0,1)/get_size(2). Our get_size CORRECTLY echoes the set size (set 1 -> (80,1), set 2 -> (80,2)), yet WS oscillates 1<->2 forever: its own measurement logic decides "need 2 rows" at height 1 and "need 1 row" at height 2. ~7M VM steps/4s; makes <2M glk calls (heavy compute between). NOT backend-specific: gvm-cli (TerminalBackend) ALSO infinite-loops (spins >12s, never reaches line input); the app's 10s wall-clock runaway guard (glulx_session.rs drive()) turns the loop into DriveStop::Quit -> quit=true, i.e. "hang ~10s then crash". char_px is not the trigger (loops at both (8,16) and (1,1)). Real interpreters converge, so this is a gvm Glk-semantics gap in what WS measures to pick the status height (needs WS source or a Lectrote/Gargoyle get_size/grid trace to pin the exact differing value). Candidate fixes: (A) root-fix the Glk semantic WS relies on; (B) mitigation — detect the set_arrangement oscillation (same pair, alternating size, no input request/no I/O progress) and break it so WS becomes playable instead of hanging+quitting. Reproduce headlessly: drive GlulxSession(WS, 80,24,accel,images) through 2 char inputs; step 1 aborts with the runaway diagnostic.
