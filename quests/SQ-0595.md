## Measured

`GlulxSession::new_in`, same story, same real save dir
(`~/.babelmap/saves/CounterfeitMonkey-11.gblorb.save`), acceleration on:

| pict_blorb | boot |
|---|---|
| `None` | **0.758s** |
| `Some(blorb)` | **5.45s** |

The app always passes the blorb when `images` is on, so a normal launch always pays the
full recompute. That is the user's "always 5+ seconds".

## How the cache actually works (established, useful regardless)

CM needs BOTH artifacts in the save dir; either alone is worthless:

| save dir | boot |
|---|---|
| neither | 5.49s |
| `_Counterfeit_Monkey-startup-data.qzl` only | 5.41s |
| `default.glkvfs` only (holds an EMPTY entry of the same name) | 5.49s |
| both | **0.729s** |

So the empty VFS entry is not a bug or a red herring — it is CM's existence marker,
checked via `glk_fileref_does_file_exist` (`glk.rs:1768`, which ORs `files` against
`saved_game_files`). The real state is the 41 KB `.qzl`, reached because
`seed_saved_games` (`glulx_session.rs:205`, SQ-0301) registers on-disk `.qzl` files
before boot. Deleting either file costs the next launch 5s and rebuilds both.

## Next step

Trace the Glk calls with and without the blorb and diff them at the point the two runs
diverge. CM is presumably consulting something whose answer differs when graphics exist
— a gestalt, a window/screen metric, or an image query — and treating the cached state
as stale. The question to answer is whether the thing it consults is something we report
INCORRECTLY when a blorb is present, or whether CM legitimately caches per-graphics-mode
and the second mode's cache is simply never written.

## Caution for whoever picks this up

Two earlier attempts at this went wrong by testing a path the app does not use:
`GlulxSession::new` skips `seed_saved_games` entirely, so any harness built on it can
never restore and will report a broken cache that is fine. Use `new_in` with a real
game_dir, and pass the vfs — the fast path needs both.

## Traced — the branch point is `glk_stream_open_resource(9998)`

Glk call traces of both boots, diffed. They are identical for 121 calls, then split at
exactly one call:

```
        WITHOUT blorb (0.73s)                 WITH blorb (5.45s)
122  glk_stream_open_resource(9998, 301)   glk_stream_open_resource(9998, 301)
123  glk_stream_get_current()              glk_stream_close(15, 0)      <-- opened, then
                                                                            closed unread
...
     glk_fileref_create_by_name(0, ..., 301)   glk_fileref_create_by_name(256, ..., 0)
     glk_fileref_does_file_exist(8)            glk_fileref_does_file_exist(8)
     glk_stream_open_file(8, 2, 301)  <-- READS  glk_fileref_destroy(8)   <-- gives up
                                                 glk_fileref_create_by_name(259, ...)
```

Re-run with stream reads unfiltered (they are normally suppressed as text I/O):
**no read calls at all** occur between the resource open and its close. CM opens
resource 9998, consumes nothing, closes it.

So the resource open is an EXISTENCE PROBE, and its success switches CM onto a different
branch. Note the two fileref call sites differ in both usage and rock — 0 (Data|Binary,
rock 301) on the fast path versus 256 (Data|TextMode, rock 0) on the slow one — so these
are distinct code sites in CM, not one site with different flags. The slow branch checks
that the file exists and then destroys the fileref without ever opening it.

## Not a data problem

`PictSource::data_resource(9998)` returns **39,178 bytes**, `text=false`. The resource
resolves correctly and `stream_open_resource` receives the full contents, so the empty
read is not us losing the data — CM simply never asks for it.

## Where this needs to go next

The remaining question is why CM abandons the cache once it knows resources exist. It is
open source, so the answer is readable rather than guessable: find the startup-data
extension's logic around `glk_stream_open_resource` and see what distinguishes its
binary/rock-301 path from its text/rock-0 path. Candidates worth checking against our
behaviour: what we return for the probe open (a valid stream where a real interpreter
might behave differently), and whether CM expects to READ the embedded resource and is
deterred by something in the stream's initial state.

Do NOT conclude from the empty `default.glkvfs` entry — it is CM's existence marker and
is supposed to be empty. And do not test through `GlulxSession::new`; only `new_in` seeds
saved games, and the fast path needs BOTH the `.qzl` and the vfs present.

## ROOT CAUSE — `@restore` ignores the stream it is given

Resource 9998 is not a data table: it is a **Quetzal save file** (`FORM…IFZS`, `IFhd`,
`Glul`, 39,178 bytes). CM ships a pre-computed game state inside its blorb and restores
from it at boot. That restore is the Glulx `@restore` OPCODE taking the resource stream,
which is why the Glk trace showed an open and close with nothing between — the work is a
Glulx instruction, invisible to a Glk tracer.

`exec.rs`, opcode 0x0124:

```rust
let (name, by_prompt) = self.glk.stream_saveload_info(l[0]).unwrap_or_default();
self.pending_saveload = Some(PendingSaveLoad { dest: s[0], restore: true, name, ... });
```

`@restore L1 S1` is specified to read the save data **from stream L1**. We instead ask the
stream for a fileref NAME and hand that to the host to open by name. For a saved-game
fileref stream that works. A **resource stream has no fileref name**, so
`stream_saveload_info` returns `None`, `unwrap_or_default()` gives an empty name, the host
finds nothing, the restore fails, and CM recomputes from scratch.

## Why it regressed when it did

Before `c20dafdd` (2026-07-13, SQ-0308) `glk_stream_open_resource` was unimplemented and
`data_resource` returned `None`, so CM's probe FAILED and it took its external-file cache
branch — fast. Implementing resource streams correctly made the probe succeed, which
routed CM onto the embedded-restore branch that our `@restore` cannot service. A correct
feature exposed a latent gap in a neighbouring one.

## Scope — not a CM quirk

Any Glulx game that restores from a stream we cannot name is affected, and shipping a
pre-baked state as a blorb Data resource is a known Inform 7 technique for slow-startup
games. `@save` to a non-host stream is presumably the same gap in the other direction and
should be checked while fixing this.

## Fix shape

In the 0x0124 arm, when L1 is a readable stream that is NOT a host saved-game conduit
(resource stream today), read its bytes directly and restore in-process — the same path
`restore_quetzal` already implements — instead of suspending for the host. Preserve the
existing semantics: the original `@save` call stub stores -1 on success (spec §2.9), and
`complete_restore_failure` stores 1. Verify with CM: boot should drop from ~5.4s to
sub-second WITH the blorb, and the external `.qzl`/`.glkvfs` cache should become
irrelevant on that path.

## Resolved — CM r11's blorb is internally inconsistent

Both of these live in the SAME `CounterfeitMonkey-11.gblorb`:

```
GLUL exec chunk : 47 6c 75 6c 00 03 01 02 00 36 87 00 …  RAMSTART 0x368700
resource 9998   : 47 6c 75 6c 00 03 01 02 00 36 75 00 …  RAMSTART 0x367500
```

The embedded startup save names a different compile than the story shipped beside it, so
its `@restore` fails the §1.8.4 identity check and always will. `extract_story` returns
the GLUL chunk byte-for-byte, so we are not transforming or mis-presenting anything.

## What CM actually does, measured

| | with blorb | without blorb |
|---|---|---|
| restores from | resource 9998 | its own `.qzl` (host, by name) |
| result | rejected on identity | restored |
| boot | 5.4–6.0s every launch | 767ms from the 2nd |
| writes `.qzl`? | yes, then never reads it | yes, reads it next boot |

Logging every `glk_fileref_does_file_exist`: with the blorb CM asks only about
`_undo-…-0..4`, `_autotesting`, `_testing`, `_monkeyac`. It **never asks about
`_Counterfeit_Monkey-startup-data`**. So the earlier theory that we misreport its save
and it falls back to the resource is wrong — it never reaches for the file on that branch
at all. Nothing we return changes the branch it takes.

## Origin

Ours, but not fixable from our side: before `c20dafdd` (SQ-0308) resource streams did not
exist, CM's probe failed, it took the file branch, and boots were fast. Implementing the
feature correctly moved it onto a branch this release cannot complete.

## Options

1. `--no-images` / `images = false` — 767ms boots today, no graphics. Workaround only.
2. Suppress resource 9998 (or any resource whose IFhd fails identity) so the probe fails
   and CM takes the working branch. Effective, and defensible ONLY if documented as a
   deliberate per-game quirk: it means lying to a game about its own blorb.
3. Leave it. Spec-correct, slow for this one release of this one game.

Awaiting the user's call on (2). The `@restore` fix (1b0b740f) stands regardless — it was
a real gap, and any game whose embedded save MATCHES now benefits.
