## Measured

`GlulxSession::new_in`, same story, same real save dir
(`~/.babelmap/saves/CounterfeitMonkey-11.gblorb.save`), acceleration on:

| pict_blorb | boot |
|---|---|
| `None` | **0.758s** |
| `Some(blorb)` | **5.45s** |

The app always passes the blorb when `images` is on, so a normal launch always pays the
full recompute. That is the user's "always 5+ seconds".

## How the cache actually works (established, useful regardless)

CM needs BOTH artifacts in the save dir; either alone is worthless:

| save dir | boot |
|---|---|
| neither | 5.49s |
| `_Counterfeit_Monkey-startup-data.qzl` only | 5.41s |
| `default.glkvfs` only (holds an EMPTY entry of the same name) | 5.49s |
| both | **0.729s** |

So the empty VFS entry is not a bug or a red herring — it is CM's existence marker,
checked via `glk_fileref_does_file_exist` (`glk.rs:1768`, which ORs `files` against
`saved_game_files`). The real state is the 41 KB `.qzl`, reached because
`seed_saved_games` (`glulx_session.rs:205`, SQ-0301) registers on-disk `.qzl` files
before boot. Deleting either file costs the next launch 5s and rebuilds both.

## Next step

Trace the Glk calls with and without the blorb and diff them at the point the two runs
diverge. CM is presumably consulting something whose answer differs when graphics exist
— a gestalt, a window/screen metric, or an image query — and treating the cached state
as stale. The question to answer is whether the thing it consults is something we report
INCORRECTLY when a blorb is present, or whether CM legitimately caches per-graphics-mode
and the second mode's cache is simply never written.

## Caution for whoever picks this up

Two earlier attempts at this went wrong by testing a path the app does not use:
`GlulxSession::new` skips `seed_saved_games` entirely, so any harness built on it can
never restore and will report a broken cache that is fine. Use `new_in` with a real
game_dir, and pass the vfs — the fast path needs both.
