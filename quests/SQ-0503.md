Deferred 2026-08-19, with the trigger written down so it can resurface on its own terms.

Scope is narrower than the title. Two halves, and only one is live:

1. TERMINAL RESTORE — not a Windows problem at all. SQ-0502's damage (raw mode + alternate screen + mouse capture left on for whatever inherits the terminal, plus the macOS watchdog for a crossterm poll() wedged on a dead pty fd) has no Windows analogue: the console being closed IS the thing destroyed, and the OS reclaims it. main.rs's install_termination_handlers is a documented no-op on non-unix for exactly this reason.

2. EXIT AUTO-SAVE — live, but only under a non-default config. `auto_save` defaults to FALSE (config.rs:1374), so the shipped build saves on exit on NO platform; a Windows console close loses precisely what a Unix `kill` would. The gap opens only for someone who turned auto_save on AND closes the tab instead of quitting. The default path's fallback doesn't survive the trip either: with auto_save off, `prompt_save_on_quit` asks on the way out, and nothing can answer a prompt during a CTRL_CLOSE_EVENT.

TRIGGER TO REOPEN: `auto_save` becoming the default. Then a closed tab loses a real session and the handler is worth writing.

Cost when it comes back: a `windows-sys` dep under [target.'cfg(windows)'.dependencies] in `app` (allowed — CLI crates and app may take deps; zvm/gvm/scott may not), and the standard pattern of the handler thread setting TERMINATE and then blocking while the main loop runs exit_auto_save inside the OS's ~5s grace. NOTE IT CANNOT BE VERIFIED BY CI: .github/workflows/test.yml does run windows-latest, so it would compile and unit-test there, but no runner can close a console window. It lands unproven until someone tries it on real Win11.
