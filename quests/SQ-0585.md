## Scope

### Symptom
advent.z6 (Inform 6 v6 library) `style` splits the screen into win3 (640x180, top), win1 (status, y=181) and win7 (prose, y=201). win3 is wrap+scroll like win7, so `cpu::exec` routes BOTH to stream 1 (the SQ-0459 rule) and their text interleaves in one app transcript — win3's text then scrolls away with the story. The game's own warning names this: "If things scroll off of the screen that shouldn't (like the windows on the top of the screen), then your interpreter probably doesn't support V6 correctly."

Related, already fixed and NOT part of this: SQ-0583 (which window is the story), SQ-0582 (status strip render), SQ-0584 (erase fills).

### What already exists
- The neutral model ALREADY supports this shape: `WinNode::Buffer` with `primary: false` carries its own `lines`/`runs`/`para`/`images`/`scroll` (`engine.rs`). Glulx uses it today for secondary text buffers. So this is not a new model concept — it is wiring the v6 path into the one that exists.
- `zvm` already tracks per-window `line_count` (ZMSD §8.8.3.2.2) for [more] paging, and per-window geometry/colour.
- SQ-0583 already picks the prose window by wrap+scroll, so "which one is the story" is settled; this quest is about the OTHERS.

### The actual work
1. **zvm (the core change).** Stream-1 output is untagged — `self.out.print_attr(s, attrs)` in `cpu::exec` does not say which window the text went to, so the host cannot separate the streams. Needs a window tag on the output path (a field on `TextAttrs`, or a sink method carrying the window number). Everything downstream follows from this; without it there is nothing to split. Note the zero-dependency rule applies.
2. **session.rs.** Keep a per-window line buffer for non-prose wrap+scroll windows and publish each as a non-primary `Buffer` entry in the layered model, instead of letting its text reach the transcript. The prose window keeps the transcript (scrollback, search, export, history, `[more]`, room detection all stay keyed to it).
3. **render.** `v6_layout::classify_windows` currently makes the first primary `Buffer` the story and puts EVERYTHING else in `chrome`; a non-primary buffer needs to render as a text region in the layered composite, in all three v6 modes (hybrid ring, raster, frameless). Hybrid is the interesting one: a second buffer is neither ring art nor a chrome text strip.
4. **Lifecycle.** A secondary window that is erased must clear its lines (interacts with SQ-0584's fill), and one resized to zero must stop rendering. `[more]` paging is per window (`line_count` already is).

### Open questions to decide before building
- Does secondary-window text belong in the transcript HISTORY (search, export, save/restore snapshots), or is it live-only screen state? Live-only is simpler and matches the interpreter; it means that text is unsearchable and absent from exports.
- On save/restore: a secondary window's contents are host state, not Quetzal state. Reconstruct them (blank until the game repaints) or snapshot them?
- Scrollback: does a secondary buffer get its own scroll, or is it a fixed pane showing its last N lines?

### Test surface
advent.z6 `style` is the reproduction (`crates/app/tests/v6_advent_status.rs` already boots and drives it). ziptest-r13-s890619.z6 is worth checking as a second case — it is an Infocom v6 test harness. Zork0/Shogun/Arthur/Journey do not use a second prose window, so they are the regression baseline: their prose window is window 0 and must be byte-identical.

### Cost/risk
Touches the dependency-free VM crate's output path, the shared screen model, and three render modes — the widest of the advent.z6 chain. The v6 suites (20 binaries) are the safety net; two of them caught the ordering error in SQ-0584 mid-build.

## Decisions (user, this session)

- A secondary prose window is **live-only screen state**. Its text does NOT enter the transcript history: no search, no export, no save-snapshot of its contents.
- **No scrollback** for a secondary buffer — it shows its current content, nothing more. Start here.
- **Restore**: do not design for it up front. Test how the game actually responds to a restore with the split layout open, then decide what (if anything) is needed.
