## What happens today

`build_chrome_canvas` rasterises **every** chrome run — glyph strokes and cell backgrounds — into the shared native canvas. The hybrid ring then draws most of those runs as crisp terminal glyphs anyway, and erases the rasterisation it just paid for:

- `clear_text_rows` (SQ-0504) carves a text strip's native rows over the strip's own column span;
- `clear_text_rows_except_art` (SQ-0902) carves the same rows over the full native width, keeping only what the art canvas accounts for;
- `clear_text_columns` (SQ-0779) does the same for a stamped border column.

So on a hybrid frame the chrome text is rasterised, then thrown away. That is pure waste per frame — on Shogun's gameplay screen it is a 548x32 window's worth of glyph rendering discarded every redraw, and the ring redraws on every keystroke.

## Why it is built this way, which is the actual problem to solve

Not an oversight — an ordering constraint. The canvas is built BEFORE the strips are classified, and the classification partly depends on the canvas:

- The chrome canvas is shared with the **raster** path, which needs every run imaged.
- `build_chrome_canvas` freezes its own art layer and probes it per run to decide how to draw that run (SQ-0727/SQ-0500/SQ-0487's block rule, SQ-0499's gap fill) — so rasterising is entangled with deciding.
- `ChromeStrip::Text` vs `ChromeStrip::Art` is decided later, by `ChromeRowOracle`/`over_art`/`strip_has_art`, off the finished canvases.

So "just don't rasterise it" needs the strip classification, or a cheap conservative predicate for it, available before the canvas is painted. The art-only canvas (`build_graphics_canvas`) is already built first and is the oracle those predicates use, which is the thread to pull: if a run's own rows carry no art, the ring will draw it as glyphs and raster is the only consumer of its pixels.

## Suggested shape

1. Decide, per chrome run, whether the hybrid ring will draw it as a glyph — from the art-only canvas, which exists before the chrome canvas is painted.
2. Skip rasterising those runs when the frame is going to the ring. The raster path must still get all of them, so this is conditional on the render mode, or the canvas gains a "text layer" built only on demand.
3. Retire the three carves as their inputs disappear, one at a time, keeping whichever still has a source of pixels to remove.

Falsify by measuring, not by assuming: time a hybrid redraw on Shogun's gameplay frame and on Zork Zero (whose banner text sits ON art, so it must stay rasterised) before and after. The correctness oracle is that the carves become no-ops — assert the canvas is byte-identical with and without them, which is the honest proof that nothing else depended on the rasterise-then-erase sequence.

**Watch for**: Zork Zero's banner is text over artwork and is an Art strip, never a Text run — it must keep being imaged (SQ-0750 reserves raster for pixels the runs cannot account for, and that banner is exactly such a case). Any predicate that skips rasterising it is wrong.

**The two columns are not the same cost and the big one is the cheap one.** "Px carved" is dominated by window PAGE fill — a flat colour written across a rectangle — because the carve clears the full native width on a text row. Journey's 148,000 px is almost entirely page, and producing it is close to a memset. The work that is actually per-glyph is the "glyph cells" column, and it is **31 to 169 cells** per frame, i.e. **4 KB to 22 KB** of rasterised pixels. That is real but small, and it is the honest size of this quest's prize.

So the CPU case for SQ-0903 is weaker than it looked when it was filed. Worth doing for clarity — rasterise-then-erase is confusing to read and it is what let SQ-0902's boundary bug hide — but it should not be sold as a performance fix without profiling a redraw first. If page fill turns out to dominate a redraw, the bigger win is skipping the page fill on rows the ring draws as cells, which is a different change from skipping the glyph rasterisation.

**Zork Zero confirms the trap empirically: 0 runs carved.** Every one of its chrome runs sits on artwork, so all of them are legitimately imaged and none is waste. A predicate that skipped rasterising them would break its banner — exactly the failure this quest's note warns about, now with a number behind it.

**fmvpoker has no ring canvas at all** (0 opaque px) because `picture_takeover`'s `art_paints_anything` sends its frame to the raster composite. Any measurement that averages over the corpus must not count it as "no waste"; it is "not on this path".

## Scope: exactly which windows this is about

`classify_windows` (`v6_layout.rs:283`) is purely structural, and **chrome is a default bucket rather than a positive test**:

1. the FIRST primary `Buffer` → `story`
2. the FIRST window-0 `Graphics` → `story_gfx`
3. **everything else** → `chrome`, in input order

Only chrome **Grid** windows' `px_texts` are rasterised-then-carved. `build_chrome_canvas`'s Pass 2 images them, and the carve removes the ones whose own span carries no art. Chrome **Graphics** windows ARE the artwork and are never carved. Chrome **Buffer** windows are rasterised by `draw_secondary_prose`, which lives inside `build_v6_raster_canvas` — raster-only — so secondary prose panels are not part of this waste and must not be swept into a fix for it.

## Nothing unexpected lands in the bucket — MEASURED over 33 frames

11 fixtures (including the ProDOS Journey and Arthur and the Amiga Shogun) at 0, 2 and 6 turns. The two `is_none()` guards mean a second primary Buffer or a second window-0 Graphics would silently become chrome; **neither happens on any frame measured**. Two real cases worth knowing:

- **fmvpoker at 6 turns puts a non-primary Buffer in chrome** — its bet panel (SQ-0746). The `draw_secondary_prose` case, and the reason that path must stay out of scope.
- **scopa has NO primary Buffer at all**, so `story` is `None` and every window is chrome. It also has **no Graphics at all**, so every one of its chrome runs has no art beneath it and all four are carved. Its chrome canvas is 640x400 fully opaque — 256,000 px, entirely page and rasterised text — on a frame with no artwork anywhere. If any title makes the case for building the chrome canvas lazily rather than for skipping individual runs, it is this one.

Chrome grid runs per frame, for sizing: zork0 29 (none carved — all on art), Arthur 72, Shogun 8 (34 cells), Journey 66, mysterious01 95, scopa 4, advent 5, Shogun Amiga 109, Arthur ProDOS 65, Journey ProDOS 65.

## CORRECTION: scopa DOES have artwork, and the earlier note about it was wrong

The user challenged the claim that scopa has no graphics — correctly. Its start page shows three cards for the available decks, and every frame of play is cards.

What is true is narrower and more interesting: **scopa publishes no `Graphics` window at all.** It DRAWS with `draw_picture`, which reaches the ring as the paint surface `blit_paint_ground` lays down (SQ-0706), not as a display list. MEASURED at boot: three Grid windows, zero Graphics, `build_graphics_canvas` returns an empty canvas, and the paint surface carries **28,296 opaque pixels** — of which **8,256 sit on rows carrying chrome text**.

Two things follow, and both matter more than the CPU question:

1. **The "scopa argues for building the canvas lazily" conclusion in the previous note is withdrawn.** It rested on reading an empty art canvas as an artless frame. Its chrome canvas is not 256,000 px of pure waste; it carries the game's own cards.
2. **`build_graphics_canvas` is not a general "is there art here?" oracle** and must not be treated as one. It answers only for art published as a display list. Any predicate in this quest that decides "the ring will draw this run as glyphs, so skip rasterising it" has to consult the paint surface as well, or a painting game loses artwork. This already bit once: SQ-0902's carve was gated on the art canvas alone and erased scopa's cards (fixed in `fba9ae3d`, with a regression case in scopa's own shape).

The earlier waste table also under-counted for scopa specifically, because the probe built the chrome canvas without `blit_paint_ground` — so its cards were not in the "opaque px" column at all. The glyph-cell counts (the column that actually sizes this quest) are unaffected: they come from the runs, not the canvas.
