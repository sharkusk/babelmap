--- note 2026-08-09T06:11:51Z ---

MEASURED 2026-08-09 — Shogun DOES declare the layout; we are not honouring the window boxes. Sequence: boot shows the GRAPHIC SPLASH (win0 and win7 both full-screen 640x400, win1 collapsed 640x0) and waits on read_char. The intro TEXT streams into win0 WHILE IT IS STILL FULL-SCREEN, so we capture it as ordinary transcript: 'SHOGUN / A Story of Japan / Copyright (c) 1988 by Infocom / ... / IBM Interpreter version 6.65 / You may choose to:'. THEN, on the first keypress, the game repositions into its real three-window layout: win1 = HEADER (47,1) 548x32 (inset ~46px each side of 640 — that inset IS the 'centred' look the user sees, and 548 = 640-2*46); win0 = STORY (47,337) 548x64, i.e. only 4 text rows, anchored at the BOTTOM (y=337..401), Lmargin=2 Rmargin=2; win2 = MENU (235,337) 169x48, opened to the RIGHT of win0's left edge. win2 carries the three menu items as PAINTED runs (per-glyph V6Text), style=1 for the selected one: y=337 'START the game', y=353 'RESTORE a saved game', y=369 'QUIT...'. That is exactly the reported Spatterlight layout — 'You may choose to:' on the left (win0's last prose line at x=47) with the 3-item menu on the right (win2 at x=235). So the placement hints are all present in the window table; the render is not using them. NOT the margin properties: Lmargin/Rmargin are 2/2 here (session.rs:240-253 already reads them, but only for the margin-PICTURE case; a later screen shows Rmargin=328 which is that feature). Likely the same class as SQ-0696: v6 text is PAINT, so text streamed into win0 while it was full-screen must stay where it was painted when win0 later shrinks to the 548x64 bottom box — plus win2 needs rendering at its own (235,337) origin rather than being folded into the story viewport.

--- note 2026-08-09T06:15:32Z ---

CENTRING RESOLVED 2026-08-09 — the game does NOT centre; Spatterlight does. Measured every header line the game emits: SHOGUN / A Story of Japan / Copyright (c) 1988 by Infocom / All rights reserved. / SHOGUN is a trademark... / Original Literary Work... / Licensed by Noble House... / Release 322 / Pix 322 / Serial number 890706 / IBM Interpreter version 6.65 / You may choose to: — EVERY ONE has leading_spaces = 0, and they arrive through the PROSE stream (win0's transcript), not as painted V6Text runs with x coordinates. So there is no padding for us to be losing and no cursor positioning for us to be ignoring. Combined with the spec check done earlier this session (ZMSD has NO centring/justification/alignment facility anywhere — sect 8.8.6.1 is the only picture text and sect 8 carries nothing on alignment), per-line centring cannot come from the story file. Also ruled out INTERPRETER NUMBER as the source: booted with none/2/3(Macintosh)/4(Amiga)/5(Atari ST)/10(Apple IIgs) — the header text is byte-identical and unpadded in every case (2 and 10 skip straight to 'You may choose to:', i.e. a shorter banner, still unpadded). So identifying as something other than IBM PC does not unlock a centred layout. CONCLUSION: same disposition as SQ-0698 — Spatterlight is applying a per-game presentation enhancement, not reading a hint we are missing. The genuinely actionable half of this quest is UNCHANGED and still stands: win2 (the menu, box (235,337) 169x48, 50 painted runs) must render at its own origin, and text painted into win0 while it was full-screen must survive win0 shrinking to the (47,337) 548x64 bottom box — that part IS the game's own declared layout.

--- note 2026-08-09T06:21:51Z ---

*** CORRECTION 2026-08-09 — MY EARLIER 'Spatterlight enhancement' CONCLUSION WAS WRONG. DISREGARD THE TWO NOTES ABOVE THAT SAY THE CENTRING IS OUT OF SCOPE. *** User checked Apple II and DOS (IBM) walkthroughs on YouTube: BOTH show the intro text centred, on real Infocom interpreters. That falsified the enhancement theory, so I traced the boot screen ops (trace_from_boot) instead of only inspecting the emitted text — and the game centres every line ITSELF, by CURSOR POSITION rather than by padding. Per line it reads the window's own geometry and positions in PIXELS: '@get_wind_prop(win=0, prop=4) -> 49' (current y_cursor), '@get_wind_prop(win=0, prop=3) -> 640' (window WIDTH), then '@set_cursor(row=49, col=297, window=0)'. Verified the arithmetic is exact centring at 8px/char on a 640px window: SHOGUN len 6 -> col 297 (ideal 297); 'A Story of Japan' len 16 -> 257 (257); 'Copyright (c) 1988 by Infocom' len 29 -> 205 (205); 'All rights reserved.' len 20 -> 241 (241); 'SHOGUN is a trademark of James Clavell' len 38 -> 169 (169); 'Original Literary Work Copyright 1975 by James Clavell' len 54 -> 105 (105). ALL MATCH, row stepping 49/65/81/97/113/129/145 (16px = one text row). WHY I MISSED IT: I measured the emitted TEXT and found leading_spaces=0 on every line, and concluded there was no centring information. The centring is not in the text at all — it is in the set_cursor x that precedes each line, and our capture streams that text to the host transcript while discarding the pixel column. Lesson: for v6, inspect the SCREEN OPS, not just the text; 'the game emits no padding' does not mean 'the game does not position'. THE CENTRING IS THEREFORE IN SCOPE and is the same root cause as the rest of this quest: we are dropping the game's declared placement. Retitle/rescope accordingly.
