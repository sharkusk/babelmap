--- note 2026-08-09T20:36:07Z ---

User hypothesis 2026-08-09, worth testing first: "at startup we are not rendering an image (perhaps this should be over the top of the 'Mysterious Adventures' title graphic)?"

So the second title card may be intended to composite **over** the first rather than replace it or sit beside it. That reframes the quest: it may not be a picture that fails to arrive, but a picture that arrives and is discarded or overdrawn because it lands on top of one already on screen.

That would also explain the strangest fact on this quest — the card DOES show on restart. A restart clears the screen first, so the second card lands on a blank window and survives; at boot it lands on the title graphic and does not. If that is the mechanism, the differential to measure is not "boot vs restart code path" but "what happens to a picture drawn over an existing one".

FIRST MEASUREMENT: trace the boot picture sequence — which picture numbers are drawn, into which windows, at which coordinates, and in what order — and compare against the same trace after a restart. If both sequences issue the same draws and only the boot one loses the second card, the loss is downstream of the story and the overlay hypothesis is live. If the boot sequence never issues the draw at all, the hypothesis is dead and this is a story-side gating question instead (compare SQ-0706's scopa investigation, where the game genuinely never issued a draw).

Relevant recent work that changed picture handling under this title: SQ-0715 (`98b29882`) made pictures record the window box at the moment of the call and freeze onto the paint surface when their window moves, and made picture draws and erase fills drain as ONE ordered timeline. A picture dropped by an erase that replays in the wrong order is exactly the failure mode that fix addressed for scopa — check whether the boot sequence here has the same shape.

--- note 2026-08-09T20:38:02Z ---

MEASURED 2026-08-09 by headless zvm probe (throwaway, deleted). The overlay hypothesis in the previous note is REFUTED, and the story-side gating question is answered: the game DOES issue the draw.

Boot picture sequence, verbatim from `Machine::pending_pictures`:

    pic 0 win 0..7 at (1,1) erase=true          <- clear every window
    pic 33 win 0 at (1,1)   erase=false at_cursor=true
    pic 34 win 0 at (1,192) erase=false at_cursor=false

Dimensions from `Mysterious01.blb`: **pic 33 = 512x192**, **pic 34 = 512x192** (and pic 32 = 512x16). With `art_scale` now 1 for this story (no `Reso` chunk — SQ-0715/SQ-0718), pic 33 occupies y 1..192 and pic 34 is drawn at y=192, i.e. **immediately BELOW it, not over it**. Two stacked 512x192 cards filling y 1..384 of a 640x400 screen. The user's "perhaps this should be over the top" is wrong — they are stacked.

So the second card is drawn, at a sane coordinate, into the same window as the first, on the same turn. Whatever loses it is HOST-side, downstream of the story. Candidates, in order:
- the two draws differ in exactly one published field: `at_cursor` is **true** for pic 33 and **false** for pic 34. SQ-0714's backdrop rule keys on a picture spanning window 0's full width; SQ-0695's float/placed discriminator keys on `at_cursor`. A picture that is neither "at the cursor" nor "spanning the window" may be falling between the two classifications.
- pic 34's y=192 is exactly pic 33's bottom edge, so an off-by-one or a clip at the first card's boundary would drop it entirely.

ALSO NOTE — the restart differential is gone. The user now reports: "i'm no longer able to see it on restart for some reason." So the card is missing in both paths, and the boot/restart comparison this quest was going to rest on is no longer available. Whether that is a regression from the recent v6 wave (SQ-0714/0715/0697/0727/0729 all landed today) or a misremembering is unknown; do not spend long on the archaeology, since the draw is now known to be issued and the loss is reproducible at boot.

UNRELATED BUT SEEN: the probe hit `StepResult::Fault` shortly after supplying input past the boot screens. That is very likely an artefact of a bare zvm harness with no app-side screen setup feeding 'n' to both char and line reads — NOT a reported defect, and not confirmed against the real app. Mentioned only so the next person is not surprised by it.
