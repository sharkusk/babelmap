FIXTURE CORPUS COMPLETE 2026-08-11. The user supplied the missing CGA archives, so `stories/` now carries the full PC set: **17 files, 15 distinct** (SHA-256 checked).

    arthur.cg1  arthur.eg1  arthur.eg2  arthur.mg1
    journey.cg1 journey.eg1 journey.eg2 journey.mg1
    shogun.cg1  shogun.eg1  shogun.mg1
    zork0.cg1   zork0.eg1   zork0.mg1
    beyondzo.mg1

TWO ARE DUPLICATES, and one of them settles a story: **`FMVPOKER.EG1` is byte-identical to `zork0.eg1`** (`5ab967cd…`). That is direct confirmation of the motivation SQ-0713 was opened on — fmvpoker.z6's own readme tells players to rename a Zork Zero graphics file to `FMVPOKER.EG1`, and the file in `stories/` is exactly that, unmodified. Also `zorkzero.mg1` == `zork0.mg1` (`5cbaa181…`). Neither is an independent specimen.

**A DISCRIMINATOR RECORDED ON SQ-0713 IS WRONG.** Its codec note states: *"Header byte 8 = 14 = the directory record size, and is the field that distinguishes Amiga/Mac (14, big-endian) from the PC flavours."* Measured across every archive on disk:

    Amiga .pic (arthur.pic, zork0.pic)   byte 8 = 0x0e = 14
    .MG1  (all five)                     byte 8 = 0x0e = 14   <-- collides
    .CG1 / .EG1 / .EG2  (all ten)        byte 8 = 0x0c = 12

MCGA shares the Amiga record size, so byte 8 alone would route an `.MG1` into the Huffman decoder. A correct discriminator has to come from the source.

BETTER CANDIDATE, from the raw headers and to be confirmed against Infocom's own interpreter code rather than adopted: **offset 2-3 is the doubled Huffman-tree offset** on the Amiga side (`zork0.pic` reads `0d91`, matching SQ-0713's `0x0d91*2 = 6946 = end of directory`; `arthur.pic` reads `04a7`). **Every PC archive reads `0000` there** — there is no Huffman tree in an LZW container, so there is no offset to record.

    arthur.pic     01 06 04a7 00a9 0000 0e00 ...
    zork0.pic      01 06 0d91 01ef 0000 0e00 ...
    arthur.cg1     01 38 0000 aa00 0000 0c00 ...
    arthur.eg1     01 38 0000 7d00 ec05 0c00 ...
    arthur.eg2     02 38 0000 6500 0000 0c00 ...
    arthur.mg1     01 30 0000 ab00 0000 0e00 ...
    zork0.cg1      01 38 0000 f701 0000 0c00 ...
    zork0.mg1      01 30 0000 f701 0000 0e00 ...

ALSO MEASURED:
- **Byte 0 is the part number, confirmed.** Every `.EG2` reads `02`, everything else `01` — so Arthur and Journey split their EGA art across two parts and a complete EGA corpus for those titles means reading both.
- **Byte 1 tracks the FLAVOUR, not the title**: Amiga `0x06`, CG1/EG1/EG2 `0x38`, MG1 `0x30`. Possibly the cleanest discriminator available; meaning unknown and not to be guessed.
- **Endianness confirmed**: PC counts only make sense little-endian (`0xaa00` = 43520 read big-endian is absurd; `0x00aa` = 170 is not). The Amiga side reads big-endian and reproduces SQ-0713's recorded `0x01ef` = 495 for `zork0.pic` exactly.

CROSS-FLAVOUR ORACLE — picture counts at offset 4:

    zork0    cg1=503  eg1=503  mg1=503     <- all three renditions agree EXACTLY
    arthur   cg1=170  mg1=171  eg1=125  eg2=101
    journey  cg1=134  mg1=134  eg1=80   eg2=67
    shogun   cg1=50   eg1=50   mg1=48
    beyondzo mg1=1

Zork Zero carrying 503 pictures in all three PC renditions is a strong structural assertion — same ids and dimensions at three colour depths — and it does not depend on the Blorb, which matters because `Zork0.blb` was built from the **Amiga** release and PC pixels are therefore NOT expected to match it byte-for-byte the way the Amiga decode did (383/388).

`beyondzo.mg1` at 1 picture is legitimate, not a truncated file: Beyond Zork is text with a decorative border. It is the single-entry-directory edge case.

All of the above is header arithmetic taken to unblock the implementation lane; the format itself must still be established from `github.com/erkyrath/infocom-zcode-terps`, and where the source disagrees with any of it, the source wins.
