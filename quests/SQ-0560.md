DECISION (user, 2026-07-29): **DROP THE CLAIM. `[map.overrides]` stays the one mechanism.** Do NOT teach the map renderer to read per-selector glyph slots.

Rationale: `[map.overrides]` is a slot-keyed glyph override table that already works and already does this job. Adding a second, per-selector route to the same outcome is a redundant mechanism for one job — YAGNI. The per-selector capability that route WOULD have bought (e.g. a different corner glyph for the current room than for an ordinary one) was considered and judged not worth a parallel system.

IMPORTANT SCOPING — do not over-delete. The Theme glyph channel is LIVE and load-bearing elsewhere; this quest is narrowly about map selectors:
  - `crates/app/src/render/panel.rs:29` reads `r.glyph.and_then(|g| g.single)`; `:86` passes `spec.glyphs`
  - `crates/app/src/render/dialog.rs:319` passes `glyphs: &st.glyphs`
  - `crates/app/src/render/saves.rs:182` reads `.glyph`
  - `crates/app/src/render/debug_panel.rs:77,81` read `.glyph.single`
Panel/dialog border glyph SLOTS and single-glyph markers must keep working exactly as they do. Only the `map.room` / `map.connector` `glyphs = { ... }` sub-map — which `render/map.rs` never consumes (it reads only `.style` and draws from `state.symbols`) — should stop being an accepted-but-ignored input.

Preferred outcome: a user who writes `glyphs = { tl = "+" }` on a map selector should not be silently ignored. Either the key is rejected/warned, or it simply isn't part of the schema for those selectors. Silently parsing into a dead end is the actual defect here — that is what made the docs plausible enough to ship a false claim.

`docs/features/customization.md` was already corrected during SQ-0558 to describe `[map.overrides]` instead. Verify that text is accurate against whatever you land; do not reintroduce the old claim.
