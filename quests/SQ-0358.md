ROOT CAUSE FOUND AND FIXED. Not Loud-Room-specific and not a mapper bug at all — a v4+ location-detection bug that affects any game which skips a status-line redraw.

REPRODUCTION (headless, from the user's save standing in the Round Room, driven through the game's own restore path so the status line redraws as in a real session):
  after restore  detect=PlayerParent room="Round Room"  | status_line="Round Room"
  east           detect=StatusName   room="Round Room"  | status_line="Round Room"   <- actually in the Loud Room
  east           detect=PlayerParent room="Damp Cave"   | status_line="Damp Cave"
  west           detect=StatusName   room="Damp Cave"   | status_line="Damp Cave"    <- actually in the Loud Room
  west           detect=PlayerParent room="Round Room"  | status_line="Round Room"
So the mapper saw Round Room -E-> Damp Cave and Damp Cave -W-> Round Room; the Loud Room never existed. Exactly the report. The user's ids check out independently: #16 = Round Room, #26 = Damp Cave, and the Loud Room is #213.

WHY: Zork's Loud Room echoes your commands ("look look ...") — its routine intercepts input, so the game never runs its status-line update while you stand there and the bar keeps naming the room you came FROM. Confirmed in zvm-cli: the status line jumps straight from "Round Room  Moves: 454" to "Damp Cave  Moves: 455" with no redraw in between.

THE ACTUAL DEFECT: `detect_location` on v4+ treats the STATUS LINE as ground truth and the object tree as mere corroboration. It asks "does any player candidate's ancestor chain reach the room the text names?" and, when nothing validates, falls through to `StatusName` — which resolves the STALE TEXT to an object and returns it. But "nothing validates" is precisely the signal that text and tree DISAGREE. The tree was right all along:
  east  chain: cretin#46 -> Loud Room#213 -> #41 -> <root:0>
`Location::StatusName` firing on a v4+ game is therefore a smell worth remembering: it means the avatar's chain could not confirm the text.
Global 0 is NOT an option here: zork1 v5 returns None for it (checked), so there is no shortcut — despite the module header still claiming v4+ "tries the same strategy" with global 0, which `detect_location` has not done for some time (stale doc, left alone as out of scope).

FIX (`player_room_beside`): when nothing validates, believe the tree. The status line still names a room we CAN resolve, so its object teaches us what a room looks like STRUCTURALLY — its container — and the player's nearest ancestor sharing that container is the room they are really in. Nothing is hard-coded: Zork's rooms all hang under container #41 (learned per-turn from the shown room), and Inform's rooms sit at top level (container 0); the same rule covers both. Candidates are tried in order, which is what rejects decorative avatars — Zork has TWO player candidates, and the decoy `you#21` (chain: it#65 -> 0) never reaches #41 while `cretin#46` does.

BLAST RADIUS, MEASURED NOT ASSUMED: the new branch only fires where nothing validates today, i.e. where the answer was already the suspect one; with no player candidates it cannot fire, so `StatusName` still serves games with no identifiable avatar. Swept all 42 local z-stories (boot + one turn) before and after: ZERO changed their answer. The six v4+ titles that legitimately ride StatusName (LostPig, amfv, hitchhiker-invclues, leathergoddesses-invclues, nordandbert, planetfall-invclues) are all unmoved.
