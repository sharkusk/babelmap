## Reproduction

`stories/Zork Zero - The Revenge of Megaboz.adf` — **release 366, serial 890323**, booted as `Amiga off Adf`, screen 320x200 with art scale (2,2) so a 640x400 native. Not the `.z6` (r393), which is a different build and a different profile.

At any prompt: submit an empty line (the game answers "[I beg your pardon?]"), then `define`, then any key to clear "[Hit any key to continue.]". The key-definition menu is then on screen and the game is at a CHARACTER read.

## MEASURED

```
MODEL default pair:  fg = Standard(9)  bg = Standard(12)
win 640x400@(0,0)    Buffer(primary=true, fg=Some(Standard 2), bg=Some(Standard 10))
win 273x304@(199,47) Grid(526 runs, fg=Some(Standard 2), bg=None, fill=true)
win 640x400@(0,0)    Grid(0 runs,   fg=Some(Standard 2), bg=None, fill=true)
```

Every one of the menu's 526 runs is a single character with `style=0`, `fg = Standard(2)` (**black**) and `bg = 0` (**Default/inherited**).

So on this frame:

- the STORY window is what the game dressed: black on **light grey (10)**;
- the MENU window names a foreground and no background, and carries an `ErasedFill` — the game erased it, and ZMSD §8.8.5.3 fills an erased window with *its* background, which is unset;
- both the fill and every run's inherited background therefore resolve through `v6_machine_page` to the header's default page, `Standard(12)` — the Amiga's dark grey, `#424242` under Infocom's `colortable[]`.

**Black ink on dark grey.** That is the "very dark" the user reports, and it is not a rendering accident — every layer is doing what it was told. `v6_machine_page`'s own doc states the rule it follows: *"This decides only what an INHERITED channel resolves to: text that names its own colours still wins."* Journey under the same profile names neither channel, so it gets white on grey and looks right; Zork Zero names only the ink, and the pair it lands on is one the game never asked for.

## The open question — needs a REFERENCE RENDITION, not more measurement

Two candidate faults, and internal measurement cannot separate them (the standing rule: use another interpreter, an emulator or footage to falsify a behavioural assumption):

1. **The inheritance target is wrong.** An erased window with no background of its own should perhaps inherit the *current/story* window's page — light grey (10) here, which would make the menu black-on-light-grey and match the screen the game dressed — rather than the header default. The header default is what a window gets at RESET; whether it is what an erase should paint years into a session is the question.
2. **The Amiga profile's default pair is wrong for this build.** `InterpreterProfile::default_colours()` answers `(12, 9)` for Amiga. If release 366's Amiga screen is actually light, the header default is the thing to correct, and the menu falls out right for free.

Note what is NOT in doubt: the menu window's foreground WAS captured (`fg=Some(Standard 2)`), so a `set_colour` for that window did reach us and only its background came through unset. Worth reading zvm's `set_colour` handling to see whether the game passed "default" for the background (in which case behaviour 1 is the question) or passed a colour we dropped (in which case this is a zvm bug and neither candidate above applies).

Do not guess between them. Get a Spatterlight capture, real-Amiga footage or a screenshot of release 366's define menu first; the whole class of colour work here has been settled that way before.

## Scope note

If the fix turns out to be (1), it is not Zork-Zero-specific — it changes what every inherited channel resolves to on every v6 title, which is the surface `v6_machine_page` was written for (SQ-0740) and which Journey's Amiga frame depends on. Pin Journey's white-on-medium-grey before touching it, both `honor_game_colours` modes.

## The decision is made, and the first two attempts were both aimed at the wrong site

**User's ruling: an inherited channel should resolve to the STORY WINDOW'S BACKGROUND**, falling back to the header default only when the game named none. That settles the open question in the note above — candidate (1), not the profile's default pair.

Two attempts, both reverted, both instructive:

**Attempt 1 — widen `v6_page_pair`** (publish the story window's bg as the machine page). MEASURED as correct on the corpus: only three frames name a story background at all (Amiga Zork Zero `Standard(10)`, DOS zork0 and fmvpoker `Standard(9)`), the latter two publish no machine pair so the theme still owned them, and Arthur/Shogun/Journey leave it unset and kept the header default. But it broke `v6_float_machine_page::an_explicit_window_page_still_beats_the_machines` on its **premise** assertion — *"the window's page and the machine's really are different colours here"*. That case exists because the Amiga floppy is the one medium where both layers are live, and collapsing the machine pair into the story page leaves it unable to tell them apart. The machine pair is also the ground a float sits on (`v6_machine_page_rgba`, SQ-0848). So the pair must stay the machine's.

**Attempt 2 — override the RING's `base`** (`v6_machine_page` at the chrome-ring site, which `draw_erased_fills` shares). Narrow and correct in shape, and **it does nothing for this frame**, which is the finding that matters:

```
PROBE  Zork Zero .adf   path="cell — painted menu takeover routed here"
                        story_bg=Some(Standard 10)   grounds={"Black"}
```

**The DEFINE menu never reaches the hybrid ring.** It is routed by `has_menu && hybrid && !menu_over_art` (`screen.rs` ~2726) to the **plain cell path**, which renders through `render_node(&story.node, …, grid_colors)` and has its own base style. That is where the fix belongs. Note the ground there is **Black**, not the machine's `Rgb(66,66,66)` dark grey — so the earlier diagnosis ("inherited resolves to the header default 12") describes the RING's rule and is not what this frame actually does. The symptom is the same to the eye; the mechanism is a third thing, still unidentified.

## Also found — worth fixing regardless

- `v6_amiga_global_colour_pair.rs`'s `boot()` uses `picts.std_window().or_else(|| profile.std_window())`, **missing `picts.native_std_window()`** — the SQ-0901 rule, in a suite that boots disk media exclusively. Its frames may not be the ones the app draws.
- A test built on `AppState::default()` has **no `game_picker`**, so `render_story_pane` logs `"cell — no image protocol"` and never enters the v6 Layered arm. Any colour case written that way measures the fallback path, not the ring. Cost an hour here; worth a sweep of which suites do it.

## Fixed, at the third site — the cell path's `status_style`

`status_style` (`screen.rs`, the v6 cell-path arm) was the **bare theme style**:

```rust
let status_style = state.colors.theme.get("upper_window").style;
```

and it is the base for all three of that path's stampings — `draw_erase_fills` (whose `ErasedFill` carries `bg = 0`, "the page default"), `draw_anchored_status_band`, and `draw_painted_screen`, which is what draws a menu's items. So every inherited background resolved to the THEME's black, however the game had dressed the screen a cell away. That is why the earlier probe read `grounds={"Black"}` and not the machine's `Rgb(66,66,66)`: the header default was never in play on this path at all.

It now takes the story window's own background when the game named one, gated on `honor_game_colours` because a page the game chose is a game colour. One override fixes the fill and the runs together, exactly as the ring's `base` does for its side.

FALSIFIED: with it reverted, `chrome_inherits_the_page_the_game_dressed` reports *"the game dressed this screen in Rgb(173, 173, 173) and NO inked cell sits on it. Grounds seen: {"Black"}"* — black on black, the reported symptom.

## Blast radius

Only three corpus titles dress a story background at all (MEASURED): Amiga Zork Zero `Standard(10)`, DOS zork0 `Standard(9)`, fmvpoker `Standard(9)`. Every other title — Arthur, Shogun, Journey on all presses, mysterious01, scopa, advent — leaves it unset, so `status_style` is untouched for them and the theme owns it exactly as before. Arthur and Journey ride in the new case as controls, asserting they still dress nothing rather than asserting about their panes (Arthur's frame is all image bands and has no inked cell to read).

**Worth the user's eye on DOS Zork Zero and fmvpoker as well as the Amiga press**, since those two also dress a page and their cell-path chrome now inherits white where it used to inherit the theme's ground.

## Fixed along the way

- `v6_amiga_global_colour_pair.rs`'s `boot()` now uses `startup.rs`'s full screen-size chain, `native_std_window` included (CLAUDE.md, SQ-0901). This suite boots disk media exclusively, so it was measuring a screen the app may never give these presses.
- The new case builds its `AppState` with `Picker::halfblocks()`. Without a picker, `render_story_pane` logs `"cell — no image protocol"` and never enters the v6 arm — the trap that made two earlier drafts pass against the defect.

## Still open, deliberately

The RING path has the same latent question — `v6_machine_page` resolves an inherited channel to the machine's header default, not to the story window's page. No corpus fixture demonstrates it (the frames that dress a page and route to the ring do not also inherit a background), so it is left alone rather than changed speculatively. If a title ever shows the symptom on a ring frame, the fix is the same one line at the ring's `base`, and attempt 2 in the notes above is what it looks like.
