SCOPE CONSTRAINT, user 2026-08-11 — and it is the difference between a fix and a regression. Asked whether Zork Zero's side art could also be extended without stretching, the user answered: **"no, we stretch which in the right approach for this case."**

So this quest is NOT "replace stretching with tiling". Both behaviours are correct, for different artwork:
  - **STRETCH** — Zork Zero. Its columns are a single tall architectural element (capital, shaft, base) that must scale to the frame's height. Measured at 115x61: upload 128x972px, placed rows 8..61 cols 1..16 and 100..115 (16 cols x 54 rows) — placement matches upload, and unlike Arthur/Shogun the canvas is FULLY PAINTED, columns reaching the bottom with a proper base. Nothing is wrong here and nothing should change.
  - **TILE** — Arthur (48x792px, rows 18..61) and Shogun (64x612px, rows 4..37). Both leave the lower ~25% of the canvas empty, and Arthur's right strip carries two rules ending at different heights — the signature of a repeating unit stamped once.

THEREFORE THE FIX NEEDS A DISCRIMINATOR, not a switch. Whatever decides tile-vs-stretch must be derived from the artwork or the game's own draw ops — not hard-coded per title, and not applied globally. Candidate signals to measure before choosing: how many draw ops the game issues into the strip and at what native y positions (a tiling game repeats; a stretching one does not), and the source picture's own height against the region it must fill. Establish the signal on Arthur and Shogun, then verify it classifies Zork Zero as STRETCH without being told to.

CORPUS GUARD, non-negotiable: Zork Zero's frames are pinned frame-by-frame in the render corpus tests. A tiling change that moves a single Zork Zero pixel has broken something, and those tests are the tripwire. Same for any other title whose side art is a single tall element rather than a repeat — check the corpus before assuming Arthur and Shogun are the only two affected.

SCALING RULES FOR SIDE ARTWORK, set by the user 2026-08-11. These govern the HORIZONTAL treatment; tiling (this quest's subject) is the VERTICAL one. Both apply to the same strip.

> "a couple more rules to stretching (when tiling). If there is artwork on top (e.g. arthur) horizontal stretch should be done for the side artwork (so it matches the top artwork). If there is ONLY side artwork (e.g. shogun) then only the standard 2X scale factor should be used, with no other stretching."

(The user first wrote "e.g. journey" and confirmed on being asked that they meant **Arthur** — Journey's top is a glyph border, not artwork, and its "sides" are repeated characters that SQ-0750 is converting to text. Journey is therefore OUT of scope for these rules entirely.)

RULE 1 — TOP ARTWORK PRESENT: horizontally stretch the side artwork by whatever factor the top artwork is stretched by, so the frame's pieces agree at the corners. Specimens, measured 2026-08-11:
    Arthur ADF r74, 117x64:  top banner plate rows 1..15 (uploads 920x270px and 920x18px), sides 48x792px at rows 18..61
    Zork Zero r393, 115x61:  top banner rows 1..7 (upload 920x126px), sides 128x972px at rows 8..61
  Both have a full-width top plate whose horizontal scale the sides must match.

RULE 2 — SIDE ARTWORK ONLY: apply the standard 2x scale factor and nothing else — no stretch-to-fit. Specimen:
    Shogun ADF r295, 100x40:  no top artwork (its top row is a TEXT status line), sides 64x612px at rows 4..37

CORROBORATION for rule 2 being the natural scale: at 2x, the measured side uploads imply native widths of 24px (Arthur, 48/2), 32px (Shogun, 64/2) and 64px (Zork Zero, 128/2) — all plausible native artwork widths, so "2x and no more" is what the art itself is drawn for.

INTERACTION WITH THE STRETCH-VS-TILE DECISION already on this quest: Zork Zero STRETCHES vertically (single tall element — capital, shaft, base; canvas fully painted; user: "we stretch which in the right approach for this case"), while Arthur and Shogun TILE vertically (canvas empty below ~75%). So the two axes are decided separately, and Arthur takes rule 1 horizontally while tiling vertically. Do not collapse them into one switch.

VERIFY BEFORE IMPLEMENTING: nothing here says how "is there top artwork?" should be detected. Derive it from the frame (a full-width plate above the side strips) rather than from a title list, and confirm the derivation classifies all three specimens correctly before building on it.

--- note 2026-08-11T22:23:02Z ---

REFERENCE IMPLEMENTATION READ 2026-08-11, at the user's suggestion ("just in case we are missing something"). We were missing something, and it is worth having in full before implementing.

**Bocfel — which Spatterlight ships — has a dedicated `terps/bocfel/z6/draw_border.cpp`.** Its header: *"Used by Arthur, Shogun, and Zork Zero."* **Journey is not in it at all**, which independently corroborates our own finding that Journey's frame is TEXT, not artwork (SQ-0750), from a completely separate source.

WHAT IT DOES — tiling only, never stretching:
  - `tile_section_down(uint8_t *section_to_repeat, size_t linessize, int pillar_height, int overlap, int start_y, int desired_height, bool initial_parity, bool flip)` and `tile_strip_down()` stamp a horizontal strip repeatedly downward. **Stride is `pillar_height - overlap`, so tiles OVERLAP rather than butt**, and `flip` alternates each tile's vertical flip from `initial_parity`. Both devices exist to hide seams in a repeated pattern — worth copying, not just the repetition itself.
  - `extend_pillars(int top_cut, int foot_height, int total_height, int pillar_height, int overlap, bool flip, bool bw_hint_foot, int desired_height)` — snapshot the pillar strip, tile it down, then draw a FOOT section. So the structure is **capital → tiled shaft → foot**, which is exactly what Zork Zero's columns look like in our own renders.
  - Ordering caveat they hit and documented: *"Snapshot the pillar strip before erasing anything: for Arthur, top_cut equals total_height - foot_height, so the strip's source rows sit inside the foot region erased just below."*
  - It only extends when the pane is taller than the art: `if (desired_height <= total_height) return;`
  - Zork Zero has THREE specialised routines — `extend_mac_bw_castle_pillars`, `extend_underground_pillars`, `extend_jungle_pillars` — the underground one alternating left/right drawing to keep the masonry consistent.
  - Arthur: top banner (pic 54), optional wide room image, left/right pole images (170/171); poles extend via a 2-line tiled strip from 90% down, then a foot, with a SHORTER foot on Amiga.
  - Shogun: Amiga and Mac B/W use one image with overlap-based duplication; CGA/EGA/VGA use separate left and right border images with custom overlap offsets.
  - Design rationale, verbatim: *"The original games did not do this, but it looks better with modern screen sizes."* So tiling is a modern-interpreter courtesy, not fidelity to the originals — which means neither approach can claim authenticity as an argument.

**CAUTION FOR OUR DESIGN GOAL.** This quest wants a DERIVED discriminator rather than per-title code. The reference did not find one: it hard-codes per game AND per platform (Arthur's Amiga foot, Shogun's per-adapter overlaps, Zork Zero's three scene-specific pillar routines). That is evidence a fully general rule may not exist. Do not treat "derive it" as a hard requirement if measurement shows the artwork genuinely differs per title; prefer deriving what can be derived (does the canvas need extending at all; where the repeat unit begins and ends) and keeping any irreducible per-title data small, named, and commented with its source.

**USER DECISION 2026-08-11, after being shown the above:** *keep stretching Zork Zero; tile Arthur and Shogun.* We diverge from Bocfel deliberately and knowingly. Reasons: Zork Zero currently renders correctly with a fully-painted canvas and its frames are pinned byte-for-byte in the render corpus, so switching it to tiling would move every pinned frame for no visible gain; Arthur and Shogun are the two whose canvases are measurably unfilled below ~75%. Revisit only if Zork Zero shows distortion at some pane size we have not captured — and if it ever is revisited, `extend_pillars`'s overlap + flip + foot structure above is the shape to copy.
